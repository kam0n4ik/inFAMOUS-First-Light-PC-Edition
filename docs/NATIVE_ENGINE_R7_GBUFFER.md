## 3. G2: нативный проход геометрии 0x1a2030

### 3.1 Что делает функция (своими словами)

`0x1a2030(M, chunk)` — проход по диапазону ключей сортировки одного чанка G-buffer. `chunk` = {R (контекст
рендера), S (сцена/вид), —, диапазон `[lo, hi)` (два s32)}. Вид — `*S`; ключи — `*(S+0x4dc0)` (u64, младшие 16 бит —
индекс экземпляра), экземпляры — `*(S+0x4db8)` (шаг 0x80).

Общая подготовка: смещение камеры (16 байт по `view+0x420`, если в `M+0x21` бит 2, иначе 0), четыре строки матрицы вида
(`view+0x430` или `view+0x200`), строки камеры `view+0x6c0..0x6f0` (последняя минус смещение, w=1), порог дизеринга —
s32 из таблицы `0xda08c0` по индексу кадра (`frame 0xf1bcd0 + 0x1dca8`).

Вариант A (`M+0x1f == 0`, по объекту): инициализация структуры границ `0x26ac70`, затем на каждый ключ — дизеринг
через общий генератор случайных чисел `0x612110` (остаток от деления на 1025 сравнивается с порогом), пропуск пустых
мешей (`mesh+0x18 == 0`), смена материала `0x448640` при отличии от предыдущего; строки освещения из таблицы источников
`0x7dff1e0+0x1c0` (сдвинутые на смещение камеры) → `0x1a0a80`; буферы скиннинга (`M+0x125/0x126`) через
`0x61e260` + `0x16b70`; для прохода 0x1d — матрица прошлого кадра `0x1a1b90` и три потока вершин; константы объекта
`0x11c890` (блок `R+0xd190`, флаг изменений `R+0xd2e8`: новый буфер `0x11be90` + копия 0x140 байт + привязка
`0x11bed0` к VS и PS, либо только привязка); вторые константы `0x11cde0` (блок `R+0xd2f0`, флаг `R+0xd388`, 0x80 байт);
настройки `0x446490`, `0x445e00`; константа LOD `0x11e5d0`; `0x450460`, `0x1742f0`; фиксация констант `0x120280`;
кэш трафарета `R+0xde64` → `0x6229a0`; при `M+0x124` — дополнительная отрисовка с битами render control = 1
(`0x6270e0`) и восстановлением; отрисовка `0x1a1960`.

Вариант B (`M+0x1f != 0`, инстансинг): ключи группируются по старшей части (`key ^ key0 < 0x10000`); на группу —
кадровая аллокация `0x1f0870(frame, n*0xd4, 16)` под записи экземпляров; запись 0xd4 байт строится из матрицы мира
экземпляра (нормированные строки, произведение на матрицу вида, параметры затухания, поля экземпляра); `0x451440` на
запись при `M+0x94 > 0`; после группы — материал, `0x451290`, (двойная) отрисовка `0x1a1770(M, R, recs, k, mesh)`.

### 3.2 Реализация

* `src/native_engine/r7/gbuffer/geometry_pass.{h,cpp}` — проход как C++: `PassFns` (таблица вызываемых функций),

### 3.3 Механизм проверки на уровне функции

Оригинал выполняется как *записывающий клон* (все вызываемые функции с побочными эффектами перенаправлены в thunk'и
трассы `gbuffer_trace`), нативный проход — с таблицей вызовов, указывающей на те же thunk'и. Оба прогона получают
одинаковые входы и *теневую копию* полей контекста R `0xd190..0xde90` (копируется из живого контекста перед каждой
проверкой), общую арену под аллокации. Сравниваются: порядок вызовов, аргументы (указатели нормализуются: стек /
регион / арена), байты по указателям (матрицы 0x40, записи экземпляров n×0xd4, V#, границы 0x80), арена (записи и
загруженные константы), теневой R в конце. Расширения трассы для этого: до 4 снимков на вызов, маска игнорируемых
регистров (`0x1a0a80` не читает RDX — там мусор), 32-битные стековые аргументы (`0x11c890` stack0).

Вызовы, выполняемые по-настоящему внутри проверки: `0x11c890`, `0x11cde0` (пишут только теневые блоки констант;
проход читает их флаги изменений), чистые `0x26ac70`, `0x61e260`, `0x635350` (их хеши закреплены в спецификации).

### 3.5 Крах guarded и проверка контрактов аргументов

Первый guarded-прогон упал в 0x451440 (чтение байта по нулевому указателю + 0x11). Причина: 0x451440 читает
**шестой** аргумент R9 — указатель на mesh instance записи. Явно 0x1a2030 его не передаёт: R9 остаётся с момента
построения записи экземпляра (загрузка `*(inst+0x18)` по 0x1a32b5). Моя реконструкция передавала 5 аргументов,
спецификация трассы сравнивала 5 регистров. В записывающих прогонах 0x451440 не исполняется, поэтому verify (2.3M
равных проверок) ошибку не видел.

Исправление: mi передаётся шестым аргументом, спецификация сравнивает 6 регистров. Чтобы такие расхождения ловились
механически, добавлен `r7/gbuffer/arg_liveness.{h,cpp}`. Анализатор (Zydis) для функции eboot определяет, какие
аргументы System V (RDI..R9, XMM0..7, стековые слоты) читаются до записи хотя бы на одном пути. Прямые вызовы он
учитывает рекурсивно, после вызова caller-saved считаются записанными. Отдельные правила:

* запись младшего байта/слова делает определённым последующее чтение той же части (`mov cl, …; and cl, 2`);
* zero idioms — не чтение;
* первый источник AVX-скалярного слияния (`vcvtsi2ss xmm0, xmm0, edx`) даёт только верхние полосы — не аргумент.

Тест проверяет все 23 записываемых callee на второй, нетронутой копии eboot: более ранние тесты ставят входные
переходы в 0x11c890, 0x1a1770 и др. Ни один callee не читает регистр, который его спецификация не сравнивает; сам
0x1a2030 читает только RDI/RSI. Вывод для всех реконструкций с трассой: арность callee берётся из кода самого callee,
а не из подготовки аргументов в месте вызова.

## 5. NativeDrawCommand для R7-Core

`src/native_engine/r7/gbuffer/draw_command.{h,cpp}`: `BuildInstancedDrawCommand(module, M, R, records, n, mesh,
material_changed, out)` и `BuildMeshDrawCommand(module, M, R, inst, out)` — на входе в 0x1a1770 / 0x1a1960, только из
объектов движка (через `NativeDraw::BuildDrawOp`): producer GBuffer, fn GBufferInstanced / GBufferMesh, indexed,
`index_count = u32 mesh+0x68`, `index_base = u64 mesh+0x58`, prim_type 4, index_size 0 (16 бит),
`num_instances = n` (0x1a1770). `run_tag` = `Source::GBuffer | kMaterialChanged` (по параметру `material_changed`) или
`Source::Mesh`. Ресурсы: форма таблиц стадий из layout, `version = 0` (версии ресурсов — зона R7-R; до этого StateKey
ничего не переиспользует). Оговорка: 0x1a1960 сам не пишет NUM_INSTANCES — регистр хранит прошлое значение контекста;
в команде указано 1, R7-Core не должен полагаться на это без проверки.

## 6. Отрицательные результаты и блокеры

* A/B `r7g_ab1`: ускорение от нативного 0x1a2030 не подтверждено (§4.3).
* Крах guarded-прогона `r7g_g2_pass_guarded` из-за неучтённого R9 у 0x451440 (§3.5). Исправлено; в записывающих
  прогонах такие ошибки не видны в принципе, их ловит только проверка контрактов.
* verify пропускал 0.18% вызовов: лимит трассы 8K вызовов. Поднят до 64K, повторный verify после этого не делался
  (guarded2 и native — без пропусков).
* Не сделано: A/B предвыборки (G4); игровая проверка ветвей pass 0x1d / skin2 / дизеринг (нет сцены, где они
  встречаются; можно искать в beach/harbor/village); оптимизация повторных 0x11c890 (§4.2); вызов хелпера
  NativeDrawCommand из пути C3 (это зона R7-Core).
* Блокеров нет. Изменения [shared] не требуются.
