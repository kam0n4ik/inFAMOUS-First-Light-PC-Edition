# P2.3.4 — игра на собственном менеджере памяти (`--native memory`)

Статус (2026-10-09): **реализовано, экспериментально.** По умолчанию игра по-прежнему работает на менеджере
моста (`Core::MemoryManager`); флаг `--native memory` (только `--loader sspc`) запускает её на своём менеджере
(`Memory::VirtualMemory`, P2.3.3b/c) через те же интерфейсы `Core::Guest*`/`Core::GpuMemory`. Режим
`--memory-commit on-demand` — то же с commit физической памяти по требованию (E1). Игровой A/B — §9.
Предыдущий этап и точка входа: `docs\PHASE2_P233_NATIVE_VMM.md` §8.

Коммиты: `2891977` D19 в своём менеджере, `5a38223` патч `0012` (API libkernel через интерфейсы + выбор
менеджера), `e51cd4f` `--native memory` / `--memory-commit` / самотест запуска / скрипты, `e4caf8d` правки по
ревью.

## 2. Выбор менеджера

```
main.cpp ── --native memory [--memory-commit upfront|on-demand]   (по умолчанию — мост)
bootstrap.cpp RunGame:
   ... SecondSonBootstrap::Fill (SDK eboot) ...
   InstallNativeMemory(cfg, SDK, атрибуты param.sfo)       ← только с --native memory
       GameLayout(карта хоста сейчас) → VirtualMemory::Create (плейсхолдеры + секция)
       Core::SelectGuestMemory({NativeGuestMemory ×3, NativeGpuMemory})
   Core::GetGuestVirtualMemory().Reserve()                 ← мост: создаёт MemoryManager; свой: ничего
   Trace::Init, окно, Vulkan, StartBridgeLibraries (GnmDriver → растеризатор → SetListener) ...
```

- **Одна точка, до первого обращения.** `SelectGuestMemory` отказывает (`false`), если хоть один `Get*()`
  уже вызывался или менеджер моста уже создан; иначе меняет реализацию всех четырёх интерфейсов разом.
  Отказ при `--native memory` — `Fatal` с причиной в логе (молча на мосту не продолжаем).
- **Второго менеджера не будет.** После выбора своего конструктор `MemoryManager` моста — `ASSERT` с
  причиной (он занял бы адресное пространство гостя повторно); отладочное окно карты памяти моста (devtools)
  пишет «недоступно» вместо обращения к нему; `--memory-map` пишет карту своего менеджера.
- **Цена в горячем пути.** Геттеры (`GetGpuMemory()` вызывается и в обработчике нарушений доступа:
  `ProtectTracking`) — плюс одно relaxed-чтение флага, без записи в общий кэш-лайн.
- **Сочетания флагов.** `--native memory` требует `--loader sspc` (загрузчик shadPS4 ходит в менеджер моста
  напрямую, исключение E2); с `--native kernel-dmem` — отказ при разборе аргументов; `--memory-commit
  on-demand` без `--native memory` — отказ.
- **Сводка привязок не меняется** (NATIVE 120 / BRIDGE 275): функции памяти libkernel остаются BRIDGE-кодом
  (проверки аргументов моста), меняется менеджер под ними. NATIVE-переписывание API — отдельная задача, не
  этот этап.

неподдержанные игра не импортирует. **Известные отличия своего адаптера** (не встречаются в игре): `VirtualQuery`
с флагами ≠ 0/1 и адресом ниже первого региона — EACCES (мост отвечает областью у начала); в промежутке между

`MapDirectMemory2` возвращает успех отображения, хотя тип памяти не меняется (это API моста не проверяет
результат `SetDirectMemoryType`; адаптер пишет `LOG_CRITICAL`).

## 5. D19 — защита остатка частично снимаемого вида

**Что было.** Windows не умеет укорачивать вид секции: `HostAddressSpace::Unmap` (как и `AddressSpace` моста)
снимает вид целиком и отображает остаток заново — с защитой по умолчанию RW(+X). Терялись: (1) защита гостя
(`mprotect` NoAccess/exec) на остатке; (2) защита отслеживания GPU (page manager держит счётчики наблюдателей
по страницам и ставит Read/None через `ProtectTracking`): после переотображения запись CPU в такую страницу не
вызывает нарушения доступа, буферный/текстурный кэш GPU не узнаёт о ней → устаревшие данные на GPU.

**Решение (свой менеджер, `2891977`).** До снятия вида защита хоста оставшихся частей читается
(`VirtualQuery`, по сериям одинаковой защиты), после переотображения — возвращается (`VirtualProtect` только там,
где она отличалась от RW(+X)). Всё — под листовой блокировкой хоста, которую берёт и `ProtectTracking`
(обработчик нарушений доступа): параллельное изменение отслеживания дождётся и ляжет поверх итогового
состояния. Уведомления GPU для остатка не нужны: адреса, физические страницы, данные и защита остатка не
меняются — для гостя и GPU вне снимаемого диапазона ничего не происходит. Цена — только у частичного снятия
вида (в игре не встречается: `unmaps 0` за прогон).

**Почему не «дать OnGpuUnmap/Register по остатку»** (вариант из §5 P2.3.3): GPU сбросил бы кэши и счётчики
остатка, хотя данные не менялись, — дороже и меняет поведение для GPU; а защиту гостя это не возвращает.

**Остаточный риск (общий с мостом, не исправим без отказа от видов секции).** Между снятием вида и его
переотображением (микросекунды, под блокировкой) остаток не отображён: обращение другого потока к нему —
нарушение доступа. Если страница отслеживается GPU, обработчик дождётся блокировки и продолжит; если нет —
необработанное исключение. У моста то же окно. В игре частичных снятий видов нет.

**Мост не менялся** (по умолчанию поведение прежнее): D19 у него остаётся, `docs\KNOWN_ISSUES.md`.

Тесты: `NativeVmm(D)` (NoAccess гостя на первой странице, Read отслеживания на последней, данные остатка);
модель `NativeVmm(model)` (3000 операций) теперь сохраняет защиту остатка; `NativeStart(prot)` — то же в
раскладке игры через `sceKernelMunmap` и `Core::GetGpuMemory().ProtectTracking`.

## 6. Commit по требованию (E1)

`--memory-commit on-demand`: секция `SEC_RESERVE`; страницы секции коммитятся, когда физическая память
выдаётся (`AllocateDirect`, flexible при отображении), и не возвращаются до конца процесса (страницу секции
нельзя декоммитить). Игра забирает всю direct-память (4608 МиБ) на старте и flexible 130 МиБ, поэтому ожидание
— около 4,7 ГиБ вместо 8,4 ГиБ, т. е. ≈3,7 ГиБ системного commit меньше за весь прогон. Цифры игры — §9. Отказ
системы в commit при выдаче — `ENOMEM` гостю (в upfront такого отказа нет: всё заряжено на старте).

## 7. VEH и горячий путь

- Обработчик нарушений доступа моста не менялся; его единственный путь в менеджер — `ProtectTracking` (одна
  листовая блокировка хоста + `VirtualProtect`, без выделений и логов). Замер в раскладке игры (`NativeStart(prot)`,
  20 000 вызовов): P50 500–600 нс, P95 600–700 нс (P2.3.3: мост 496, свой 493 нс; разрешение часов 100 нс).
- Регистратор SecondSonPC (SSPC-002) не менялся.
- В игре на своём менеджере: 49,9 тыс. обработанных нарушений доступа в секунду (как у моста), не
  обработанных — 0 (§9).
- `map` своего менеджера вдвое дороже моста (RWX → RW, D18), но игра делает 44 отображения за прогон, все на
  старте — переотображения RW по требованию не понадобилось.

  первый захват цели перехода). Ошибки моста в логах — те же 8 заглушек.
- **Тесты после A/B:** `--fault-test` 22 / 0, `game_process_tests.ps1` 85 / 0, повторные запуски самотестов
  (`native_memory_tests.ps1`) — без отказов.

## 11. Несовместимости и риски (не скрываются)

- **Не поддержано своим менеджером:** пулы памяти, файловые отображения `mmap`, смена типа памяти отображённой
  direct-памяти (`MapDirectMemory2` тип, `Mtypeprotect`) — `LOG_CRITICAL` + ошибка. Игра их не импортирует.
- **Отличия ответов** (§3) — на путях, которых игра не вызывает.
- **Библиотеки моста, которые игра не импортирует** (исключение E4: `font`, `ime_dialog`, `np_signaling`,
  `vr_tracker`, `camera`, `avplayer`), ходят в менеджер моста напрямую. С `--native memory` первый вызов в них
  создал бы менеджер моста → `ASSERT` (громкая остановка с причиной, а не тихая порча). Достижимы только через
  импорт игры; `check_memory_deps.py` проверяет по `imports.csv`/`prx_imports.csv`, что импортов нет.
- **D17 (SSPC-006), D20 (SSPC-007)** — дефекты моста, у своего менеджера их нет; поэтому мост — не вполне
  эталон на этих путях (в игре не встречались).
- **D19** — исправлено только у своего менеджера; окно переотображения — общее (§5).
- **Commit по требованию:** отказ системы в commit при выдаче памяти даёт гостю `ENOMEM` посреди игры (в
  upfront отказ возможен только на старте). Игра выделяет всё на старте — практически то же место.
- **Не проверено в игре:** граффити, бой, долгая сессия (> 100 с), смена уровня/загрузка контрольной точки,
  `sceKernelReleaseDirectMemory` (игра вызывает только при выходе) — на обоих менеджерах; `--loader shadps4` со
  своим менеджером невозможен по построению.
