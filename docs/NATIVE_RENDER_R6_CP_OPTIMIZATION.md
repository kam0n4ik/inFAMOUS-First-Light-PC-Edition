# R6-P: оптимизация CPU / командного процессора

Ветка `feature/r6-cp-optimization` (от R6.0 `5752e0f`). Зона — локальные оптимизации в `src/runtime/gpu/*` (кроме
`shader/*`, `gcn/*`), собственные файлы `src/runtime/gpu/cp_r6_opt.{h,cpp}` (`SSPC_R6_CP_SOURCES`), этот документ.
База сравнения — пресет стенда (`run_native_engine.ps1`: `SSPC_CP_MODE=native`, `SSPC_REA_MERGE_RUNS=1`,
`SSPC_CP_ROUND_NODRAIN=1`, `SSPC_P411_ASYNC_ACQUIRE=1`, `SSPC_ASYNC_PIPELINES=1`, `SSPC_CITY_PERFORMANCE=1` с
`SSPC_CITY_ENGINE_GBUFFER_RUNS=1`). Ничего из R6-P не включено по умолчанию.

Метки: [E] — измерено, [A] — по коду, [H] — гипотеза.

**Итог.** Кадр в городе ограничивает поток 1 (CP + фронтенд шейдеров), 34 мс. Главная находка — скрытый фактор,
который и был «медленным режимом» базы. Это WAIT_REG_MEM `>= 0` (истинно при любом значении) на записях occlusion-запросов
игры: каждое такое чтение сливало очередь и ждало GPU, 0,4–11 с за прогон. `SSPC_R6_CP_POLL_TRIVIAL=1` такие опросы не
читает. Против базы: +3,97 FPS (28,80 → 32,77), 1 % low +4,9, p99 −7,6 мс, разброс 2,1 → 0,35 FPS (§4.1). Остальные
кандидаты при эквивалентности (0 расхождений) поверх T прироста не дали и отклонены.

## 1. Флаги

| Переменная | Что делает | По умолчанию |
|---|---|---|

(FB-6/FB-7 списывали его на машину). Средние P и G выше A (+3,0 и +2,8 FPS), но внутри каждой конфигурации разброс
27–34 FPS, и он объясняется этим фактором, а не флагом. **Прирост P и G по s1 не подтверждён.**

Откуда чтения (диагностика `SSPC_R6_CP_DIAG=1`, `r6p_pk_verify`): все — первое чтение `WAIT_REG_MEM` по адресам
0x2f97cd000 / 100 / 200 / 300. Это блоки DB-записей occlusion-запросов игры (`PIXEL_PIPE_STAT_DUMP at 0x2f97cd000, DBs
0xff, stride 16`). Начало запроса пишет в блок на шкале GPU постоянные {0, valid} (`Executor::ZpassOnTimeline`),
конец — счётчики хоста в `begin + 8 + 16k`. Опрос попадает на ещё не выполненную GPU запись начала → слив очереди +
ожидание GPU (`SyncFrom(2)`), пузырь на обоих потоках. Перед каждой occlusion-записью CP тоже сливает очередь.

Параметры этих опросов (`r6p_pk_verify2`, 35 148 опросов): все — `function 5 (>=) ref 0 mask 0xffffffff`, прочитанное
значение 0. **Условие истинно при любом значении**: чтение не может изменить исход, но каждый раз стоит слива и ожидания GPU.
Число таких опросов игра меняет от прогона к прогону (386 … 36 356).

Промежуточная попытка `SSPC_R6_CP_POLL_KNOWN` (значение метки из пакета WRITE_DATA / из блока начала запроса, таблица на
потоке 1): 35 148 известных значений, расхождений с честным чтением 0. Её заменил более простой и точный по построению
вариант 4.1 (одна точка вызова вместо ~15); код POLL_KNOWN не закоммичен.

### 4.1 `SSPC_R6_CP_POLL_TRIVIAL=1` — опрос с всегда истинным условием не читает память [E] — ПРИНЯТ (флаг выкл.)

`CommandProcessor::WaitRegMem`: если опрос по памяти и `TrivialPoll(function, ref, mask)` (`function 0`; `>=` с ref 0;
`<=` с ref ≥ mask), значение не читается (`value = 0`, условие выполнено). Остальное как раньше: статистика,
`MemoryAcquired` (CPU-записи, опубликованные к ожиданию, применяются к работе после него). Occlusion не затронут: запись
начала запроса, счётчики хоста (`vkCmdCopyQueryPoolResults`) и их порядок на шкале не меняются; пропускается только
чтение для условия, которое от значения не зависит. Единственное отличие: при включённом флаге недоступный адрес опроса с
тривиальным условием больше не даёт ошибку `MemoryUnreadable` (на PS4 такой опрос тоже ничего не ждёт).

**Когда опрос тривиален (основа доказательства).** WAIT_REG_MEM сравнивает `v = value & mask` с `ref` **беззнаково**
(GCN; у нас `u32` в `WaitRegMem`). При произвольном 32-битном `value` значение `v` пробегает все подмаски `mask`:
минимум 0, максимум `mask`. Условие истинно при любом `value` тогда и только тогда, когда оно истинно на всём этом
множестве:

| function | сравнение | истинно при любом value ⇔ | в `TrivialPoll` |
|---|---|---|---|
| 0 | always | всегда | **да** |
| 1 | `v < ref` | `mask < ref` | нет |
| 2 | `v <= ref` | `mask <= ref` | **да** (`ref >= mask`) |
| 3 | `v == ref` | `mask == 0 && ref == 0` | нет |
| 4 | `v != ref` | у `ref` есть бит вне `mask` (`ref & ~mask != 0`) | нет |
| 5 | `v >= ref` | `ref == 0` (минимум `v` = 0) | **да** (`ref == 0`) |
| 6 | `v > ref` | никогда (при `v = 0`: `0 > ref` ложно) | нет |
| 7 | зарезервировано | — (CP отклоняет пакет раньше) | нет |

В `TrivialPoll` вошли только 0, «2 при ref ≥ mask» и «5 при ref = 0». Строки 1, 3, 4 тоже тривиальны при указанных
условиях, но в игре их нет (`r6p_pk_verify2`: все 35 148 опросов — function 5, ref 0, mask 0xffffffff). Мы их не
трогаем, чтобы не менять поведение без замеров и проверки verify. Функция 6 тривиальной не бывает. Любой опрос, не
попавший в эти три случая, идёт прежним путём: точное чтение, со сливом и ожиданием GPU, если оно поверх записи на шкале.

Почему пропуск чтения ничего не нарушает. На железе CP при тривиальном условии проходит с первого опроса и запись на шкале
не ждёт. Слив очереди и ожидание GPU — только способ нашего CP получить точное значение памяти. Само значение здесь не
нужно: в `WaitRegMem` после сравнения оно идёт лишь в статистику блокировок (`w.last`), а у тривиального опроса блокировок
нет. Порядок работы GPU задают записи и барьеры на шкале, а не это чтение. `MemoryAcquired` вызывается как раньше.

Эквивалентность:
- `verify` (`r6p_pt_verify`): опросы читаются как раньше; тривиальных 386, все поверх записи на шкале, **условие не
  выполнилось 0 раз**;
- Vulkan Validation + Sync Validation (`--gpu-native-validate`, `r6p_val_base` / `r6p_val_pt`): одинаковые 71 строка,
  20× `VUID-VkWriteDescriptorSet-descriptorType-04152` (есть и в базе), 3× `VUID-StandaloneSpirv-Flat-04744`
  (переводчик), SYNC-сообщений нет. **Новых сообщений нет.**
- draws/кадр 11 899 против 11 883 в базе (в пределах разброса), dispatches 522 / 505.

A/B — серия `s2` (город, 3 круга, порядок A T P / P T A / A T P; `env_effective.txt` каждого прогона проверен):

| | A (база) | T (`POLL_TRIVIAL=1`) | T − A |

### 4.2 `SSPC_R6_CP_PREFETCH=skip` — предвыборка Gnm не в очередь [E]

`ParallelCp::Dma`: отчёт о `DMA_DATA` в `CP_DMA_READ_TAGS` (`Cp::DmaKind::ReadTagsPrefetch`, память не пишется) не
ставится в очередь потока 2. Раньше каждый такой отчёт был записью очереди: закрывал удерживаемую серию движка, сдвигал
поколение памяти фронтенда и стоил обоим потокам по записи (на потоке 2 — `Executor::Dma`: только счётчик и вызов, который
при фронтенде на потоке 1 ничего не делает).

Эквивалентность (`r6p_eq_prefetch`: `PREFETCH=skip` + `SSPC_P410_VERIFY=1` + `SSPC_CITY_ENGINE_OPT=verify` +
`SSPC_CITY_ENGINE_GBUFFER_RUNS=verify` + `SSPC_FB_STAGE_MEMO=verify` + `SSPC_DIAG_STREAM_REUSE=verify` +
`SSPC_CITY_GEOFAST=verify`): члены серий — проверено 15 730 463, расхождений 0; реплика регистров — 9 361 641 сравнений,
различий 0; память стадий — 15,58 млн, различий 0; повторное использование потока — 14,99 млн, различий 0. Не поставлено
8 012 142 отчёта, из них 6 804 619 — при удерживаемой серии. Vulkan Validation + Sync Validation (`r6p_val_pf`): те же
сообщения, что в базе.

A/B, записей очереди −42 % (10 106 → 5 815 на кадр), сливов −55 %:

| Серия | A, FPS по прогонам | P, FPS по прогонам | P − A (ср.) |
|---|---|---|---|
| s1 | 27,29 / 30,56 / 27,43 | 33,09 / 33,68 / 27,39 | +2,96 |
| s2 | 30,03 / 28,41 / 27,97 | 32,91 / 30,51 / 33,03 | +3,35; 1 % low +3,8; CP −3,75 мс |

### 4.3 `SSPC_R6_CP_RUN_POOL=1` — пул векторов членов серии [E]

Поток 2 после каждой длинной серии (>32 членов) освобождал её вектор `RunMember` (~680 байт на член). Поток 1 растил
следующий заново, цепочкой реаллокаций (сэмплер: `_Emplace_reallocate` + memmove `RunMember` ≈ 3 % потока 1). С флагом
поток 2 отдаёт вектор в пул (до 16), а поток 1, упёршись в ёмкость, берёт вектор побольше. Члены те же, меняется только
источник памяти.

Эквивалентность (`r6p_pool_verify`: `RUN_POOL=1` + `SSPC_P410_VERIFY=1` + `SSPC_CITY_ENGINE_OPT=verify` +
`SSPC_CITY_ENGINE_GBUFFER_RUNS=verify`): члены серий — проверено 23 582 379, расхождений 0; реплика регистров —
14 002 301, различий 0; из пула взято 178 932 вектора, вернулось 178 937.

### 4.5 `SSPC_CP_ASYNC_WRITES=gds` (существующий флаг CP-9) [E]

### 4.6 `SSPC_FB_STAGE_REUSE=1` (существующий флаг FB-6) — не мерился

В городе нативный commit CUE (`0x14ad0`) копирует таблицу стадии в новый блок на каждый draw. Указатель user data каждый
раз новый, поколение стадии сдвигается, и FB-6 почти не находит неизменённых стадий. Кроме того, s3 показала: при T
копирование и записи очереди кадр не ограничивают (P: −42 % записей → 0 мс). Без новых оснований A/B не ставился (P4).

## 5. Вне зоны R6-P

- `ProgramCache::Invalidate` / `FetchCache::Invalidate` (`src/runtime/gpu/shader/shader_cache.cpp`): на каждый
  диапазон записей CPU, попавший между границами кэша, — проход по всем адресам программ (3 773) и fetch-шейдеров.
  ~3 % потока 1 в городе. Нужен интервальный индекс; файлы `shader/*` R6-P не меняет (поколение кэша шейдеров).

- Кандидат 9: occlusion-запись в очередь без слива. `ParallelCp::ZpassOnTimeline` сливает очередь перед каждой записью
  occlusion-запроса; при T это ещё 10–44 тыс. сливов / 1,6–2,6 с за прогон (≈0,5–1 мс/кадр). Чтобы ставить её в очередь
  как копию, нужен запасной путь на потоке 2 для отказа исполнителя: счётчики «видимо», как `zpass_count_` CP. Зона
  occlusion защищена (исправления CITY-OPT), поэтому R6-P это только предлагает и не реализует.

## 6. Предложения для Native Render Bridge (R6-Core)

1. **Включить T (`SSPC_R6_CP_POLL_TRIVIAL=1`) в пресет города** — решение за R6-Core и пользователем. Флаг касается только
   CP и исключает «медленный режим» базы. Без него любые A/B в городе смешаны с фактором 4.0: разброс базы 2–3 FPS,
   скачками.
2. **G. Дедупликация копии таблиц CUE (commit `0x14ad0`).** По `SSPC_R6_CP_DIAG=1` 26 % полных обходов SRT стадии VS и
   33 % PS дают ровно результат прошлого обхода той же программы: меняется только адрес копии таблицы в кольце кадра
   («те же user data, другой результат» — 0). Если нативный commit переиспользует прошлую копию, когда тень стадии побайтно
   равна (в пределах эпохи кольца), указатель user data не меняется. Тогда стадия берётся из памятки без обхода, а draw
   может войти в серию (отказы «другие user data»). Оценка ≤ 1,3 мс/кадр потока 1. Зона `src/native_engine/*`; со стороны
   CP изменений не нужно. (R6-Core ведёт A/B «дедупликации снимков CUE».)
3. Мерить любые оптимизации CP в городе поверх T, сравнивая только чередующиеся прогоны и проверяя `env_effective.txt` и
   строку «waits that waited: processor memory reads» в `gpu_native.txt` (при T должна быть 0).

## 7. Ограничения

- Всё измерено только в городе (`run_native_engine.ps1 -Scene city`). Пляж, гавань и деревня не прогонялись: окна стенда
  ушли на город. T там тоже безопасен (эквивалентность не зависит от сцены), но прирост там не измерен.
- `SSPC_R6_CP_DIAG=1` дорогой (`NoteWalk`): FPS с ним 15–17, поэтому его счётчики — для долей и мест, не для времени.
- Сэмплер искажает абсолютное время; доли §2.2 — относительные.
- Строки `TrivialPoll` для функций 1, 3, 4 (тривиальных при условиях §4.1) не включены — в игре их нет.
