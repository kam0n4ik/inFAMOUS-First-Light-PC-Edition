## 3. Управление камерой

### 3.1 Фильтр стика `0x249170` **[К]** (состояние S = obj+0x1A0 / +0x420, выход obj+0x08..0x1C)

* Линейно 0..255 → −1..+1, ось y инвертирована.
* До **первого** движения стика полоса 127 ± dz считается нулём (флаг S+2 потом не сбрасывается).
* Величина отклонения — максимум по 8 направлениям к самокалибрующемуся максимуму; **начальный максимум 0,75**
  (`0x9A1D40`): до первых полных отклонений величина усиливается до ×1,33.
* Пересчёт `[dz/127 … 0.9] → [0 … 1]`: dz — из `GetControllerInformation` (наша 1 → 0,0079; умолчание игры 20/127);
  **насыщение на 0,9**.
* История 30 значений за 0,1 с: если величина меняется быстрее ±10/с, сохраняется прежнее направление.

### 3.2 Кривая и инверсия

Геттеры стика в слотах vtable +0x110 (`0x24CB80`) и +0x118 (`0x24CC10`) отдают **x·|x|** и применяют флаги инверсии
опций (`0xEFACF8+0x6D5..0x6D8`, «По горизонтали/По вертикали») **[К]**. Какой геттер читает камера — статикой **не
найдено**. Если квадратичный — скорость камеры ∝ (скорость мыши)², а не линейна, как полагает `INPUT_MAPPING.md` **[Пр]**.
В опциях есть «Чувствительность прицела» (Медленная/Нормальная/Быстрая) — она тоже действует на мышь (мышь = стик).

### 3.3 Мышь → правый стик (как сейчас, `keyboard_mouse.cpp:419-433`) **[К]**

`full = 1500 / mouseSensitivity` отсчётов/с; `s = (dx, dy)/dt/full`; при |s| > 0:
`s *= (dz + (1 − dz)·min(|s|, 1))/|s|`, `dz = mouseDeadzone = 0.10`; `Axis(v) = clamp(lround(127.5 + 127.5·v), 0, 255)`;
`dt` = время между чтениями, зажато в [2, 100] мс (:358-359); повторное чтение быстрее 2 мс отдаёт прежнее состояние.
**Остатков нет**: накопленный dx/dy расходуется целиком (:393-394), всё сверх насыщения теряется, ошибка u8 не переносится.

Найденные проблемы (без изменения кода в P4.1):
1. `mouseDeadzone = 0.10` **в ~13 раз больше** мёртвой зоны игры (0,008) — малые движения усиливаются, отклик нелинейный.
2. Потолок скорости: при чувствительности 1 насыщение уже на ~1333 отсчётов/с (в логах x = 0/255).
3. u8-квантование без переноса остатка.
4. Возможная квадратичная кривая игры (§3.2) поверх нашей.
5. Двойное применение чувствительности/инверсии (игра + наше).

### 4.2 Подтверждённый формат двух контактов **[К]**

`ScePadData` (static_assert в `pad.cpp:69-74`; смещения от начала ScePadData, в объекте игры +0xD0):
`touch_num` u8 @+0x34, reserve[3], `time_since_touch_held_down` u32 @+0x38, `touch[0] {x u16, y u16, id u8, reserve[3]}`
@+0x3C, `touch[1]` @+0x44.

Что читает игра (vtable пада `0xCDDF70`): +0xA0/+0xA8 — x/y первого пальца (`0x24E8A0`/`0x24E8F0`); +0xB0/+0xB8 —
x/y **второго, только при `touch_num ≥ 2`** (`0x24E940`/`0x24E990`); +0xC0 — `touch_num`; +0xC8 — `res_x/res_y`.
Нормализация `0x618C40`: x 0..res_x → −1..+1, y 0..res_y → **+1..−1** (вверх положительно), с зажимом. Умолчание игры —
**1920×942** (`0x9A1BA0`/`0x9A1BB0`), заменяется `touch_resolution` из `GetControllerInformation` (`0x24B088-0x24B0B9`).
**`id` и `time_since_touch_held_down` в модуле пада не читаются** — позиция берётся по номеру слота (статика; доступ
другим путём на 100 % не исключён). Логические биты: парсер `0x24B340`, таблица `0x9A1EC0`.

### 4.3 Текущие возможности обработки DS4 **[К]**

* SDL HIDAPI отдаёт оба пальца в каждом отчёте (`SDL_hidapi_ps4.c:1025-1035`), но только при `enhanced_reports`; x
  нормирован ×1/1920, **y ×1/920** (`:1018-1019`); мост переводит в пиксели x×1920, y×941 (`controller_state.cpp:51-55`) —
  y растянут на 2,3 %, низ доходит до ~963, а наш `GetControllerInformation` сообщает 950 → нижняя полоса зажимается.
* id мост генерирует сам (1..127, общий счётчик, `controller.cpp:141-144`); при отпускании первого пальца
  `input_host.cpp:62-71` сдвигает второй в слот 0 — **оба пальца сохраняются, ничего не теряется до SecondSonPC**.
* Физический клик (`SDL_GAMEPAD_BUTTON_TOUCHPAD`) идёт отдельной кнопкой (`sdl_window.cpp:423-427`) — касание и клик
  различаются.
* Клавиатура: Tab — клик + один палец в центре (y 471 при высоте 942); T + мышь — один палец (`keyboard_mouse.cpp:397-445`).

### 4.4 Недостающие функции

1. **Клавиатура/мышь не может дать `touch_num = 2`** — двухпальцевый клик (`0x20000`) недостижим: поглощение «двумя
   пальцами» и толкание машины **не выполнимы без DS4** (обязательно для кампании, если игра не предлагает обходной путь —
   **не проверено в игре**).
2. Высота тачпада: `GetControllerInformation` 950 и `kTouchHeight` против умолчания игры 942 и y×941 моста (выровнять
   на 942 — **[Пр]**: значение реального DS4; пересчитывать y SDL как ×920 → 942).
3. Свайп: направление и порог неизвестны — нужна игровая проверка у двери (`u_hint_vor_door`).
4. Режим G (держать боком) при потере фокуса не сбрасывается (`keyboard_mouse.cpp:328-344`) **[К]**.

### 4.5 Предлагаемая схема клавиатуры и мыши для тачпада

Принцип: для обычной игры — назначаемые действия; для сложных случаев — виртуальный тачпад.

* **Режим C (готовые жесты, основной):** назначаемые действия
  * `TouchClick` (Tab): клик + один палец в центре (как сейчас);
  * `TouchClickTwoFingers` (по умолчанию Shift+Tab — **[Пр]**, назначаемо): два пальца (0.25, 0.5) и (0.75, 0.5) +
    бит клика, удерживается пока держится клавиша → `0x20000`;
  * `TouchSwipe{Left,Right,Up,Down}`: макрос — палец ставится и сдвигается на заданную долю ширины за N кадров
    (≥ 2 кадров движения: игра считает скорость за кадр); направление по умолчанию для двери — подтвердить в игре.
* **Режим A (один виртуальный палец):** T + мышь (есть) — палец рисуется движением мыши.
* **Режим B (два виртуальных пальца):** удерживаемая клавиша включает пару; мышь двигает пару целиком, колесо — расстояние
  между пальцами, Ctrl+колесо — угол; отпускание клавиши — оба пальца отпускаются (корректное завершение касаний).

### 4.6 Возможности сенсорных устройств Windows (по документации и исходникам SDL; на железе не проверено)

* Сенсорный экран: `WM_TOUCH` → `SDL_EVENT_FINGER_*` (SDL: `SDL_windowsevents.c:2144`, `RegisterTouchWindow` в
  `SDL_windowswindow.c:541`); `WM_POINTER` SDL 3.5 обрабатывает только для пера (`:1355`). Можно отображать пальцы
  экрана на виртуальный тачпад (2 первых контакта).
* Precision Touchpad: сырые контакты — через Raw Input на HID usage page **0x0D / usage 0x05** + `HidP_*` (Contact Count,
  Contact ID, Tip Switch, X, Y); только PTP-тачпады (Windows 10+); устаревшие драйверы Synaptics/ELAN отдают только мышь;
  Windows продолжает двигать курсор и выполнять системные жесты, `RIDEV_NOLEGACY` на дигитайзеры не действует **[Пр]**. В
  SDL3 этого пути нет — свой код. **Независимые сырые контакты не обещаются** до проверки на устройстве.
* Тачпад DS4 Windows как PTP не видит (вендорский отчёт, читает SDL HIDAPI); Steam Input может забирать DS4 себе **[Пр]**.

### 4.7 Архитектура слоя

```
Host Input (SDL / Raw Input / WM_TOUCH)
  → Touch Input Adapter (SecondSonPC, src\input\touch.*): до 2 контактов, стабильные id в рамках жеста,
    координаты → 0..1919 × 0..941, порядок «начало → движение → конец», источник (DS4 / виртуальный / экран)
  → Guest DualShock Touch State (Pad::Fill, src\runtime\pad\pad.cpp): touch_num, touch[0..1], бит клика
```
Правила: один источник за жест (реальный DS4 и виртуальные контакты не смешиваются в одном жесте — побеждает начавший);
при потере фокуса все виртуальные пальцы отпускаются; не зависит от Vulkan и графического бэкенда; слоты заполняются с 0
(игра читает второй палец только при `touch_num ≥ 2`).

### 4.8 Ограничения и риски

* Если игра где-то читает `id` (не найдено статикой) — сдвиг слотов при отпускании первого пальца может дать «прыжок» жеста.
* Свайп-макрос может не совпасть с порогом игры — нужна игровая проверка.
* Двухпальцевый клик у DS4 физически — клик + 2 касания; виртуальный — то же; если игра требует `time_since_touch` —
  не найдено.

### 4.9 Программа проверки игровых эпизодов (PENDING, нужен пользователь и/или DS4)

## 10. Источники игровых подсказок (закрывает главный пробел `PC_INPUT_PROMPTS_PLAN.md`)

### 10.1 Пакет KCAP **[К]** (проверено на lang_*, pulse, i3, core_common)

`+0x04` u16 версия (13) и u16 вид; `+0x28` u32 размер заголовка H (с него — данные); `+0x2C` u32 размер данных; `+0x78`
16 байт хэша; `+0xA0` число сегментов; `+0xB0` число блоков. Сегменты `{u8 флаги, 0xFF, u16 пул, u32 размер, u32 смещение}`:
пул 0 — память CPU; пул 1 (флаги 0x12/0x13) — память GPU (текстуры); пул 2 — служебные. Блоки по 12 байт
`{u16 выравнивание, u16 тип, u32 размер, u32 смещение}`; имён ресурсов нет. Заголовков `GNF `/`DDS ` нет: текстура — сырые
данные в GPU-сегменте + 32-байтный T# в CPU-сегменте (в объекте текстуры T# по +0x18, id по +0x38). Проверенные текстуры —
тайлинг 13 (Thin_1dThin: микротайлы 8×8 Мортона, построчно) — снимается без макротайлов.

### 10.2 Иконочный шрифт в `lang_<язык>_text.xpps` **[К]**

* Корневой список: 15 указателей на 7 текстур, 7 шрифтов и таблицу строк.
* Объект шрифта: +0x18 id, +0x20 слот (у иконочного −1), +0x28 id текстуры, +0x30 1/size, +0x34 size (50), +0x38 глифы,
  +0x40 число глифов, +0x50 1/ширина и 1/высота атласа; глиф — 32 байта `{u16 код, x, y, w, h, s16 ox, oy, u16 advance}`.
* Иконочный шрифт: id `6369609b6db87e0f`, 58 глифов U+F080…U+F116. Русский пакет: объект 0xdda38, таблица глифов 0xdda90
  (прежнее 0xdda50 — поле id шрифта); английский — таблица 0xbf570.
* **Атлас:** id `29c11c0cac5b95ed`, T# по смещению 0x4f0; **512×512, формат 10 (8_8_8_8 UNORM, RGBA8), тайлинг 13, 1 mip,
  ровно 1 МиБ**; данные: ru 0x153ce8, en 0x135808; хранится снизу вверх (строка = 511 − y); иконки белые, форма — альфой.

  только смещения.
* Содержимое (проверено на декодированном изображении): F080–F083 ○□△✕ (50×50); F084–F087 L1/L2/R1/R2 (58×50); F088/F089

* Кодов F08E, F08F, F09B, F0B5, F0B6 в атласе **нет** — их подменяет код игры (§10.3).
* `lang_*_text.xpps` открывается **один раз за сессию** и читается целиком (~8 мс между open и close, в т. ч. в 30-мин

## 12. Автоматическая смена подсказок (гистерезис)

Режимы `prompts = auto | keyboard | gamepad`. В `auto`: на геймпад — при отклонении стика > 0,5 или нажатии кнопки; на
клавиатуру — при нажатии клавиши/кнопки мыши или «заметном» движении мыши (сумма > N отсчётов за 100 мс); после
переключения режим держится не меньше 1,5–2 с; дрожание стика в мёртвой зоне и фоновое движение мыши не переключают.
Смена = перезапись атласа (A2) — дешёвая, не чаще раза в 1,5 с.

## 15. Возможные проблемы

* Нажатие короче кадра теряется (нет защёлки) — при 30 FPS короткие тапы клавиш могут не срабатывать; решение — удерживать
  нажатие до следующего чтения (защёлка «до первого чтения»), **[Пр]** проверить, не ломает ли это двойные нажатия.
* Esc = пауза и отпускание курсора одновременно.
* Гравитация в эмуляции и у моста 9,81 × 0,098 = **0,961 g**; игра пересчитывает калибровку только при ||a| − 1| < 0,05 →
  запас 0,011; реальный DS4 с погрешностью может выпасть **[Пр]**; честно — ×1/9,80665.
* Тряска засчитывается только при > 2,5 g по любой оси (`0x24B790`) — эмуляция X даёт (1 + 2,5·sin) g, т. е. до 3,5 g —
  достаточно; прежние ±1,5 g были малы **[К]**.
* Вертикальный хват (`u_brief_tilt_controller`) не эмулируется — режим G даёт только «боком».
* Привязка всех адресов к версии 01.07.

## 16. Порядок реализации (следующая фаза PC Input, не P4.1)

1. Тачпад: `TouchClickTwoFingers` + высота 942 + сброс G при потере фокуса (малые, изолированные, тестируемые).
2. Мышь: мёртвая зона 0,01–0,02, перенос остатка, X/Y-чувствительность, проверка квадратичной кривой в игре.
3. Подсказки: A (оверлей ФС с проверкой SHA-256 и разбором KCAP) → A2 (смена на лету) → гистерезис.
4. `input.toml` + своё меню (ImGui-оверлей) переназначения.
5. Свайп-макрос после игровой проверки двери; режим B; сенсорный экран.
6. B1-камера — исследовательский прототип; B2 — отдельная фаза.

## 17. Минимальный работоспособный прототип (следующая фаза)

Флаг `[Input] prompts = "keyboard"`: при чтении `lang_*_text.xpps` нативная ФС подменяет байты атласа (1 МиБ, тайлинг 13)
готовыми ячейками для текущей раскладки, после проверки SHA-256 атласа; плюс клавиша `TouchClickTwoFingers`. Проверка:
поглощение двумя пальцами, меню улучшений, подсказка прыжка «Space».

## 18. Задачи, требующие отдельной фазы

Нативная камера B2; HD-иконки через свой рендерер (B'); Precision Touchpad; перекрытие строк про тачпад/наклон (`_p`);
своё окно и полноэкранный режим (Phase 4/5); профили Steam Input.

### Проверено / не проверено

* Проверено статикой и логами: цепочка ввода, опрос раз в кадр, формат тачпада и его чтение игрой, логические биты, карта
  действий, атлас (декодирован, ✕○□△ видны), механизм выбора глифа.
* **Не проверено в игре:** свайп-порог, квадратичная кривая камеры, перезаливка атласа на лету, прохождение эпизодов с
  двумя пальцами, сенсорные устройства Windows. **DS4 — PENDING HARDWARE.**
* Прототип в P4.1 **не делался**: изменения ввода в P4.1 не требуются для графики, а без игровой проверки (двери, двух
  пальцев) прототип не доказуем; отделён в следующую фазу, чтобы не задерживать графику.
