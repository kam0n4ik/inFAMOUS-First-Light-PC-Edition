## 2. Как движок формирует draw (доказано кодом и измерениями)

### Тени: `0x43d590` → `0x43d480`

`0x43d590(param_1, list)` — метод класса прохода (вызывается через таблицы `0xcd87e0`, `0xd68678`, `0xd78d70`) [A]:

- вход — диапазон `[lo, hi)` отсортированного списка видимых объектов `plVar5[0x9b8]` (8-байтные записи: младшие 16 бит —
  индекс объекта в таблице `plVar5[0x9b7]` (записи 0x80 байт: `+0x18` экземпляр меша → меш и материал, `+0x40..0x7f`
  матрица объекта), старшие биты — ключ сортировки);
- вариант с экземплярами (`param_1 + 0x1f != 0`): соседние записи, у которых ключ совпадает выше 16-го бита
  (`key ^ first < 0x10000` — тот же меш и материал), — одна группа. Для группы — память из кадрового аллокатора
  `0x1f0870(&0xf1bcd0, n * 0x48, 16)`, на каждый объект запись 0x48 байт: 4 строки (матрица объекта × матрица
  вида-проекции каскада) + 8 байт нулей (+ `0x451700`, когда у прохода есть доп. данные). Материал (`0x448640`)
  ставится, только если он сменился; затем `0x43d480(param_1, R, records, n, mesh)`;
- вариант без экземпляров: на каждый объект — отсечение (`0x11c890` / `0x11cde0`), V# буфера костей (шаг 0x30) и
  `0x1a1960`.

`0x43d480` [A, REA и Ghidra]: `0x61e260` строит V# констант (шаг 0x48, n записей), `0x16b70` ставит его в слот
`param_1 + 0x121` стадии `0x27530(0)`, `0x16aa0` — таблица V# вершин меша (`mesh + 0x60`, `mesh + 0x6c` потоков) в VS,
`0x6250b0` — `NUM_INSTANCES n`, `0x623740` — список треугольников, `0x624f80` — 16-битные индексы, commit `0x14ad0`,
`0x623c60` — `DRAW_INDEX_2` (`mesh + 0x68` индексов от `mesh + 0x58`) и 4-словный NOP после него.

Измерено (`SSPC_DIAG_ENGINE_RUNS`, город, 3 окна по 10 с, на кадр) [E]:

| | draw | экземпляров | уникальных мешей | мешей в > 1 контексте (их draw) |
|---|---|---|---|---|
| тени `0x43d480` | ~4 900 | ~22 650 (4,6 на draw) | ~3 830 | ~275 (~640) |
| меши `0x1a1960` | ~4 750 | — | ~3 270 | ~400 (~930) |

Контекстов (проход × подконтекст; каскады — свои контексты) — 54 за кадр.

Ответы на вопросы этапа 1:

- **откуда список теневых кастеров** — видимые объекты прохода, отсортированные по ключу (меш + материал); каскад —
  свой вызов цикла со своим диапазоном и своей матрицей вида-проекции [A];
- **почему ~4 800 теневых draw** — по одному на группу одинаковых объектов в каскаде: движок **уже рисует одинаковые
  объекты одним draw с экземплярами** (22 650 объектов → 4 900 draw) [A + E];
- **повтор между каскадами мал**: только ~275 мешей рисуются больше чем в одном контексте (~640 draw, ~13 % теневых).
  Объединить каскады в один draw можно только с выбором каскада в шейдере (другая семантика вывода) — не делалось;
- **повторная CPU-подготовка одинаковых объектов** на стороне движка — нет: матрицы на кадр, каскад и объект свои [A];
- **что меняется между draw одного материала**: таблица V# вершин (адрес копии CUE в памяти кадра), индексы, у теней —
  V# констант (адрес и число записей) и `NUM_INSTANCES` [A + E].

### Меши: `0x1a1960` (проход 14 и другие)

Подробно — `docs/CITY_ENGINE_REVERSE.md` §3. Draw за draw одного материала отличаются только таблицей V# вершин и
индексами [A + E].

### PM4 на draw

Город, 34,3 млн draw за прогон (`SSPC_DIAG_PACKET_TIME`, `logs/runs/p5_diag1`) [E]: на draw ~13 пакетов — SET_SH_REG
4,3, NOP 3,9 (маркеры CUE, NOP драйвера после draw), SET_CONTEXT_REG 1,9, SET_UCONFIG_REG 1,0 (тип примитива), INDEX_TYPE
1,0, NUM_INSTANCES 0,65; записей регистров ~23, из них меняют значение ~8 (34 %). Время CP на всё, кроме самого пакета
draw, — ~0,5 мкс на draw (≈6 мс за кадр); пакет draw вместе с подготовкой и публикацией записи — ~2,2 мкс.

## 3. Где лишняя работа (этап 2)

| Поток | Что | Доля / цена |
|---|---|---|
| движок | запись PM4, CUE | не на критическом пути: главный поток игры большую часть кадра ждёт CP (docs/PHASE2_P25_PERFORMANCE.md) |
| 1 | разбор PM4, запись регистров, журнал | ~0,5 мкс на draw, ~6 мс за кадр |
| 1 | подготовка draw (`PrepareDraw`): обход SRT, разбор ресурсов, ключ, модуль, копия стадии в запись | ~23 мс за кадр (Phase 4, перепись); у draw меша/тени по шаблону 0,6–0,9 мкс |
| 1 → 2 | запись в очередь (`Record` с `DrawDescriptor` и двумя копиями стадий) | копирование — ~10 % потока 1 |
| 2 | на каждую запись: журнал регистров, `Batchable` с соседями, `RecordDraw` (цели, привязки, дескрипторы, состояние) | p462 — 2,4 мкс на запись даже со склейкой Phase 3 (6,4 мс за кадр), тени ~1,6 мкс |

Главная избыточность — **draw, отличающиеся от предыдущего только геометрией (и константами экземпляров), каждый
проходит весь путь draw в обоих потоках**: запись в очередь, проверки, подготовку стадии, сверку с соседями, полную
запись Vulkan. Таких draw в городе ~7–8 тыс. из ~12 тыс. за кадр.

## 4. Реализация: серии draw движка (`SSPC_CITY_ENGINE_OPT=1`, в пресете `SSPC_CITY_PERFORMANCE=1`)

### 4.1 Движок: метка draw (`src/engine/render/draw_runs.*`)

Зонды на входе (`guest_probe.h`) `0x1a1960` и `0x43d480`: устанавливаются только при совпадении FNV-1a тел функций
(те же, что у переписи Phase 3), ELF на диске не меняется. Функция выполняется как есть, затем зонд проверяет, что
последние 4 слова DCB записаны этим вызовом и это NOP драйвера после draw с нулевым первым словом тела, и пишет в тело
метку `{0x52505353 "SSPR", источник (1 меш, 2 тень)}`. **Ни одного слова PM4 больше**: тело этого NOP аппаратура
игнорирует (его же использовал прямой путь P5.3). Метка — только подсказка: решение принимает рантайм по регистрам.
Без нашего бэкенда (мост shadPS4) зонды не ставятся.

### 4.2 Поток 1: серия — одна запись (`parallel_cp.cpp`)

- помеченный draw, который может вести серию (подготовлен, VS + PS, VS без обхода SRT с вершинами из fetch-таблиц, без
  записей в память), **не публикуется сразу**: его запись удерживается, журнал регистров — на момент этого draw;
- следующий помеченный draw присоединяется к серии, если с предыдущего изменились только группы user data VS, индексов
  и параметров draw; шейдеры, user data остальных стадий, тип примитива и индексов, экстенты — те же; вершинные V#
  прочитаны из его таблиц (как `DecodeResources`) и совпадают с первыми по формату и шагу. Если отличаются и другие
  user data VS (константы экземпляров теней), план стадии разбирается заново (`RedecodeStage`, тот же ключ
  специализации) и допускается отличие только в гостевых буферах VS (тот же формат и шаг, не записываемые, ≤ 16 КиБ);
- член серии — компактная запись `Cp::RunMember` (~0,6 КБ: user data VS, индексы, экземпляры, потоки вершин, свои
  буферы) в векторе записи первого draw: **без своей записи в очереди, подготовки, копии стадий и проверок**;
- любая другая запись, слив очереди, изменение памяти или иной вызов процессора сначала публикует удерживаемую серию —
  порядок команд не меняется. До 256 draw в серии.

### 4.3 Поток 2: запись серии (`vk_executor.cpp`, `DrawRunMembers`)

Первый draw — обычный `RecordDraw` (цели, конвейер, все дескрипторы, push-константы, динамическое состояние). Каждый
следующий — только своё: вершинные буферы и индексы прямо из видеопамяти кэша буферов (`Classify` = All), для теней —
push-дескрипторы своих констант (копия в потоковое кольцо) и своих user data (flatbuf), байт `buf_offsets` в
push-константах, затем `vkCmdDrawIndexed` со своими индексами, смещением вершин и числом экземпляров. Если так нельзя
(диапазон не резидентен, первый draw не записан как простой индексированный, раскладка без push-дескрипторов, буфер
команд полон) — draw записывается полностью обычным путём с подготовкой первого draw и своей геометрией.

### 4.4 Быстрый путь PM4 (`SSPC_CITY_ENGINE_AHEAD=1`, не в пресете)

После помеченного draw командный процессор просматривает пакеты до следующего помеченного draw; если это только
SET_SH_REG, тип примитива, тип индексов, NUM_INSTANCES и обычные NOP, исполняет их тем же `Execute` подряд, без общего
цикла `Step` (декодирование, учёт, указатель чтения). Корректен (проверка регистров — 0 различий), но выигрыша не дал
(раздел 6) — оставлен отдельным флагом.

## 7. Отклонено и не сделано

- **Сокращение числа draw внутри движка** (склейка разных мешей, каскадов): движок уже рисует одинаковые объекты
  экземплярами; общих мешей между каскадами ~13 % теневых draw, и их объединение требует выбора каскада в шейдере.
  Не делалось.
- **Подавление PM4 членов серии в движке** (не вызывать оригинал, писать компактный пакет): CUE движка хранит тень
  стадий и флаги изменений — пропуск его вызовов ломает его состояние для следующих draw. Вместо этого PM4 остаётся, а
  рантайм не готовит и не записывает каждый draw отдельно.
- **Быстрый путь PM4** (`SSPC_CITY_ENGINE_AHEAD=1`) — корректен, выигрыша нет (B ≈ A): цикл `Step` — малая доля потока 1.
- Кэш по содержимому таблиц ресурсов (P5.3 Native Render Frontend) не повторялся: ~3 500 из ~4 700 стадий читают
  уникальные данные объекта (docs/REA_ENGINE_REVERSE.md §6).

## 8. Ограничения и что дальше

- 60 FPS не достигнуты (~30 FPS в городе, раздел 6). После серий ограничитель — поток 1: полная подготовка draw, не попавших в серии
  (G-буфер `0x1a1770`, освещение: обход SRT ~22 % потока), разбор PM4 и запись регистров (~20 %), копирование записей
  (~10 %).
- Дальше: G-буфер `0x1a1770` (константы 0xd4 байт на draw + обход SRT PS) — серии с разбором таблицы движка вместо
  общего обхода SRT; меньше копий в записи очереди.
- Phase 6 (`docs/CITY_ENGINE_RESOURCES.md`): серии G-буфера `0x1a1770` с зондом смены материала — поток 1
  34,1 → 30,3 мс в контрольной серии, `SSPC_CITY_ENGINE_GBUFFER_RUNS=1` — в пресете `SSPC_CITY_PERFORMANCE=1`.
- Метка — по хешам тел двух функций; на другой версии игры зонды не ставятся, серий нет (поведение прежнее).
