# P4.7 — листва без потери качества: причина падения FPS и ускорение

Дата: 2026-10-11. База — `b2f1292` (в ней исправленный дым SSPC-020, `01a3edd`). Бэкенд — нативный
(`--gpu-backend sspc`), ПК: RTX 2060 6 ГБ, Ryzen 5 5500, 32 ГБ. Файлы игры не менялись, листва не отключалась,
настройки качества не трогались.

## Коротко

- **Причина** — время процессора на каждый draw в потоке GPU (командный процессор один). Листва удваивает число
  draw (2760 → 5640 за кадр), время CP растёт с 21,9 до 32,0 мс, а время GPU — только с 15,8 до 16,5 мс (GPU
  простаивает около половины кадра). Перерисовка и альфа-тест — не причина: на GPU листва добавляет 0,7 мс.
- **«Падение в 2 раза»** — квантование кадров по vblank (60 Гц). Без листвы кадр укладывается в 16,7 мс через раз
  (медиана 56–58 FPS), с листвой — нет, и кадр ждёт второй vblank (33,3 мс, медиана 30 FPS); часть кадров уходила на
  третий (50 мс, 10,7 % кадров, 1 % low 19,7 FPS).
- **Сделано** (каждое изменение — отдельно, A/B ×3 чередованием, с режимом проверки):
  1. мемо подготовки стадий шейдеров — включено, CP −1,8…−3,3 мс в каждой паре;
  2. чтения памяти фронтендом из уже найденных участков — включено, CP −1,8 мс в среднем (−4,2 / +0,9 / −2,1);
  3. повторное использование потоковых копий в пределах пакета — включено, CP −0,45…−0,58 мс в каждой паре;
  4. тень привязок дескрипторов/буферов — проверено, выигрыша нет → выключено по умолчанию (эксперимент);
  5. общие layout-ы конвейеров — проверено, выигрыша нет → выключено по умолчанию (эксперимент);
  6. мемо «сплющенных» пользовательских данных — 0 попаданий за все прогоны → удалено.
- **Итог «до/после»** (2 пары чередованием, раздел 7):
  - пляж в густой листве: CP 29,0 → 26,7 мс, средний FPS 32,0 → 34,5;
  - тяжёлый участок гавани: CP −3,8 мс, кадров на 50 мс 38,7 → 17,7 %;
  - деревня: пара 1 −3,1…−3,5 мс, пара 2 испорчена посторонней нагрузкой — вывод по деревне не окончательный.

  Медиана остаётся 30 FPS: до 16,7 мс за кадр нужно CP < ~15 мс (раздел 9).
- **Изображение:** режимы проверки сравнивают каждое попадание кэша с полным пересчётом — 0 расхождений на трёх
  сценах (раздел 8). Vulkan Validation + Sync Validation — 0 сообщений на трёх сценах. На скриншотах грубых
  отличий нет.

## 0. Как мерили

- Сцены `tools\tests\p46_runs.ps1`: `beach` — маршрут пляжа (после поворота камеры на 56–60 с — густая листва),
  `early` — гавань, `user1022` — лесная деревня с кострами. Каждый прогон — 90 с со свежей копии сохранения.
- Окно **A** — 30–55 с (`warmup.json`, пляж до поворота, листвы в кадре нет), окно **B** — 62–88 с (`stats.json`,
  густая листва). Метрики — из `gpu_frames.csv` (`tools\frame_stats.py`): средний FPS, медиана, 1 % low, P95/P99
  времени кадра, доля кадров дольше 33 мс (третий vblank и дальше), время CP, запись команд, занятость GPU,
  draw/dispatch на кадр. VRAM — из итоговой строки прогона.
- A/B одного изменения — один и тот же exe, переключатель окружения, «выкл»/«вкл» чередуются (3 пары, скрипт
  `fol_ab.ps1`). Разброс между прогонами одной конфигурации — ±1–2 мс CP, поэтому решение принималось по знаку
  разности **в каждой паре** и по счётчикам работы, а не по одному среднему.
- Диагностика: `SSPC_DIAG_DRAW_HISTO` (draw по конвейерам двух кадров), `SSPC_DIAG_SAMPLE` (сэмплирующий профиль
  CPU потока GPU), `SSPC_DIAG_MEMO_STATS`, `SSPC_DIAG_STREAM_STATS`. Логи — `logs\foliage\`.

## 1. Почему листва роняла FPS

Пляж, исходная сборка (`fol_base`, 3 прогона):

| | A — без листвы | B — густая листва |
|---|---|---|
| средний FPS | 39,5 | 29,1 |
| медиана FPS | 39,2 (кадры 16,7 и 33,3 мс вперемешку) | 29,9 |
| 1 % low | 26,9 | 19,7 |
| P95 / P99 кадра | 33,9 / 34,2 мс | 44,9 / 50,5 мс |
| кадры дольше 33 мс | 0,17 % | 10,7 % |
| время CP за кадр | 21,9 мс | 32,0 мс |
| из него запись команд | 17,9 мс | 26,2 мс |
| занятость GPU | 15,8 мс | 16,5 мс |
| draw / dispatch за кадр | 2760 / 581 | 5644 / 579 |
| VRAM | 1557 МиБ | 1557 МиБ |

Кадр игры — это время CP (разбор PM4, подготовка шейдеров, запись Vulkan) плюс хвост GPU: игра ждёт конца кадра
(EOP). +2880 draw дают +10 мс CP — около 3,5 мкс процессора на draw. GPU остаётся недогруженным (16,5 из 33 мс),
поэтому дело не в перерисовке листвы и не в альфа-тесте: на GPU весь прирост листвы — 0,7 мс.

Куда уходит время CP в окне B (сэмплирующий профиль потока GPU, `logs\foliage\fol_sampleB`, 14 771 сэмпл):

| функция | включительно |
|---|---|
| `Executor::Draw` | 66,3 % |
| драйвер NVIDIA (символ `vkGetInstanceProcAddr` — ближайший экспорт драйвера без символов) | 42,9 % |
| `ShaderFrontend::PrepareStage` (подготовка двух стадий на каждый draw) | 30,9 % |
| `Executor::BindStage` | 17,8 % |
| `SrtProgram::Run` (обход SRT игры) | 10,7 % |
| `memmove` | 6,1 % |
| `ProgramCache::Get` | 4,7 % |
| `Core::MemoryManager::CopySparseMemory` | 4,6 % |
| `Executor::TimelineReader::Read` (чтения памяти фронтендом) | 4,1 % |

В окне A доля драйвера — 52,7 %: с листвой растёт в основном наша подготовка draw, а не драйвер.

## 2. Как рисуются листья и ветки

Гистограмма draw по конвейерам двух кадров (`logs\foliage\fol_histo\draw_histo.txt`, кадр 1900 — до поворота,
кадр 2553 — листва; 2760 → 5627 draw, 300 → 337 конвейеров). Что добавила листва:

| конвейер | цель | draw A → B | экземпляров на draw | вершин на draw |
|---|---|---|---|---|
| p86 | карта теней 1024×1024, только глубина | 965 → 2053 | 5,47 | 1555 |
| p314 | 1920×1080, цвет (формат 97) + глубина | 55 → 883 | 1,0 | 214 |
| p92 | карта теней 1024×1024 | 16 → 798 | 1,0 | 300 |
| p105 | G-buffer 1920×1080 (RGBA8) + глубина | 16 → 142 | 2,0 | 126 |
| p87 | карта теней | 132 → 230 | 11,9 | 4017 |
| p89, p94, p88, p90 | карта теней | +108 | 2,8–72 | 180–4015 |
| p103, p139, p461, p102, … | G-buffer | +~150 | 1–10 | 16–850 |

- Около 2100 из ~2870 добавленных draw — **тени**: каждый куст/ветка рисуется в карту теней, часть — инстансингом
  (p86: 2053 draw = 11 230 экземпляров).
- Основной вид — p314 (~830 draw по одному экземпляру) и G-buffer (~250 draw).
- Смешивания в этих конвейерах нет (`blend0 0x0`): листва не прозрачная, без сортировки и без альфа-смешивания.
- Конвейер на тип листвы один и тот же; draw отличаются пользовательскими данными (указатели на константы и
  буферы экземпляров) — промахи мемо по пользовательским данным приходятся на регистры VS 0x0014, 0x0004, 0x0054.

## 3. Можно ли использовать общую геометрию

Проверено, а не предположено:

- **Игра уже делится геометрией.** Один и тот же меш рисуется инстансингом (p86 — по 5,5 экземпляра на draw) и
  ссылается на одни и те же буферы вершин. Буферы игры в SecondSonPC импортированы как память хоста
  (`VK_EXT_external_memory_host`, резидентно 181 МиБ) — крупная геометрия не копируется вовсе.
- **Повторно копировались мелкие диапазоны.** Константы и небольшие буферы читаются через потоковое кольцо, и одни и
  те же байты копировались по нескольку раз за кадр: один меш рисуется в каждый каскад теней и в основной проход.
  `SSPC_DIAG_STREAM_STATS` за прогон пляжа: новых копий 2,66 млн (2823 МиБ), повторов тех же байт в этом же кадре
  3,80 млн (2382 МиБ) — **57 %**, изменившихся 371. Это закрыто изменением 3 (раздел 6).
- **Объединять draw с разными константами в один** (мульти-draw/инстансинг на стороне эмулятора) — не делали: это
  меняет поток команд игры (порядок, состояние на draw, запросы), риск велик, а выигрыш упирается всё равно в
  подготовку каждого draw.

## 4. Что уже кэшировалось

- Программы шейдеров (по адресу, идентичность — XXH3-128 кода), модули по ключу специализации (643 за прогон),
  конвейеры (406 графических + 102 вычислительных за весь прогон, в установившейся сцене новых нет), состояние
  конвейеров, текстуры (`texture memo`: 21,7 млн попаданий / 53 тыс. промахов), цели рендера (9,3 млн / 0,32 млн),
  буферы игры (кэш буферов, импорт памяти).
- **Не кэшировалось:** подготовка стадии на каждый draw (обход SRT, разбор ресурсов, ключ специализации, поиск
  модуля), чтения памяти игры фронтендом, мелкие потоковые копии.

## 5. Где SecondSonPC делал лишнюю работу

1. **Подготовка стадии с теми же входами.** 27,5 % всех подготовок стадий (5,67 млн из 20,6 млн за прогон,
   `fol_diag3`) имели тот же адрес программы, начало привязок, регистры, пользовательские данные и не видели
   изменений памяти, но заново проходили SRT, разбирали ресурсы, строили ключ и искали модуль.
2. **Каждое чтение памяти фронтендом** (обход SRT — около 11 мелких чтений на стадию, 165 млн за прогон) шло через
   менеджер памяти игры: виртуальный вызов, обход таблицы страниц, `CopySparse`.
3. **Мелкие диапазоны копировались в кольцо повторно** в том же пакете: 10,2 млн диапазонов, 2,48 ГиБ за прогон.
4. **Дескрипторы переотправлялись целиком на каждый draw**: 64 % из них совпадали с предыдущим draw. Убрать их
   получилось (изменение 4), но времени это не дало: push-дескрипторы драйвера дешёвые.

## 6. Что ускорено

| # | изменение | переключатель | счётчики работы (пляж) | A/B ×3, CP «вкл − выкл» по парам | решение |
|---|---|---|---|---|---|
| 1 | мемо подготовки стадий (`ShaderFrontend::PrepareStage`) | `SSPC_DIAG_STAGE_MEMO=off` / `verify` | 27,5 % стадий берут прошлую подготовку | −3,34 / −2,01 / −1,83 мс | **включено** |
| 2 | чтения памяти из найденного участка памяти (`TimelineReader::Read`) | `SSPC_DIAG_READ_RUNS=off` / `verify` | 199 млн чтений из участка, 9 поисков, 0 через менеджер | −4,18 / +0,93 / −2,12 мс | **включено** |
| 3 | повтор потоковой копии в том же пакете (`GuestRangeImpl`) | `SSPC_DIAG_STREAM_REUSE=off` / `verify` | 10,2 млн копий (2,48 ГиБ) не делались | −0,54 / −0,58 / −0,45 мс; GPU −0,15…−0,34 мс | **включено** |
| 4 | тень привязок (инкрементальные push-дескрипторы, пропуск VB/IB) | `SSPC_DIAG_BIND_SHADOW=on` | дескрипторов отправлено на 64 % меньше | +0,27 / −0,84 / −0,08 мс | выключено (не доказано) |
| 5 | общие layout-ы конвейеров по сигнатуре | `SSPC_DIAG_SHARED_LAYOUTS=on` | доля переотправленных дескрипторов 36,5 → 34,3 % | 0,00 / −0,12 / +0,70 мс | выключено (не доказано) |
| 6 | мемо «сплющенных» пользовательских данных | — | 0 попаданий во всех прогонах | — | удалено |

Подробности:

1. **Мемо стадий.** У каждой аппаратной стадии запоминается последняя готовая подготовка и её входы: адрес
   программы, начало привязок, версия регистров времени выполнения, эпоха кэша программ, 16 слов пользовательских
   данных и поколение памяти. Поколение увеличивается при любом изменении памяти игры, о котором знает бэкенд
   (запись CPU, DMA, запись шейдером, map/unmap, новый кадр). Совпали все — стадия берётся как есть. Многоэлементный
   мемо проверен счётчиком: 8 записей не добавили бы ни одного попадания — оставлен один элемент.
2. **Чтения памяти.** Фронтенд держит 4 последних найденных участка физической памяти игры (адрес → память хоста) и
   копирует из них напрямую — те же байты, что вернул бы менеджер. Любой map/unmap в игре сбрасывает участки
   (поколение отображений); адреса без участка запоминаются блоками по 1 МиБ.
3. **Потоковые копии.** Диапазон, уже скопированный в кольцо в этом пакете, без изменений памяти с того момента,
   берёт тот же кусок кольца. Только в пределах пакета: кусок живёт, пока пакет не завершится на GPU.

Попутно исправлено: в запасном пути через наборы дескрипторов (`vkCmdBindDescriptorSets`) не сбрасывалась тень
push-дескрипторов — на включённом по умолчанию пути не сказывалось.

## 7. Прирост FPS

Итоговый A/B «до/после»: `fol_base` (`b2f1292`) против `fol_final` (изменения 1–3 включены, 4–5 выключены),
чередование, по одной сцене за прогон (`logs\foliage\fin_base_r*`, `fin_final_r*`). Сделано 2 полные пары по трём
сценам. Третью пару и дополнительные пары деревни по решению пользователя не запускали: на пляже и в гавани
результат в обеих парах совпал.

| сцена, окно | CP до → после (пара 1 / пара 2) | средний FPS до → после | 1 % low | кадры > 33 мс |
|---|---|---|---|---|
| пляж, B (листва) | 28,80 → 26,37 (−2,43) / 29,11 → 27,06 (−2,05) | 32,0 → 34,5 | 23,7 → 24,7 | 0,5 → 0,5 % |
| пляж, A | 20,2 → 20,0 | 42,6 → 42,4 | — | 0 → 0,05 % |
| гавань, A | 37,47 → 33,58 (−3,89) / 37,27 → 33,60 (−3,67) | 25,1 → 27,5 | 19,6 → 19,7 | **38,7 → 17,7 %** |
| гавань, B | 30,15 → 30,68 (+0,53) / 29,97 → 29,07 (−0,90) | 30,4 → 30,5 | — | 0,6 → 3,1 % |
| деревня, A | 38,83 → 35,77 (−3,06) / 38,58 → 40,02 (+1,44) | 23,6 → 24,1 | — | 53,6 → 46,8 % |
| деревня, B | 32,62 → 29,12 (−3,50) / 27,53 → 35,87 (+8,34) | 29,2 → 27,0 | — | 9,5 → 23,5 % |

- **Пляж и гавань — ускорение подтверждено**: в каждой паре один знак. CP пляжа в листве −2,0…−2,4 мс; в
  тяжёлом участке гавани (окно A) −3,7…−3,9 мс, кадров на третьем vblank (50 мс) вдвое меньше. Окно B гавани
  — в пределах разброса (CP ~30 мс у обеих сборок).
- **Деревня — неоднозначно.** Пара 1: −3,1 / −3,5 мс; кадры > 33 мс в листве 18,7 → 1,4 %. Пара 2 — хуже. Но
  она испорчена с двух сторон:
  - у исходной сборки в окне B было другое содержимое кадра: 3459 draw против 4061–4146 в трёх других прогонах;
  - у новой сборки с 50-й по 85-ю секунду одновременно выросли и CP (+6…+9 мс), и **занятость GPU (+3 мс)**. Работу
    GPU эти изменения не добавляют: режимы проверки показали те же команды, а изменение 3 убирает копии. Похоже на
    постороннюю нагрузку, но доказательства нет — для уверенного вывода по деревне нужны ещё пары.
- Тренд по пляжу при включении изменений по одному (окно B, разные сессии): CP 32,0 → 28,6 (1) → 27,9 (+2) →
  26,2 (+3) мс; кадры > 33 мс 10,7 → 0,8 %; средний FPS 29,1 → 35,1.
- VRAM не изменилась (1557 МиБ у обеих сборок): новых глобальных кэшей нет. Мемо стадий — один элемент на
  стадию, участки чтений — 4 записи, повтор копий живёт только до конца пакета.

## 8. Изменения изображения

- **Режимы проверки** (`fol_verify`, все три сразу): каждое попадание кэша всё равно считается полностью, и
  результат сравнивается с закэшированным (мемо стадий — отпечаток модуля, ключа, плана привязок, адресов и размеров
  буферов, привязок вершин; чтения — побайтно с чтением через менеджер; копии — хеш байт).

  | сцена | мемо стадий: попаданий / различий | чтения: сравнений / различий | копии: повторов / различий |
  |---|---|---|---|
  | пляж | 4 908 490 / 0 | 256 821 492 / 0 | 8 728 618 / 0 |
  | гавань | 5 101 356 / 0 | 284 943 435 / 0 | 11 039 857 / 0 |
  | деревня | 4 156 863 / 0 | 251 366 401 / 0 | 8 676 182 / 0 |

  Значит, GPU получает те же шейдеры, те же привязки и те же байты — изображение не может отличаться из-за этих
  изменений.
- **Vulkan Validation + Sync Validation** (`--gpu-native-validate`: `VK_LAYER_KHRONOS_validation` с
  `VK_VALIDATION_FEATURE_ENABLE_SYNCHRONIZATION_VALIDATION_EXT`, `fol_validate_final`): пляж, гавань, деревня —
  **0 сообщений** (`vk_validation.log` пуст, слой работал: 5–7 FPS под ним). Исходная сборка (`fol_validate_base`) на тех же сценах — тоже 0: новых сообщений нет.
- **Скриншоты** (`screen.png` в конце прогона, 2 исходных против 2 новых на сцену). Сцена живая: частицы, вода,
  время суток, камера дрейфует за анимацией персонажа. Поэтому попиксельное сравнение ищет только грубые поломки.

  | сцена | исходная против исходной | новая против новой | исходная против новой |
  |---|---|---|---|
  | пляж | PSNR 18,0 дБ | 17,9 дБ | 18,6 дБ (17,1–) |
  | гавань | 19,5 дБ | 23,5 дБ | 15,7 дБ |
  | деревня | 15,5 дБ | 19,3 дБ | 17,3 дБ (15,5–) |

  На пляже и в деревне разница «до/после» на уровне разницы между прогонами одной сборки. В гавани она больше:
  на снимках другой ракурс камеры и поза персонажа, при этом освещение, тени, листва деревьев и текстуры
  одинаковые (просмотрено глазами). Пропавшей листвы и артефактов нет ни в одной сцене.

## 9. Дальнейшие доказанные оптимизации

Профиль итоговой сборки (`logs\foliage\fol_sampleB_final`, пляж, окно B, 14 135 сэмплов), включительно:

| функция | до (`fol_sampleB`) | после |
|---|---|---|
| драйвер NVIDIA | 42,9 % | 45,2 % (доля растёт, потому что наша часть уменьшилась) |
| `ShaderFrontend::PrepareStage` | 30,9 % | 23,3 % |
| `SrtProgram::Run` | 10,7 % | 5,1 % |
| `Executor::GuestRangeImpl` (потоковые копии) | — | 12,2 % (из них `memmove` 5,3 %) |
| `PushDescriptors` / `SetDynamicState` (ближайшая функция с драйвером под ней) | — | 4,6 % / 2,9 % |
| `Timeline::Wait` (ожидание GPU, не работа CPU) | — | 5,3 % |
| разбор PM4 (`Step`, `Execute`, `SetRegs`, `RegisterFile::Write`, `Next`, `Decode`) | — | ~11 % собственного времени |
| хеш-таблицы `TexMemo` / `FetchCache` (`std::unordered_map`) | — | 1,8 % / 0,8 % |

Что можно делать дальше, по убыванию отношения «выигрыш / риск» (ни одно не сделано — каждое сначала нужно
доказать счётчиком и A/B так же, как изменения 1–3):

1. **Потоковые копии между пакетами.** Диапазоны, не менявшиеся с прошлого кадра, — 1,08 млн копий (505 МиБ) за
   прогон (`fol_diag3`). Кусок кольца надо держать живым до забора своего пакета, а не до конца пакета. Оценка —
   до ~1 мс CP.
2. **Плоские хеш-таблицы** вместо `std::unordered_map` в `TexMemo` и `FetchCache` (открытая адресация) — ~2,5 %
   CPU, оценка 0,3–0,6 мс, риск низкий.
3. **Тень динамического состояния** (`vkCmdSet*` только при изменении) — 4,6 % включительно вместе с драйвером.
   Осторожно: такая же тень дескрипторов (изменение 4) сократила вызовы, но не время.
4. **Частичный мемо обхода SRT** — промахи мемо стадий (72,5 %) отличаются пользовательскими данными (указатели на
   константы и экземпляры), а сам обход SRT может зависеть только от части из них. Сначала нужен счётчик: сколько
   промахов имеют ту же таблицу SRT.

Предел этих точечных правок — 2–4 мс CP: больше кадров останется в 33,3 мс, но **60 FPS в листве так не
получить**. Для кадра 16,7 мс нужно CP меньше ~15 мс (сейчас 26,4), а почти половина CP — сам драйвер. Это
возможно только с записью команд Vulkan во втором потоке параллельно разбору PM4 и подготовке draw. Это
многопоточное изменение, по условию задачи его не делали; эти замеры — обоснование для отдельной задачи.

В деревне, кроме CP, загружен и GPU (26 мс из 33): там отдельная причина — 1550 асинхронных вычислительных
dispatch 1×1×1 за кадр (профиль GPU P4.6-G, `a8eaf5c`), к листве не относится.

## Переключатели

| переменная | по умолчанию | значения |
|---|---|---|
| `SSPC_DIAG_STAGE_MEMO` | вкл | `off` — без мемо; `verify` — каждое попадание считается полностью и сравнивается |
| `SSPC_DIAG_READ_RUNS` | вкл | `off` — все чтения через менеджер; `verify` — каждое чтение повторяется через менеджер |
| `SSPC_DIAG_STREAM_REUSE` | вкл | `off` — каждая копия заново; `verify` — каждый повтор копируется заново, байты сравниваются |
| `SSPC_DIAG_BIND_SHADOW` | выкл | `on` — эксперимент 4 |
| `SSPC_DIAG_SHARED_LAYOUTS` | выкл | `on` — эксперимент 5 |
| `SSPC_DIAG_MEMO_STATS`, `SSPC_DIAG_STREAM_STATS` | выкл | `1` — диагностические счётчики (замедляют) |

Итоги — в `gpu_native.txt`: строки `stage preparations (P4.7 memo)`, `frontend reads (P4.7)`,
`streamed copies reused in their batch (P4.7)`, `graphics bindings (P4.7 shadow)` и строки проверки.

## Запуск

`play_native.cmd` — то же, что `play.cmd`, но с нативным бэкендом (`--gpu-backend sspc`), где эти оптимизации
включены по умолчанию. Обычный `play.cmd` по умолчанию идёт через рендерер моста (`--gpu-backend bridge`), этих
изменений там нет.
