  A/B той же схемой (ABBA, ≥3 пары, одна копия exe на серию) и берут bench-замок только на время своей серии.

- **Окружение прогона.** До `3b9730a` скрипт после прогона чистил только `SSPC_NATIVE_ENGINE*`, и флаги одного прогона

- Полный `SecondSonPC.exe --selftest` не запускать (стресс стеков исчерпывает commit, падал весь ПК).

### 5.1 B1: путь draw сегодня [A — по коду и документам, ссылки ниже]

| Шаг | Где | Что происходит | Источник |
|---|---|---|---|
| 1. состояние CUE | `0x16aa0/0x16b70/0x169d0/0x16d10/0x16eb0`, материал `0x448640` | дескрипторы → тень стадии `CUE+0x90+stage·0x1800` (или прямой `SET_SH_REG` при бите 15), флаг `CUE+0xC1D0+stage` | NATIVE_RECOMP_R5_D.md §2 |
| 2. commit | `0x14ad0` | для грязной стадии: снимок `0x123d0` в кольце кадра, `memcpy` тени, указатель в user data (`0x626400`), прямые SGPR (`0x626520`), предвыборка кода (`0x623630`, `CP_DMA`), привязка шейдера Gnm (`0x625100…0x625aa0`), `SPI_PS_INPUT_CNTL` (`0x638540`) | NATIVE_RECOMP_R5_D.md §5 |
| 3. draw | `drawIndex 0x623c60` / `drawIndexAuto 0x623a40` | пакет `DRAW_INDEX_2`/`DRAW_INDEX_AUTO` + NOP из 4 dword (тело не читает железо) | NATIVE_RENDER_INTERFACE.md §2, §7.2 |
| 4. разбор PM4 | `CommandProcessor` (поток 1) | `SET_*_REG` → `RegisterFile`, `DMA_DATA`, `ACQUIRE_MEM`, draw → `BuildDraw` → `DrawDescriptor` | command_processor.cpp |
| 5. подготовка draw | фронтенд шейдеров (поток 1) | поиск программы/раскладки, обход SRT по указателю user data, `DecodeResources`, копии стадий; Phase 5/6 — серии, GEOFAST | CITY_ENGINE_RESOURCES.md §4 |
| 6. запись Vulkan | поток 2 (Recorder/Executor) | конвейер, дескрипторы, барьеры, `vkCmdDraw*` | NATIVE_CP.md |

**Повторные преобразования** [A + E из Phase 6]: (а) таблица ресурсов копируется в новый блок кольца на каждом
commit, поэтому указатель user data всегда новый и обход SRT повторяется даже при том же содержимом; (б) значения,
которые движок уже держит структурировано (регистры шейдеров в объектах `CUE+0xC0A8/0xC0B0`, тени стадий, параметры
draw), сериализуются в PM4 и снова разбираются в `RegisterFile`; (в) по профилю Phase 6 поток 1 ≈ 29–30 мс на кадр в
городе, из них полные подготовки ≈ 11–12 мс, остальное — разбор PM4, запись регистров, журнал, записи очереди.

### 5.2 Что уже есть: P5.3 — мост движок → CP без PM4 своих операций [A]

`docs/native-reconstruction/NATIVE_RENDER_INTERFACE.md`. За флагами, по умолчанию выключено:

- `SSPC_P53_NATIVE_DRAW=apply:<проходы>` — commit `0x14ad0` (`NativeCommit`, ручная реконструкция в
  `src/engine/render/native_draw.cpp`) и draw выполняются без PM4: записи регистров (`OpKind::Registers`) и `DrawOp`
  уходят в CP, который исполняет их через тот же `Draw()`/`BuildDraw`/Executor, что и пакет;
- `SSPC_P53_NATIVE_STATE=apply` — состояние прохода (SetRenderTargets, TransitionTo, prim/index, 15 установщиков);
- `SSPC_P53_DIRECT=1` — операции в собственных блоках памяти, в DCB один токен на серию (порядок = место токена);
- `SSPC_P53_NATIVE_FRONTEND` — подготовки стадий по описанию движка (форма таблицы), общий кэш;
- `--render-mode hybrid` = apply:1,9 + state apply + describe + frontend all, без проверок.

побитово (кроме G-буфера 0/2 в гавани). **Не проверено:** город, пресет Phase 6 (нативные draw идут через

Фронтенд по описанию движка: F — 13,3 млн поисков, из кэша 23,6 %, «известно некэшируемых» 2,58 млн; hybrid (B0 в
`r6c_ab2`, с `DESCRIBE=1` на всех проходах) — 46,2 млн поисков, из кэша 41,9 %.

Вывод (по сериям, межсерийное сравнение — оценка): нативные commit/draw/state сами по себе — **+1,5 мс потока 1,
потеря не подтверждена** (FPS H внутри разброса A); фронтенд без описания добавляет ещё ≈1 мс (F вне диапазона A по
FPS); описание всех проходов (`DESCRIBE=1`) + фронтенд по нему — основная часть из +6,9 мс hybrid. То есть дорого не
«убрать PM4», а **подготовка стадий по описанию движка**: поиск в кэше на каждый draw дороже, чем подготовка Phase 6
(GEOFAST/память стадий P4.7), которую он заменяет. Мост в форме P5.3 ускорения не даёт; ни один его режим не
включается по умолчанию.

Профиль потока 1 (`r6c_prof`, `SSPC_DIAG_SAMPLE=1` с 70 с, по одному прогону A0 и B0 hybrid, доли выборок потока;
с сэмплером всё медленнее, сравниваются доли): в hybrid `ShaderFrontend::PrepareStage` **10,2 % собственного
времени против 3,1 %** (включительно 49,4 против 35,6 %), появились хеш-таблица `unordered_map<u64,u32>` 3,0 %,
XXH3 ≈ 3,5 %, `RtlAllocateHeap` 1,7 %, `NativeKeyOf` 4,2 % вкл., `NativeMarker` 30,1 % вкл.; ушли
`ResolveResources` 20,2 % вкл. и ожидания (`WaitHead` 12,0 %, `NtWaitForAlertByThreadId` 10,3 → 3,2 %). То есть
стоимость моста — поиск подготовки стадии по описанию движка (хеш формы таблицы + поиск + выделения памяти на каждый
draw) в `src/runtime/gpu/shader/shader_frontend.cpp`. Эта зона — поколение кэша шейдеров пользователя, её R6 не
трогает; исправление (поиск без хеширования всей формы, без выделений) — предложение, не сделано.

Вывод B1: мост R6 строится на P5.3, а не с нуля. Первое — измерить его в городе поверх пресета (корректность, затем
A/B), найти, что съедает выигрыш, и только потом расширять.

## 6. B2: повторное использование снимков CUE в commit 0x14ad0 (`SSPC_R6_CUE_DEDUP=1`) [A + код]

Исходный факт (R6-P, `SSPC_R6_CP_DIAG=1`, город): 26 % полных обходов SRT стадии VS и 33 % PS дают тот же результат,
что прошлый обход той же программы — меняется только адрес снимка в кольце. Повторное преобразование порождает сам
движок (§5.1 а), и устранять его логично там, где оно возникает, а не в CP.

**Аллокатор снимков** [A, дизассемблер `0x123d0`, `0x12390`, `0x11ef90`]: `cur` `CUE+0x20`, `start` `CUE+0x28`,
`end` `CUE+0x30`; выделение — `cur += dwords·4` (без выравнивания); при нехватке колбэк `CUE+0x00` (у контекстов R —
`0x11ef90`: кусок 32 КиБ из арены снимков кадра `0x1f0b20`) и `start = cur = кусок`; сброс `0x12390` (из
`CUE::Reset 0x13da0`) берёт следующий буфер своего кольца и тоже ставит `start = cur`. Других записей этих полей в
`0x13a50/0x13d20/0x13da0` нет. Следовательно, `[start, cur)` в любой момент состоит только из выделений текущего
экземпляра куска, и время жизни любого байта в нём — время жизни куска.

**Правило** (`src/native_engine/r6/cue_dedup.{h,cpp}`, работает только в нативном commit — `recomp_14ad0` под
`SSPC_NATIVE_ENGINE=native`, ключ `cue_commit`, через перенаправление трёх вызываемых `recomp_set_redirect`):
для копии тени стадии `s` в только что выделенный снимок `D` прежний снимок `P` той же пары (CUE, s) берётся, если
`start` тот же, что при создании `P`, `start ≤ P`, `P + n ≤ D` и `memcmp(P, тень, n) == 0`. Тогда копия не делается,
`D` остаётся выделенным (расход арены — как у игры), а указатели user data в `D` (`0x626400`) переносятся на то же
смещение в `P`. Кэш — потоковый, прямого отображения, 2048 записей; запись другого потока или старого куска
проверяется теми же условиями (устаревшая только промахивается).

**Что доказывает эквивалентность:** (1) байты — `memcmp` при каждом решении; (2) время жизни — `P` и `D` в одном
экземпляре куска; (3) неизменность — пользователи аллокатора пишут снимок один раз при выделении [A для `0x14ad0`;
для `0x13ec0/0x140d0/0x132b0` — H, проверяется в игре]; (4) никто, кроме `0x626400`, адрес снимка не получает —
офлайн-тест по записанным вызовам (§6.1); (5) в игре — `SSPC_DIAG_STAGE_MEMO=verify` (каждое попадание памяти
стадий CP подготавливается полностью и сравнивается) и серии Phase 5/6 в режиме verify.
