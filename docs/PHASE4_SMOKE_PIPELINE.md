# Фаза 4: конвейер дыма и SSPC-020

Дата: 2026-10-11. База: `59abc53` (финал ночного спринта N1–N12). Сцены: пляж (маршрут P4.3–P4.6), деревня
`user1022`. RTX 2060 (subgroup 32), Ryzen 5 5500. Карта шейдеров и ресурсов — `docs\SMOKE_SHADER_MAP.md`.
Результаты прогонов — `logs\smoke_research\<tag>\` (локально, в git не входят).

**Итог:** причина мерцания найдена и устранена. Сортировка частиц дыма выдавала список с повторами: 10–17 %
частиц за кадр не рисовались, а набор пропавших менялся от кадра к кадру. Корень — семантика wave64: проход сортировки
сливает несколько уровней в одном dispatch без барьеров, полагаясь на то, что 64 потока группы — одна синхронная
волна GCN. Исправление — уровни слияния этой программы записываются отдельными dispatch с барьером между ними.

## A. Исходные симптомы и база

Прежние эксперименты (метки часов, барьеры, синхронный submit) меняли только частоту «скачков», не причину.

## B. Draw, pipeline и шейдеры дыма

Все идентификаторы — из трассировки команд (`SSPC_DIAG_CMD_TRACE`), подробно в `docs\SMOKE_SHADER_MAP.md`.

- Основной draw: VS `0x2edac4000` (footer `bbd2d927`, content `7d22e10251c65380`), PS `0x2edad2700` (footer
  `24dad4be`, content `1a4f64edc772a286`); `DRAW_INDIRECT`, quad list, 1 за кадр, 20 900–24 200 вершин (5,2–6 тыс.
  частиц), цель HDR `0x2fcdf0000` (R16G16B16A16_SFLOAT), без depth, CB_BLEND0 `0x61000501`. Pipeline на пляже 382
  (номер не стабилен между маршрутами — отбор по адресу/хешу).
- Второй проход дыма: VS `0x2edadae00` / PS `0x2edaaf300`, 1 за кадр, цель `0x304eb0000`; читает тот же
  отсортированный список.
- Сортировка: CS `0x2edaa1800` (footer `a16fa93a`, content `80279384190567be`), 9 dispatch за кадр, 92–94 группы
  по 64 потока.
- Эмиттеры: 46 программ CS очереди 1, ~520 dispatch за кадр, в основном 1×1×1.

Диагностическое отключение (P4.5, бисекция по pipeline): без основного draw столб исчезает полностью, остальная сцена
не меняется. Механизм `SSPC_DIAG_SKIP_DRAWS=vs:2edac4000,vs:2edadae00` / `SSPC_DIAG_SKIP_DISPATCHES=cs:…` пропускает
только сами команды (их барьеры, загрузки и учёт записей остаются) — для измерений, не для сборки.

## C. Цепочка compute → память GPU → graphics

```
кадр N, очередь 1 (compute)                              кадр N+1, очередь 0 (graphics)
  ~520 dispatch эмиттеров (46 CS, ds_append)
     -> пул частиц   0x26f358000 / 0x26d558000 (12 МиБ)  ----> VS 2edac4000 читает пул по индексам
     -> список (ключ, индекс) 0x26ff58100 / 0x26e158100       (и 139+58+29 draw других частиц — только пул)
  заголовок-счётчик 0x26ff58000 / 0x26e158000 (пишет CP/CPU, не draw/dispatch)
  сортировка CS 2edaa1800, 9 проходов, ping-pong с 0x271158000
     -> отсортированный список (по убыванию глубины) -------> VS 2edac4000 / VS 2edadae00 (порядок частиц)
     -> indirect-аргументы 0x270058100 / 0x26e258100 -------> DRAW_INDIRECT (count << 2 вершин)
                                                            -> HDR 0x2fcdf0000 (смешивание, без depth)
```

Наборы A/B чередуются по чётности кадра (двойная буферизация, задержка один кадр): адреса стабильны во всех трассах,
указатели не устаревают.

## D. Сравнение с shadPS4

Сравнение шло через мост P4.5: рендерер shadPS4 внутри SecondSonPC, тот же exe, та же сцена. Установленный shadPS4
и игровые файлы не менялись.

- Мост с настройками по умолчанию (readbacks выключены): дыма нет, сцена темнее.
- Мост с `readbacks=2`: дым есть и мерцает так же, как в нативном бэкенде.

Вывод: дым зависит от данных, которые пишет GPU и затем читает CPU/CP (заголовок-счётчик не пишет ни одна команда
GPU; его читает только сортировка). Без readbacks эти данные гостю не видны, число частиц и аргументы draw нулевые —
draw ничего не рисует. Поэтому в shadPS4 (по умолчанию без readbacks) дыма нет. С readbacks shadPS4 исполняет ту же
сортировку тем же одним dispatch на той же 32-поточной подгруппе — и даёт то же мерцание (наблюдение P4.5
согласуется с найденной причиной). Кто именно пишет заголовок (код игры на CPU или пакет CP) — не установлено
(прогон `SSPC_DIAG_WATCH` не выполнялся). Более высокий FPS shadPS4 нельзя объяснять отсутствием дыма: см. F.

## E. Источник SSPC-020 и доказательства

Проверки по стадиям (пробы `SSPC_DIAG_PROBE` / `SSPC_DIAG_PROBE_CS`, 4–6 кадров на прогон, ≤1 МиБ на привязку):

| Вопрос | Ответ | Доказательство |
|---|---|---|
| Частица пропала уже в выходе compute? | нет | вход сортировки (выход эмиттеров): 0 повторов индексов (s4, s5, s6) |
| Изменился её индекс / порядок сортировки? | **да** | отсортированный список: 549–956 повторов и 100–300 нарушений порядка за кадр (s3–s5) |
| Где впервые? | **проход 1 сортировки** | выход прохода 1: 464–468 повторов; проходы 2–9 их умножают до 795 (таблица в карте, §6) |
| Устаревший указатель? | нет | адреса наборов A/B стабильны по чётности кадра во всех трассах |
| Пропущен draw (Pending shader module)? | нет | `not executed` = 0 в `gpu_native.txt` (база и исправление) |
| Сменились специализация/привязки? | нет | трасса: тот же pipeline и те же диапазоны в каждом кадре |
| Отброшены фрагменты depth? | нет | draw без depth, смешивание постоянное |
| Координаты / alpha? | отдельно не проверялись | после исправления сортировки мерцание 0 — не причина |

**Механизм.** Сортировка — слияние (merge path) без LDS, барьеров и волновых операций. Уровень ширины w сливает две
серии по w/2 в одну (после прохода 1 список в сериях по 64: 85 разрывов порядка на 5455 частиц). Проход 1 получает
параметры (2, 64) и в одном dispatch выполняет шесть уровней: 2, 4, 8, 16, 32, 64. Каждый уровень читает то, что
другие потоки той же группы записали на предыдущем, без барьера. На PS4 группа из 64 потоков — одна волна wave64:
все её lanes идут синхронно, и записи предыдущего уровня видны следующему. На RTX 2060 та же группа — две
независимые 32-поточные подгруппы. Уровень 64 читает половину, которую пишет другая подгруппа: гонка. Бинарный
поиск merge path по несогласованным данным даёт повторы и пропуски.

**Подтверждение.** Те же уровни, в том же порядке, по одному на dispatch с барьером между ними:

- повторов 0 на каждом из 9 проходов;
- число нарушений порядка честно падает вдвое за проход (170 → 85 → … → 0);
- мерцание по метрике 0 (s6, f1).

Диагностика `keep:32` (уровни 2–16 одним dispatch, внутри подгруппы) — тоже 0 повторов. Внутриподгрупповые уровни
на практике безопасны. Прогон `keep:64` (уровни 2–32 вместе, 64 отдельно — изоляция межподгруппового уровня)
прерван и отдельно не подтверждён.

**Аудит wave64 (этап F задания).**

- Предупреждение `Ballot instruction in non uniform control flow` даёт только CS `0x2edafa400` (освещение,
  SSPC-021), к дыму не относится.
- `LowerWave64BallotPass` понижает Ballot, ReadLane(imm) и MaskedBitCount32. `ReadFirstLane`, `InverseBallot`,
  `Shuffle` и `WriteLane` не понижаются — известные пробелы, на пути дыма их нет.
- `ds_append`/`ds_consume` эмулированы верно: выход эмиттеров без повторов.
- Подтверждённая ошибка wave64 — не трансляция инструкции, а неявная синхронность 64 lanes, на которую опирается
  шейдер. Общего исправления в трансляторе нет:
  - NVIDIA не даёт подгруппу 64;
  - записи стоят в расходящемся потоке управления, а барьер требует равномерного;
  - межуровневая синхронизация на всю группу меняет программу.

## F. Стоимость дыма (CPU / GPU)

Измерено только GPU-профилем (`SSPC_GPU_PROFILE`, метки времени вокруг каждой команды, ночной прогон 20:06, окна
по 300 кадров; сумма меток 24–64 мс против 17–26 мс GPU без профайлера — завышение 1,4–2,5×, особенно для 1×1×1
dispatch). Сцены окон в файле не помечены.

| Окно (сумма меток за кадр) | Draw дыма | 2-й проход | Сортировка (9 проходов) | Эмиттеры (26–32 программы) | Другие draw частиц |
|---|---:|---:|---:|---:|---:|
| 23,9 мс | 0,46 мс | 0,01 мс | 0,045 мс | 1,39 мс | 0,05 мс |
| 62,6 мс | 1,84 мс | 0,04 мс | 0,052 мс | 4,26 мс | 0,27 мс |
| 63,6 мс | 1,93 мс | 0,04 мс | 0,054 мс | 4,24 мс | 0,29 мс |

Оценка: draw дыма — около 2–3 % времени GPU, сортировка — меньше 0,2 %. Самая дорогая часть — compute эмиттеров
(~520 мелких dispatch за кадр), но они общие для всех частиц сцены, и их время профайлер завышает сильнее всего.
Пляж CPU-bound (CP 29,8 мс против GPU 17 мс): экономия GPU на дыме там почти не дала бы FPS. Двукратное падение FPS
из-за дыма **не подтверждается** данными. A/B NORMAL против NO_SMOKE_DRAW по FPS **не выполнен** (см. H).

## G. Исправления и оптимизации

**Исправление SSPC-020** (`Executor::SplitMergeLevels`, `src\runtime\gpu\vulkan\vk_executor.cpp`):

- dispatch программы с content hash `80279384190567be` и параметрами (w, max) при 2w ≤ max записывается как один
  dispatch на уровень: свой 16-байтный блок параметров (w, w) в кольце, `GlobalBarrier` между уровнями;
- на нечётных уровнях привязки #3/#4 меняются местами, ровно как в собственном цикле шейдера;
- уровни, их порядок, данные, число частиц и результат не меняются — это порядок, который PS4 получает от wave64;
- форма привязок проверяется: 5 гостевых буферов, параметры только для чтения ≤ 16 байт, списки равного размера;
  иначе dispatch записывается как есть;
- включено по умолчанию; `SSPC_DIAG_SORT_SPLIT=off` — как в игре, `keep:<w>` — диагностика;
- цена: +5 dispatch и +5 барьеров на очереди 1 за кадр; FPS / CP / GPU в пределах шума одиночных прогонов
  (31,05 / 29,8 / 17,0 против 31,01 / 29,9 / 16,9).

**Оптимизации** дыма не вносились: доказанно дорогой стадии, принадлежащей только дыму, нет (draw ~2–3 % GPU на
CPU-bound сцене). Мелкие dispatch эмиттеров — общая статья всех частиц, её затрагивали N10 (барьеры между dispatch
одной очереди) и тени записей ночного спринта.

**Диагностика** (по умолчанию выключена): `SSPC_DIAG_CMD_TRACE`, `SSPC_DIAG_SKIP_DRAWS` / `_DISPATCHES`,
`SSPC_DIAG_PROBE` / `_PROBE_CS`, `SSPC_DIAG_CAPTURE_FRAMES=t<сек>:…`, `SSPC_DIAG_BRIDGE_DUMP_SHADERS`; разбор —
`tools\smoke_trace.py`, `tools\smoke_probe.py`, `tools\imgcmp\smoke_stats.py`.
