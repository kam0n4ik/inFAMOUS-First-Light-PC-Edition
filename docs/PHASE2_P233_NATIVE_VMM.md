# P2.3.3 — собственный менеджер виртуальной памяти (P2.3.3b/c)

Статус (2026-10-09): **P2.3.3 закрыт.** Свой менеджер реализован и проверен в изоляции, игрой не используется.
Игра по-прежнему работает на `Core::MemoryManager` моста (через интерфейсы патчей `0008`/`0009`); свой менеджер
создаёт только самотест на свободных окнах адресного пространства выше 1 ТиБ. Финальный игровой A/B (патчи
`0010`/`0011` и весь код этапа в бинарнике) — без регрессий (`docs\PHASE2_TEST_RESULTS.md`, «P2.3.3»).
Переключение игры — P2.3.4, точка входа — §8.
Первая часть этапа (P2.3.3a, аудит и интерфейс для не-GPU пользователей) —
`docs\PHASE2_P233_MEMORY_DEPENDENCIES.md`.

Коммиты: `024b304` менеджер (P2.3.3b), `49996f9` SSPC-005/D11 (патч `0010`), `0717c37` D10/D12 (патч `0011`),
`ba07cbf` адаптеры (P2.3.3c), `d334c71` дифференциальные тесты, `34b6ffe` замеры.

## 1. Слои

```
Core::GuestVirtualMemory / GuestPhysicalMemory / GuestWriteNotifier (патч 0009)   Core::GpuMemory + Listener (патч 0008)
        │ NativeGuestMemory                                                                │ NativeGpuMemory
        └──────────────── src\bridge\shadps4\native_memory.{h,cpp} ────────────────────────┘
                                         │ (каждый вызов — один вызов менеджера, без своего состояния)
                    Memory::VirtualMemory  (src\runtime\memory\virtual_memory.{h,cpp})
          ┌──────────────┬──────────────┬──────────────┬───────────────────┐
     VmaMap (области)  DirectMemory   FlexibleMemory   BackingTable (GPU, без блокировок)
       vma_map.{h,cpp}  (P2.3.1)       (свободные куски)  2 уровня, атомарные указатели
          └──────────────┴──────┬───────┴──────────────┘
                     HostAddressSpace (host_address_space.{h,cpp}): плейсхолдеры Windows,
                     одна секция-подложка, постоянный RW-вид всей секции (H2)
```

- **HostAddressSpace** — только хост: резерв диапазонов гостя плейсхолдерами (`VirtualAlloc2
  MEM_RESERVE_PLACEHOLDER`, перед этим `VirtualQuery` проверяет, что диапазон свободен), одна секция
  (`CreateFileMapping2`: `SEC_COMMIT` как у моста или `SEC_RESERVE` с commit по требованию — E1), постоянный
  вид всей секции (H2). Виды (`MapViewOfFile3 MEM_REPLACE_PLACEHOLDER`) и частная память
  (`VirtualAlloc2 MEM_REPLACE_PLACEHOLDER`) встают на место плейсхолдеров; разрез — `MEM_PRESERVE_PLACEHOLDER`,
  склейка свободного — `MEM_COALESCE_PLACEHOLDERS`. Частично снимаемый вид снимается целиком, плейсхолдер
  режется, остатки отображаются снова (у моста так же). Отказ хоста записывается (`LastError`), счётчики
  (`protect_failures`, `coalesce_failures`) — без логов: `Protect` работает в обработчике нарушений доступа.
- **VmaMap** — области как разбиение диапазона (`std::map` base → `Vma`), правила разреза и слияния моста
  (`CanMerge`: тип, защита, имя, для direct — непрерывность физических адресов и тип памяти; direct сливаются
  начиная с SDK 2.00). Физические куски хранятся в области (`PhysPiece`), как `phys_areas` моста.
- **VirtualMemory** — семантика `MemoryManager` моста на уровне менеджера: `Map/Unmap/Protect/NameRange/
  Query/QueryProtection/IsValid/Areas`, поиск свободного (`SearchFree`), бюджеты (`SetupRegions` с
  `DirectMemory::Resize`), direct (`DirectMemory` P2.3.1, учёт отображений по страницам) и flexible
  (`FlexibleMemory`) в одной секции, GPU-сторона: `CopySparse` (таблица подложки без блокировок), `TryWriteBacking`
  (D11 правильно, без выделений — H4), `ProtectTracking` (только блокировка листа хоста), `ClampRange`, PRT.
- **GameLayout** — раскладка игры так, как её считает мост (`address_space.cpp`, `memory.cpp` @ 0fe263a):
  свободные регионы хоста > 16 МиБ в [0x400000, user_max], выравнивание по гранулярности, user_max по сборке
  Windows и SDK, бюджеты. Самотест `NativeVmm(game)` сверяет её с регионами и бюджетами моста.

## 2. Структуры данных

| Что | Мост (0fe263a) | Свой менеджер | Почему |
|---|---|---|---|
| Области | `std::map vma_map` (разбиение) | `VmaMap`: `std::map` разбиение | поиск по адресу O(log n), разрез ≤ 2 split, слияние с соседями O(log n), обход O(log n + k). Интервальное дерево ничего не даёт разбиению; отсортированный вектор — O(n) на разрез; таблица страниц — O(страниц) и 64 Ми записей на 1 ТиБ |
| Direct memory | `std::map dmem_map`, состояние участка Free/Allocated/**Mapped** (без счёта видов: D20) | `DirectMemory` (P2.3.1): участки + **счётчик отображений** | частичные псевдонимы (D20) |
| Flexible | `std::map fmem_map` | `FlexibleMemory`: свободные куски, наименьший первым | — |
| Подложка для GPU | `MultiLevelPageTable` (40 бит, без проверки границ — D12) | `BackingTable`: 2 уровня, листы по 1024 страницы (16 МиБ), атомарные указатели, листы живут до конца | чтение без блокировок, за пределами — нули (D12), очистка пропускает целые пустые листы |
| Хост | `AddressSpace` (регионы плейсхолдеров) | `HostAddressSpace` (`std::map` регионов: плейсхолдер / вид / частная) | — |

## 3. Блокировки и уведомления GPU

Порядок (как у моста): unmap-блокировка → writer/reader (`ReaderFirstMutex` — читатели первыми, как
`SharedFirstMutex`) → блокировка листа хоста → блокировка `DirectMemory`. Уведомления: `OnGpuUnmap` до
изменения (writer не взят), `OnGpuRegister` после того, как страницы хоста отображены или сняты (обе
блокировки), `OnGpuMap` после (только unmap); PRT — без блокировок. Без блокировок — `CopySparse`. В
обработчике нарушений доступа — `ProtectTracking`: только блокировка листа хоста, без выделений и логов
(один системный вызов `VirtualProtect`, как у моста). Слушатель не должен брать блокировки, под которыми
вызывают менеджер (контракт `core/gpu_memory.h`); чтение (`ClampRangeSize`, `CopySparseMemory`) из
`OnGpuUnmap`/`OnGpuMap` разрешено и проверяется тестами.

Отличия по порядку отказов (ревью ECC, исправлено до коммита): хост снимает страницы **до** освобождения
физической памяти (запись гостя не может попасть в уже очищенную flexible-память); отказ хоста на
собственной памяти (`Unmap`/`Protect` своего отображения) останавливает процесс с причиной в логе
(`quick_exit(6)`), а не оставляет области и хост рассогласованными (у моста здесь `ASSERT`).

## 4. Свойства контракта

| Свойство | Как обеспечено | Проверка |
|---|---|---|
| H1 гостевой адрес = адрес хоста | области отображаются по своим адресам, без трансляции | `NativeVmm` (запись по указателю ↔ чтение через подложку), `NativeMem(diff)` |
| H2 постоянный RW-вид секции | вид всей секции при создании, живёт до конца | `NativeVmm`, `NativeMem(diff)` («write across A and C through the backing» — запись при защите только на чтение) |
| H3 анонимная память читается нулями | таблица подложки только для direct/flexible | `NativeMem(diff)` («S and R have none»), `NativeVmm(model)` |
| H4 нет выделений в `TryWriteBacking` | обход областей без копирования | `NativeVmm(D)`; замер: 36 нс против 254 у моста |
| H11 любые R/W-биты → RW у хоста | как `ProtectBytes` моста | `NativeVmm(model)`, `NativeMem(rand)` |

## 5. Дефекты моста и различия

| Id | Что у моста | Свой менеджер | Статус у моста |
|---|---|---|---|
| D5 | `Protect` на неуправляемом диапазоне — `ASSERT` | EINVAL | не исправлялось |
| D6 | бюджет flexible проверяется до unmap-блокировки | под блокировкой | не исправлялось |
| D10 | `IsValidGpuMapping` переворачивает сумму | без переворота | **исправлено патчем 0011** |
| D11 = SSPC-005 | запись через два физических участка повторяет начало данных | правильно | **исправлено патчем 0010** |
| D12 | `CopySparseMemory` за 2^40 читает за таблицей | нули | **исправлено патчем 0011** |
| D13 | `IsValidMapping` без блокировки | под reader | не исправлялось |
| D14 | дополнительная flexible-память складывается как число МиБ, а не байты | документировано, `GameLayout` воспроизводит бюджет моста | не исправлялось |
| D16 | промежутки между регионами хоста считаются «валидными» | невалидны | не исправлялось |
| D17 = SSPC-006 | снятие анонимной памяти из нескольких VMA — `ASSERT` | снятие по диапазону; частичное — EINVAL | не исправлялось |
| D18 | `mprotect` +exec на виде, отображённом RW: хост отказывает, мост `ASSERT` | виды RWX, понижаются до RW | не исправлялось |
| D19 | частичное снятие вида: остаток отображается снова **с защитой по умолчанию** — пользовательская `Protect` и защита отслеживания GPU на остатке теряются | **так же, как мост** (тесты сравнивают состояние) | не исправлялось; решить в P2.3.4 (вернуть защиту остатку и дать `OnGpuUnmap/Register` по нему) |
| D20 = SSPC-007 | два частично перекрывающихся вида одной direct-памяти: снять меньший, потом больший → `CarvePhysArea` `ASSERT` (найдено `NativeMem(rand)`) | счётчик видов, всё проходит (`NativeMem(D20)`) | не исправлялось, `docs\KNOWN_ISSUES.md` |

Намеренные отличия без дефекта у моста: пулы (`Pooled/PoolReserved`) и файловые отображения не поддержаны
(EINVAL с сообщением; игра их не вызывает — аудит P2.3); физические адреса flexible-памяти у каждого
менеджера свои (гостю не видны); `SetupRegions`, не помещающийся в секцию, оставляет прежние бюджеты с
сообщением (мост задаёт без проверки).

Окна: свободный диапазон ищется `VirtualQuery` от 2 ТиБ (`FindFreeNativeWindow`), у моста — свободное окно

## 7. Замеры

**E1, commit секции** (`NativeVmm(commit)`, системный commit, МиБ): секция 8448 МиБ `SEC_RESERVE` при создании
**+33**; выделение 64 МиБ direct — ещё +64; касание страниц — без изменений; освобождение — commit не
возвращается (страницы секции не декоммитятся); после уничтожения секции — commit вернулся к исходному.
Для сравнения `SEC_COMMIT` 256 МиБ — +256 при создании. То есть commit по требованию снимает с процесса
~8,4 ГиБ commit на старте (у моста подложка 8448 МиБ заряжается целиком). В игре не включался (P2.3.4,
отдельный режим отладки).

**Одни и те же вызовы через одни и те же интерфейсы** (`NativeMem(perf)`, 2000 × вид direct 64 КиБ,
P50 / P95 / P99, мкс; горячие пути GPU — нс, лучшее из 3):

| | map | protect | unmap | CopySparse 64 Б | TryWriteBacking 64 Б | ClampRange 1 ГиБ | ProtectTracking 16 КиБ |
|---|---|---|---|---|---|---|---|
| мост | 6,1 / 7,0 / 8,6 | 2,9 / 6,0 / 6,5 | 7,7 / 15,2 / 18,1 | 6,9 | 253,8 | 28,5 | 496 |
| свой | 13,7 / 17,6 / 19,9 | 0,9 / 1,0 / 1,0 | 6,1 / 6,7 / 9,4 | 9,2 | 36,2 | 28,8 | 493 |

`map` у своего в ~2 раза дороже: вид отображается RWX и понижается до RW (лишний `VirtualProtect`, цена D18).
Игра отображает память крупно и в основном на старте (10 вызовов за прогон, P2.3), поэтому это не горячий
путь; при необходимости — отображать RW и переотображать вид при первом `mprotect` с exec. `ProtectTracking`
(путь обработчика нарушений) одинаков: один `VirtualProtect`. Счётчики за 2000 циклов: областей разрезано
6002 / слито 6002, видов 2001, разрезов плейсхолдеров 4002, склеек 2001, отказов хоста 0.

Игровые метрики (FPS, RAM, commit, VRAM) у своего менеджера не измерялись: игра на нём не запускается
(условие этапа). Игра на мосте с кодом этапа: P2.3.3a — `docs\PHASE2_P233_MEMORY_DEPENDENCIES.md` §8;
финальный A/B (`logs\performance\p233_final_ab`) — до 24,60 / после 25,62 FPS (шум: та же сборка «до» в другой
сессии — 25,92), время кадра, private, commit, VRAM и карты памяти без изменений, аварий и first-chance нет.

**Что сделать в P2.3.4** (каждый пункт — отдельный шаг с самотестом и игровым A/B против эталона):

1. Функции памяти libkernel (`sceKernelMapDirectMemory`, `Munmap`, `Mprotect`, `VirtualQuery`,

   слушатель `NativeGpuMemory` до первого отображения.
3. Решения по D19 (защита остатка вида) и по commit по требованию (E1) — отдельными шагами с замерами;
   `map` дороже моста вдвое (RWX → RW, цена D18) — измерить в игре, при необходимости RW + переотображение.
4. Игровые A/B: обоими менеджерами, карты памяти `--memory-map`, FPS / время кадра / commit / VRAM, долгая
   сессия, граффити и бой (с разрешения пользователя, без внешнего ввода во время замера).

поддержаны (игра их не вызывает — проверять по `--memory-map` и логу при переключении).
