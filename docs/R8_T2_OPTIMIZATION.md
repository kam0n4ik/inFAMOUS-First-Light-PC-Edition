## 1. Этап 1: draw со сменой материала (~650 на кадр)

**Что сделано** (`native_gbuffer_prep.h/.cpp` `MemberPlan`/`CheckMemberPlan`, `parallel_cp.cpp` `JoinRun`, коммит
`b53dff6` + доводка этого захода): член run G-буфера с другими T#/S# присоединяется к run, если его PS-план (из
состояния CUE движка) совпадает по модулю и привязкам; ему передаются только отличающиеся текстуры и сэмплеры

## 2. Этап 2: причина регрессии T2 на нативном пути

### 2.1. Что измерено

- **Размер кольца CP** [E] (`runs/s2_ring`, одиночные прогоны): T2 busy 21,7 (128) / 23,2 (256) / 23,2–24,5 (512) /
  26,5 (1024) / 29,1 (2048) мс; простой T2 2,2 / 1,8 / 0,9–1,2 / 0,6 / 0,14. Чем больше кольцо, тем дороже та же
  работа T2: записи (3112 байт + векторы) уходят из кэшей — стоимость объёма данных, а не числа операций.
- **Счётчики PMC** (`runs/r8pmc`, off против native, по 2 прогона): разницы по промахам кэша T2 между off и native
  нет — ~55–56 млн обращений, L2 ~1,7 млн, межъядерных ~0,4 млн, DRAM ~118 тыс. на кадр. Сводка в прошлом заходе не
  сохранилась; числа — из рабочих заметок, пересчёт `pmc_sample.py` по `etw/dump.txt` в план [E, требует повтора].
  **Гипотеза «холодного кэша CPU» как главной причины этим не подтверждена.**
- **Связь трёх потоков через удерживаемые run** [A]: в режиме front фронтенд держит голову (`fhead_`) на лидере run,
  пока присоединяет членов; T2 не может пройти лидера; кольцо заполняется → T1 ждёт («full queue» 68 120 мс за прогон
  `r8m_plan_native_a`) → фронтенд закрывает run. Инструментирование (`T2IdleHeld`, `t1_full_held_`) добавлено в этом
  заходе, замер — в плане (§6).
- **Передача команд emitter** [A]+[E]: каждая из ~44 000–53 000 команд за кадр (A/B `gmat_2` / verify-прогон)
  публиковалась отдельной seq_cst-записью в
  `g_w` — строку, которую emitter читает в цикле ожидания. Это переезд строки между ядрами на каждую команду на пути
  T2. Сделано `SSPC_VK_EMIT_BATCH` (§4.2); эффект — §5.

### 2.2. Чего нет

uProf/VTune на машине нет; выводы о кэше — по PMC через ETW (`pmc_cal`), с ограничением выборки (sampling) и без
разбивки по функциям внутри T2.

## 3. Проверка образов раз на сегмент (`SSPC_TEX_SEGMENT`)

### 3.1. Что

Аналог `TexturesValid` из native passes Castlesea, но без шаблонов: «сегмент» — интервал, в котором не изменилось
состояние кэша образов и командный буфер. `ImageCache::Generation()` = сумма растущих счётчиков: барьеры
(`Transition` с записью барьера), загрузки (`Upload`), применённые инвалидации, изменения флагов в `Find`
(target/storage, `memory_newer`), эпоха (набор образов), кадр (возраст `Touch`). `Executor::SegSync()` открывает новый
сегмент при смене поколения или `cur_.value`; дополнительно сегмент сбрасывается на любом storage-образе и draw с
записью в память.

### 3.2. Штамп

После барьеров draw (`RecordDraw`, после исправления layout дескрипторов) каждая текстура, прошедшая полный путь,
получает штамп сегмента, если: memo указывает на тот же образ той же эпохи; образ валиден; не цель draw; его layout —
layout текстуры (`TextureLayout`); `ImageCache::ReadSince(kGraphicsShaders, SHADER_READ)` — новый вызов `Transition`
ничего бы не записал; `last_seq`/`last_frame` — этого буфера и кадра (Touch уже сделан). Члены run ставят штамп в
`own_sharps` по тем же условиям.

### 3.3. Быстрый путь

Попадание memo (тот же T#, флаги, эпоха) со штампом текущего сегмента и образом не из целей draw — дескриптор из memo
(`view`, `seg_layout`), без обращения к `CachedImage`: без проверки валидности, `Touch`, вычисления layout, без записи в
`bound` (циклы feedback / need_transition / Transition / исправление layout его не видят — для него они ничего не
сделали бы, это и проверяет verify). Исключены: compute, storage, FMask, массивы mip, дисплейный draw апскейлера,
диагностики, которым нужен `bound`.

### 3.4. Проверка [E]

`runs/r8n/v_all_verify` (город, gmat + все три новых флага, фон 18,9%): попаданий в draw 46 631 430, в членах
5 679 183; штампов 69 832 061; сегментов 1 016 008 (~183 на кадр при 157 render pass на кадр); **проверено
52 310 613, расхождений 0**; `[Error]` 0, DEVICE_LOST нет, выход чистый. Попадания — ~75% привязок текстур полного
пути (62,5 млн попаданий memo) и ~67% собственных текстур членов (8,5 млн).

## 4. Многопоточная запись: native passes

### 4.1. Что делает Castlesea [A]

`pc-port/gpu/native_passes.h/.cpp`, `native_passes_rasterizer.inl`, `native_material_rasterizer.inl` (GPL-2.0-or-later,
читалось как справка, код не переносился): хук на `DrawCommandBuffer::drawIndex` движка; на сабмите — скан записей
регистров и пул из 6 потоков пишет «сегменты» (подряд идущие draw с теми же attachments, до 4096) во вторичные
командные буферы (`VkCommandBufferInheritanceRenderingInfo`); CP находит сегмент по адресу первого draw, один раз
сверяет регистры и делает `vkCmdExecuteCommands`, не разбирая пакеты. Шаблоны материала (PassKey + хэш материала):
первый draw — полным путём. Их уроки: compute — в первичном буфере (во вторичном ломалось освещение), dispatch,
оставшийся на CP, закрывает сегмент (иначе пропадали огонь и дым), защиты feedback/depth, снимок памяти на сабмите,
blended indirect — не в сегментах.

### 4.2. Почему у нас не перенесено напрямую [E]+[A]

1. **Вызовы драйвера у нас уже не на критическом пути.** Их делает emitter: «ring full 0 times» во всех прогонах —
   он успевает за T2. Параллельная запись вторичных буферов разгрузила бы emitter, а не T2.
2. **Узкое место — сама логика записи T2** (22–28 мс busy за кадр), и она работает с общим изменяемым состоянием:
   `images_` (memo, Find, барьеры), `buffers_` (Classify, продвижение), `ring_` (потоковое кольцо), сэмплеры,
   пайплайны, тени состояния (`gfx_pipeline_`, `dyn_`, дескрипторы, вершинные буферы). Параллельный `RecordDraw` —
   переработка всех этих структур под потоки.
3. **Вторичные буферы не наследуют состояние**, а после `vkCmdExecuteCommands` состояние первичного не определено.
   Тени T2 предполагают непрерывность внутри командного буфера; каждый сегмент пришлось бы начинать с полного
   состояния — это дополнительная работа именно T2.
4. **Render pass с вторичными буферами — только вторичные буферы** (`VK_RENDERING_CONTENTS_SECONDARY_COMMAND_BUFFERS_BIT`)
   без `VK_KHR_maintenance7`/`VK_EXT_nested_command_buffer`; их поддержка на этом драйвере не проверялась (в логе
   упоминаются только maintenance1/5).

Поэтому в этом заходе сделана часть, которая ложится на нашу схему и бьёт по T2:

- **`SSPC_VK_EMIT_BATCH=1`** (`vk_emit.cpp`): поток T2 (`EnableBatching`) кладёт команды в кольцо как раньше, но
  публикует `g_w` один раз на запись (`Publish` в `ParallelCp::Loop` до публикации записи как исполненной), а также при
  любом `Sync` и при заполненном кольце. Порядок команд не меняется: публикуется позиция, все записи до неё целы под
  `g_lock`. T1 публикует как раньше (его публикация включает и записи T2). Проверено [E]: 22 201 337 публикаций на
  232 937 013 команд.
- **`SSPC_VK_EMIT_RING_MB`**: размер кольца emitter 1..16 МБ (по аналогии с кольцом CP, §2.1) — не измерено.
- **Проверка образов раз на сегмент** (§3) — аналог их `TexturesValid`.

### 4.3. Проект многопоточной записи (не реализовано)

**Фаза A — разделение draw на «разрешение» и «кодирование» на T2.** Разрешение (последовательно, как сейчас): цели,
барьеры, загрузки, инвалидации, поиск ресурсов, выделение в потоковом кольце. Результат — компактный пакет draw:
пайплайн, push-константы, записи дескрипторов (готовые хэндлы), вершинные/индексный буферы, значения динамического
состояния, аргументы draw. Кодирование пакета в вызовы Vulkan — отдельно. Измеримая цель: стоимость этапа «commands»
G-буфера 1478 нс/draw [E, R8 gmat_a] против стоимости записи пакета.

**Фаза B — кодировщики сегментов.** 2–4 потока, у каждого свой `VkCommandPool` на кадр в полёте; сегмент = render pass
(одни attachments, без clear/барьера/dispatch внутри). Каждый вторичный буфер начинается с полного состояния своего
первого draw (пайплайн, всё динамическое состояние, дескрипторы, push-константы, вершинный ввод), внутри — разностное
кодирование. Первичный: `vkCmdBeginRendering(CONTENTS_SECONDARY)` + `vkCmdExecuteCommands` по порядку сегментов.
Остаются последовательными и в первичном буфере: барьеры и переходы layout между сегментами, compute (урок
Castlesea), копии/загрузки, запросы окклюзии, метки времени, flush/submit. После `ExecuteCommands` тени T2
сбрасываются.

**Фаза C — параллельное разрешение для «лёгких» членов run.** Только чтение: снимок резидентности буферов на сегмент,
выделения потокового кольца — непересекающиеся куски на поток, memo текстур — через штампы сегмента (§3), сэмплеры —
созданные заранее; любой промах — откат в последовательный путь.

**Новые узкие места** [H]: фронтенд (busy ~24 мс, почти насыщен), T1 (compute 11–15 мс), GPU (~18 мс в городе),
SMT: 6 ядер на T1 + фронтенд + T2 + emitter + кодировщики + потоки игры.

**Проверка**: Vulkan Validation + Sync Validation на вторичных буферах; режим verify — хэш закодированного потока
команд каждого draw во встроенном и вторичном пути; скриншоты против base; Flat-04744 / 04152.

### 5.1. Почему серия перезапускалась [E]

Первый раунд шёл с порогом 10%: принятые прогоны имели фон 8,9–9,6% (Telegram, msedgewebview2, node/esbuild),
единственный чистый — `fence_1` (3,3%) — дал 39,2 FPS против 35,3–37,8 у остальных. Флаг fence в Mailbox ждёт
0,001 мс, значит разница — фон: ~6% фона стоили ~3–4 FPS, больше ожидаемых эффектов флагов. Прогоны с ~9%
переименованы в `<tag>_bg9` (сохранены, в сводку не входят), серия перезапущена с порогами gate 4% / замер 5%
(4 попытки; грязный на последней — исключается). Владелец на это время закрыл приложения; принятые прогоны —
фон 0,6–1,7% (кроме `fence_1`, 3,3%). Остановлена мной в 00:49 после `fence_3_dirty1`: Telegram и браузер
закрыть было нельзя; `seg_3` исключён (4 грязные попытки), `fence_3`, `all_3` не сняты.
