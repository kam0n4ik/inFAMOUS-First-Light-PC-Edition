## 2. Инструменты

### 2.1. Профилировщик геймплея `SSPC_R9_GPROF` (`src/runtime/gpu/r9/gprof.cpp/.h`)

Поток профилировщика с периодом (тик) 1 мс в режиме 1 и 2 мс в режиме 2 (`SSPC_R9_GPROF_US`, 250–100000; порог
выборки — поток отработал ≥ `SSPC_R9_GPROF_MIN_PCT` = 5% тика):

- **режим 1**: `QueryThreadCycleTime` каждого потока процесса за тик — CPU по потокам и группам (game_main, jobs, cp_t1,
  cp_front, cp_t2, cp_emit, present, shader, audio, …) без остановки потоков;
- **режим 2**: плюс выборки кода: поток, который в тике отработал не меньше порога, приостанавливается
  (`SuspendThread`/`GetThreadContext`), пишется rip, первый вызывающий в eboot, до 8 адресов возврата в `.text`
  SecondSonPC.exe из первых 512 слов стека и цепочка кадров eboot по rbp (одна копия стека, проверки границ без
  переполнения). Раз в 10 тиков наблюдаемые потоки (Game:Main, JobWorker, SecondSonPC:Gpu*, ShaderCacheIO,
  VideoOutPresent, Pipeline*), которые в тике не работали, тоже выбираются — **выборки ожидания** (флаг bit1): где поток
  стоит. Формат записи — версия 3 (`gprof.h`).
- Счётчики CP/шейдеров/файлового ввода (`Gprof::Count`) и метки фаз (`Gprof::Mark`) — агрегатами в тике, не на каждый draw.
- Диапазон eboot берётся лениво (`Engine::GuestImageEnd()` в `Refresh`): профилировщик стартует раньше
  `SetGuestImage` (bootstrap), заголовок файла содержит 0 — отчёт берёт диапазон из записи модуля «eboot».
- Адрес возврата в eboot принимается, только если он в исполняемых страницах образа (`FindCode`, VirtualQuery; в лог
  `R9 gameplay profiler: eboot code [...]`) и сразу после `call` (E8 rel32 / FF /2) — `IsReturn`. Без этого
  [E] (`runs/prof/trav_f1_gprof_1`) у потоков JobWorker «вызывающим» становился указатель на данные eboot `0x1d1c250`
  (рядом с менеджером очереди задач `0x1d1bfe0`), и скан стека останавливался до кадров SecondSonPC.
- Стек над rsp читается одним блоком до базы стека TEB (если rsp на нём), иначе 16 КБ, иначе до конца региона rsp
  (у рабочих потоков с неглубоким стеком до верха меньше 4 КБ — прежнее чтение 4 КБ не проходило целиком).
- Выборка «работал» у потока, который к моменту снимка стоит в системном вызове ожидания (`ZwWaitForAlertByThreadId`
  и др., `gprof.py` `WAIT_SYSCALLS`), — это поток, который отработал часть тика и заснул; где ушли его циклы, она не
  показывает. Отчёт выносит такие выборки отдельной строкой («ran in the tick, blocked in a wait when sampled»), а не
  в CPU `ntdll` (до этого у jobs 8,9 мс/кадр «в ожидании» — артефакт).

Отчёт: `py -I -X utf8 tools/r9/gprof.py report <прогон> [--marks] [--phase имя=с0-с1]` →
`r9/frames.csv` (покадрово: CPU групп, лог CP, счётчики, разбивка ожиданий Game:Main), `phases.txt`, `hot_<фаза>.txt`
(eboot эксклюзивно/инклюзивно по `E:\research\r9\ghidra\functions.tsv`, SecondSonPC по `llvm-symbolizer`, системный код
по ближайшему экспорту PE, системное время по вызывающему в SecondSonPC, ожидания), `hitches.txt` (кадры > 50/90 мс:
CPU групп, листья, ожидания наблюдаемых потоков со стеками SecondSonPC).

Разбивка ожиданий Game:Main [A] (по адресам возврата из спина `0x53b2b0` `sspc_delay_us_spin`):

| Колонка | Где игра ждёт | Что это |
|---|---|---|
| `cw_emitters` | ожидание async compute из EndFrame `0x3edef0` (через `0x1695e0`) | CPU игры читает состояние эмиттеров частиц, посчитанное на GPU |
| `cw_light` | из `0x3ee470` (возврат `0x29cd5b`) | DMA света частиц |

## 4. F1: фризы 1–4,5 с раз в минуту при перемещении

### 4.1. Причина [E]

`runs/cal/trav_city_cal2`, кадр 4544 мс (~60 с прогона), выборки ожидания:

- `cp_front` стоит в `ntdll < ShaderDiskCache::ReadRecord < LoadModule < … < BuildSpecializationKey` — фронтенду нужен
  модуль шейдера из дискового кэша (новый вид при перемещении);
- `ShaderCacheIO` в это время работает в `PipelineCacheFile::SaveOwned` (`xsputn`, `operator new`, `_Zero_range`);
- T1 стоит в `WaitHead` (кольцо CP полно), игра — в спине ожидания.

[A] `Backend::MaybeSavePipelineCache` (поток ShaderCacheIO, проверка раз в 10 с, сохранение не чаще раза в минуту,
если число созданных конвейеров менялось и 10 с стабильно) выполняет `PipelineCacheFile::Save` внутри
`ShaderDiskCache::WithWriteOwnership`, который держит `io_mutex_` всё сохранение: `vkGetPipelineCacheData` (866 МБ),
буфер с нулевой инициализацией, вторая копия с заголовком, запись 866 МБ. `ShaderDiskCache::ReadRecord` берёт тот же
`io_mutex_`. ShaderCacheIO был занят на ~60,3 с в каждом прогоне по 1,3–1,8 с CPU.

### 4.2. Исправление `SSPC_R9_PCACHE=1` (`src/runtime/gpu/r9/pcache.h`)

- `ShaderDiskCache::WithWriteOwnership` в режиме 1 берёт собственный `lease_mutex_` вместо `io_mutex_`: сохранение
  не держит чтения и дозаписи модулей; `Close` берёт оба (`scoped_lock{lease_mutex_, io_mutex_}`), т. е. дожидается
  идущего сохранения (`shader_disk_cache.cpp/.h`);
- `PipelineCacheFile::SaveR9` (`vk_precompile.cpp/.h`): данные драйвера пишутся как пришли (`make_unique_for_overwrite`,
  без второй копии; заголовок и данные — двумя write; тестовый «разрыв» записи `tear_` сохранён); сохранение
  пропускается, если размер данных драйвера равен загруженному/последнему сохранённому (кэш драйвера растёт только при
  новом конвейере; конвейер, созданный из кэша, его не меняет);
- отчёт: `pipeline cache (driver): … skipped N (R9-F1: nothing new)` в `gpu_native.txt`, на выходе —
  `pipeline cache: not saved - nothing new since it was loaded (R9-F1, N checks)` вместо «0.0 MiB saved».

### 4.3. Корректность

[A] Формат файла и заголовок не изменились (`CacheHeader`, те же хеши); файл заменяется так же (`.tmp` +
`MoveFileExW(REPLACE_EXISTING|WRITE_THROUGH)`). Владение записью (lock-файл `lock_`, `writable_`) проверяется так же.
Конкуренция сохранения с дозаписью модулей: они пишут разные файлы (`vulkan.bin` против файла модулей), общий только
лок — его больше не делят. [E] `runs/f1/trav_city_f1_1`: все сохранения пропущены (размер данных драйвера не менялся:
новых конвейеров 0), прогон без ошибок.
