# Phase 4 — Graphics Backend (стратегия, карта, границы)

Статус на 2026-10-10: **P4.1, P4.2 и P4.3 выполнены экспериментально** (`docs\PHASE4_P41_GPU_FOUNDATION.md`,
`docs\PHASE4_P42_COMMAND_PROCESSOR.md`, `docs\PHASE4_P43_SHADER_TRANSLATION.md`). Игру рисует **мост shadPS4**
(по умолчанию, без изменений). Собственный бэкенд SecondSonPC — **фундамент**: Vulkan-устройство и тестовое окно
(уровни A/B), свой командный процессор PM4 (тень и воспроизведение), свой путь шейдеров в тени (`--gpu-shaders`:
идентичность по содержимому, runtime-параметры, ресурсы, модули SPIR-V через адаптер транслятора, ключи пайплайнов).
Ни одного игрового кадра свой бэкенд не рисует.

Пометки: **[К]** — подтверждено кодом/логами (место указано), **[Пр]** — предположение.

## 1. Архитектурная карта (как сейчас, по коду)

```
Гостевой код игры (eboot)
  │ libSceGnmDriver (85 импортов, BRIDGE) — пишет PM4 в свои командные буферы (DrawIndex ≈ 2950/кадр — только запись)
  │ sceGnmSubmitAndFlipCommandBuffers — ровно 1 на флип; DingDong (ASC) ≈ 1,1/кадр; SubmitDone ≈ 1/кадр
  ▼
GnmDriver моста (core\libraries\gnmdriver\gnmdriver.cpp)
  │ WaitGpuIdle → PatchFlipRequest (NOP PatchedFlip + метка VO) → PerformSubmit → Liverpool::SubmitGfx / SubmitAsc
  ▼
Liverpool (video_core\amdgpu\liverpool.cpp), поток shadPS4:GpuCommandProcessor — единственный
  │ корутины очередей; ProcessGraphics (DCB, 40 опкодов), ProcessCeUpdate (CCB — игра не использует),
  │ ProcessCompute (ASC, 14 опкодов); Regs (reg_array 0xD000, memcpy без признаков изменения);
  │ неизвестный опкод / type-0 → UNREACHABLE (смерть процесса)
  │ EOP/WRITE_DATA/RELEASE_MEM пишутся в гостевую память в момент разбора, не по выполнению на GPU
  ▼
Vulkan::Rasterizer (renderer_vulkan\vk_rasterizer.cpp) — на том же потоке
  │ Draw: ключ пайплайна заново (memset+CB) → GetProgram/StageSpecialization → BindResources (ObtainBuffer,
  │ FindImage/FindTexture) → BeginRendering → барьеры → bindPipeline (каждый draw) → drawIndexed
  │ PipelineCache (+кэш шейдеров на диске, патч 0013), BufferCache (stream 128 МиБ), TextureCache (детайлинг на GPU),
  │ PageManager (трекинг записей CPU через защиту страниц + AV), Scheduler (1 очередь, vkQueueSubmit на кадр)
  ▼
VideoOut (core\libraries\videoout\driver.cpp) + Presenter (vk_presenter.cpp)
  │ GfxFlip (IRQ на NOP-маркере) → SubmitFlip → PrepareFrame (на потоке моста) → PresentThread на vblank 60 Гц
  ▼
WindowSDL (создаёт SecondSonPC) → swapchain моста → экран
```

Гостевая память: один владелец адресного пространства — выбранный менеджер (моста или SecondSonPC с `--native memory`);
GPU видит её через контракт `GpuMemory` (у моста — `Core::GpuMemory`, у SecondSonPC с P4.1 — `Gpu::GuestMemory`,
`src\runtime\gpu\gpu_memory.h`, адаптер `src\bridge\shadps4\gpu_memory_host.cpp`).

Подробная таблица компонентов (файл, владелец, поток, состояние, точка перехвата, риск) — P4.1 §2.

## 2. Границы компонентов

**Заменимы независимо (контракт есть):** гостевая память (`GpuMemory` / `Gpu::GuestMemory`), исключения
(`BridgeHandlers`, патч 0022), часы (патч 0024), очереди событий (`Kernel::EventQueues`, патч 0025), остановка
(`Lifecycle`), диагностика (`--gpu-stats`, патч 0027).

**Заменяются только вместе (общее состояние):**
* **A** — Liverpool + Regs + Rasterizer + PipelineCache + Buffer/TextureCache + Runtime + PageManager + Scheduler (кэши
  держат `liverpool*`, все читают `liverpool->regs`, сбросы через `SendCommand` в поток моста);
* **B** — VideoOutDriver + Presenter + IrqC(`GfxFlip`) + `vo_port` (зависит от A: `PrepareFrame` использует кэш текстур).
* GnmDriver и VideoOut переключаются **только вместе**: если одни экспорты Gnm станут NATIVE, `RegisterLib` моста не
  вызовется, `presenter` останется null, а `PresentThread` его разыменует **[К]** (`driver.cpp:276`).

## 4. Совместимость с P3.2–P3.6

Всё P3.x остаётся под флагами и не зависит от выбора бэкенда. Свой бэкенд потребует: (1) `--native memory` или
адаптер `Gpu::GuestMemory` над менеджером моста (есть с P4.1); (2) слот обработчика трекинга в диспетчере
(`--native exceptions`) — P4.4; (3) `Kernel::EventQueues` (есть), `Kernel::Clock` (есть), шаги `Lifecycle` (есть).

## 5. Зависимости от shadPS4 на сегодня (графика)

GnmDriver, Liverpool, весь `renderer_vulkan`, `texture_cache`, `buffer_cache`, `page_manager`, `shader_recompiler`,
VideoOut, ImGui-оверлей, окно SDL (создаёт SecondSonPC), Vulkan-устройство моста. Своё: декодер PM4, статистика,
реестр владельцев, контракт памяти, Vulkan-основа (свои instance/device на той же `vulkan-1.dll`).

## 6. Критерии готовности собственного бэкенда (по умолчанию)

1. Исполняет все команды, которые игра реально шлёт (список P4.1 §3), без UNREACHABLE.
2. Попиксельное совпадение с мостом (с допуском) в замороженных сценах `logs\p25\scene_*` и ручная проверка.
3. Не медленнее моста ни в одной контрольной сцене; 30-мин сессия без сбоев и утечек.
4. Один владелец всего GPU (реестр `src\runtime\gpu\backend.h`), трекер страниц один.
5. Мост остаётся собранным как запасной бэкенд до Phase 5.

## 7. Стратегия fallback

Выбор бэкенда — **один раз при старте** (`--gpu-backend bridge|sspc`; в P4.1 `sspc` для игры отклоняется с сообщением).
**Никакого переключения во время работы** и тихого возврата на мост после частичного исполнения: состояния двух
реализаций не смешиваются (реестр владельцев отказывает второму владельцу и пишет, кому принадлежит ресурс).
Запасной путь — перезапуск с `--gpu-backend bridge` (сообщение пользователю), не автоматический переход.

## 8. План сравнения изображений

Снимки по номеру флипа обоими бэкендами в одной замороженной сцене (тот же `--press`, те же сохранения), попиксельная
разница с допуском + визуальный просмотр; в отладочном режиме — снимки целей рендеринга по номеру draw. Эталон перевода
шейдеров — SPIR-V моста (тот же транслятор через адаптер).

## 9. Риски

* Наивный пересчёт пайплайнов/привязок на каждый draw (как у моста) — не даст прироста (P4.1 §7).
* Синхронные ожидания GPU на метках; неверный темп vblank (бимодальность 30/60 — «медленный режим» есть и у моста).
* Трекинг страниц через исключения (~70–90 тыс. AV/с в игре) — дорогой путь; два трекера одновременно недопустимы.
* Метки EOP/RELEASE_MEM у моста пишутся при разборе, а не по завершении на GPU — свой бэкенд должен решить, сохранять ли
  это поведение (корректность игры может на него опираться **[Пр]**).
* Привязка к версии игры 01.07 (адреса eboot).

## 10. Известные ограничения (P4.1)

Свой бэкенд не исполняет ни одного игрового пакета; Vulkan-основа — отдельный процесс-режим `--gpu-probe` (уровни A/B);
PM4-трассы покрывают загрузку, главное меню, мир, густую листву, способности и меню паузы; **сцены «огонь + листва» нет**
(не воспроизводится автосценарием) — данных нет.
