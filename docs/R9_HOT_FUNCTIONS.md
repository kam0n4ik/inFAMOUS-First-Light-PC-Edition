# R9: горячие функции игры и runtime по сценариям

Ветка `feature/r9-gameplay-perf` (worktree `E:\SecondSonPC-r9`). Общий отчёт — `docs/R9_GAMEPLAY_PERFORMANCE.md`,
метки [E] / [A] / [H] — как там.

## 1. Метод и адреса

- Источник — профилировщик геймплея `SSPC_R9_GPROF=2` (`R9_GAMEPLAY_PERFORMANCE.md` §2.1): выборки кода с весом —
  циклы потока в тике, мс/кадр — CPU-время. «Эксклюзивно» — функция eboot, в которой стоял rip (лист в eboot);
  «инклюзивно» — функция встречается в цепочке кадров eboot по rbp. Отчёты: `r9/hot_<фаза>.txt` прогонов
  `runs/prof/fight_f1_gprof_1` (бой способностями, 56,5–136,5 с), `runs/prof/trav_f1_gprof_2` (перемещение,
  51,9–136,9 с), `runs/cal/look_user_1` (сейв владельца: набережная и трасса с трафиком, 40–100 с, маршрут `look`;
  прогон до F1 и до исправления скана стека профилировщика — для Game:Main это не важно, у него стек eboot).
- **Адреса eboot** — смещения функций в образе eboot v1.07 (база 0), как в проекте Ghidra
  `E:\tools\ghidra-projects\SecondSon` (`/eboot`, выгрузка `E:\research\r9\ghidra\functions.tsv`). `FUN_xxxxxx` —
  функция без имени; `sspc_*` — имена из прошлых фаз SecondSonPC. **Функции runtime** (SecondSonPC.exe) — по
  символам (`llvm-symbolizer`), адресами не приводятся. Код драйвера/системы — по ближайшему экспорту PE.
- Частота вызовов и время одного вызова выборками не измеряются; они есть только у функций, которые измеряли пробы
  входа прошлых фаз (`NATIVE_ENGINE_FUNCTIONS.md`). Для функций вне критического пути (§4) это и не нужно: их время
  кадр не определяет.
- Назначение функции указано только по документу с разбором (ссылка в таблице) или по декомпиляции (§7); без этого —
  «не установлено». Подписи «ИИ / физика / анимация» без доказательства не ставятся.

## 2. Критический путь кадра: Game:Main [E]

Кадр игры последователен (`RENDER_ENGINE_ARCHITECTURE.md` §0, `REA_ENGINE_REVERSE.md`): Game:Main выполняет свою
работу кадра, ждёт async compute (ожидание A из EndFrame `0x3edef0`, ожидание B из `0x3ee470`, оба через `0x1695e0` и
спин `0x53b2b0`), затем EOP прошлого кадра в SubmitFrame `0x1f1e30` / `0x196c30`. Профили сняты с F1, **без**
ожидания B на GPU (REA-3), мс/кадр:

| Сценарий | кадр | работа Main | ожидание A (cw_emitters) | ожидание B (cw_light) | EOP | GPU busy |
|---|---|---|---|---|---|---|
| спокойно (бой, 41,5–56,5 с) | 18,2 | 3,84 | 6,56 | 1,14 | 5,74 | 16,47 |
| **бой способностями** | 22,1 | **4,27** | **9,50** | **5,30** | 2,14 | 17,69 |
| **перемещение** | 20,2 | **4,55** | **7,80** | **5,26** | 1,82 | 15,57 |
| сейв владельца (город с трафиком) | 33,1 | 6,37 | 16,71 | ≈ 8,5 ¹ | 0,55 | 24,98 |

¹ у `look_user_1` разбивки ожиданий в `phases.txt` нет (прогон до неё): `0x1695e0` 25,23 мс инклюзивно, из них из
`0x3edef0` 16,71 — остаток ≈ 8,5 мс приходится на других вызывающих `0x1695e0`, главный из них — ожидание B.

Собственная работа игры на главном потоке — **4,3–4,6 мс** кадра в бою и перемещении (6,4 мс на сейве владельца);
остальное — ожидания compute и GPU. С REA-3 ожидание B уходит на GPU (`R9_GAMEPLAY_PERFORMANCE.md` §8: p50 боя
−2,4 мс), но REA-3 в текущем виде небезопасен — зависание в долгой сессии, причина в коде игры — §8 ниже и
`R9_GAMEPLAY_PERFORMANCE.md` §11.

## 6. TOP-10 кандидатов в нативизацию по месту на критическом пути [E/A]

Шум итоговой серии ±0,5 FPS ≈ ±0,25 мс кадра при 48 FPS: экономию меньше ~0,25 мс серия A/B подтвердить не может.
Код eboot и так исполняется процессором напрямую (x86-64): переписывание функции игры на C++ даёт только разницу
компиляторов (`0x11c890`: native ≤ 0,19 мс/кадр всей стоимости, FPS не изменился — `NATIVE_ENGINE_FUNCTIONS.md`).

## 8. Очередь async compute игры: почему REA-3 небезопасен [A]

Декомпиляция (`E:\research\r9\ghidra\dec_rea3\*.c`) после зависания сессии владельца (`R9_GAMEPLAY_PERFORMANCE.md` §11).
Объект очереди — `DAT_07d3cf10` (q); буфер команд — q+0x10 (текущая позиция q+0x20, конец q+0x18), его память q+0x1b70
(0x100000 байт, `0x3e9780` → `0x168b70`), метки — массив `DAT_00e17e80`.

| Функция | Что делает |
|---|---|
| `0x168b70` | создание очереди: буфер команд 1 МиБ, кольцо IB 0x8000 байт (q+0x1bb0, указатель чтения q+0x1ba0), две метки: q+0x1b8c — счётчик отправок (её ждёт `0x1695e0`), q+0x1b80 — **позиция, до которой GPU прочитал буфер команд**; обработчик нехватки места — `0x168cc0` → `0x169020` |
| `0x1691e0` | отправка: RELEASE_MEM ++q[+0x1b88] в метку отправок и RELEASE_MEM позиции конца отправки в метку q+0x1b80; IB [начало отправки, текущая позиция) в кольцо (ждёт место по указателю чтения), `sceGnmDingDong` |
| `0x169020` | нехватка места в буфере команд: ждёт, пока метка q+0x1b80 (позиция, прочитанная GPU) освободит нужное, при переходе через конец переносит начатую часть в начало — **кольцо, защищённое прогрессом GPU** |
| `0x196c30` | конец кадра: `0x1f1e30` (SubmitFrame: ожидание EOP прошлого кадра, flip), освобождение памяти кадра, затем `0x3ed640` |
| `0x3ed640` → `0x169660` | **безусловный сброс** буфера команд compute в начало (q+0x20 = q+0x1b70, q+0x1b7c = 0) и запись 0 в метку позиции q+0x1b80 — без проверки, что GPU дочитал |

Сброс на каждом кадре корректен только потому, что перед `0x196c30` главный цикл прошёл ожидание B (`0x3ee470`):
вся работа очереди compute выполнена. С REA-3 ожидание B не блокирует игру: если командный процессор не успел прочитать
последнюю отправку кадра (он отстаёт на ~90 отправок), следующий кадр пишет команды с начала буфера поверх неё —
процессор читает чужие данные (в сессии: «type-0 packet on queue 1 (depth 1) at 0x24bede6c0»), останавливает отправку,
метка отправок больше не растёт, игра и ворота REA-3 ждут её бесконечно. Это объясняет и редкость (окно — задержка
процессора больше ~кадра в нужный момент): ни одного случая в ~35 прогонах стенда по 2,5 мин, один — через 16 мин игры.

Направление исправления (не реализовано в R9): сохранить гарантию игры, но позже — перед сбросом `0x3ed640` дождаться
той же метки отправок, что ждало ожидание B (q[+0x1b88]). Сброс стоит в конце `0x196c30`, после ожидания EOP, поэтому
ожидание B перекрывалось бы с ожиданием EOP, а не шло перед ним. Эффект и корректность такого варианта не измерены.
