# R9: исправление REA-3 (ожидание B игры на GPU)

Ветка `feature/r9-gameplay-perf` (worktree `E:\SecondSonPC-r9`), прогоны — `E:\research\r9\runs\rea3fix` и серии,
названные ниже. Push не выполнялся, `main` не тронут. REA-3 по-прежнему **выключена по умолчанию**; рекомендуемый набор
R9 остаётся F1 + F3 (`R9_GAMEPLAY_PERFORMANCE.md` §0). Метки: **[E]** — измерено, **[A]** — анализ кода, **[H]** —
гипотеза.

REA-3 (`SSPC_REA_DEFER_WAIT_B=1`, `src/engine/render/frame_trace.cpp`): второе ожидание async compute кадра (хвостовой
вызов `0x1695e0` из `0x3ee470`, возврат `0x29cd5b` в главном цикле) не блокирует поток игры — следующая графическая
отправка начинается с `WAIT_REG_MEM(метка >= цель)` (`Gpu::Gnm::SetGraphicsGate`). У неё были две проблемы:

1. зависание через ~16 мин игры (`R9_GAMEPLAY_PERFORMANCE.md` §11, `R9_HOT_FUNCTIONS.md` §8);
2. кадры парами 17/40 мс на сейве владельца (сцена упирается в GPU): p95 42,5 мс против 35,3 у базы при FPS 35,4 / 30,8
   (`runs/final_user`).

## 1. Зависание: время жизни буфера команд compute [A/E]

### 1.1. Как игра использует буфер

Очередь `q = 0x7d3cf10` (`render_layout.h`): память буфера команд q+0x1b70 (1 МиБ), позиция q+0x20, начало ещё не
отправленной части q+0x1b7c (в dword), счётчик отправок q+0x1b88 и его метка q+0x1b8c, метка позиции q+0x1b80 (метки —
массив `0xe17e80`, по 8 байт).

- **Отправка `0x1691e0`**: RELEASE_MEM ++q[+0x1b88] в метку счётчика (7 dword), затем RELEASE_MEM позиции в метку q+0x1b80
  со значением `((cur − mem)/4 + 0x16) & ~0xf` — ровно новое начало после второго 7-dword пакета и выравнивания на 64
  байта; затем INDIRECT_BUFFER на `[mem + start, cur)` в кольцо (`0x63d8c0`, заголовок `0xc0023f02`), `sceGnmDingDong`.
  **Буфер не копируется: GPU читает команды на месте.**
- **Нехватка места `0x169020`**: ждёт, пока метка позиции освободит нужное, и переиспользует память ниже неё.
- **Сброс `0x169660`** (через `0x3ed640` в конце хвоста кадра `0x196c30`, после SubmitFrame `0x1f1e30` и освобождения
  памяти кадра): `cur = mem`, `start = 0`, метка позиции = 0. **Без проверки, что GPU дочитал.**
- Порядок главного цикла: обновление частиц `0x3ee7d0` (пишет буфер **с нуля**) → `0x3edef0` (ожидание A + DMA света
  `0x3f3ed0`) → `0x3ee470` (ожидание B) → `0x45e840` → `0x196c30`. Следующий кадр переписывает буфер **до** своего
  ожидания A.

Без REA-3 сброс безопасен: ожидание B стоит перед `0x196c30`, вся работа очереди выполнена.

### 1.2. Гонка при REA-3

С отложенным ожиданием B отправки кадра N после ожидания A (DMA света) могут быть ещё в полёте, когда хвост кадра
сбрасывает буфер, а кадр N+1 пишет в него свои команды. Командный процессор читает перезаписанные данные — «type-0 packet
on queue 1 (depth 1) at 0x24bede6c0» в сессии владельца, — останавливает отправку, метка счётчика больше не растёт, игра
и ворота REA-3 ждут её бесконечно. Вторая форма той же гонки: поздняя запись метки позиции переживает сброс (0 → старое
значение), и `0x169020` переиспользует ещё не прочитанную память.

**[E]** Наблюдение без исправления (`SSPC_R9_REA3_SAFE_RESET=0`, `runs/rea3fix/smoke_unsafe_user`, сейв владельца,
100 с): **474 из 1000 кадров** сбрасывают буфер, пока работа очереди в полёте (метка счётчика < цели или метка позиции ≠
концу последней отправки). Зависание требует ещё, чтобы процессор успел прочитать перезаписанную часть раньше, чем
кадр N+1 её допишет, — отсюда редкость (0 случаев в ~35 прогонах по 2,5 мин, один через 16 мин).

### 1.3. Исправление: safe reset (по умолчанию при REA-3; `SSPC_R9_REA3_SAFE_RESET=0` — только для A/B)

На возврате из SubmitFrame (уже существующая входная проба `0x1f1e30`, **новых перехватов машинного кода нет**), только в
кадре, где ожидание B было передано GPU, поток игры ждёт (`delay(50 мкс)` игры `0x53b2b0`), пока:

1. метка счётчика ≥ q[+0x1b88] — выполнена последняя отправка очереди;
2. метка позиции = q[+0x1b7c] — её поздняя запись уже легла (до 40 × 50 мкс после счётчика; иначе — `[Error]` и сброс как
   в коде игры).

Это та же гарантия, что давало ожидание B, но там, где она нужна, — перед сбросом, после ожидания EOP прошлого кадра
внутри SubmitFrame (обычно GPU к этому моменту уже закончил). Ворота REA-3 перед графикой кадра остаются: графика N
по-прежнему ждёт работу compute N на GPU, а не на CPU. Барьер взводится только из отложенного ожидания B, поэтому экраны
загрузки и разбор очереди (SubmitFrame без отложенного ожидания) не затронуты. Установка проверяет хеши `0x196c30`,
`0x3ed640`, `0x169660`, `0x1691e0`, `0x169020` (другая версия игры — REA-3 не включается).

Циклов нет: барьер ждёт работу compute, отправленную **до** графики кадра N; ни эта работа, ни метка позиции не зависят
от графики N или потока игры.

**[E]** `runs/rea3fix/smoke_safe_user` (сейв владельца, 100 с): барьер ждал в 497 из 1000 кадров, максимум 2,85 мс,
метка позиции опоздала 0 раз, отправок после ожидания B 0. FPS 35,94 (без барьера 35,27, в шуме): барьер ускорение не
съедает.

**[E] Долгий прогон** `runs/rea3fix/soak_safe_user` (сейв владельца, бой каждые 15 с, F1 + F3 + REA-3 safe): 20 мин 11 с
игры (остановлен по просьбе владельца на 20-й из 26 мин, поэтому без `stats.json`; журнал сохранён), > 40 000 кадров —
дальше 16 мин, где REA-3 без исправления зависала. Барьер ждал в 19 007 из 40 000 кадров (макс. 126 × 50 мкс = 6,3 мс),
метка позиции опоздала 0 раз, `[Error]` / `[Critical]` 0, остановок отправок CP 0.

## 2. Подача кадров: откуда пары 17/41 мс [E]

### 2.1. Где поток игры проводит кадр

Трасса lifecycle (`runs/rea3fix/t_safe_user`, `SSPC_P54_FRAME_TRACE=1`, `SSPC_P412_STALL_TRACE=deep,window=60:66`;
скрипты `gframe.py`, `waita.py`, `c1pos.py` — в отчёте ниже), 200 кадров, safe REA-3:

| часть кадра игры (SubmitFrame → SubmitFrame) | мс |
|---|---|
| период | 30,0 |
| ожидание A (C1 — симуляция частиц, `0x3edef0`) | **17,8** |
| SubmitFrame (шаг 5: EOP прошлого кадра) | 6,4 |
| барьер safe reset | 0,18 |
| своя работа CPU | 5,6 |

Ожидание A: ~5,7 мс CP обрабатывает C1 до его RELEASE_MEM (первая порция compute через ~0,5 мс после DingDong, дальше
C1 чередуется с порциями графики), ~12 мс — от RELEASE_MEM до записи метки на GPU (C1 за уже отправленной графикой
кадра N в единственной очереди Vulkan + выполнение самого C1).

Период потока игры почти ровный (25–35 мс), неровен present: всё решает, куда в потоке команд попадает C1(N+1)
относительно конца графики кадра N (FlipMarker). В 173 кадрах из 198 RELEASE_MEM C1(N+1) обработан CP раньше
FlipMarker(N) — C1 выполняется внутри G(N), кадры ровные (26–30 мс). В 25 кадрах C1(N+1) опаздывает за FlipMarker(N):
GPU заканчивает G(N) без C1 (короткий интервал), потом выполняет C1, игра выходит из ожидания A поздно, и GPU стоит, пока
CPU (~5,5 мс) и CP готовят G(N+1) (длинный интервал). Это гонка: C1(N+1) приходит через шаг 5 SubmitFrame(N) и хвост
кадра после передачи G(N) (early submit, шаг 4), а CP тратит на G(N) 15–20 мс.

### 2.2. Порядок «compute сразу» — чередование уходит вместе с ускорением

Одиночные чистые прогоны, сейв владельца, окно 40–100 с (`runs/rea3fix/c_*`), фон стенда ≤ 3,5 % кроме отмеченного:

| конфигурация | FPS | 1 % low | p95 мс | p99 мс | lag1 | < 22 мс | > 36 мс | CP пусто мс | GPU мс |
|---|---|---|---|---|---|---|---|---|---|
| F1 + F3 | 31,12 | 21,2 | 39,2 | 43,8 | +0,66 | 0 % | 13 % | 10,6 | 24,7 |
| F1 + F3 + REA-3 (safe) | **35,52** | 20,1 | 41,1 | 45,8 | **−0,74** | 19 % | 17 % | 7,4 | 24,7 |
| + `SSPC_R9_REA3_ORDER=1` (фон 9,2 %) | 29,50 | 19,8 | 38,3 | 43,5 | +0,29 | 0 % | 18 % | 11,0 | 25,1 |
| + FP-1 `SSPC_FP_GPU_AHEAD=4` | 29,09 | 22,2 | 39,1 | 41,9 | +0,41 | 0 % | 26 % | 11,9 | 26,4 |
| + FP-1 `SSPC_FP_GPU_AHEAD=2` | 26,56 | 19,8 | 40,9 | 46,1 | +0,72 | 0 % | 81 % | 16,3 | 27,6 |

- **ORDER** (`SSPC_R9_REA3_ORDER=1`, новый эксперимент, выкл.; `CommandProcessor::SetComputeOrder`): compute-отправка
  начинается только после всей графики, отправленной до неё (кроме ожидания графики на памяти, отличной от меток
  VideoOut — тогда сразу). C1 всегда после G(N): пары уходят, но каждый кадр получает простой GPU — ниже базы.
- **FP-1** (FrameBreak, существующий): CP не берёт графику, пока на GPU n и больше пачек. Ожидание A не короче
  (20,1 мс в трассе `t_fp4_user`: 7,2 у CP + 12,9 на GPU) — GPU-часть ожидания — в основном выполнение самого C1, а не
  очередь графики перед ним; при этом кадр CP растягивается до темпа GPU, ускорение теряется. FP-1 к тому же несовместим
  с CP-9 (сдача пачки — на drained round end), т. е. в этих прогонах нет и round end без drain пресета.

Вывод: ускорение REA-3 и пары даёт один механизм — перекрытие C1(N+1) с хвостом G(N); удержание графики или compute
его не разделяет. Устранять надо гонку: C1(N+1) не должен опаздывать за конец G(N).

### 2.3. CC-2: compute игры первым у CP, пока игра его ждёт (`SSPC_CC_CRITICAL=1`, существующий, выкл.)

На PS4 очередь async compute разбирает свой фронтенд (ACE) параллельно с графическим CP; у нас один поток CP чередует
очереди, и C1 ждёт за порциями графики. CC-2 (FrameBreak; Validation + Sync там — 0 сообщений) ставит compute первым,
пока игра блокирована в ожидании compute. С REA-3 он проходит через тот же хук ожидания (`g_critical`): ожидание A
сигнализирует CP, ожидание B — ворота, не сигнализирует.

- Трасса `t_cc2_user` (окно 60–66 с, фон 10 %): CP доходит до RELEASE_MEM C1 за 4,3 мс (5,8), ожидание A 15,2 мс
  (17,8); C1(N+1) опоздал за FlipMarker(N) в **1 из 208** кадров (25 из 198 без CC-2).
- Но прогон без трассы `rea3_pace_user/cc2_1` (фон 4,2 %): FPS 34,91, lag1 −0,59, < 22 мс 14 %, рассогласование шагов
  игры и экрана 4,0 / 11,2 мс (F1 + F3: 1,4 / 4,2; safe: 3,2 / 8,0). CC-2 сужает окно гонки, но не закрывает её.

### 2.4. AQ: compute игры на своей очереди Vulkan (`SSPC_FB_ASYNC_COMPUTE=1`, FrameBreak, выкл.)

Как на PS4: пачка только из команд compute-очередей игры идёт на вторую очередь (семейство compute) и выполняется рядом
с графикой; ждёт основную очередь только при конфликте. Это убирает и сам механизм пар: C1(N+1) не стоит в очереди за
хвостом G(N). В FrameBreak AQ отвергнут из-за потери устройства (7 из 8 прогонов), гонка не найдена.

- **[E]** `runs/rea3fix/aq_safe_user` (F1 + F3 + REA-3 safe + AQ): `VK_ERROR_DEVICE_LOST` через ~28 с игры (~440 кадров);
  NVIDIA device fault — 8 адресов «instruction pointer (unknown)» в пределах 1 КиБ (один шейдер, который не заканчивается
  — истечение времени, не MMU-сбой). На очереди compute 2555 пачек, рядом с основной 2215, конфликтов по диапазонам 4.
- **[E]** С `--gpu-native-diag` (`aq_diag_user`, 150 с) — без потери, но 14,7 FPS: журнал и маркеры замедляют пачки
  compute в разы (60 с GPU против 3,6), гонка не проявляется. В отчёт о потере добавлены контрольные точки и маркеры
  очереди compute и признак очереди у пачек (`vk_diagnostics.cpp`).
- **[E]** Validation + Sync Validation с AQ (`aq_val_user`, 240 с): 3 сообщения, все `VUID-StandaloneSpirv-Flat-04744`
  (создание шейдера, не AQ); опасностей синхронизации 0, потери нет — но рядом с основной очередью лишь 330 мс из 14 с.
- **[A]** Пробел в проверке конфликтов: у основной очереди отмечаются записи, загрузки и обращения команд compute, но
  **не чтения графики** (`GuestRangeImpl`, `RunRange`, zero-copy и lean-пути отрисовок). Пачка compute, пишущая то, что
  ещё читает графика пачки в полёте, ждать её не будет. Эксперимент `SSPC_FB_ASYNC_NOTE_READS=1` (выкл.): чтения графики
  тоже отмечаются.
- **[E]** `aq_reads1_user` (NOTE_READS): конфликтов 5 → 806 (дыры WAR были), но устройство потеряно (на 69 с). Не причина.
- **[E]** Бисекция: `aq_base1_user` (только `SSPC_FB_ASYNC_COMPUTE=1`, без F1/F3/REA-3) — потеря через 26 с; R9 и REA-3
  ни при чём, дефект в самом AQ. `SSPC_FB_ASYNC_SERIAL=1` (пачки без перекрытия) — без потери.

#### 2.4.1. Какой шейдер не заканчивается: маркеры у dispatch (`SSPC_DIAG_AQ_MARKERS=1`, диагностика)

`vkCmdWriteBufferMarkerAMD` до и после каждого dispatch (и у каждой смены pipeline отрисовок) в слова своей очереди;
отчёт о потере перечисляет начатые и не законченные. Потеря замечается и потоком презентации (`VkResult -4` при
`vkQueueSubmit2`) — теперь и тогда пишется `gpu_device_lost.txt` (`native_backend.cpp`).

- **[E]** `aq_mark1/2_user`, `aq_base1_user`: во всех трёх на очереди compute STARTED и не закончен **cs 0x2edaa0c00**
  (1–4 группы по 64, очередь игры q1); основная очередь в это время свободна или рисует.
- **[A]** Шейдер (`SSPC_DIAG_DUMP_SHADER`, `runs/rea3fix/shaders/cs_2edaa0c00.glsl`): цикл частиц по
  `[start, start + count)` из привязки 0 — `start = b0[2]`, `count = b0[3]`; атомарный счётчик в GDS. Огромный `count` —
  миллиарды итераций — TDR.

#### 2.4.2. Что он читает (`SSPC_DIAG_AQ_WATCH=<cs>`, диагностика)

Для каждого dispatch этого шейдера — привязка 0: путь в `GuestRangeImpl`, байты 0..15 у CPU при записи и у GPU перед
dispatch (копия в зонд), и все команды, пишущие эти диапазоны.

- **[E]** Привязка 0 — 48-байтовый заголовок эмиттера в пуле частиц (видеопамять, путь resident); `[2]` (`start`) пишет
  CPU, `[3]` (`count`) — GPU (у CPU там 0 — копия хоста старше). В норме `count` ≤ 0x32. С копией в зонд (барьер перед
  dispatch) потери нет: 80 000 проверок, ни одного `count` больше потоков dispatch.
- **[E]** Без зонда (`SSPC_DIAG_AQ_WATCH_PROBE=0`, `aq_wnp1_user`): потеря; зависший dispatch читает заголовок
  `0x27005b700` (раскладка пула сменилась), а там у хоста `[0x21a, 0x41f00006, 0, 0x3f800000]` — данные частиц,
  `count = 1.0f` = 1 065 353 216. Основная очередь в этот момент рисует (пачка 9778, тени), пачка compute 9779 идёт рядом.

#### 2.4.3. Причина: блочная загрузка P4.9-B не отмечалась для конфликтов [A/E]

`BufferCache::Prepare`: первая недействительная страница блока (64 КиБ) тянет за собой остальные использованные
недействительные страницы блока — **за пределами** диапазона привязки (P4.9-B, вкл. по умолчанию). Для конфликтов AQ
отмечался только диапазон привязки. Запись CPU в заголовок (`[2]`) делает страницу недействительной; пачка основной
очереди, читающая пул (частицы на экране), копирует всю страницу из хоста — с его старыми байтами там, где GPU записал
`[3]`, а пачка compute рядом её не ждёт: заголовок, который она записала или читает, перезаписывается копией хоста.

- **[E]** `SSPC_P49_BLOCK_UPLOAD=0` (только страницы привязки) с AQ: `aq_nobu1–4_user` — **4 из 4 без потери** (обычный
  AQ: потеря в 7 из последних 8 прогонов, на 26–69 с).
- **Исправление** (`vk_executor.cpp`, `GuestRangeImpl`): страницы, которые загрузка фактически скопировала
  (`BufferCache::LastUploads()`), отмечаются для конфликтов AQ целиком. `SSPC_FB_ASYNC_NOTE_UPLOADS=0` возвращает старое
  поведение — только для A/B.
