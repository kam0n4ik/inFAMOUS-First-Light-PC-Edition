# R9: нативные замены и шаги от универсального моста

Ветка `feature/r9-gameplay-perf` (worktree `E:\SecondSonPC-r9`). Общий отчёт — `docs/R9_GAMEPLAY_PERFORMANCE.md`,
горячие функции — `docs/R9_HOT_FUNCTIONS.md`; метки [E] / [A] / [H] — как там.

## 1. Правило выбора

ТЗ R9: переписывать нативно только подтверждённые узкие места, сохраняя логику игры, порядок побочных эффектов,
потоки и время жизни; режимы off / verify / native; нестабильное — выключено по умолчанию. Узкое место — то, что
стоит на критическом пути кадра в реальном геймплее, а не то, что просто тратит CPU.

## 2. Что показали профили

- **Код игры уже исполняется процессором напрямую** (eboot — x86-64): переписывание его функции на C++ даёт только
  разницу компиляторов. Прошлые фазы это измерили: `0x11c890` в native — ≤ 0,19 мс/кадр всей стоимости, FPS не
  изменился (`NATIVE_ENGINE_FUNCTIONS.md`); нативный G-буфер R8 (`0x1a1770`, 99,98% draw) — прироста FPS не
  подтверждено (`NATIVE_GBUFFER_DRAW_0x1a1770.md`).
- **Собственная работа игры на критическом пути — 4,3–4,6 мс** кадра (Game:Main в бою и перемещении), профиль
  плоский: самая дорогая функция 0,13 мс (`R9_HOT_FUNCTIONS.md` §3). Задания (отсечение, подготовка рендера) — вне
  критического пути: Main ждёт их 0,40–0,44 мс/кадр (§4 там же).
- **Кадр держат синхронизация и GPU**: ожидания async compute A + B — 14,8 мс кадра боя (до REA-3), EOP 2,1 мс,
  GPU busy 17,7–18,0 мс; T2 простаивает 7 мс (`R9_VULKAN_MULTITHREADING.md`).
- Рывки геймплея — инфраструктура моста: лок кэша шейдеров при сохранении кэша конвейеров (фризы 4–5 с) и повторный
  импорт кучи вершин драйвером (кадры 219–252 мс).

Отсюда цель «нативной» работы R9 — места, где универсальный мост воспроизводит поведение PS4 буквально и платит за
это на критическом пути: синхронизация, память, ввод-вывод кэша. Функции игры по месту на критическом пути
(`R9_HOT_FUNCTIONS.md` §6) экономии выше шума серии (±0,25 мс) не дают — ни одна не переписывалась.

Не вошло в итоговый набор: ленивый write-back + чтения кучи (`SSPC_FB_LAZY_WB=1; SSPC_REA_HEAP_READS=1`) — +0,34 FPS
поверх core, диапазоны перекрываются (§8); приоритет compute в CP (CC-2, compute-first) — без прироста (§6.1).
Многопоточная запись Vulkan — не оправдана профилями (`R9_VULKAN_MULTITHREADING.md` §4).

## 4. Функции игры, которые рассматривались и не переписывались

| Функция | Почему нет |
|---|---|
| задачи отсечения `0x58b510` / `0x1d1710` (0,75 / 0,48 мс эксклюзивно на заданиях) | вне критического пути: Main ждёт задания 0,40 мс/кадр, предельная экономия ≤ 0,4 мс |
| EmitterUpdate `0x3efde0` (Main 0,13 мс; сейв владельца 0,37 мс) | ниже шума серии; кандидат, если на сцене владельца предел станет CPU |
| поддеревья `0x571c20`, `0x47cf40` (Main ~1 мс инклюзивно) | плоские: несколько систем, эксклюзивно ≤ 0,035 мс у корня — одной горячей точки нет |
| прочие функции TOP-30 Game:Main | ≤ 0,11 мс каждая |

Реконструкции прошлых фаз (R5–R8: `0x11c890`, `0x1f0870`, сеттеры CUE, `0x14ad0`, `0x448640`, `0x1a1770`) остались
как в R8: в пресете стенда только нативный G-буфер (`SSPC_NATIVE_GBUFFER=native`), он был включён во всех прогонах R9.

## 5. Шаги от универсального моста shadPS4

1. **Синхронизация игры — по смыслу, а не буквально.** REA-3 — первая замена на критическом пути кадра, где знание
   кода игры (что CPU делает после ожидания) заменяет общее поведение PS4 «CPU ждёт метку». Это даёт больше, чем
   перевод любой функции игры: −2,4 мс на обычном кадре боя.
2. **Память игры — по её устройству.** F3 обрабатывает кучу вершин движка как постоянную кучу, а не как произвольные
   диапазоны: импорт один раз, без исчерпания памяти устройства, без обрезанного хвоста.
3. **Инфраструктура моста без общих замков на горячем пути** (F1).
4. **Что от универсального моста осталось на критическом пути** (бой, после R9): эмуляция командного процессора для
   compute игры (CP до метки 2,65 мс на ожидание), одна очередь Vulkan (compute игры стоит за графикой 2,94 мс),
   поток PM4 → Vulkan (~6000 draw: T1/фронтенд/T2/emitter по 14–16 мс CPU, сейчас не предел), ~290 мелких dispatch
   async compute на кадр, которые на GPU исполняются в одной очереди с графикой (`R9_GAMEPLAY_PERFORMANCE.md` §9).
   Следующий нативный шаг по профилям — путь compute частиц игры: отдельная очередь с корректной синхронизацией
   (попытка AQ в FRAMEBREAK — потеря устройства 7 из 8, причина не найдена) или сокращение числа dispatch.
