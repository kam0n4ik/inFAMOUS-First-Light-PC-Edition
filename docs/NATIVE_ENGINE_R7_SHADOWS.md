## 3. NativeDrawCommand для `0x43d480`

`src/native_engine/r7/shadows/shadow_draw_command.{h,cpp}`:

```cpp
struct ShadowDrawInputs { u64 records; u32 record_stride = 0x48; u32 instances; u32 instance_slot;
                          u64 vertex_table; u32 vertex_buffers; };
void BuildInstancedDraw(u64 module_base, u64 pass, u64 r, u64 records, u64 n, u64 mesh,
                        NativeRenderContext& ctx, NativeDrawCommand& cmd, ShadowDrawInputs& inputs);
std::string CheckAgainstTrace(const NativeRenderContext&, const NativeDrawCommand&, const ShadowDrawInputs&,
                              const STrace::Trace& original_calls);
```

`BuildInstancedDraw` вызывается на входе `0x43d480` (до любой работы) и заполняет: `ctx` (r, CUE `r+0x128`, DCB
`r+8`, проход), `cmd` (producer `Shadows`, fn `ShadowInstanced` = 0x43d480, indexed, `index_count=[mesh+0x68]`,
`index_base=[mesh+0x58]`, `run_tag = Source::Shadow` (2), `state.prim = 4`, `state.index_size = 0`,
`state.num_instances = (u32)n`, `resources.cue`) и `inputs` — то, чего в контракте R7.0 нет (буфер записей экземпляров
с шагом 0x48, слот VS `pass[0x121]`, таблица вершинных буферов меша). `CheckAgainstTrace` проверяет 9 вызовов
оригинала по порядку и аргументам плюс V# записей (база 44 бита, stride, num_records).

Проверка: офлайн 2 000 draw, 0 различий (и неправильная команда ловится: +1 экземпляр, сдвиг базы); в игре
в режиме verify каждая сверка `0x43d480` сопровождается проверкой команды — **16 777 216 проверок, 0 расхождений**.
Submit команды не используется (R7.0 `Submit` — заглушка Off/Fallback), путь отрисовки остаётся оригинальным.

## 4. S2: `0x450460`, виды 0x10 и 0xa с объектом

### 4.1 Что делают ветки [A, Ghidra — своя копия `E:\research\r7\shadows\ghidra`]

`0x450460(records, block, atlas, view, table, buffers, owner)`: до 4 записей (`[records]` — счётчик, виды `+8`,
индексы `+0x18`), 18 видов через таблицу `0xaad7c0`, запись в блок `R+0xda18` (0x100 float + грязный байт `+0x404`)
через `0x11e5d0`. Поле слота по виду (смещение u16 в записях): 1/2/5→0x28, 0/3→0x2a, 4→0x2c, 7→0x2e, 6→0x30,
9→0x32, 0xa→0x36, 0xc→0x38, 0xd→0x3a, 0xe→0x3c, 0xf→0x3e, 0x10→0x40, 0x11→0x42; 8/0xb — без записи.

- **Вид 0x10** → `0x4502e0(n = (int)table[i], use_owner = table[i+1] > 0, owner[0x11], &4 float)`: ячейка листа
  спрайтов. `0x290380` — значения по умолчанию, `0x28fa30(0x1d1faa0, &rec)` под pthread-мьютексом объекта
  (`+0x20`; инициализация мьютекса и condvar при `[+0x30] == 0`) копирует текущую 32-байтную запись
  (`+0x230 + [+0x270]*0x20`: столбцы `+8`, строки `+0xc`, T# `+0x18`); затем `n % (cols*rows)`, деления, при T#
  — полутексельная поправка из ширины/высоты (`dword2` биты 13:0 / 27:14) и множитель 0.5625. Пишет 4 float.
- **Вид 0xa с объектом** (`buffers+0x88 != 0`): виртуальный геттер `[vtable+0x28]` (тип), ветка при
  `type − 5 < 0x46`: `0x4740c0(obj[5], 0xe4e35609ac35b83a)` (кость по хешу; при `[skel+0x190] == 0` → −1, иначе
  `0x785b0 → 0x6b860`), `0x476ed0` (родитель из таблицы short), обратная 3×3 родителя (`vrcpps` + шаг Ньютона,
  `vhaddps`) × перенос; результат ×0.01 → 1 float. Без объекта или вне диапазона типа — 0.0.

### 5.2 Дедуп draw-состояния (`SSPC_R7_SHADOWS_DEDUP=1`, OFF по умолчанию)

В ручном `0x43d480` (только живые вызовы из живого вызова цикла на том же контексте): после draw запоминаются
начало чанка DCB, позиция после draw и число экземпляров. Перед следующим draw пакеты DCB между запомненной позицией
и текущей разбираются (`UntouchedState`): разрешены только NOP, SET_SH_REG, SET_CONTEXT_REG, DRAW_INDEX_2,
DRAW_INDEX_AUTO, WRITE_DATA, INDEX_BASE, INDEX_BUFFER_SIZE, SET_UCONFIG_REG вне 0x242/0x24d (≤16 КБ). Любой другой
пакет, другой чанк, откат указателя назад или выход за конец → ничего не пропускается. Пропуск: `NUM_INSTANCES` —
если не тронут и число то же; `VGT_PRIMITIVE_TYPE`+`INDEX_TYPE` — если не тронуты (значения у этого draw всегда 4 и
0). Ни один draw, экземпляр, каскад, разрешение не меняется: GPU получает то же состояние на каждом draw (регистры
VGT — постоянное состояние CP: shadPS4 `liverpool.cpp` пишет их только этими пакетами; наш CP читает их из
регистров при draw, `command_processor.cpp` — его быстрый путь draw-run принимает и такие последовательности).
Порядок draw не меняется. Офлайн-тест сканера — 11 случаев (`dedup scan` в `r7_shadows_tests.cpp`).

В игре: записано ≈4 990 пакетов на кадр, пропущено ≈7 240 (из ≈12 230).

## 6. Отрицательные результаты

- Нативизация цикла теней сама по себе не ускоряет: N − O = −0,03 FPS (серия `r7s_ab1`); ручной цикл на ≈5 %
  дороже по CPU (9 707 против 9 214 тиков/вызов, одиночные прогоны) — время цикла почти целиком в вызываемых.
- Повторных матриц, повторной работы между каскадами по объектам и повторной подготовки материала практически нет
  (0 / 0 / 0,7 на кадр) — кэши под них не делал.
- Дедуп draw-состояния: −59 % пакетов состояния теней, но FPS/CP-эффект меньше разброса стенда — не подтверждён.
- `SSPC_R7_SHADOWS_STATS` очень дорог (глобальный мьютекс на запись экземпляра: 131 000 тиков/вызов) — только
  для подсчётов, никогда в замерах.
- Верификатор держит 64 записанных случая на процесс (`native_engine_verify.cpp`, `kRing`): повторная инъекция
  сбоя в тестах R7 съела кольцо и уронила две чужие проверки `main.cpp:1439/2355` (`CasesRecorded() == recorded+1`).
  Исправлено у себя (инъекция один раз на процесс).
- Объединение `shadow_trace` с `gbuffer_trace` (необязательный пункт) не делал: `gbuffer_trace` — зона R7-G, а
  общий модуль трассы требует [shared]-правки обеих веток.

## 7. Блокеры и нужные [shared]-изменения

- Блокеров по S1/S2 нет.
- [shared] предложение для R7-Core: в `NativeDrawCommand`/`NativeResourceBindings` нет полей для буфера экземпляров
  (база, шаг 0x48, число, слот VS) и таблицы вершинных буферов меша; сейчас они в `ShadowDrawInputs` (моя
  структура). Чтобы `Submit` мог исполнить теневой draw, их нужно добавить в контракт.
- [shared] к сведению R7-Core: кольцо случаев верификатора (64) общее для всех тестов процесса — тесты, вызывающие
  много расхождений, ломают последующие проверки `CasesRecorded()`.
- Игровой проверки веток 0x10/0xa `0x450460` в теневом движке нет и не будет (не встречаются); если нужна —
  в проходах других вызывающих `0x450460` (не зона R7-S).
