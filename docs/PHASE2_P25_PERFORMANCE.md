# P2.5 — Kernel Stabilization & Performance Optimization

Состояние на 2026-10-10 (живой документ: методика, измерения, найденные узкие места, история исправлений).
Дорожная карта не меняется: P2.4 Native Thread Manager → **P2.5** → Phase 3 Independent Runtime → Phase 4 Own
Graphics Backend. P2.5 оптимизирует существующий рантайм и GPU-мост и устраняет подтверждённые дефекты; свой
графический бэкенд — Phase 4.

Цель — максимальный нативный FPS без генерации кадров (промежуточно стабильные 30, дальше 60+ на RTX 2060 6 GB,
1080p). Ни одна цифра ниже не обещание: только измеренное.

## 5. Отслеживание записей CPU в память GPU (45–49 тыс. нарушений/с)

Механизм (код моста): `BufferCache::SynchronizeMemory` загружает изменённые CPU страницы в GPU и снимает
с них право записи (`RegionManager::ChangeRegionState` → `PageManager::UpdatePageWatchersForRegion` →
`SignalImpl::Protect` → `GpuMemory::ProtectTracking` → `AddressSpace::Protect` → `VirtualProtectEx`, под
**глобальным** мьютексом адресного пространства). Первая запись игры в такую страницу → нарушение доступа →
VEH моста (`core\signals.cpp`) → `GuestFaultSignalHandler` (`page_manager.cpp`) → `Rasterizer::InvalidateMemory`
(`IsMapped`: разделяемый замок + `boost::icl`; кэш буферов: блокировка региона, пометка «изменено CPU», снятие
защиты **одной страницы**; кэш текстур: поиск образов на странице) → продолжение.

Измерено (`--track-stats`, `logs\performance\p25_track*`, окна по 10 с геймплея):

## 7. Исправления

### 7.1 `barrier-memo` — без повторного перебора подресурсов (патч моста `0015`)

`Image::GetBarriers` для образа, уже разбитого на подресурсы, на каждый частичный запрос обходит весь
запрошенный диапазон, чтобы выяснить, что барьер не нужен. Сохранённый результат: для частичного запроса только
на чтение после обхода весь диапазон гарантированно в нужном состоянии; подложка образа (`BackingImage`) хранит
поколение `state_gen`, которое растёт при любом изменении состояний подресурсов (барьер, создание/очистка
вектора) и при записи состояния в `Runtime::SetBackingSamples`, и до 4 таких «чистых» запросов. Тот же запрос
при том же поколении пропускает обход: те же барьеры (ноль), те же состояния. **Включена по умолчанию** после
A/B; `--no-perf-opt barrier-memo` выключает (режимы `perf_runs.ps1`: `PO0` — все изменения P2.5 выключены, `PO1`
— по умолчанию).

Проверка: обойдённых состояний за 10 с 1,77 млрд → 5,5 млн (`--track-stats`); самотест 802/0, `--native memory`
92/0, fault-test 22/0; скриншоты 60-й секунды с оптимизацией и без совпадают (сцена, свет, тени, интерфейс).
Результаты A/B — §9.

## 8. Стабильность

* **P2.4, независимое ревью потоков** (ecc:cpp-reviewer по `dca227b`): критических и высоких дефектов нет.
  Исправлены средние: (1) выделения памяти на пути выхода/отсоединения гостевого потока (`g_free` — кольцо
  фиксированного размера, `g_pending`/`g_stacks` зарезервированы, `ReapPending` без вектора) — при нехватке commit
  они могли бросить `bad_alloc` на гостевом потоке, а VEH моста завершает процесс на любом C++-исключении;
  (2) `scePthreadOnce` навсегда блокировал остальных, если поток выходил (`scePthreadExit`) внутри init-функции —
  теперь, как у моста, состояние возвращается в «не выполнено» и ждущие просыпаются; (3) лог создания потока
  читал `detached` без замка (другой поток уже может отсоединить его по дескриптору); (4) размер стека > 1 ГиБ
  отклоняется `EAGAIN` до арифметики, которая переполнялась. Самотест 802/0 (дважды), `--native memory` 92/0.
  Не исправлено (паритет с мостом, низкий риск): строки имён потоков могут выделять память, ABA устаревших
  дескрипторов после 1024 циклов слотов.
* **Зависание в геймплее** (`p25_track\M0_2`, 1 из 6 прогонов этой сессии): кадры и нарушения доступа
  прекратились на ~36-й секунде, процесс жив, ошибок в логах нет, свободного commit ~2,5 ГиБ (рядом шла
  обработка трассы xperf). Причина не установлена (нехватка commit или редкий дедлок моста). Для следующего
  случая нужен дамп зависшего процесса перед принудительным завершением.

### 8.1 SSPC-002 — падение на ~15-й секунде загрузки: причина найдена

**Механизм.** На Windows мост патчит гостевые `mov reg, qword ptr fs:[disp]` во время работы: первое выполнение →
нарушение доступа → `core\cpu_patches.cpp` `TryPatchJit` (под мьютексом модуля) пишет в код `jmp rel32` на
трамплин + NOP. Запись идёт **побайтно** (Xbyak `db`) прямо в код, который в этот момент могут выполнять другие
гостевые потоки. Поток, выбравший инструкцию посреди записи, получает «разорванный» `jmp`: новый опкод `E9` и
часть старых байт смещения. Старший байт старого смещения — SIB-байт исходной инструкции `0x25`, поэтому
переход уходит на **модуль + 0x25xxxxxx** — в незамапленную память.

**Доказательства.**
* Все 9 записанных падений SSPC-002 (сессии P2.3–P2.5) — переход на `база eboot + 0x25xxxxxx`. Если старший байт
  смещения — старый `0x25`, адрес трамплина = адрес падения − 0x25000000: для 6 падений это база + 0x11AA7A2…
  0x11AC126 — начало области трамплинов (сразу за образом eboot, `src\loader\module.cpp:151`) к ~15-й секунде
  загрузки; у падения `p25_memo_ab\PO1_1` разрыв после двух байт смещения (`53 e9 34 25`: новые, новые, старые,
  старые) у места `eboot+0x18be20` (`mov r14, fs:[0]` сразу за последним верным адресом возврата `[rsp-8]`)
  восстанавливает трамплин база + 0x11AA778 — тот же диапазон.
* `--patch-race-test` (`src\bridge\shadps4\selftest_patch_race.cpp`): свой модуль из 32 768 мест
  `mov rax, fs:[0]; ret`, 8 потоков приходят к каждому в случайный момент окна 20 мкс (как потоки заданий игры).
  На мосте без исправления — **4 из 4 прогонов падают** в первые ~15 мс: execute fault в свободной памяти на
  модуль + 0x25081236 / 0x250805cc / 0x250503b8, `[rsp]` — адрес возврата, ни один регистр не содержит цель —
  та же сигнатура, что в игре.
* Первая версия теста (потоки в ногу) гонку не ловила: все потоки получали нарушение доступа на старой
  инструкции ещё до записи. Ранние «падения» той версии (код 127) — закрытие окна «не отвечает» пользователем:
  тест тогда запускался после создания окна игры; теперь — до него, окна нет.

**Исправление (патч моста `0016`).** `WriteLiveCode`: в первый байт — `int3` (одним атомарным байтом), затем
остальные байты новой инструкции, затем её первый байт; между шагами `FlushProcessWriteBuffers` (IPI на все
процессоры процесса — сериализация выборки команд), как `text_poke_bp` в Linux. Поток, попавший на `int3` во время
записи, ловится в VEH моста (`HandlePatchBreakpoint`): ждёт мьютекс модуля (патч завершён) и возвращается на начало
инструкции. Ядро Windows иногда сообщает о такой ловушке как о привилегированной инструкции (`0xC0000096`) — если к
моменту разбора `int3` уже заменён на `jmp`; этот случай обрабатывается так же (на пропатченном `jmp` настоящей
такой ошибки быть не может). В лог необработанного исключения моста добавлены байты по `rip` и параметры.

**Проверка.** Первая версия (без обработки `0xC0000096`): 18 из 20 прогонов теста проходят, по ~4 100–4 800
пойманных и возвращённых потоков за прогон; 2 падения — `0xC0000096` на начале места патча (место № 1427). Версия с
обработкой: **20 из 20** (`logs\p25\race_fixed3`), 3 345–5 068 пойманных потоков за прогон (≈ 84 тыс. всего), из
них 1 сообщён ядром как привилегированная инструкция и обработан — без этой обработки тот прогон упал бы. Игровая
проверка (`tools\sspc002_runs.ps1`, exe `build\ab\p25_fix0016`, загрузка «Продолжить» 40 с): **8 из 8 без падений**
(`logs\runs\p25fix_sspc_1..8`, first-chance 0), серия остановлена по просьбе пользователя; пользователь сам
подтверждает, что игра не падает. Восемь загрузок сами по себе слабое доказательство (при прежних ~15 % вероятность
случайно не упасть 8 раз ≈ 27 %) — решающее подтверждение даёт воспроизводимый тест: 4/4 падений без исправления
→ 0/20 с ним.

## 12. Частота кадров: что задаёт потолок (этап E)

### 12.1 Игра просит 60 Гц

Лог моста (патч `0017`): `sceVideoOutSetFlipRate: handle 1 rate 0` (поток `Game:Main`, один вызов при старте).
`rate 0` = 60 Гц: режим ограничения 30 FPS в игре выключен, **потолок 60 FPS — родной режим игры**. Разблокировка
таймеров или частоты симуляции не нужна и не делалась; путь к 60 — только удешевление кадра.

### 12.2 Как мост выводит кадры

* `SecondSonPC.toml`: `vblankFrequency = 60`, `presentMode = "mailbox"` (Vulkan-свопчейн не ждёт vsync).
* Поток `shadPS4:PresentThread` (`videoout\driver.cpp`, `PresentThread`) крутится с периодом эмулируемого
  vblank (16,67 мс) и берёт запрос флипа только на каждом `(flip_rate + 1)`-м vblank. Игра ждёт флипа (метки и
  события VideoOut), поэтому интервал кадра = работа кадра, **округлённая вверх до 16,7 мс**: 17–33 мс работы
  дают кадр 33,3 мс. Отсюда ступени 16,7 / 33,3 / 50 мс и «падение вдвое»: 28 мс работы показываются как 30 FPS.
* Present (`Presenter::Present`) — на потоке презентации, не на критическом потоке GPU-моста; `Game:Main` ждёт
  поток GPU-моста (§4), а не present.

### 12.3 Попутно: дефект сборки

Глоб патчей в `cmake\shadps4_bootstrap.cmake` был без `CONFIGURE_DEPENDS`: **новый** файл патча не
перезапускал configure. `build.ninja` последний раз генерировался с 15 патчами — для `0016`–`0018` не
выполнялась проверка цепочки, а поколение кэша шейдеров считалось без них. Код в дереве был верным (сверено:
рабочее дерево = HEAD + 0001…0018). Исправлено (`32e3ed5`); следующий configure: «the 18 shadPS4 patches are
applied». Заодно не собирался патч `0018` (нет `#include "bridge/shadps4/perf_opts.h"`) — исправлен до коммита.

### 14.1 `image-memo` — `FindImage` без обхода таблицы страниц (патч `0018`)

пока набор образов не менялся (`sspc_registry_gen` растёт в `RegisterImage`/`UnregisterImage`, а `DeleteImage`
требует снятой регистрации — освобождённый `ImageId` вернуться не может), тот же запрос получает тот же образ с
тем же касанием LRU. Запоминается только идеальное совпадение без подгонки вида.

| без (PO1_1, PO1_2) | 55,64 · 58,00 | 33,4 · 18,5 | 28,3 · 29,0 | 32,36 · 35,22 | 51,0 · 35,2 | 18,9 · 26,7 |
| с (PI_1, PI_2) | **59,96 · 59,92** | 18,1 · 18,1 | **50,4 · 48,2** | **38,50 · 38,62** | 35,4 · 35,3 | 26,3 · 28,2 |

Скриншоты: на 50-й секунде разница «с / без» 0,08–0,10 % пикселей (> 15 уровней) — как между двумя прогонами

### 14.2 `stream-host` — потоковый буфер в системной памяти (патч `0019`)

Потоковый буфер моста (128 МиБ) лежал в видимой процессору видеопамяти (`MemoryType::Stream`; лог:
`device-local true, host-visible true, coherent true, cached false` — BAR): каждая из ~27 тыс. копий на кадр —
запись по PCIe. С `stream-host` он в системной памяти (`MemoryType::HostUncached`, лог: `device-local false`),
GPU читает копии по PCIe при выполнении.

| `p25_shost_ab` (прогрев, затем ABBA) | L0 FPS | L0 1 % low | L3 FPS | L3 P50, мс | GPU 3D L0 / L3 |
|---|---|---|---|---|---|
| без (PO1_2, PO1_3) | 59,84 · 59,84 | 43,0 · 43,5 | 38,37 · 37,91 | 32,5 · 32,6 | 55,7 / 38,6 % |
| с (PS_1, PS_2) | **60,00 · 60,00** | **53,4 · 53,0** | **41,12 · 40,83** | **17,7 · 18,1** | 63,4 / 45,2 % |

На листве медиана кадра перешла с 33-мс ступени на 17-мс. Цена — видеокарта: +7 пунктов GPU 3D при тех же
60 FPS (≈ +1 мс работы GPU на кадр, чтение по PCIe), запас остаётся большим. Память: private и системный commit
без изменений, 128 МиБ переехали из VRAM (4260 → 4135 МиБ) в общую память (54 → 180 МиБ). Скриншоты — как
между прогонами одного режима. **Включена по умолчанию** (`602b619`). Риск: когда поток GPU-моста станет
короче, чтение констант по PCIe может стать заметной частью времени GPU — тогда сравнить снова (PresentMon).

### 14.2a Повторный профиль после 14.1–14.2 (`logs\p25\etw\foliage_L3_v2`)

Листва L3 в окне трассы — 43,75 FPS, P50 17,2 мс; работа потока GPU-моста 28,2 → **22,9 мс** на кадр

Дедупликация повторных копий в потоковый буфер (52 % — тот же диапазон и содержимое в кадре) **не делалась**:
проверка содержимого хэшем читает те же байты, а сэкономить можно только запись в write-combined память —

памяти гостя или свой путь констант).

### 14.2b `stream-reads` — без учёта интервалов чтения потокового буфера (патч `0020`)

`Runtime::AccessBuffer` записывал каждую привязку в `IntervalList` чтения/записи буфера. Интервалы чтения
спрашивают только у приёмника записи (`IsBufferAccessed(..., check_read_access)` в `CopyBuffer`,
`FillBuffer`, `InlineData`), а потоковый буфер приёмником не бывает (его пишет CPU; копии/заливки GPU идут в
буфер, который `ObtainBuffer` вернул для записи). С `stream-reads` доступ только на чтение к потоковому буферу
добавляет в отложенный барьер только стадию — как и раньше, — без интервала; запись и прочие буферы — как
раньше.

Серия `p25_stream2_ab` (прогрев, затем PO1 / PR / PC / PC / PR / PO1):

| | L0 FPS | L3 FPS | GPU 3D L3 |
|---|---|---|---|
| PO1 (умолчания) | 53,4* · 59,96 | 41,47 · 41,15 | 45 % |
| **PR** (`stream-reads`) | 60,0 · 60,0 | **43,20 · 44,52** | 49 % |
| PC (`stream-cached`) | 59,9 · 60,0 | 40,18 · 40,46 | 44 % |

\* PO1_2: 41 кадр > 33 мс на L0 (в PO1_3 — 60 ровно); на L3 оба PO1 сходятся. **`stream-reads` включена по
умолчанию** (`2d1cafe`). **`stream-cached` отклонён** (потоковый буфер в кэшируемой системной памяти,
`MemoryType::HostCached`, GPU читает со snoop): медленнее write-combined памяти `stream-host` — запись 28 МиБ

записан и непуст, но запись не уложилась в ожидание); 3 повтора подряд — 22/0. Код `crash.cpp` в P2.5 не
менялся; вероятная причина — диск/антивирус на свежем 64-МБ exe. Наблюдать.

### 14.2c Что упирается в архитектуру моста (блокеры для Phase 4)

Даже после 14.1–14.2b на густой листве поток GPU-моста тратит ~20–21 мс на кадр при 2–3 тыс. draw, то есть
~7–8 мкс процессорного времени на один draw, и он один (видеокарта занята на 45–65 %, из 6 ядер работают
~2,8). Точечные правки моста дают единицы процентов каждая; для стабильных 60 на листве нужно сократить
работу кадра ещё на ~4–5 мс. Это задачи своего графического рантайма (Phase 4), а не P2.5:

1. **Пересчёт состояния на каждый draw.** `GetGraphicsPipeline` заново строит ключ пайплайна, для каждой
   стадии ищет программу (`SearchBinaryInfo` читает заголовок кода гостя), строит `StageSpecialization` (разбор
   fetch-шейдера, чтение всех V#/T#/S#) и линейно сравнивает с перестановками — ~4 мс/кадр. Свой рантайм
   должен отслеживать изменения регистров (`SET_SH_REG`/`SET_CONTEXT_REG`) и пересчитывать только изменённое,
   а идентичность шейдера вести по адресу + поколению записи памяти (трекинг страниц), без чтения кода на
   каждом draw.
2. **Копия каждой маленькой константы.** ~27 тыс. копий (28 МиБ) на кадр в потоковый буфер, ~52 % — те же
   данные в том же кадре. Свой рантайм: прямое чтение памяти гостя GPU (импорт памяти хоста
   `VK_EXT_external_memory_host` или BDA поверх отслеживаемой арены), копия только изменённого.
3. **Учёт доступов и барьеров по интервалам на каждую привязку** (`IntervalList`, `Transit` на каждую
   текстуру) — нужен учёт на уровне проходов рендера, а не draw.
4. **Один поток записи команд.** Разбор PM4 и запись Vulkan — последовательно на одном ядре; нужна
   параллельная запись (вторичные командные буферы по проходам) или перенос подготовки на потоки заданий.
5. **Квантование vblank** — поведение самой игры (`flip rate 0` с ожиданием vblank, как на PS4): кадр
   длиннее 16,7 мс показывается 33,3 мс. Обходить его нельзя без изменения поведения игры; цель — работа кадра
   < 16,7 мс.
