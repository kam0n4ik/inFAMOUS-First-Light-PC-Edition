# Контекст рендера движка (GfxContext-подобный объект) и отправка кадра

Дата: 2026-10-14. Адреса — eboot (Ghidra, база 0). Имена наши. [A] анализ дизассемблера/декомпилятора, [H] гипотеза,
[?] неизвестно. Источник — функции `0x14ad0` (commit перед draw), `0x140d0`, `0x1f1e30` (кадр).

> **Уточнение P5.2B (RENDER_ENGINE_ARCHITECTURE.md §4).** Объект, описанный в §2, — это **Constant Update Engine
> (CUE)**, вложенный в контекст рендера движка R: `CUE = R + 0x128 = G + 0x120`, где `G = R + 8` — GfxContext с DCB
> по смещению 0. Все смещения §2 — относительно CUE. Commit для CS — `0x13ec0` (не `0x140d0`); `0x140d0` вызывается
> только из `0x18210` [H: dispatch draw]. Полный формат таблицы раскладки, сеттеры по видам слотов, пул контекстов,
> сортировка и связь с объектами сцены — там же.

## 1. Нумерация стадий (как в Gnm) [A]

Таблица `0xaf0070` (u16 на стадию, +0x2C00 = регистр SPI_SHADER_USER_DATA_*_0) используется `setUserDataRegion`
`0x626520` и `setPointerInUserData` `0x626400`:

| stage | 0 CS | 1 PS | 2 VS | 3 GS | 4 ES | 5 HS | 6 LS |
|---|---|---|---|---|---|---|---|
| USER_DATA_0 | 0x2E40 | 0x2C0C | 0x2C4C | 0x2C8C | 0x2CCC | 0x2D0C | 0x2D4C |

## 2. Объект контекста (`param_1` функции `0x14ad0`, размер > 0xC710)

Все смещения, к которым обращается `0x14ad0`, ложатся в сетку по номеру стадии [A]:

| Смещение | Поле | Доказательство |
|---|---|---|
| +0x00 / +0x08 | колбэк аллокатора и его данные (`ptr (*)(ctx, dwords, &got, user)`) | `0x123d0` [A] |
| +0x20 / +0x28 / +0x30 | линейный аллокатор встроенных данных: текущий / начало / конец | `0x123d0` [A] |
| +0x78 | указатель, передаваемый в user data всем стадиям [?] (кандидат: глобальная таблица констант) | `setPointerInUserData(…, ctx+0x78)` [A] |
| +0x88 | u8: делать ли L2-предвыборку кода шейдеров | перед `prefetchIntoL2` [A] |
| **+0x90 + stage·0x1800** | **теневой массив ресурсов стадии** (6 КиБ: V#/T#/S#/константы), копируется в аллокатор при изменении | `memcpy(alloc, ctx+0x4890 / +0x6090, n·4)` для GS/ES [A] |
| **+0xC090** | **DrawCommandBuffer\*** (Gnm::CommandBuffer, см. GNMX_RECONSTRUCTION.md §2) | первый аргумент всех методов записи [A] |
| +0xC0A0 + stage·8 | дескриптор шейдера стадии (адрес кода `>>8` в слове 2, размер в младших 23 битах слова 0) | `setEsShader/setGsShader`, `prefetchIntoL2(addr<<8, size)` [A] |
| +0xC0E4…+0xC118 | отдельные значения user data (по одному dword, напр. +0xC0EC GS, +0xC0F0 ES, +0xC110 ES) | `setUserDataRegion(…, 1)` [A]; смысл [?] |
| +0xC140 | указатель для user data ES [?] | [A] |
| +0xC170 | аргумент `setEsShader` (модификатор) [H] | [A] |
| **+0xC180 + stage·8** | **таблица раскладки user data шейдера** (байты: номер SGPR для каждой таблицы, 0xFF = нет; u16 смещения частей в теневом массиве; u16 размер в dword по +0) | разбор в `0x14ad0` [A] |
| +0xC1C8 + stage | u8: шейдер стадии изменён (установить заново) | `if (+0xC1CB) setGsShader`, `if (+0xC1CC) setEsShader` [A] |
| **+0xC1D0 + stage** | **u8: ресурсы стадии изменены (скопировать тень и выставить указатели)** | ветви копирования GS/ES [A] |
| +0xC1E4 | u16: битовые флаги (`|= 8` при смене GS) [?] | [A] |
| +0xC6E4…+0xC70E | состояние режима ES/GS (кольца, модификаторы) [?] | [A] |

### 2.1 Что делает commit `0x14ad0` для стадии с флагом «ресурсы изменены» [A]

1. `n = layout->size` (u16); `p = alloc(ctx, n)` (`0x123d0`, при нехватке — новый блок через колбэк).
2. `memcpy(p, shadow[stage], n·4)` — снимок теневого массива.
3. Для каждой таблицы раскладки (ресурсы, сэмплеры, буферы вершин, константы, …): если номер SGPR ≠ 0xFF —
   `setPointerInUserData(dcb, stage, sgpr, p + offset·4)` (`SET_SH_REG` из 2 значений).
4. Отдельные значения — `setUserDataRegion(dcb, stage, sgpr, &value, 1)` (маркер `NOP 0x6875000D` + `SET_SH_REG`).

**Следствие для SecondSonPC [A+E]:** каждый draw с изменёнными ресурсами получает таблицу по новому адресу в
линейном блоке. Поэтому user data (слоты указателей) меняются почти у каждого draw, мемо подготовки стадий фронтенда
не попадает (P52_PERFORMANCE.md §1.6), и фронтенд заново обходит SRT. Это свойство движка, не ошибка эмуляции.
**Значение для нативного пути [H]:** снимок теневого массива — естественная точка перехвата: нативный рендер мог бы
брать дескрипторы прямо из `shadow[stage]` по раскладке вместо обхода SRT по адресу из user data.

## 3. Отправка кадра `0x1f1e30` (`SubmitFrame(frame, flip)`) [A]

Объект кадра `frame` (поля):
- +0x14 handle VideoOut; +0x20 индекс буферов экрана; +0x17DC переключатель двойной буферизации (0/1);
- +0x28…+0x110: **5 пар двойных буферов** (шаг 0x30: два базовых адреса, текущий, конец, размер, индекс пары);
  после отправки индекс каждой пары переключается — следующий кадр пишет в другую половину;
- +0x118 GPU-таймер кадра; +0x124 индекс метки; +0x128 счётчик кадров (значение fence, 0 пропускается);
  +0x130 значение fence прошлого кадра; +0x1DCA0 контекст/командный буфер кадра.

Порядок:
1. `sspc_gpu_timer_end_eop` (`0x196ea0`); `0x11f910`, `0x170b00`, `0x16df30` [?].
2. `frame+0x128 += 1`; в DCB: `0x625e80(dcb, 0, 0xFFFFFFFF, 0x7FC0, 0x38, 0x6000000, 0)` — [H] полный сброс/acquire
   кэшей; `0x627aa0(dcb, 4, 0, &labels[frame+0x124], 2, fence, 0, 0)` — **EOP: запись счётчика кадра в метку**
   (массив меток `DAT_00e17e80`; P4.4: метка в 0x248000000).
3. Сбор списка командных буферов кадра, `qsort`.
4. `SubmitDone` (если режим `DAT_01d20388` = 0).
5. **Ожидание: `while (labels[frame+0x124] < frame+0x130) delay(50 мкс)`** — GPU должен закончить прошлый кадр
   (≤1 кадр в полёте). Здесь главный поток проводит 42–58 % времени (P52_PERFORMANCE.md §1.1).
6. `SubmitDone` (режим 1); `0x28eb20` [?]; `sceGnmSubmitAndFlipCommandBuffers(n, dcbs, sizes, 0, 0, videoOut,
   buffer = +0x20·2 + +0x17DC, flipMode 1, flipArg DAT_01d20384)` или `sceGnmSubmitCommandBuffers` без флипа;
   `frame+0x130 = fence`; `SubmitDone` (режим 3).
7. `while (sceVideoOutIsFlipPending(videoOut) > 1 (или 5)) delay(50 мкс)`.
8. Переключение 5 пар буферов, сброс счётчиков кадра.

**Значение для нативного пути [H]:** модель кадра — двойные буферы команд + одна EOP-метка на кадр + ожидание
прошлого кадра перед отправкой. В нативном Vulkan-рендере это прямо отображается на timeline-семафор (значение =
счётчик кадра) и `vkWaitSemaphores`; флип — на present с очередью ≤2.

## 4. Поток draw: от движка до драйвера [A+E]

- Динамика (счётчик вызовов импортов `logs\calls.json`, 3 мин игры, 8 681 кадр): `sceGnmDrawIndex` 17,9 млн (~2 070
  на кадр), `DrawIndexIndirect` 1,95 млн (~225), `DrawIndexAuto` 0,79 млн (~91), `DispatchDirect` 4,4 млн (~510),
  `SetVsShader` 1,7 млн / `UpdateVsShader` 4,3 млн, `SetPsShader350` 2,1 млн / `UpdatePsShader350` 3,9 млн.
  **Каждый draw идёт через драйвер Gnm** (заранее собранных draw-пакетов в обход драйвера нет) [E].
- Статически draw-обёртки вызываются из ~20 мест (`0x623c60` ← `0x1a1770`, `0x1a1960`, `0x448b30`, `0x43d480`,
  `0x5a8f40`; `0x623a40` ← `0x19050…0x19a00`, `0x1d0ce0`, `0x448…`, `0x457a10`) — это циклы по объектам [A].
- Цепочка на draw: `commit(ctx)` `0x14ad0` (шейдеры, тень ресурсов → линейный блок → указатели в user data) →
  обёртка draw → `sceGnmDrawIndex*` (драйвер дописывает пакеты в `ctx+0xC090`) [A].
- **Потоки (сырые сэмплы, пляж):** commit и циклы draw исполняются в основном на **`JobWorker1..5`** (commit 0,27 %
  сэмплов воркеров, `0x1a1960` 0,11 %, `0x1a1770` 0,10 %, обёртка draw 0,09 %), реже на главном (0,13 %) [E].
  Значит, движок записывает командные буферы **параллельно, задачами** (кандидаты: `JOBAK_Draw`, `JOBAK_DrawSort`
  [H]), а главный поток в `SubmitFrame` собирает их список, сортирует (`qsort`) и отправляет одним вызовом с флипом.
- Стоимость записи команд на CPU игры — доли процента времени воркеров (весь CPU-код игры ~2 мс/кадр,
  P52_PERFORMANCE.md §1.1).
