# План последовательного переноса (Native Engine Reconstruction)

Дата: 2026-10-14. Принципы: каждая замена — за флагом, с проверкой хеша гостевого кода, с тестами и A/B; статус
NATIVE — только после анализа зависимостей и замеров; shadPS4 остаётся основным, пока замена не проверена.

## 0. Состояния подсистем

`BRIDGE` — через совместимость с PS4 (мост shadPS4 или гостевой код с PS4-вызовами через мост);
`HYBRID` — часть нативно; `NATIVE` — PS4-специфичного механизма этой подсистемы не осталось. Текущие статусы —
RECONSTRUCTION_PROGRESS.md.

## 1. Сделано (этап 1, эта ветка)

- Разметка импортов в Ghidra, инструменты `tools/native-reconstruction`.
- Механизм замены гостевых функций `src/engine/guest_hooks` (хеш + `jmp` на SysV-функцию).
- Система задач: реконструкция NextJob/TryNextJob/WaitBatch (`SSPC_NATIVE_JOBS=1`), тесты, A/B — эквивалентна,
  не узкое место (воркеры заняты 7–8 %).

## 2. Следующий этап (рекомендация): атрибуция CPU-времени гостевого кода

**Почему:** выбор следующей подсистемы должен опираться на то, где игра тратит CPU. Сейчас известно только
«CP ~26–29 мс» (наш эмулятор GPU) и «воркеры движка простаивают». Сколько времени главный поток и потоки игры тратят
на свои подсистемы (мир, анимация, сборка командных буферов) — неизвестно.

**Работа:** WPR-сэмплирование (CPU Usage Sampled) прогонов p46 → сэмплы по гостевым адресам eboot (база модуля из
лога) → агрегирование по функциям Ghidra (`fm.getFunctionContaining`) → дерево по потокам (имена из таблицы
`0xae0f70`).

**Критерии завершения:** для пляжа и гавани — топ-30 гостевых функций с долей времени главного потока и воркеров;
≥90 % сэмплов в eboot отнесены к функциям; топ-10 совпадает между двумя прогонами.

**Риски:** посторонняя нагрузка меняет поведение (P4.12: «медленный режим») — во время прогона только сэмплы, анализ
после.

## 3. Кандидат №1 по пользе: гостевая сборка командных буферов (Gnmx / GfxContext)

**Гипотеза [H]:** библиотека Gnmx (сборка PM4: draw, состояние, константы) статически собрана в eboot, а 85 импортов
`sceGnm*` — только низкоуровневый драйвер. Каждый кадр игра кодирует ~85 DCB в PM4 → наш CP декодирует PM4 обратно
→ Vulkan. Перехват функций Gnmx (draw/set-state) мог бы передавать состояние Vulkan-исполнителю напрямую, минуя
кодирование и разбор PM4 (CP сейчас 26–29 мс/кадр — главное узкое место).

**Зависимости:** разметка Gnmx в Ghidra (по шаблонам PM4-заголовков в коде, по вызовам `sceGnmDrawIndex*`/
`sceGnmSetVsShader`), разметка структуры GfxContext; совместимость с существующим CP (смешанный поток: часть команд
через PM4, часть напрямую — порядок и синхронизация).

**Риски:** высокие. Порядок команд, метаданные (fence, labels, write-back), совместимость с путём моста; объём кода
Gnmx большой. Начинать с измерений (п. 2): если сборка PM4 в игре дешёвая, а дорого наше декодирование — выгоднее
ускорять CP, а не реконструировать Gnmx.

**Критерии завершения первого шага:** список функций Gnmx с подтверждёнными адресами и семантикой (сверка их вывода PM4
с трассой CP: тот же пакет на тот же вызов) и доля кадра, которую они занимают (по п. 2).

## 4. Прочие кандидаты (по возрастанию риска)

| Кандидат | Польза | Риск | Предусловие |
|---|---|---|---|
| NATIVE-потоки по умолчанию (`--native threads`) | убрать мост из потоков; применить приоритеты/аффинность Windows | низкий | soak 3 сцены × 3 мин без ошибок (формат P4.11) |
| Политика ожидания WaitBatch (`pause`/`yield`) | ≤2 % времени главного потока | низкий | A/B ≥2 пары; сейчас эффект ниже шума |
| `delay()` игры `0x53b2b0` (спин без PAUSE; главный поток так ждёт EOP, P4.4/P4.9) | освободить SMT-соседа ядра | низкий | замер, сколько главный поток спинит за кадр |
| Поточные арены памяти (`0x5b9ec0`) | понимание аллокаций | средний | разметка |
| Havok `hkTaskScheduler` | нет по текущим данным (воркеры простаивают) | средний | — |
| Стриминг (Fios2 LLE → свой асинхронный I/O) | время загрузок | средний | замер загрузки уровней |
| Аудио (AudioOut/Ajm → WASAPI + декодеры) | убрать мост | средний | выбор декодера AT9 |

## 5. Цель и честная оценка

Путь PS4 Game → Reverse Engineering → Reconstructed Engine → Windows Native Engine. CPU-код игры уже нативный;
остаточная PS4-специфика — платформенные библиотеки (большинство уже NATIVE или имеют NATIVE-вариант) и, главное,
**GPU-модель** (PM4, GCN-шейдеры). Поэтому «полностью нативный порт» — прежде всего реконструкция гостевого
рендер-пайплайна и замена GCN-шейдеров; это многомесячная работа, начинать её стоит после п. 2.
