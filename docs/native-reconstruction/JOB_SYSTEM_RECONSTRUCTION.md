# Job System — реконструкция (первая подсистема Native Engine Reconstruction)

Дата: 2026-10-14. Бинарник: `E:\shdps4\CUSA00004\eboot.bin` (inFAMOUS Second Son v1.07, fake-SELF, x86-64).
Все адреса — смещения модуля (Ghidra, база 0). Имена функций и полей — **наши**, оригинальных символов в eboot нет.

Обозначения достоверности: **[A]** подтверждено анализом (дизассемблер/декомпилятор), **[E]** подтверждено
экспериментом (игра/тесты), **[H]** обоснованная гипотеза, **[?]** неизвестно.

## 3. Объект JobManager (`0x1d1bfe0`, синглтон)

| Смещение | Тип | Назначение | Доказательство |
|---|---|---|---|
| +0x000 + i·0x78 | s32 | индекс воркера i | `0x243460` пишет 0..4 [A] |
| +0x008 + i·0x78 | объект потока WWS | поток воркера | `0x896a30(slot+8, 0x243680, slot)` [A] |
| +0x258 | s32 | число воркеров (5) | инкремент в `0x243460` [A] |
| +0x260 | u8 | флаг выхода | чтение в `0x243f30/0x243c50/0x243680`, запись в `0x243770` [A] |
| +0x268 | ScePthreadMutex | замок очереди | `scePthreadMutexLock(+0x268)` [A] |
| +0x270 | ScePthreadCond | «есть работа» | `scePthreadCondWait(+0x270, +0x268)` [A] |
| +0x278 | u8 | mutex/cond созданы (ленивая неатомарная инициализация) | [A] |
| +0x280 / +0x288 | GuestBatch* | голова / хвост списка пачек | [A] |
| +0x290 | s32 | курсор: следующая запись головной пачки | [A] |
| +0x298 / +0x2a0 | ptr | буфер 1 МиБ (выравнивание 0x80) и его конец | `0x243460`; назначение [?] |

Глобальные списки «безопасных итераторов» `0x1d1c290` (по `next`) и `0x1d1c298` (по `prev`): узел `{void* slot; next}`;
при снятии узла итераторы, указывающие в его поля, переводятся на соседей [A] (тот же код встроен в `0x244320`,
`0x244460`, `0x2432e0`, `0x3ae830`).

## 4. Структуры

```
GuestBatch (заголовок 24 байта, затем count записей)
  +0x00 u32 state   0 пусто | 2 отправлена | 3 все записи розданы | 4 дождались
  +0x04 s32 count
  +0x08 GuestBatch* next
  +0x10 GuestBatch* prev
GuestEntry (24 байта)
  +0x00 u32 state   0 в очереди | 1 взята | 2 выполнена
  +0x04 u32 ?       очередь не использует [?]
  +0x08 fn          void fn(u64 arg) (System V)
  +0x10 u64 arg
JobGroup (узел графа зависимостей)
  +0x00 u32 state, +0x04 s32 pending (атомарный счётчик зависимостей)
  +0x08 mutex (тип 4), +0x10 глубина захвата, +0x14 u8 инициализирован
  +0x18/+0x20 список пачек группы, +0x28 массив зависимых групп, +0x30 их число
```

## 5. Алгоритмы (по дизассемблеру)

| Функция | Наше имя | Что делает | Статус |
|---|---|---|---|
| `0x243460` | Init | буфер 1 МиБ, 5 воркеров (параметры потоков 11..15), вход `0x243680` | [A] |
| `0x243680` | WorkerMain | TLS `fs:-0x30` = индекс; MXCSR \|= FTZ; поточная арена 2 МиБ (`0x5b9ec0`); контекст Havok (`0x640990`, `fs:-0x14` = индекс+1); цикл `while(!quit){e=NextJob(); if(e){e->fn(e->arg); e->state=2;}}` | [A] |
| `0x243f30` | **NextJob** | lock; пока голова пуста — `CondWait` (выход при quit); запись `head[cursor]`, `cursor++`; если пачка исчерпана — `state=3`, правка итераторов, снятие из списка, `cursor=0`; `entry.state=1`; unlock | [A] **→ натив** |
| `0x243d70` | **TryNextJob** | то же без сна; сначала проверка головы без замка | [A] **→ натив** |
| `0x243c50` | **WaitBatch** | если `state∈{0,4}` — выход; пока есть невыполненные записи: взять **любую** задачу (TryNextJob) и выполнить, иначе `delay(1 мкс)`; после каждого шага скан с первой записи; затем под замком `state=4` | [A] **→ натив** |
| `0x243a40` | Submit | пачки списка → `state=2`, под замком в хвост очереди | [A] |
| `0x244770` | KickGroup | `state=2`; Submit + `CondBroadcast`; снять зависимые группы и для каждой `0x2446b0` | [A] |
| `0x2446b0` | Release | атомарно `--pending`; при 0 — под mutex группы KickGroup | [A] |
| `0x244460` | ResetGroup | очистить список пачек и зависимых | [A] |
| `0x243770` | Shutdown | quit=1; broadcast; ждать воркеров с `delay(1000)`; join | [A] |
| `0x53b2b0` | delay(us) | >500 мкс → `sceKernelUsleep`, иначе спин по `rdtsc` **без PAUSE** (частота TSC из `0x7f91f88`) | [A] |

Вызывающие: WaitBatch — 23 функции, Release — 15, ResetGroup — 9 [A] (какие подсистемы игры это — [?]).

## 6. Свойства (ответы на вопросы ТЗ §7)

1. Потоки: 5 рабочих (`JobWorker1..5`); главный (и любой ждущий) поток помогает в ожидании [A]; в игре NextJob
   вызывают ровно 5 потоков [E].
2. Распределение: одна глобальная FIFO пачек; записи выдаются по одной по курсору под одним mutex [A].
3. Work-stealing: **нет** [A].
4. Очереди: одна глобальная; поточных нет [A].
5. Синхронизация: один `ScePthreadMutex` + `ScePthreadCond`; состояния записей — обычные записи (x86 TSO) [A].
6. Spin/yield/sleep: воркеры спят на cond (без спина); ожидающий поток крутится `delay(1)` = rdtsc-спин 1 мкс без
   PAUSE; при выходе — `delay(1000)` = `sceKernelUsleep` [A].
7. Зависимости: группы с атомарным счётчиком; при 0 группа отправляется и освобождает зависимых [A].
8. Задачи графических команд: какие записи связаны с подготовкой отрисовки — **[?]** (нужна атрибуция `fn` по
   адресам; кандидаты — `JOBAK_DrawSort`, `JOBAK_Draw`, `JOBAK_Visprog`).
9. Задержки и ожидания — §7.
10. Соответствие Parallel CP: **не связаны**. Parallel CP (P4.10) — потоки SecondSonPC внутри эмуляции GPU (разбор PM4
    и запись Vulkan); система задач движка — гостевой код игры, готовит данные кадра до отправки командных буферов.
    Общих механизмов нет [A]; общая только конкуренция за ядра CPU [H].

## 7. Измерения в игре [E]

`SSPC_NATIVE_JOBS=1` (реконструкция со счётчиками), бэкенд sspc, однопоточный CP, 90 с
(`logs\native-reconstruction\nj_smoke`, `ab_native`), установившийся режим, за 10 с:

| Метрика | Пляж | Гавань |
|---|---|---|
| Задач выдано воркерам | 236–292 тыс. (~24–29 тыс./с, ~800–900 на кадр при ~33 FPS) | 220–266 тыс. |
| Загрузка 5 воркеров (busy / (busy+idle)) | **7–8 %** | 7–8 % |
| Ожиданий пачек (WaitBatch) | 29–36 тыс. (~3 тыс./с) | 29–35 тыс. |
| Время в WaitBatch всего | 176–258 мс (**~2 %**, ~0,6–0,8 мс на кадр) | 145–158 мс |
| Среднее ожидание | 6–8 мкс (макс. 2,9 мс за прогон) | 4,4–5,0 мкс |
| Задач выполнено ожидающим потоком | 2,7–3,4 тыс. | 3,0–3,4 тыс. |
| Шагов спина `delay(1)` | 142–213 тыс. | ~100 тыс. |

«busy» — время между возвратом из NextJob и следующим вызовом тем же потоком, т.е. выполнение задачи. 7 % от 5×10 с
= 3,5 с на ~290 тыс. задач ≈ **12 мкс на задачу** в среднем.

**Вывод:** система задач движка на ПК — **не узкое место**. Воркеры простаивают >90 % времени, ожидание главного
потока ~2 % времени. Больше воркеров или другая очередь FPS в этих сценах не дадут [E+H]. Узкое место кадра по-прежнему
вне кода игры: CP ~26–29 мс (эмуляция GPU, P4.x).

## 8. Нативный прототип

`src/engine/job_system.{h,cpp}`, `src/engine/guest_hooks.{h,cpp}`; флаг `SSPC_NATIVE_JOBS=1` (по умолчанию выкл.).

- Заменяет `0x243f30`, `0x243d70`, `0x243c50` переходом `jmp [rip]` на C++-функции с ABI System V, до старта гостевого
  кода (`bootstrap.cpp`, между `LoadModule` и `Execute`).
- Работает на **гостевых** структурах и гостевых mutex/cond (вызов через PLT-заглушки `0x9845b0/0x984590/0x9845c0/
  0x9845d0/0x984d10`), поэтому незаменённый код (Submit, воркеры, KickGroup, Release) совместим без изменений.
- Ставится только если FNV-1a 64 тел трёх функций и 10 функций-предпосылок совпадает с эталоном
  (`tools/native-reconstruction/function_hashes.py`); иначе ничего не ставится, причина в логе.
- Поведение эквивалентно ассемблеру построчно (ленивая инициализация, правка итераторов, пересканирование с первой
  записи); отличается только политикой ожидания при `SSPC_NATIVE_JOBS_WAIT=pause|yield` (по умолчанию `guest` =
  оригинал).
- Статистика раз в `SSPC_NATIVE_JOBS_STATS` с (по умолчанию 10) в лог, категория `Engine`.
- **Статус: функционально эквивалентная реконструкция** по установленному поведению (оригинального исходника нет).

Зависимости от PS4 внутри компонента: нет (гостевые mutex/cond реализует NATIVE-группа `kernel-mutex` SecondSonPC).
Подсистема в целом — **HYBRID** (RECONSTRUCTION_PROGRESS.md).
