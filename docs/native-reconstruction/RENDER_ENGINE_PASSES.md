# Render Engine: контексты между кадрами, 41 проход, зависимости (P5.3A)

Дата: 2026-10-14. Адреса — смещения eboot (Ghidra, база 0). Имена — наши. [A] анализ дизассемблера/декомпилятора,
[E] эксперимент (динамическая трасса в игре), [H] гипотеза, [?] неизвестно. Продолжение RENDER_ENGINE_ARCHITECTURE.md.

## 1. Метод: зонды на входе функций (только чтение)

`src/engine/guest_probe.*` — зонд на входе функции игры. Целые инструкции пролога (≥ 14 байт) переносятся в
трамплин, за ними — переход обратно. Вход функции прыгает в функцию SecondSonPC (System V), которая читает аргументы
и данные игры и вызывает трамплин как исходную функцию. Код игры не меняется. Пролог каждой точки проверен в Ghidra:
он позиционно-независим, переходов внутрь нет (`tools/native-reconstruction/ghidra/queries/prologue.py`). Хеш функции
закреплён, поэтому на другой версии eboot зонд не ставится.

`src/engine/render/frame_trace.*` — трасса кадра, флаг **`SSPC_P53_RENDER_TRACE=1`** (по умолчанию выключен;
`_EVERY`, `_DUMPS`, `_DIR`, `_STATS` — см. заголовок). Зонды:

| Точка | Что читает |
|---|---|
| `SubmitFrame 0x1f1e30` | каждый кадр: первый кусок DCB каждого слота пула (сброшен ли буфер с прошлого кадра); каждый N-й кадр: все контексты в порядке отправки, их DCB (сканер PM4 `dcb_scan.*`), привязанные ресурсы → граф проходов (`pass_graph.*`) → JSON |
| `Reset 0x11f050` | вызовы по адресу возврата и по виду контекста |
| `DcbReserve 0x11eed0` | новые куски DCB за кадр |
| сеттеры CUE `0x16d10` / `0x16de0` / `0x16b70` / `0x16c40` | T# / RW T# / V# / RW V#, привязанные к контексту (только в выбранном кадре) |

Порядок контекстов в JSON повторяет `SubmitFrame`: деформация (если есть команды) → pre → слоты пула, отсортированные
как `qsort` с компаратором `0x1ef490` (проход со знаком, sub без знака, адрес), с пропуском слотов с пустым текущим
куском (как в `0x1f1e30`) → post. DCB читается после возврата `SubmitFrame`, поэтому переходы состояния
(`0x120020`), дописанные в конец предыдущего контекста, учтены. Регистровое состояние сканера переносится из контекста
в контекст в порядке отправки, как на GPU.

Прогоны: `tools/tests/p46_runs.ps1 -Tag p53_trace -OutRoot logs\p53` (пляж и гавань, по 90 с, нативный бэкенд),
дампы `logs\p53\trace_beach\frame_*.json`, `logs\p53\trace_early\frame_*.json`.

## 2. Сброс и переиспользование 254 контекстов [A+E]

**Ответ:** сброс делает `BeginFrame 0x1f0be0(frame, flags)` в начале каждого кадра, до записи. В P5.2B эта функция
была ошибочно отнесена к перенастройке видеовыхода: ветка `sceVideoOut*` в ней условная, а сброс выполняется всегда.

Цепочка: главный цикл `0x29c8d0` → `0x196970` → `0x1f0be0(&DAT_00f1bcd0)`. Второй путь — `0x196d90`
(из `0x29ce10`, `0x5054b0`): `0x1f0be0`, затем сразу `EndFrame 0x196c30`, то есть кадр без сцены [H: экраны
загрузки].

`0x1f0be0` по порядку [A]:
1. `frame+0x121 = 1`; `Reset(pre)`, `Reset(post)` (`frame+0x1F80`, `frame+0xFE10`), `0x11f330(pre)`,
   `0x11f760(pre/post)`, `SetRenderTargets(pre/post, frame+0x17E0, 0)`; текущий контекст `frame+0x1DCA0 = pre`.
2. Условно: перенастройка видеовыхода (смена режима, буферов, гаммы).
3. `0x170980(&DAT_00e18350, flags)` — сброс 5 контекстов системы деформации (5 вызовов `Reset` из `0x1709xx`).
4. **Цикл по всем инициализированным слотам** (`frame+0xDF0EE0`, = 254 после `0x1f04e0`): `Reset(slot)`;
   ключ `{pass = -1, sub = 0}`, `recordFn = arg = 0`, `isJob = 0`; начальное состояние = `0x11eb20` (по умолчанию).
5. `frame+0xDF0EF4` (записано) `= 0`; метка начала кадра для GPU-таймера.

Счётчик захваченных слотов `frame+0xDF0EF0` обнуляет конец `SubmitFrame`. Тот же цикл сброса встроен в ветку
переполнения `0x1f14e0` (кадр отбрасывается).

`Reset 0x11f050(R)`:
- обнуляет DCB (`G+0..0x18`: начало, конец, указатель записи = 0) и список кусков (`R+0xD070 = 0`);
- помечает 10 кэшей констант грязными;
- сбрасывает CUE (`0x13d20`) и пару шейдеров/программу CS (`R+0xDE38`).

Первая запись в слот вызывает колбэк `0x11eed0`. Он берёт кусок из арены 3 текущей половины кадра (32/128/512 КиБ)
[A].

**Измерено (пляж, 3 200 кадров) [E]:**
- `Reset` вызывается 254 раза за кадр из `0x1f10fc` (внутри `0x1f0be0`) — 812 800 вызовов за 3 200 кадров. Ещё по
  одному из `0x1f0c1f`/`0x1f0c2e` (pre/post) и 5 из `0x1709a0…0x1709dd` (деформация). Других вызывающих нет.
- Слоты в `SubmitFrame` (контрольный прогон `logs\p53\p53_trace2`, 10 с ≈ 400 кадров): свежий первый кусок у
  20 706 слотов, тот же, что в прошлом кадре, — **0**, пустых (адрес 0: сброшен, ничего не записано) — 8 526,
  примерно 21 на кадр. Пустые — проходы без экземпляров: контекст захвачен, но в отправку не идёт.
- Кусков на контекст: не больше 1 завершённого.
- CCB GfxContext (`G+0x80`; P5.3A трасса проверяла и `G+0x40`) **ни разу не содержал команд** к моменту отправки
  (0 контекстов за прогон, §5).

Модель времени жизни: слот — объект на всю жизнь процесса (254 штуки, `0x1f04e0`). Ключ, состояние и DCB живут один
кадр, от `BeginFrame` до `SubmitFrame`. Память команд — арена 3 половины кадра N. GPU читает её, пока CPU пишет
кадр N+1 в другую половину. `SubmitFrame` ждёт EOP кадра N−1, поэтому к записи кадра N+1 половина N−1 свободна.

## 3. 41 проход: что делает каждый [A+E, назначение — H]

## 4. Зависимости и время жизни ресурсов [E]

Граф (рёбра «записал → читает», по адресу; JSON `edges`). Пляж, кадр 2000:
- деформация 1 → 3 → проходы 4, 8, 12, 13 (RW-буфер `0x268000000`);
- проход 0 → 32; 1 → 8; 4 → 6, 8, 9, 12, 13 (основная глубина `0x26b200000`); 6 → 8 → 12, 13, 16;
- 12 → 13, 16, 25, 30, 31, 32; 14 → 15 → 16 → 17, 30; 17 → 19, 25, 29, 30;
- 29 → 30 → 31 → 32; 34 → post;
- **с прошлого кадра** (читатель раньше писателя): 30 → 12, 16, 29; 31 → 12; 32 → 12 (история для TAA/экспозиции).

Время жизни (`lifetimes`): основная глубина — от прохода 0 до 34, 11 читателей. Цели G-буфера живут от прохода 1
до 8–13. Цепочка пост-эффектов живёт от 29–31 до 32. 119 записываемых адресов за кадр, 26 из них читаются позже.
Ограничение: связь только по точному адресу. Виды с другим базовым адресом (мип, срез массива) не связываются.

## 5. Три CommandBuffer GfxContext [A+E]

`BaseGfxContext::init 0x4c80(G, dcbBuf, dcbSize, ccbBuf, ccbSize)` [A]:
- создаёт **два** `Gnm::CommandBuffer` по `0x61ec00`: DCB по `G+0` и CCB (constant command buffer) по `G+0x80`;
- `G+0x40…0x58` — поля контекста, не буфер (обнуляются);
- `0x18090` (из `R::Init 0x11efc0`) создаёт оба пустыми и сразу ставит DCB колбэк `0x11eed0`.

У CCB колбэка нет. За два прогона (6 000 кадров) у CCB не было ни одного dword к отправке [E]. Движок не пользуется
constant engine: CUE пишет снимки в память кадра, а указатели — в DCB. Вывод P5.2B про «три CommandBuffer»
исправлен: их два, используется один.

## 6. Стоимость и ограничения трассы

- Каждый кадр: чтение ≤ 254 слотов, около 1 мкс. Выбранный кадр: 0,4–0,5 с (сканирование 3–5 МБ PM4, декодирование
  десятков тысяч привязок, граф). Один такой кадр раз в 400 — заметный рывок, поэтому это только диагностика.
- Зонды сеттеров при `g_armed = false` стоят одной атомарной загрузки.
- Привязки к контекстам вне пула (`unattributed_bindings`) — 0 в обеих сценах.
