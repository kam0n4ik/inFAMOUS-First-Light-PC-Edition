Дата: 2026-10-14. Источник — eboot v1.07 (Ghidra 12.1.4, база 0, только чтение). Символов и RTTI в образе нет, все
имена **наши** по поведению. Метки: **[A]** — прочитано в дизассемблере/декомпиляторе, **[E]** — подтверждено замером,
**[H]** — гипотеза, **[?]** — неизвестно. Запросы — `tools/native-reconstruction/ghidra/queries/` (README там же).
Связанные документы: GFX_CONTEXT_LAYOUT.md (поля контекста, исправлено этой работой), GNMX_RECONSTRUCTION.md
(методы записи PM4), JOB_SYSTEM_RECONSTRUCTION.md (очередь задач).

## 0. Цепочка целиком

```
Главный цикл 0x29c8d0
 ├─ 0x41bb50  построение кадра рендера (мир DAT_07f111e0)
 │   ├─ для каждого вида: сбор видимого (gather 0x198d50 … 0x19a320)
 │   │     модель 0x1ec170 → часть меша 0x1ecf70 → материал по типу вида → 0x199270 → AddRenderInstance 0x1992b0
 │   │     запись 0x80 байт + ключ сортировки + номер прохода  →  глобальная таблица экземпляров DAT_07f2d5a0
 │   ├─ 0x1980d0: 41 задача сортировки (0x1982f0, по одной на проход) → ключи S+0x4dc0, диапазоны S+0x4dcc
 │   └─ 0x198a70: 41 контекст из пула (ключ = номер прохода) + задачи записи (зависят от сортировки)
 │         задача прохода 0x198720 → режет диапазон на куски (0x19af30) → по контексту на кусок (подключ 1..n)
 │         кусок 0x198990/0x198670: группы по ключу → Material::BindAndDraw 0x448260
 │             шейдеры VS/PS 0x11f3c0, сэмплеры 0x16eb0, константы материала → vtbl+0x28 (настройка класса)
 │             → 0x4484d0 (растр/стенсил) → vtbl+0x30 DrawItems (0x1a2030 и др.)
 │                 одиночный 0x1a1960 / инстансы 0x1a1770: VB 0x16aa0, ресурсы 0x16b70, константы 0x120280,
 │                 commit 0x14ad0 (тень ресурсов → снимок → указатели в user data), sceGnmDrawIndex 0x623c60
 ├─ 0x1f2e30  ждать, пока записаны все контексты (главный поток помогает выполнять задачи)
 └─ 0x196c30 → SubmitFrame 0x1f1e30
       EOP-метка кадра; сбор буферов: деформация(5) + пре-контекст + пул (qsort по ключу) + пост-контекст;
       перенос состояния между контекстами 0x120020; ожидание GPU прошлого кадра; SubmitAndFlip; смена половин арен
```

Всё ниже — расшифровка каждого звена с доказательствами.

## 1. Сцена → экземпляр рендера

### 1.1 Модель и части меша [A]

| Адрес | Имя | Сигнатура (SysV) | Что делает | Вызывающие |
|---|---|---|---|---|
| `0x1ec170` | ModelInstance::SubmitToView | `(model, gather, mode)` | проверка маски вида (`gather+8 & model->def+0xE0`), выбор LOD (`0x6094a0`), цикл по частям: `def+8` = число частей, флаги части — `*(def)+4+i·8`; режим 0 → `0x1ecf70`, режим 1 → `0x1ed740` | `0x26cd20`, `0x26cda0`, `0x4758f0`, `0x475940`, `0x475990` (методы сущностей, напр. `0x26cd20`: `entity+0x350` → модель) |
| `0x1ecf70` | MeshPart::Submit | `(model, meshInst[2], gather)` | набор материалов `set = meshInst[1]->+0x20`; материалы — массив `set+0x90`, индекс по типу вида: биты вида `0xA1` (основные) → байты `set+0x6C/0x6D/0x6E` (с проверкой `0x446dc0(mat, 0x3A9)`), `0x1152` → `set+0x78`, `0x2000` → `set+0x7B`; `0xFF` = нет | `0x1ec170`, `0x1d2540` |
| `0x199270` | SubmitWithMaterial | `(gather, material, part, meshInst)` | `AddRenderInstance(gather, mat->sortId(+0x28), mat->pass(+0x110), mat->flags(+0x21), mat, part, meshInst)` | `0x1ecf70`, `0x1ed740`, `0x1745b0`, `0x1fe9c0`, `0x1ff750` |
| `0x1992b0` | AddRenderInstance | `(gather, sortId, pass, flags, material, part, meshInst)` | см. 1.2 | `0x199270`, `0x58d2c0` |
| `0x199790` | AddRenderInstance (вариант) | `(gather, material, …)` | то же; проход берётся из `material+0x110` | `0x1745b0`, `0x1ed740`, `0x1fe9c0`, `0x1ff750` |

Ещё 7 функций пишут в тот же сбор (`0x199b00`, `0x199bd0`, `0x199c90`, `0x199fd0`, `0x19a0b0`, `0x19a190`,
`0x19a260`), каждая вызывает сброс `0x198f70` при заполнении. Их вызывающие — `0x3ed7b0/0x3edba0` (адаптивное качество),
`0x2e9cb0`, `0x46d660…0x46d720`, `0x566e00`, `0x5a19f0`, `0x1cfb50`. Какие объекты они подают, пока не разобрано [?].

### 1.2 Запись экземпляра рендера (0x80 байт) [A]

`0x1992b0` вычисляет мировую матрицу (матрица кости/узла `part+0x30` × матрица меша `part+0x28`, масштаб из
`mesh+0x44`, смещение относительно камеры при флаге 2) и пишет запись в буфер сбора (`gather+0x78`, номер — `gather+0x88`):

| Смещение | Поле | Источник |
|---|---|---|
| +0x00 | u64 **ключ сортировки** (см. 1.3) | вычисляется здесь; младшие 16 бит дописываются при сбросе |
| +0x08 | `Material*` | аргумент |
| +0x10 | часть модели (draw record) | аргумент |
| +0x18 | `meshInst*`: `[0]` геометрия, `[1]` описание части (`+0x48` id вершинных данных) | аргумент |
| +0x20 | данные деформации (скиннинг/морф), иначе 0 | `0x16f5d0(…, DAT_00e18350, …)` при флаге 8 |
| +0x28 | id зонда освещения (`probe+0x1A0`) или −1 | `0x45d560` при флагах 0x30 |
| +0x2C | индекс зонда (u16) или 0xFFFF | то же |
| +0x30 | 0 | — |
| +0x40…+0x7F | мировая матрица 4×float4 (строка 3 = позиция, w = 1) | вычислена |

Параллельно `gather+0x80[i] = pass` (u32): номер прохода для раскладки по корзинам.

### 1.3 Ключ сортировки [A]

- Обычные проходы: `key = (sortId & 0xFFF) << 48 | vtxDataId(part+0x48) << 32 | geomId(mesh+0x54) << 16`; биты
  0..15 = индекс записи в глобальной таблице (дописываются в `0x198f70`).
- Проходы `0x13`, `0x17` (условие `(pass|4) == 0x17`) и `0x0E`: `key = depth << 32 | sortId << 16`, где depth — квадрат
  расстояния (биты float), со знаком минус для `0x13/0x17` (дальние раньше: прозрачные) и плюс для `0x0E`.
- Следствие: внутри прохода экземпляры идут группами «материал → вершинные данные → геометрия», а соседние ключи,
  различающиеся только в младших 16 битах, — **один и тот же меш с тем же материалом** (используется для инстансинга, 3.3).

### 1.4 Сбор кадра (gather) и глобальная таблица [A]

| Адрес | Имя | Что делает |
|---|---|---|
| `0x198d50` | Gather::Begin | буферы потока: 0x800 записей × 0x80, 0x800 × u32 (проходы), 0x200 × 0xB0 / 0x50 / 0x10 [?]; ссылки на глобальные таблицы `DAT_07f2d5a0/5a8` (экземпляры: база, счётчик, предел) и `DAT_07f2d590/598` |
| `0x198f70` | Gather::Flush | атомарно берёт блок в `DAT_07f2d5a0` (`+= n`, запись 0x80) и описатель блока (0x68 байт) из второго пула; считает гистограмму по 41 проходу, пишет префиксные смещения `u16 block+0x12+pass·2`, раскладывает записи по проходам, дописывает индекс в ключ |
| `0x19a320` | Gather::End | `Flush`; затем данные второго вида (`0x16dcc0` в `DAT_00e17f90`) [?] |
| `0x198f20` | — | пустая функция (заглушка конца сбора) |

Блоки сбора связаны списком `S+0x4718` (S — объект видового рендера, 2.1).

## 2. Проходы рендера

### 2.1 Объект видового рендера S [A]

`S = мир + 0x1C3D0` (аргумент `0x198a70`). Поля, к которым обращается конвейер:

| Смещение | Поле |
|---|---|
| +0x0000 | `View*`: матрицы вида (`+0x200`, вариант `+0x430` при флаге материала), камера `+0x6C0…+0x6F0`, `+0x420` смещение мира |
| +0x000D | u8: в кадре есть работа |
| +0x00A8 / +0x00E8 | группы задач: сортировка / запись проходов (`0x2446a0(S+0xE8, 41)` — счётчик зависимостей) |
| +0x0130 | данные `0x589090` [?] |
| +0x4718 | список блоков сбора |
| +0x4738 | пачка из 41 задачи сортировки; `+0x4B28 + pass·0x10` — их аргументы `{S, pass}` |
| +0x4DB8 | база глобальной таблицы экземпляров (`DAT_07f2d5a0`) |
| +0x4DC0 | массив отсортированных ключей (≤ 65 536) |
| +0x4DC8 | u32: занято ключей (атомарно) |
| +0x4DCC + pass·8 | `{begin, end}` диапазон прохода в +0x4DC0 |

### 2.2 Сортировка проходов [A]

`0x1980d0(S)` (из `0x41bb50`, для каждого вида из `мир+0x1C1D0`): 41 задача `0x1981b0 → 0x1982f0(S, pass)`, затем
`Release(S+0xE8)`. Задача: собрать ключи записей прохода из всех блоков сбора (по префиксам `+0x12`), атомарно занять
место в `S+0x4DC0`, записать диапазон в `S+0x4DCC+pass·8`, отсортировать (`0x19adf0`, рекурсивная). Группа записи
`S+0xE8` стартует только после 41 `Release`: **запись команд начинается, когда все проходы отсортированы**.

### 2.4 Запуск записи проходов `0x198a70(S, mainCtx)` [A]

Для `pass = 0..40`: `ctx = AcquireContext()` (`0x1f2c60`), `ctx.key = {pass, 0}`, `ctx.stateBlock = ` состояние
предыдущего контекста (цепочкой от `mainCtx+0xDE48`), `ctx.recordFn = 0x198a60` (→ `0x198720(ctx, 0x198670)`),
`ctx.arg = S`, `ctx.isJob = 1`; setup прохода — сразу. Затем `0x1f2d70(frame, S+0xE8)`: пачка задач `0x1ef5c0(ctx)` по
одной на контекст с флагом задачи, в группу `S+0xE8` (ждёт сортировку).

### 2.5 Задача прохода `0x198720(ctx, chunkFn)` [A]

1. Диапазон `S+0x4DCC+pass·8`; пустой → выход (контекст остаётся пустым и в отправку не попадёт).
2. `begin` прохода (по маске).
3. `0x19af30`: режет диапазон на куски по `0x197050(pass)` экземпляров (200 для проходов `0x13/0x17`, иначе 1000),
   границы сдвигаются, чтобы не резать группу с одинаковым ключом по маске `0x197130(pass)` (`0x197070`). Первый кусок
   пишется в контекст прохода, каждый следующий — в **новый контекст** `0x1f2d00(frame, ctx, ctx+0xDE48)` с ключом
   `{pass, i}` и состоянием, унаследованным от контекста прохода. Описатель куска (0x30 байт из аллокатора задач):
   `{fn = 0x198670, ctx, S, …, {begin, end} @+0x20, флаги @+0x28}`.
4. `0x1ef4e0`: пачка задач по контексту на кусок, отправка и ожидание (`0x243b00`, `0x243940`) [A]; первый кусок
   исполняется на текущем потоке.
5. `end` прохода; если у куска флаг `+0x29` — `ACQUIRE_MEM` (полный сброс кэшей, 5.3).

### 2.6 Кусок: группировка по ключу `0x198990` / `0x198670` [A]

Маска группировки: проходы 32–36 (`0x1F00000000`) → `0x7FFF0000`; проходы 10, 14, 19, 23 (`0x884400`) →
`0xFFFF0000`; остальные → `0xFFFF000000000000` (только материал). `0x198670(chunk, mask)`: идёт по ключам, собирает
серию с одинаковыми битами маски и вызывает `Material::BindAndDraw(table[key & 0xFFFF].material, chunk)` (`0x448260`).
**Один вызов материала на серию экземпляров с одним материалом**.

## 3. Материал → ресурсы шейдера → draw

### 3.1 Material::BindAndDraw `0x448260(material, chunk)` [A]

`chunk = {ctx, S, ?, {begin,end}}`. Порядок:
1. `0x11f3c0(ctx, material)` — пара шейдеров: `prog = material[2]`; `prog+0x38` VS, `+0x30` fetch shader [H],
   `+0x48` таблица раскладки VS, `+0x40` PS, `+0x50` таблица раскладки PS (вызовы `0x165b0`, `0x16690` в CUE);
   все 10 кэшей констант контекста помечаются грязными; запись регистра `0xA003` (`0x6221a0`) [?].
2. Сэмплеры: `prog+0x90` штук, привязки `prog+0x88` = пары байт `{engineStage, i}`; дескриптор S# — `material[1]+0xC0 +
   i·0x20 + 0xC`, слот — `+8`; `setSamplers(cue, Stage(engineStage), slot, 1, S#)` (`0x16eb0`).
3. `0x120230(ctx, material[0x1C])` [?].
4. Константы материала (если `material+0xD4`): `0x11c120` заполняет `ctx+0xD080` (0xF0 байт); при грязном флаге
   `ctx+0xD180` — блок в командном буфере (`0x11be90`, 4.3), копия, `setConstantBuffers(VS и PS, slot DAT_00e15c20)`.
5. Хвостовой вызов `vtbl+0x28` — настройка класса материала.

### 3.2 Классы материалов (vtable, 0x58 байт, без RTTI) [A]

| Смещение | Метод | Примеры реализаций |
|---|---|---|
| +0x00 / +0x08 | деструкторы | `thunk 0x446fb0`, … |
| +0x10 | ResolveParameters: имена параметров шейдера как 64-битные хэши → смещения констант (`0x446120(mat, hash, kind, &u16)`) и слоты текстур (`0x445ae0(mat, 3, hash, &u8)`) | `0x1746f0` |
| +0x18 / +0x20 | общие `0x447070` / `0x447e00` | — |
| +0x28 | SetupDraw (константы класса: время, ветер, …) → `0x4484d0` | `0x174920`, `0x19bd50`, `0x19f8e0`, `0x43d330`, `0x561440` |
| +0x30 | DrawItems (цикл по экземплярам куска) | `0x1a2030`, `0x19cf20`, `0x19fbd0`, `0x43d590`, `0x561810` |
| +0x38 / +0x40 | [?] | `0x2de660/0x2de670`, … |

`0x1a2030` — DrawItems ~30 классов (vtable `0xcd5cb8…`, `0xcd8078…`, `0xcdb6c8…`, `0xd0fac8…`, `0xd668c0`); остальные
реализации — у 1–10 классов. `0x4484d0(material, chunk)` — общая обёртка: временно меняет `PA_SU_SC_MODE_CNTL`
(`material[2]+0x24 & 1`), стенсил-референс (`material+0x1C/+0x1E`), вызывает `vtbl+0x30`, восстанавливает; при
`material+0x1F` — `NUM_INSTANCES = 1`.

### 3.3 DrawItems стандартного меша `0x1a2030(material, chunk)` [A]

`chunk[1]` → S; таблица экземпляров `S[0x9B7]` (=+0x4DB8), ключи `S[0x9B8]` (=+0x4DC0), диапазон `chunk[3]`.
Предварительно: матрица вида из `View+0x200` (или `+0x430`), камера `View+0x6C0…`. Режим по `material+0x1F`:

**Без инстансинга** (на каждый экземпляр; экземпляры могут прореживаться счётчиком `0x612110 % 0x401` [H: отсев по
качеству]):
- `inst = table + idx·0x80`; `meshInst = inst+0x18`; `geom = meshInst[0]`; пропуск при `geom+0x18 == 0`;
- `0x448640(material, ctx, meshInst[1])` при смене вершинных данных;
- ресурсы движка: зонд освещения (`DAT_07dff3a0[inst+0x28]`, слоты `material+0x135/0x13C`), буферы скиннинга
  (`0x16b70` в слоты `material+0x125/0x126/0x16D…0x16F`);
- константы объекта 0x140 байт (`0x11c890`: матрицы мира/вида) → блок в командном буфере → `setConstantBuffers(VS, PS)`;
- константы draw (`0x11e5d0` в `ctx+0xDA18`) → `0x120280` (4.3);
- `0x1a1960(material, R, inst)` (3.4); при `material+0x124` — второй вызов с изменённым `PA_SU_SC_MODE_CNTL`
  [H: двусторонняя отрисовка].

**С инстансингом:** серии ключей с `(key ^ next) < 0x10000` (тот же материал, вершинные данные и геометрия):
блок `n × 0xD4` байт из атомарного аллокатора кадра (`0x1f0870`), в него матрицы и параметры каждого экземпляра,
затем `0x1a1770(material, R, instData, n, geom)`.

### 3.4 Draw [A]

| Адрес | Имя | Сигнатура | Действие |
|---|---|---|---|

## 4. Контекст рендера (R), GfxContext (G), Constant Update Engine (CUE)

### 4.1 Вложенность (исправление GFX_CONTEXT_LAYOUT.md) [A]

```
R (0xDE90 байт, vtable 0xcd14f8) — объект движка «контекст рендера»
 +0x008  G — GfxContext:  G+0x00 DCB (Gnm::CommandBuffer), G+0x40 и G+0x80 — ещё два CommandBuffer [?]
```

### 4.4 CUE: тень ресурсов, раскладка, commit [A]

**Тень:** 8 стадий × 0x1800 байт с `CUE+0x90` (`memset 0xC000` в `0x13a50`); стадии 0 CS, 1 PS, 2 VS, 3 GS, 4 ES,
5 HS, 6 LS, 7 [?] (`0x13e30` отдельно обрабатывает 7 и `+0xC6D8`). Перевод стадий движка в стадии Gnm — таблица
`0x987c80` (`0x27530`): `{0→VS, 1→LS, 2→ES, 3→PS, 4→HS, 5→VS, 6→ES, 7→GS}`.

**Таблица раскладки шейдера** (`CUE+0xC180 + stage·8`, приходит вместе с шейдером из программы; пустая — 0x138 байт
из `0xFF` с количествами в конце, `0x13a50`):

| Смещение | Тип | Смысл | Кто читает |
|---|---|---|---|
| +0x00 | u16 | размер снимка в dword | commit |
| +0x04 / +0x05 / +0x06 | u8 SGPR | указатель: `CUE+0xC140` (только ES/GS) / снимок + `[+0x18]·4` / снимок + `[+0x20]·4` | `0x14ad0` |
| +0x07 | u8 SGPR | указатель на весь снимок | `0x14ad0`, `0x13ec0` |
| +0x08 / +0x09 | u8 SGPR | снимок + `[+0x16]·4` / `[+0x1A]·4` | то же |
| +0x0A / +0x0B | u8 SGPR | снимок + `[+0x1C]·4` / `[+0x1E]·4` | то же |
| +0x0C | u8 SGPR | глобальный указатель `CUE+0x78` | то же |
| +0x0D / +0x0E | u8 SGPR | одно значение `CUE+0xC0E0+stage·4` / `CUE+0xC100+stage·4` (`hi16<<16 \| lo16`; сеттеры `0x16970`, `0x169a0`) [H: диапазон GDS / счётчики append-consume] | то же |
| +0x10 | u8 SGPR, u8 count | прямой участок user data (`0x16fb0` пишет count dword сразу в SGPR) | `0x16fb0` |
| +0x16…+0x21 | u16 | смещения подтаблиц в снимке (dword) | commit |
| +0x22 + i·2 | u16 × 64 | **ресурсы** (T# 32 байта или V# 16 байт) | `0x16d10` (T#), `0x16b70` (V#) |
| +0xA2 + i·2 | u16 × 16 | **RW-ресурсы** | `0x16de0` (T#), `0x16c40` (V#) |
| +0xC2 + i·2 | u16 × 16 | **сэмплеры** (S#, 16 байт) | `0x16eb0` |
| +0xE2 + i·2 | u16 × 20 | **константные буферы** (V#) | `0x169d0` |
| +0x10A + i·2 | u16 × 16 | **вершинные буферы** (V#) | `0x16aa0` |
| +0x132…+0x136 | u8 × 5 | количества слотов (0x40, 0x10, 0x10, 0x14, 0x10) | `0x13a50` |

Элемент слота: `0xFFFF` — шейдер слот не использует; бит 15 = 1 — дескриптор пишется **прямо в SGPR** `value & 0x3FFF`
(`setUserDataRegion`, `0x626520`); иначе — **смещение в dword в тени стадии**: дескриптор копируется в
`shadow[stage] + value·4`. Каждый сеттер ставит флаг «ресурсы стадии изменены» (`CUE+0xC1D0+stage`).

**Commit** (`0x14ad0` — графика, `0x13ec0` — CS): для стадий с флагом «шейдер изменён» (`+0xC1C8+stage`) —
установка шейдера (`sceGnmSetVsShader` `0x625220`, `SetPsShader350` `0x625100`, ES/GS/HS/LS `0x625a40/0x625370/…`,
CS `0x625710`) и при `CUE+0x88` — L2-предвыборка кода (`0x623630`); для стадий с флагом «ресурсы изменены» —
`snap = alloc(layout+0x00)` (`0x123d0`), `memcpy(snap, shadow[stage], n·4)` и `SET_SH_REG`-указатели (`0x626400`) по
полям 0x04…0x0E. `0x140d0` (через `0x18210`) — вариант commit для пути `0x63c…`/`0x6247a0` [H: dispatch draw].

**Время жизни данных:**
- тень — живёт в контексте; сбрасывается только при `CUE::Init` (memset) — между кадрами старые дескрипторы
  остаются, флаги и указатели шейдеров обнуляются (`0x13d20/0x13da0`) [A];
- снимок — в арене снимков кадра (`0x1f0b20`, пара 4, 4.5), живёт до конца исполнения кадра на GPU; адрес новый на
  каждый commit с изменёнными ресурсами (поэтому user data почти всегда отличаются, P52_PERFORMANCE.md §1.6) [A];
- константы объекта/материала/draw — встроены в DCB (`NOP 0x6875…` + данные), живут вместе с буфером команд [A];
- данные инстансов — атомарный аллокатор кадра (`0x1f0870`, пары 0/1) [A].

## 5. Синхронизация

### 5.1 Внутри кадра (CPU) [A]

1. Главный поток: сбор видимого (задачи), `0x1980d0` — 41 задача сортировки → `Release(S+0xE8)`.
2. `0x198a70` — 41 контекст + задачи записи в группу `S+0xE8` (стартуют после сортировки).
3. Задача прохода порождает пачку задач-кусков и **ждёт её** (`0x1ef4e0`); кусок пишет только в свой контекст —
   общих изменяемых данных между кусками нет, кроме атомарных аллокаторов (пул контекстов, арены, инстансы).
4. `0x1f2e30` (главный поток): пока `записано != занято`, выполнять чужие задачи (`TryNextJob`) и `delay(1 мкс)`.
5. `SubmitFrame` вызывается только после этого.

### 5.2 Порядок команд на GPU [A]

`SubmitFrame 0x1f1e30` строит один список (≤ 512 кусков):
1. до 5 контекстов системы деформации `DAT_00e18350` (`+0x938/+0x948` — есть команды) [H: скиннинг/морф до кадра];
2. пре-контекст `F+0x1F80` (EOP-метка кадра, `ACQUIRE_MEM`);
3. контексты пула с командами, **отсортированные `qsort` по `(pass, sub, адрес)`** (`0x1ef490`); перед каждым
   контекстом в **конец предыдущего** дописывается переход состояния `0x120020(prev, next.stateBlock)` — контексты
   пишутся независимо, а порядок и наследование состояния восстанавливаются при отправке;
4. пост-контекст `F+0xFE10` (флип-NOP `0x6286a0` при флаге 4).

Список кусков берётся из каждого контекста через `0x11f2c0`. При флаге `DAT_00f1bcc0` все куски копируются (`memcpy`)
подряд в один блок арены DCB, с разбиением на буферы ≤ 0x3FFFFC байт — отправляется несколько больших буферов вместо
сотен мелких [A].

Затем `sceGnmSubmitDone` (по режиму), **ожидание `label ≥ fence(N−1)`** (`delay(50 мкс)`), `SubmitAndFlip`, ожидание
`IsFlipPending ≤ порога`, смена половин 5 арен, `занято = 0`.

### 5.3 CPU ↔ GPU [A]

- EOP: `0x627aa0` = **`EVENT_WRITE_EOP`** (`0xC0044700`): событие 4, индекс 5, 64-битные данные, адрес метки
  `DAT_00e17e80[F+0x124]`, данные = счётчик кадра (0 пропускается).
- `0x625e80` = **`ACQUIRE_MEM`** (`0xC0055800`, 7 dword): `CP_COHER_CNTL = (bits & 0x30)<<18 | (bits & 0xB)<<15 |
  action`, размер `0xFFFFFFFF`, база, интервал опроса 10. Кадр: `action 0x6000000`; конец куска/прохода и смена целей:
  `0x2E000000`.
- Кадров в полёте ≤ 1: CPU собирает кадр N, пока GPU исполняет N−1; арены двойные, поэтому половина кадра N−1 не
  перезаписывается до его завершения.

## 6. Что это даёт переносу на Windows/Vulkan [H]

| Оригинал | Естественное соответствие в Vulkan |
|---|---|
| слот пула R, запись задачей | вторичный командный буфер / буфер на поток; ключ `{pass, sub}` — порядок `vkCmdExecuteCommands` или порядок отправки |
| `0x120020` (перенос состояния между контекстами) | явное начальное состояние каждого командного буфера (динамическое состояние задаётся в начале) |
| тень CUE + раскладка шейдера | набор дескрипторов на draw: раскладка = схема дескрипторов шейдера; снимок = запись в descriptor buffer / push descriptors |
| встроенные в DCB константы | кольцевой uniform-буфер кадра с динамическими смещениями |
| 5 пар арен | кольцевые буферы кадра (2 половины) |
| EOP-метка + ожидание прошлого кадра | timeline-семафор (значение = счётчик кадра) |
| `ACQUIRE_MEM` в конце прохода | барьер прохода |
| запись экземпляра 0x80 + ключ | готовый вход для нативного рендера списка: материал, геометрия, матрица, зонд |

Ключевой вывод: в движке **уже есть** высокоуровневые точки, где известны материал, меш и матрица (`0x448260`,
`0x1a1960`, `0x1a1770`), и низкоуровневые (`commit` с тенью и раскладкой). Нативный путь может перехватывать на
любом из этих уровней без разбора PM4.

1. **Сброс слотов пула между обычными кадрами.** `R::Reset` вызывается статически только при переполнении арен
   (`0x1f14e0`), смене видеорежима (`0x1f0be0`), из `0x170980` (деформация) и `0x1ef410` (сброс слота, вызывающих нет:
   ни `call`, ни указателей в данных). Как куски DCB слотов возвращаются к началу в обычном кадре — **не найдено** [?].
   Проверка: счётчик вызовов `0x11f050` и `0x11eed0` за кадр (гостевой хук, выкл. по умолчанию).
2. Назначение 41 прохода (какой рисует G-буфер, тени, прозрачные, UI) — снять число экземпляров и контекстов на проход в
   игре.
3. Второй и третий CommandBuffer G (`G+0x40`, `G+0x80`) — CCB/ACB? Кто в них пишет [?].
4. Стадия 7 CUE и `0x140d0`/`0x18210` [H: dispatch draw].
5. Система деформации `DAT_00e18350` (5 контекстов до кадра) и `DAT_00e17f90` (второй вид сбора) — разобрать.
6. Пара арен 2 (256 КиБ) — назначение.
7. Поля `+0x38/+0x40` vtable материала; `0x120230`; регистр `0xA003` в `0x11f3c0`.
