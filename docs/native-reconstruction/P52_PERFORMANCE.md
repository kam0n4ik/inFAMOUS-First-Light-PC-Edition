## 2. Исправление: доверие коду шейдеров по отслеживанию записи (`SSPC_P52_CODE_TRUST`)

`shader_cache.{h,cpp}`, `shader_frontend.{h,cpp}`, `native_backend.cpp`:
- перед чтением кода программы/fetch-шейдера его страницы ставятся под отслеживание записи (`PageTracker::Arm`, тот же
  механизм, что у буферного кэша); если ставить нельзя (`CanArm` = false), запись проверяется каждый кадр, как раньше;
- пока страницы не записаны и не переотображены, запись доверена в любом кадре (без чтения и сравнения);
- запись CPU (через защиту страниц), чтение файла в эту память (уведомление `InvalidateGuestMemory`), unmap уже
  приходят в `ShaderFrontend::Invalidate` → запись помечается «грязной» → читается заново;
- `verify` — отслеживание включено, но чтение каждый кадр остаётся и считает пропущенные записи.

Ограничение: запись в код шейдера со стороны GPU/DMA (не CPU) отслеживанием не ловится. Раньше она обнаруживалась в
следующем кадре; признаков, что игра так делает, нет (код за все прогоны не менялся ни разу).

### 2.1 Проверка

`verify`, пляж и гавань: пропущенных записей 0; изменений кода 0; ошибок 0. Срабатываний защиты записи за прогон

### 2.3 Проверки корректности (2026-10-14, после принятия; флаг по умолчанию **выключен**)

Добавлено: записи GPU и командного процессора с известным диапазоном сверяются с блоками (64 КиБ) отслеживаемого кода
и при пересечении инвалидируют его — записанные гостевые буферы draw/dispatch (план ресурсов фронтенда), записи CP
(`Memory::Write`: WRITE_DATA, метки, DMA через CPU), DMA-копии на шкале GPU (`CopyOnTimeline`; в Parallel CP —
`ParallelCp::AddGpuWrite`). Всё на потоке фронтенда (в Parallel CP при `SSPC_P410_FRONTEND=0` записи CP не сверяются —
фронтенд на другом потоке).

| Проверка (`logs\p52\…`) | Результат |
|---|---|
| Parallel CP + `verify`, пляж (`ct_par_verify`) | 44,8 FPS, ошибок 0; код не менялся; пропущено 0; записей GPU/CP проверено 42,1 млн — поверх кода **0** |
| Parallel CP + `verify`, гавань | 40,3 FPS, ошибок 0; код не менялся; пропущено 0; записей 33,9 млн — поверх кода **0** |
| Vulkan Validation + Sync, флаг `1`, пляж (`ct_validate`) | **сообщений валидации 0**, ошибок 0, без потери устройства; доверенных обращений к программам 1,42 млн, к fetch 2,05 млн |
| Длительная игра 3 мин, пляж, ходьба/рывки/стрельба/повороты, `verify` (`soak\ct_soak_beach`) | ошибок 0, корректный выход; новых программ за игру 518 (против 421 в 90-с прогоне — подгрузка); код не менялся; записей 67,9 млн — поверх кода **0** |
| Длительная игра 3 мин, гавань, бой + Parallel CP, `verify` (`soak\ct_soak_early`) | ошибок 0, корректный выход; 591 программа; код не менялся; записей 94,4 млн — поверх кода **0** |

Синхронизация инвалидации: CPU-записи (защита страниц) применяются в `DrainCpuWrites` перед работой, отправленной после
них, и на каждом выполненном WAIT_REG_MEM; записи GPU/CP — в порядке потока на потоке фронтенда; чтение кода после
инвалидации идёт через читатель фронтенда, который ждёт незавершённые записи GPU (`TimelineReader`).

**Ограничение (не закрыто):** записи без известного диапазона — GDS, эмулируемый LDS, BDA, storage-образы — не
сверяются. На PS4 шейдер технически может записать в память кода шейдера через них; в 7 прогонах (вкл. 6 мин игры)
код не изменился ни разу, но полное покрытие **не доказано**. Поэтому `SSPC_P52_CODE_TRUST` остаётся экспериментальным
флагом, выключенным по умолчанию; при включении рекомендуется периодически запускать `verify`.
Не проверено: смена локаций быстрым перемещением / сюжетная загрузка другого района (сценарии не автоматизированы);
деревня (сейв удалён).

## 3. Следующие узкие места (по §1)

   push-дескрипторы.
3. Параллельный CP: «сливы» ~2,8 мс/кадр на критическом потоке (62 % — ожидание памяти, 34 % — лимит раунда).
