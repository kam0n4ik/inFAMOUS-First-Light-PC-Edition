# Phase 3 — Independent Runtime

Живой документ фазы (состояние на 2026-10-10). Дорожная карта не меняется: P2.3 Native VMM → P2.4 Native Thread
Manager → P2.5 Kernel Stabilization & Performance → **Phase 3 Independent Runtime** → Phase 4 Own Graphics Backend.
Phase 3 заменяет системный runtime shadPS4 собственными компонентами SecondSonPC; графика shadPS4 (Gnm, обработка
команд GPU, VideoOut, Vulkan-рендерер, трансляция шейдеров, кэши буферов/текстур, GPU-трекинг памяти) остаётся до
Phase 4. Таблица гостевых импортов — `docs\PHASE3_BRIDGE_DEPENDENCIES.md` (генерируется `tools\phase3_deps.py`).

Уровни готовности в этом документе: **написано** → **собирается** → **самотесты прошли** → **проверено в игре** →
**по умолчанию**. Это разные уровни; «проверено в игре» не означает «по умолчанию».

## 1. Подэтапы Phase 3 (уточнены по аудиту)

| Подэтап | Содержание | Состояние |
|---|---|---|
| P3.1 Runtime Dependency Audit | инвентаризация гостевых импортов (метрика 1) и внутренних механизмов (метрика 2), аудит `fs:`-инструкций игры, граф зависимостей, риски | **сделан** (§3–§4, §6) |
| P3.3 Native TLS/TCB & FS Runtime | свой слот TCB (все потоки обоих менеджеров), свой патчер `fs:` (загрузочный проход + запасной путь с протоколом int3), свой VEH для своих событий | **сделан**: слот — по умолчанию; патчер — проверен в игре, экспериментально (§5.6) |
| P3.2 Native Memory/Threads Consolidation | жизненный цикл стеков (D17: ограниченный кэш, настоящее снятие на своём VMM), длительная сессия → свои потоки и память по умолчанию | дальше |
| P3.4 Native Exception & CPU Patch Runtime | единый диспетчер исключений SecondSonPC по владельцу события, доставка/отказ гостевых сигналов, фатальный путь, CPU-эмуляция (SSE4a/RCP для Intel) | дальше |
| P3.5 Remaining Kernel HLE | `__error`, API памяти libkernel поверх выбранного менеджера, часы процесса (с адаптером для VideoOut/AudioOut) | дальше |
| P3.6 Runtime Integration & Bridge Isolation | явные адаптеры для графического моста (очереди событий, часы, память, исключения), интерфейсы Phase 4, сквозные и длительные проверки | дальше |

**Почему P3.3 раньше P3.2.** SSPC-002 (самый опасный класс сбоев — гонка записи живого кода) живёт в патчере `fs:`,
а слот TCB, который читают трамплины, и сам патчер принадлежали мосту независимо от того, чьи потоки. Свой менеджер
потоков (P2.4) без своего слота TCB не независим: он записывал TCB в слот моста. Поэтому сначала — TCB и `fs:` (P3.3),
затем консолидация менеджеров (P3.2) уже поверх своего слота. Названия подэтапов сохранены.

## 5. P3.3 — свой TLS/TCB и патчер `fs:`

### 5.1 Аудит инструкций игры

Аудит (Python + capstone; модули игры только читаются) декодирует каждую функцию по диапазонам FDE из `.eh_frame` и
отдельно делает побайтный скан; результат — CSV по каждому месту:

| Модуль | `fs:`-инструкций | формы | внутри функций FDE | побайтных «кандидатов» не на границе инструкции |
|---|---:|---|---:|---:|
| eboot.bin | **3616** | все `mov r64, qword ptr fs:[0]` (9 байт: `64 48/4C 8B ModRM 25 00000000`) | 3616 | 2869 (ложные) |
| libc.prx | 0 | — | — | — |
| libSceFios2.prx | 0 | — | — | — |

* Все **813** мест, которые мост патчил в эталонном прогоне, входят в эти 3616.
* GS-обращений к памяти, `rd/wrfsbase`, `syscall` на границах инструкций нет. Есть `int 0x41` (1, eboot), `int1` (8),
  `int` в libc (163) — отладочные/assert-ловушки, к патчеру не относятся (учтено для P3.4).
* ~3400 FDE функций, выброшенных линковщиком, указывают внутрь самого `.eh_frame`; в поисковую таблицу `.eh_frame_hdr`
  они не входят. Загрузчик дополнительно отбрасывает любой диапазон внутри `.eh_frame`/`.eh_frame_hdr`.
* Вывод: **побайтный скан для патчинга непригоден** (ложные совпадения посреди инструкций), **декодирование функций по
  границам FDE даёт точный набор**; загрузочный патчинг закрывает практически все места игры.

### 5.2 Сравнение с исправленным механизмом моста (независимый аудит)

| | Мост (`cpu_patches.cpp` + 0016) | SecondSonPC (`fs_patcher.cpp`) |
|---|---|---|
| Когда патчится | только во время работы: первое исполнение → AV → VEH → запись в живой код | **при загрузке модуля** (до исполнения — гонки нет в принципе); запасной путь — по первому AV |
| Запись живого кода | int3 → хвост → первый байт, `FlushProcessWriteBuffers` (0016) | тот же протокол, проверен заново (ниже); нужен только для 14 мест игры |
| Поиск модуля в VEH | `GetModule` без проверки конца модуля (первопричина вторичного сбоя SSPC-002) | таблица модулей с проверкой границ, без блокировок и выделений |
| Состояние «уже пропатчено» | `std::set` под мьютексом — выделение памяти в VEH | сами байты кода (`E9` в свою область трамплинов) + атомарный адрес «пишется сейчас» |
| Чьи ловушки берёт | любой int3/priv в зарегистрированном модуле, если адрес в `patched` | только своё место (пишется сейчас или уже `jmp` в свою область трамплинов); чужие int3 и привилегированные инструкции — дальше по цепочке |
| `cmp/xor reg, fs:[x]` | **латентный дефект**: `pushfq … popfq` вокруг операции восстанавливает старые флаги — результат сравнения теряется | флаги операции сохраняются (`lea`/`push`/`pop`/`mov` флаги не меняют); проверено самотестом |
| Отрицательное смещение `fs:[-N]` (статический TLS) | **латентный дефект**: при `offset < 0` трамплин не разыменовывает и возвращает адрес TCB | читает `[TCB-N]`; проверено самотестом |
| `fs:[0]` | возвращает адрес TCB (память не читает) | читает `[TCB+0]` (self-указатель), как консоль |
| Запись `mov fs:[x], reg`, `add/sub/and/or` | не поддерживаются | поддерживаются (в игре не встречаются) |
| Кодогенерация | Xbyak | собственный кодировщик (~10 инструкций) |

Оба латентных дефекта моста для этой игры не срабатывают (таких форм в ней нет), в свой патчер не перенесены; записаны
в `docs\KNOWN_ISSUES.md` (SSPC-008).

**Протокол int3 на Windows — проверка.** Запись живого кода: `int3` одним атомарным байтом → `FlushProcessWriteBuffers`
→ остальные байты → `FlushProcessWriteBuffers` → первый байт → `FlushProcessWriteBuffers` → `FlushInstructionCache`.
`FlushProcessWriteBuffers` посылает IPI всем процессорам, исполняющим потоки процесса; приём прерывания и возврат из
него сериализуют поток команд процессора (Intel SDM требует для кода, изменяемого другим процессором, сериализации на
исполняющем; Linux `text_poke_bp` делает то же через `sync_core` на всех CPU). После каждого шага любой процессор либо
доисполняет старую инструкцию целиком (выбранную до появления `int3`), либо выбирает `int3` и ловит ловушку — смеси
старых и новых байт не бывает. Поток, поймавший `int3`, ждёт блокировку модуля (её держит пишущий поток до конца
записи) и возвращается на начало места. Ядро Windows иногда сообщает о такой ловушке как о привилегированной инструкции
(`0xC0000096`): разбирая `int3`, оно уже видит `E9`. Такой случай принимается только по адресу своего места с готовым
`jmp` в свою область трамплинов — настоящей привилегированной инструкции там быть не может.

### 5.3 Реализация

* `src\runtime\cpu\tcb_slot.{h,cpp}` — слот TCB SecondSonPC (`InitTcbSlot`, `SetCurrentTcb`, `CurrentTcb`).
* `src\runtime\cpu\fs_patcher.{h,cpp}` — декодер (Zydis — независимая библиотека MIT из externals моста, подключена
  напрямую; заголовки shadPS4 не используются), кодировщик трамплинов, реестр модулей (до 64), загрузочный проход,
  обработчик исключений, статистика (`GetStats`, итог в журнале при выходе), тестовая точка `Test::ClaimsTrap`.
* Загрузочный проход берёт **точные диапазоны функций из FDE** (`Loader::DecodeEhFrameFunctions`, разбор CIE/FDE —
  `src\loader\eh_frame.cpp`), а не «от начала до следующего начала». Если декодирование функции **точно заканчивается на
  её конце**, доверяются все границы инструкций. Если нет (в диапазоне есть данные) — только до последней безусловной
  передачи управления (`ret/jmp/ud2/int3/hlt`) перед точкой остановки; места после неё уходят на запасной путь. В eboot
  таких функций 68: switch-таблицы переходов за кодом функции (декодер успевает прочитать часть таблицы как мусорные
  инструкции и останавливается); их 14 `fs:`-мест стоят до последнего `ret/jmp` → **все 3616 мест патчатся при
  загрузке**. Распознавать сами таблицы переходов не требуется.
* Выбор один раз при старте (`InstallGuestCpu`, `src\bridge\shadps4\loader_host.cpp`): слот TCB — всегда свой (мост
  получает его через `Core::UseTcbKey`, патч **0021**); патчер — свой с `--native fs-patch`, если процессору не нужны
  другие патчи моста (`CpuNeedsOnlyFsPatches`: есть SSE4a и не Intel), иначе мостовой с предупреждением. Модули никогда
  не делятся между двумя патчерами.
* Свой менеджер потоков пишет TCB в свой слот (`kernel_host.cpp`); загрузчик читает текущий TCB из своего слота.
* Откат: без `--native fs-patch` работает мостовой патчер (патч 0016 сохранён); слот всё равно один и свой.
* `tools\perf_runs.ps1`: режимы `F` (`--native fs-patch`) и `TMF` (+ свои потоки и память).

### 5.7 Ревью и правки

Независимое ревью (ecc:cpp-reviewer) по диффу P3.3: критических ошибок нет; кодировщик (REX, ModRM/SIB для rsp/r12/rbp/
r13, disp8/disp32, `lea rsp`, push/pop r8–r15, rel32), протокол записи, публикация таблицы модулей, `UseTcbKey`, разбор
CIE/FDE и фильтр диапазонов проверены и верны. Внесено:

1. **(HIGH/MEDIUM)** места в 68 функциях с таблицами переходов уходили на запасной путь — а он берёт исключение, кадр
   которого Windows строит под `rsp` поверх red zone System V. Теперь при остановке декодирования границы инструкций
   доверяются до **последней безусловной передачи управления** (`ret/jmp/ud2/int3/hlt`) перед остановкой — таблица лежит
   за ней, исполнение туда не проваливается. На eboot все 14 мест стоят до неё (проверено отдельно capstone) → **все 3616
   при загрузке**, запасной путь остаётся страховкой. Самотест: функция «код + `ret` + данные, похожие на `fs:`-инструкцию,
   + обрезанный байт» — код пропатчен, данные не тронуты.
2. Журнал из обработчика исключений убран (риск взаимоблокировки на блокировке журнала): только счётчики, первый адрес
   неподдерживаемой формы — в итоге при выходе.
3. Комментарии: слоты ≥ 64 (TlsExpansionSlots), смещения ≥ 64 КиБ; указатель обработчика — атомарный.
4. Тест гонки проверяет значение на всех 32 768 местах (было ~1/24); жёсткие числа самотеста по eboot привязаны к
   проаудированной сборке игры (42 483 FDE), для другой — только свойства.

После правок: selftest 918/0, `--native memory` 92/0, fault 22/0, гонка мост/свой — PASS; подтверждающие прогоны

### 5.6 Готовность

| Компонент | Уровень |
|---|---|
| Свой слот TCB для всех потоков (адаптер 0021) | **по умолчанию** (меняется владелец слота, механизм тот же); проверено в игре во всех режимах |
| Свой патчер `fs:` | **проверено в игре** (4 прогона `F`, 2 `TMF`, 0 сбоев) — пока **экспериментально** (`--native fs-patch`). Режимом по умолчанию — после длительной (≥ 30 мин) сессии и серии загрузок в P3.2, вместе с решением по своим потокам и памяти; откат — простой отказ от флага |
| Разбор FDE в загрузчике | используется только своим патчером |

**Что SecondSonPC перестаёт брать у моста с `--native fs-patch`**: слот TCB, патчер `fs:` и его обработчик исключений,
`std::set`/Xbyak/Zydis-форматирование в VEH моста. Мостовой `cpu_patches.cpp` в пути игры не участвует (его модулей нет),
его обработчики даже не регистрируются (`PatchesInit` вызывается только из `RegisterPatchModule`).
**Что остаётся у моста** (метрика 2, §4): VEH моста для GPU-трекинга и SRT-walker, эмуляция SSE4a/RCP (на этом ПК не нужна),
errno, часы, очереди событий, старт libkernel, мостовые потоки AudioOut/графики.

## 6. Самые рискованные пересечения Native/Bridge

1. **Красная зона и исключения Windows.** Кадр исключения строится под `rsp` гостевого потока; System V leaf-функции
   держат данные в 128 байтах ниже `rsp`. GPU-трекинг моста даёт 30–45 тыс. AV/с на гостевых потоках. Мост держит для
   этого выключенный по умолчанию режим «static red-zone protection». Для `fs:` P3.3 риск убирает (места патчатся до
   исполнения); для GPU-трекинга — P3.4/Phase 4 (проверить, бывают ли трекинговые AV в leaf-функциях).
2. **errno.** NATIVE-функции пишут errno через мостовой `__Error()`; при переносе — один владелец, иначе игра читает не тот.
3. **Часы процесса** общие с метками VideoOut/AudioOut — переносить только вместе с адаптером для моста.
4. **Очереди событий**: в очереди игры доставляет графический мост (флипы, EOP) — до Phase 4 только через явный адаптер.
5. **`g_curthread`** в коде моста: VEH моста проверяет на null (свои потоки безопасны); функции синхронизации моста —
   нет, поэтому `--native threads` запрещён с `--bridge kernel-*` (`src\app\main.cpp`).
6. **Стеки (D17)**: VMM моста не умеет снимать стек с guard; свой менеджер потоков держит стеки в кэше. Свой VMM снимает
   стек целиком (`HostAddressSpace::SplitsPrivate` разрешает снятие всего выделения) — P3.2.
7. **Необработанное исключение в мосте** вызывает `Emulator::Shutdown()` прямо из VEH — событие, не опознанное ни одним
   обработчиком, гасит процесс; свой обработчик забирает только своё и стоит первым.
8. **CPU без SSE4a / Intel**: мостовой патчер эмулирует отсутствующие инструкции; свой патчер на таких CPU отказывается
   целиком (без смешивания) — перенос эмуляции в P3.4.
9. **AudioOut** создаёт гостевые потоки моста — их TCB теперь в слоте SecondSonPC (адаптер 0021).
10. **Выделения памяти и журнал в VEH моста** (`std::set`, форматирование Zydis, `LOG_*`) — риск взаимоблокировки на куче;
    в своём обработчике выделений нет.
