## Закрытие тестовых прогонов — исправление `run_phase0.ps1` (2026-10-09, Phase 2.2.0)

**Причина `0xC000013A`.** `SecondSonPC.exe` — консольная программа (PE subsystem 3), поэтому
`Start-Process` даёт ей своё окно консоли. Старый скрипт брал `Process.MainWindowHandle`: .NET
возвращает первое видимое окно без владельца, у которого `GetWindowThreadProcessId` даёт PID процесса,
в порядке Z-order. Окно консоли создаёт conhost.exe, но Windows приписывает его клиенту — и PID, и
даже поток клиента (проверено на тестовом процессе). Если консоль была выше окна игры, WM_CLOSE уходил
ей, conhost посылал игре `CTRL_CLOSE_EVENT`, и процесс завершался с `0xC000013A`
(`STATUS_CONTROL_C_EXIT`). Отсюда «иногда»: зависело от того, какое окно было сверху.

**Цепочка запуска.** `play.cmd` → `powershell tools\manual_run.ps1` → `Start-Process SecondSonPC.exe`
(ждёт закрытия окна человеком, ничего не закрывает). Автопрогоны: `smoke_runs.ps1` /
`repro_sspc001.ps1` → `powershell -File run_phase0.ps1` → `Start-Process SecondSonPC.exe`;
`play.cmd` в них не участвует.

**Исправлено** (`tools\game_process.psm1`, его использует `run_phase0.ps1`):
- PID — только из `Start-Process -PassThru` этого прогона; дескриптор процесса удерживается (код выхода
  читается, PID не переиспользуется); поиска процесса по имени нет;
- окно игры: верхнего уровня, `GetWindowThreadProcessId` = PID прогона, поток окна — поток этого
  процесса, класс не `ConsoleWindowClass`/`PseudoConsoleWindow` (именно это отсекает консоль), видимое,
  без владельца; `SDL_app` — только предпочтение среди нескольких подходящих (из двух `SDL_app` — большее);
- WM_CLOSE — только выбранному окну; ожидание `-CloseTimeout` (15 с); `TerminateProcess` — только
  своему процессу и только если окна нет, отправка не удалась или вышел таймаут;
- классификация (`how`): `closed-by-test`, `exited-self`, `crashed`, `crashed-while-closing`,
  `closed-with-error`, `exited-error`, `console-closed` (`0xC000013A`, ни сбой, ни успех),
  `terminated-externally`, `killed-close-timeout`, `killed-no-window`, `killed-close-post-failed`,
  `still-running`. `closed-by-test` не считается доказательством отсутствия сбоя — сбои ищет
  `analyze_run.py` по логам (поле `crash`);
- `logs\runs\<tag>\run.json`: PID, выбранное окно (HWND, класс, поток, размер, причина выбора), все
  окна процесса с причиной отказа, отправлен ли WM_CLOSE, ошибка отправки, время ожидания закрытия и
  завершения, код выхода (десятичный, hex, имя), `how`, пояснение. `smoke_runs.ps1` и
  `repro_sspc001.ps1` читают его вместо разбора текста; `analyze_run.py` добавляет в сводку
  `exit_hex`, `exit_note`, `window_class`, `window_reason`.

## Ручная проверка (для пользователя)

Перед проверкой: `E:\SecondSonPC\play.cmd` (делает копию сохранений). Сохранения на момент этих
проверок скопированы в `userdata\savedata_backups\2026-10-08_*_phase2_before_more_graffiti_runs`.

1. **Запуск и меню.** «Продолжить» — Space; пауза — Esc или Enter; выход из паузы — Space.
2. **Захват мыши.** Окно получило фокус → курсор исчезает сам, мышь крутит камеру. Esc → пауза и
   курсор возвращается; Esc ещё раз → снова захвачен. Alt+Tab и обратно → мышь сразу крутит камеру
   (клик не нужен), ни одна клавиша не «залипла».
3. **Граффити** (если игра на этом месте): G → контроллер «боком»; X удерживать 2–3 с; затем
   держать ЛКМ и закрашивать мышью **весь** щит, включая нижние углы; когда сцена сменится — G или
   любая из WASD (вернуть мышь камере). Если поза «боком» не принимается — `[Input] sideways = "left-up"`.
4. **Персонаж.** WASD — движение, Left Ctrl — шаг, мышь — камера (если медленно/быстро —
   `[Input] mouseSensitivity`), Space — прыжок; проверить V (□), F (△), E (○), Q/R (L1/R1),
   ПКМ/ЛКМ (L2/R2), Shift (L3), колесо-клик/Z (R3), Tab (тачпад), стрелки. Записать, что каждое
   делает в игре — раскладку поправлю по подсказкам.
5. **Геймпад** (если есть DualShock 4 / DualSense / Xbox): подключить до запуска или во время игры —
   стики, кнопки, курки; у DS4/DualSense — граффити наклоном и встряхиванием самого геймпада.
   Клавиатура и геймпад одновременно — оба должны работать.
6. **FPS и окно.** F10 — счётчик кадров; F11 — полноэкранный режим и обратно.

Почему BRIDGE-сторона самотеста не вызывает блокирующий `Wait`/`Poll`: оракул разыменовывает
`g_curthread` (у потока самотеста его нет) **до** проверки условия, удаляет флаг голым `delete`
(двойное удаление / устаревший дескриптор → падение), а `Set` идёт через сырой указатель. Поэтому в
общем скрипте сравниваются только коды возврата безопасных путей; блокировка, очистка, плохие
дескрипторы и повторное использование — нативной частью против ожидаемых значений.

Отличия нативной реализации от эталона (эталон здесь менее надёжен), проверены нативной частью:
1. дескриптор — через общую `HandleTable` (`shared_ptr`): удалённый при ожидании флаг живёт до выхода
   ждущих, мусорный/устаревший дескриптор → ESRCH (у эталона `delete ef` → use-after-free / двойное
   освобождение); дескриптор игре 1-based → никогда не 0 (у эталона — указатель кучи, не NULL);
2. остаток таймаута пишется в `*pTimeout` при пробуждении по `Set` (эталон только обнуляет его при таймауте);
3. конфликтующий attr (FIFO|PRIO, SINGLE|MULTI) и неверный waitMode → EINVAL (у эталона `UNREACHABLE` / UB);
4. приоритетные ждущие будятся «меньше значение — раньше» (как семафоры и `Kernel::Host`); у эталона
   event flag порядок обратный (ошибка shadPS4). В игре флаги предположительно FIFO — порядок
   приоритетов не наблюдается.

**НЕ ПРОВЕРЕНО:** event flags в игре (оба загрузчика; путь `shadps4` их не использует); атрибуты
реальных флагов игры (22 создания / 32 удаления за прогон аудита; AND/OR/CLEAR/таймауты в бою).
