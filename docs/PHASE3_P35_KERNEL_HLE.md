## 2. P3.5.1 — errno гостя

### 2.1 Аудит

* Импорт: `__error` (`9BcDykPmo1I`, libkernel/libkernel), импортируют eboot.bin, libc.prx и libSceFios2.prx;
  ~18 тыс. вызовов за 98-с прогон (`PHASE3_BRIDGE_DEPENDENCIES.md`).
* Мост: `static thread_local s32 g_posix_errno` (`core\libraries\kernel\kernel.cpp:86`); `__Error()` возвращает его
  адрес; `ErrSceToPosix`, `SetPosixErrno`, `kernel_ioctl` писали в переменную напрямую; ~200 мест моста пишут
  `*__Error() = …` (файловая система моста, память, потоки, net через `SetKernelErrnoHook`).
* SecondSonPC: своей ячейки не было; NATIVE-функции (время, сигналы, синхронизация, ФС) писали через
  `Kernel::Host::Errno()` и `FsHost::Errno()` → `__Error()` моста. Один владелец уже был — мост.
* Хранение: не в гостевом TLS и не в TCB, а в TLS хоста. На PS4 ячейка — поле структуры потока libkernel (обнуляется
  при создании, живёт до конца потока).

### 2.2 Почему thread-local исполняемого файла соответствует ABI

ABI `int* __error(void)`: указатель на ячейку **вызывающего потока**, один и тот же на всё время жизни потока; потоки
независимы; новый поток начинает с 0. Код игры не хранит указатель между потоками (вызывает `__error` при каждом
обращении к `errno`).

* Каждый гостевой поток обоих менеджеров — ровно один поток Windows, созданный для него и завершаемый с ним:
  свой менеджер — `CreateThread` на поток (`thread.cpp:731`), `ExitThread` в конце; мост — `Core::NativeThread::Create`
  → `CreateThread`, `Exit` → `ExitThread` (`core\thread.cpp`); главный поток — отдельный поток (свой `StartMainThread`
  или `Libraries::Kernel::Thread` моста). Пула потоков хоста нет.
* Статический TLS исполняемого файла (`.tbss`) выделяется загрузчиком Windows при создании потока и освобождается после
  его завершения: ячейка нулевая при старте, её адрес не меняется от первой гостевой инструкции до завершения TLS-
  деструкторов и `ExitThread` — дольше, чем может выполняться любой гостевой код этого потока. Висячих указателей нет:
  ячейка не освобождается раньше потока (в отличие от TCB, который снимается после `ExitThread` джойнером).
* Нет выделений и блокировок; работает и в потоках хоста без гостевой идентичности (потоки моста, вызывающие функции
  моста).
* errno CRT хоста (`_errno()`) — отдельная переменная: переходы в код хоста не портят гостевой errno.

### 2.3 Реализация

* `src\runtime\kernel\guest_errno.{h,cpp}`: `thread_local s32 t_errno`; экспорт `__error` (группа `errno`,
  экспериментальная); `OwnLocation()`, `Enable()`.
* Патч **0023** (`kernel.{h,cpp}` моста): `UseExternalErrno(location)` — `__Error()` возвращает `location()`; все прямые
  записи моста идут через `__Error()`. Без вызова — прежняя ячейка моста (+1 relaxed-чтение на вызов).
* `InstallKernelRuntime` (`kernel_host.cpp`) — сразу после `InstallGuestCpu`, до старта библиотек моста и до гостевых
  потоков: с `--native errno` направляет мост на `OwnLocation`.
* Один владелец в каждом режиме: по умолчанию — мост (`Kernel::Host::Errno` → `__Error()` → ячейка моста; своя
  ячейка не используется); с флагом — SecondSonPC (`__error` игры, `__Error()` моста, `Kernel::Host::Errno`,
  `FsHost::Errno` дают одну ячейку).

### 3.2 Владение и согласованность (на каждую функцию)

Общее для всех: группа требует `--native memory`; адресным пространством, физической памятью, областями, защитой и
уведомлениями GPU **владеет `Memory::VirtualMemory`** (P2.3.4). Функции P3.5.2 — слой API без собственного состояния:
делают те же вызовы менеджера с теми же аргументами, что функции моста через адаптер `NativeGuestMemory`. У моста не
остаётся данных этих отображений: его `MemoryManager` в этом режиме не создаётся (patch 0012, `ASSERT`). Согласованность
с GPU-мостом обеспечивает сам менеджер: `OnGpuUnmap` до изменения адресного пространства, `OnGpuRegister`/`OnGpuMap`
после, `OnGuestWrite` после `mprotect` — тот же порядок, что на пути моста (проверено сравнением журналов, §3.4).

| Функция | Ошибка/частичное освобождение | Откат |
|---|---|---|
| `AllocateDirectMemory` | любой отказ менеджера → EAGAIN (как оракул; код менеджера — в лог, напр. ENOMEM при отказе commit с `on-demand`) | менеджер возвращает страницы при отказе commit |
| `ReleaseDirectMemory` | непроверенное освобождение: всегда 0, как оракул; виды снимаются до освобождения (GPU первым) | — |
| `MapDirectMemory` | SDK ≥ 2.50 и не стек → эксклюзивно (EBUSY на уже отображённую direct-память); exec → EACCES; Fixed@0 при SDK ≥ 1.70 → EINVAL | `BeginMap`/`EndMap` менеджера |
| `MapNamedFlexibleMemory` | бюджет flexible проверяется под замком менеджера (D6) | — |
| `Munmap` | часть частной памяти (стек) → EINVAL (D17), остаток вида сохраняет защиту (D19) | ничего не меняется при отказе |
| `Mprotect` | целые страницы; переполнение размера → EINVAL | — |
| `mmap` | errno через владельца errno (мост или SecondSonPC) | — |

Отличия от оракула (все безопаснее, все в самотестах): нулевой указатель адреса → EINVAL (оракул разыменовывает);
нулевое имя flexible → EFAULT (оракул падает на форматировании лога); переполняющиеся размер/адрес `mprotect`/`mmap` →
EINVAL (оракул переворачивает и защищает/отображает малый диапазон).

### 3.3 Флаги

`--native kernel-memory` без `--native memory` запрещён при запуске: «it needs --native memory (on the bridge's manager
the bridge's functions are its API)». С `--native kernel-dmem` несовместим через `memory`.

### 4.2 Реализация

* `src\runtime\kernel\clock.{h,cpp}`: одно измерение TSC (алгоритм оракула, перенесён из `time.cpp` без изменений:
  100 мс против точного системного времени, округление до 100 кГц — значение, которое игра видит с P2.2) и одна эпоха
  (TSC в `Start()`); `TicksTo` — точное целочисленное `floor(ticks × единицы / частота)` без переполнения для любых
  тиков (секунды × единицы + остаток; 128-битное произведение, если остаток не помещается); чтение до эпохи (TSC
  отстающего ядра) — 0, никогда не «перевёрнутое» значение. Класс `ProcessClock` — для тестов.
* `time.cpp`: `sceKernelGetTscFrequency` → `Clock::TscFrequency()`; `CLOCK_PROCTIME` при `--native clock` →
  `Clock::ProcessTimeUs()`; enum идентификаторов часов переименован (`ClockId`).
* Патч **0024** (`kernel\time.{h,cpp}`, `debug_state.cpp` моста): `UseExternalClock(ExternalClock*)` до `RegisterTime`:
  `sceKernelGetTscFrequency`, `GetProcessTime`, `GetProcessTimeCounter(Frequency)` моста читают SecondSonPC; свой
  `NativeClock` (второе 100-мс измерение) не создаётся; `sceKernelReadTsc` — `FencedRDTSC` (та же инструкция);
  пауза отладчика сдвигает эпоху владельца (`Dev::AdvanceProcessEpoch`). `common\` не тронут (поколение кэша шейдеров
  то же).
* `InstallKernelRuntime`: с `--native clock` — `Clock::Start()`, адаптер, `Clock::Enable()` до `RegisterLib` libkernel.
* При выходе (`OnQuickExit`): «process clock at exit: owner …; TSC … Hz (the bridge's …), invariant TSC …; N s since
  the epoch, QueryPerformanceCounter N s: drift ±X ppm».

### 4.3 Контракт

Монотонность: TSC инвариантный и синхронизированный (проверяется `CPUID 0x80000007 EDX[8]`, пишется в лог); чтение
после увиденного значения другого потока не раньше него (самотест: 8 потоков × 200 000). Единицы: тики TSC,
микросекунды (`ProcessTimeUs`), точный пересчёт. Эпоха — старт часов (до `RegisterLib` libkernel с флагом; без флага
эпоха SecondSonPC используется только для отчёта дрейфа). Переполнение: тики 64-битные (сотни лет), микросекунды и
наносекунды — без промежуточного переполнения. Скорость игры не меняется: частота — то же измерение, что игра видит с P2.2.

### 4.4 Тесты

`NativeClock` (обычный самотест: 8, с `--native clock`: 10): пересчёт против точного 128-битного произведения (6 частот,
мкс и нс, края до 2⁶⁴−1, 4000 случайных) и монотонность; 30 дней TSC 5 ГГц = 2 592 000 000 000 мкс точно;
`ProcessClock`: до эпохи 0, мкс/нс, пауза; частота: одно измерение, кратна 100 кГц, TSC инвариантный; скорость: 300 мс
против QPC в пределах 500 ppm; 2 000 000 последовательных чтений (мкс и тики) без отката и согласованность тиков с мкс;
8 потоков × 200 000 чтений — ни одного более раннего; `sceKernelGetTscFrequency` игры — эти часы, экспорт
`sceKernelGetProcessTime` — эти часы. Владелец: по умолчанию — два измерения расходятся не более чем на 300 кГц (в
прогоне 100 кГц); с флагом — частота и частота счётчика моста равны, его время процесса, счётчик, TSC и
`CLOCK_PROCTIME` лежат между двумя чтениями своих часов, своего `NativeClock` у моста нет, пауза отладчика двигает эпоху
(−10 мс и обратно), повторная установка отклоняется.

Дрейф за сессию самотеста относительно QPC: −15,1 ppm (по умолчанию), +12,7 ppm (с флагом) — в пределах округления
частоты до 100 кГц (±14 ppm при 3,59 ГГц).

### 4.5 Граница (остаётся у моста)

* Темп `PresentThread` (vblank 60 Гц, `Common::AccurateTimer` на `steady_clock`): переход на часы процесса меняет цикл
  презентации и логику кадров — запрещено в P3.5 (Phase 4, свой VideoOut). Оба источника — TSC через QPC на
  инвариантном TSC; рассогласования скорости нет, эпохи у таймера нет.
* `GetGpuClock64` (`high_resolution_clock`, нс): не часы процесса, Phase 4.
* Очереди событий (доставка флипов/EOP) — P3.6/Phase 4.

## 9. Ограничения и открытые вопросы

**Существовали до P3.5 (не тронуты):** SSPC-010 (red zone затирается ядром при «грязном» AVX), SSPC-011 (короткие
`extrq` на Intel через `#UD`), точность `vrcpps/vrsqrtps` на Intel, D20 у менеджера моста (свой — без дефекта),
SSPC-008 (латентные дефекты патчера моста).

**Найдено в P3.5:**
* Двойное измерение частоты TSC: два независимых 100-мс измерения у границы округления расходятся с некоторой
  вероятностью на 100 кГц (28 ppm между игрой и VideoOut/GPU/AudioOut; в самотесте — да, в 4 игровых прогонах моста —
  нет) — исправлено флагом `--native clock`; по умолчанию сохраняется (стандартный режим не меняется без решения).
* Унаследовано от оракула (не меняли — это значение, которое игра видит с P2.2): 100-мс измерение частоты чувствительно
  к вытеснению потока во время замера (под нагрузкой смещение до ~1 %); дрейф при выходе это показывает (в прогонах
  P3.5 |дрейф| ≤ 16 ppm). Улучшение (несколько замеров, минимальная задержка) — отдельное решение: меняет частоту,
  которую видит игра.
* В функциях памяти оракула: разыменование нулевого указателя адреса, падение на нулевом имени flexible (форматирование
  лога), переворот размера `mprotect`/`mmap` — в своих функциях закрыто (§3.2); мост не исправлялся (его функции с
  флагом игре не видны; путь по умолчанию игре таких аргументов не даёт).

**Оставлено на P3.6/Phase 4:** очереди событий, `_exit`, таймер vblank презентации, PRT, `GetGpuClock64`.

**Требует ручной проверки (PENDING MANUAL):** ручная игра ≥ 30 мин в полной конфигурации P3.2–P3.5 (бой, способности,
сохранения, загрузки, смена сцен, звук на слух) — автоматический soak её не заменяет.
