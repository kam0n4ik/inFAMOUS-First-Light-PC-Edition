# P2.3 Memory Runtime — аудит, объём P2.3.1, архитектура, результаты

Статус (2026-10-09): **P2.3.1 — нативная физическая direct memory, ЭКСПЕРИМЕНТАЛЬНО, выключена по
умолчанию** (`--native kernel-dmem`). **P2.3.2 — интерфейс GPU ↔ менеджер памяти (патч `0008`),
сделано без смены поведения**: `docs\PHASE2_P232_GPU_MEMORY.md` (аудит, контракт, тесты, замеры,
разбор commit подложки, план P2.3.3). P2.3 целиком (виртуальная память, отображения, защита,
flexible) **не завершена** — блокеры в §9 (п. 2 снят P2.3.2). План всей фазы:
`docs\PHASE2_P23_P24_PLAN.md`.

Обозначения источников семантики: **G** — наблюдение за игрой (лог вызовов, код eboot);
**O** — эталонная реализация моста (shadPS4 0fe263a), это НЕ доказательство поведения PS4;
**H** — комментарий shadPS4 со ссылкой на тест на железе (вторичный источник);
**A** — предположение. Своего PS4 для проверки нет.

### Реальный сценарий игры (G, одинаков во всех прогонах, `bridge_shadps4.log`)

Бюджет: flexible `0x1c000000`, **direct `0x120000000` (4608 МиБ)**. Порядок вызовов (поток Game:Main):

| # | Кто | Allocate(searchStart, searchEnd, len, align, type) → phys | Map(addr, len, prot, flags, phys, align) → addr |
|---|---|---|---|
| 1 | игра | (0, 0x120000000, **0x48000000**, 0x10000, 0) → **0x0** | (0, 0x48000000, **0x03** CPU RW, 0, 0x0, 0x10000) → **0x200000000** |
| 2 | мост (`InitGnmDriverMemory`, загрузчик) | (0, 0x120000000, 0x10000, 0x10000, 3) → **0x48000000** | (0xfe0000000, 0x10000, **0x13** CPU R + GPU R, 0, …, «SceGnmDriver») → **0xfe0000000** |
| 3 | игра | (0, 0x120000000, **0x20000000**, 0x10000, 0) → **0x48010000** | (0, 0x20000000, **0x33** CPU RW + GPU RW, 0, 0x48010000, 0x10000) → **0x248000000** |
| 4 | игра | (0, 0x120000000, **0xb7ff0000**, 0x10000, 3) → **0x68010000** | (0, 0xb7ff0000, **0x33**, 0, 0x68010000, 0x10000) → **0x268000000** |

Игра забирает **всю** direct memory (сумма = 0x120000000): длина 4-го блока = бюджет − конец
предыдущего блока, т. е. игра опирается на **размещение first-fit от младших адресов** и на точный
`GetDirectMemorySize` (G). Дальше игра управляет этими блоками сама; других вызовов памяти нет.

## 3. Жизненный цикл и владение состоянием (как сейчас, мост)

`выделение → отображение → доступ CPU/GPU → изменение защиты → снятие отображения → освобождение`

| Шаг | Что меняется | Владелец (мост) | Кто узнаёт |
|---|---|---|---|
| Allocate | `dmem_map`: Free → Allocated(type) | `Core::MemoryManager` (mutex + unmap_mutex) | никто |
| Map (Direct) | проверка `dmem_map` (Allocated/Mapped, EBUSY при эксклюзивном), поиск VA в `vma_map` (`SearchFree` от `0x200000000`), `dmem_map` → Mapped, VMA с копией физ. участков (`phys_areas`), `AddressSpace::Map` = `MapViewOfFile3` секции-подложки по смещению phys | `MemoryManager` + `AddressSpace` | GPU: `rasterizer->UnmapMemory` **до** (сброс кэшей диапазона), `RegisterMemory` (page manager) и `MapMemory` (набор GPU-видимых диапазонов) **после** |
| Доступ CPU | прямо по VA (тождественное отображение гость = хост) | ОС | — |
| Доступ GPU | buffer/texture cache читают подложку: `TryWriteBacking`, `CopySparseMemory` (через `phys_areas` VMA и `BackingBase`), `IsValidMapping`, `ClampRangeSize` | `MemoryManager` | — |
| Отслеживание записи CPU | page manager ставит защиту страниц (`AddressSpace::Protect`), запись → AV → VEH моста (`signals.cpp`) снимает защиту и помечает страницу | `PageManager` + `AddressSpace` | buffer cache |
| Mprotect | `vma_map.prot`, `AddressSpace::Protect`, затем `InvalidateMemory` (GPU) | `MemoryManager` | GPU |
| Unmap | GPU `UnmapMemory` до, `dmem_map` Mapped → Allocated, VMA → Free, `UnmapViewOfFile2` | `MemoryManager` | GPU |
| Release | поиск VMA, ссылающихся на диапазон, GPU `UnmapMemory`, снятие отображений, `dmem_map` → Free | `MemoryManager` | GPU |

Подложка: одна секция `SEC_COMMIT` размером `ORBIS_KERNEL_TOTAL_MEM_DEV_PRO + 512 МиБ` = 8448 МиБ
(`address_space.cpp`) — commit начисляется **целиком при старте**, независимо от выделений игры
(часть «~8,9 ГБ commit» из SSPC-001). Direct memory — смещения `[0, бюджет)` секции, flexible —
после `TOTAL_MEM_DEV_PRO`. Адресное пространство гостя (всё свободное ниже 1 ТиБ) резервирует
конструктор `MemoryManager` плейсхолдерами — второго владельца того же диапазона быть не может.

Кто ещё пользуется `Core::MemoryManager` в пути `sspc`: наш загрузчик (`loader_host.cpp`: модули,
трамплины, primary TLS, `InitGnmDriverMemory`), потоки моста (`threads\stack.cpp` — стеки в гостевом
пространстве с guard-страницей, `thread_state.cpp` — куча потоков, `pthread.cpp` — имена диапазонов),
`fs_host.cpp`/`file_system.cpp` (`InvalidateMemory` после чтения в гостевую память), GPU-мост
(liverpool, buffer/texture cache, rasterizer, page manager), `gnmdriver.cpp` (`GetAddressSpace`).
Прямых пользователей `dmem_map` вне `memory.cpp` нет; `DirectMemoryQuery`, `GetDirectMemoryType`,
`SetDirectMemoryType`, `Pool*`, `DirectQueryAvailable`, `GetMemoryPoolStats` вызываются только из
одноимённых `sce*`-функций, которые игра не импортирует.

## 4. Дефекты эталона, найденные при аудите (не копируются)

| # | Где | Дефект | Последствие |
|---|---|---|---|
| D1 | `Free` | `phys_addr + size` переполняется (например, `start = 0x4000`, `len = 2^64 − 0x4000`): участки освобождаются до конца бюджета, а поиск отображений (`phys_addr + size > base`) их не находит | освобождённая физическая память остаётся отображённой — порча чужих данных |
| D2 | `Free` | длина снимаемого участка VMA = `min(phys_mapping.size − phys_offset, size)`, без поправки на часть диапазона до начала отображения | снимается больше, чем освобождается |
| D3 | `UnmapBytesFromEntry` | при снятии одного из нескольких отображений одной физической памяти участок становится Allocated, хотя другие отображения живы | следующий эксклюзивный `Map` пройдёт там, где должен быть EBUSY |
| D4 | `Free` | `start == бюджет` и последний участок занят: вырезается участок нулевой длины | неопределённое состояние карты |
| D5 | `Protect` | `ASSERT_MSG(IsValidMapping)` на диапазоне вне карты | `sceKernelMprotect` с плохим адресом роняет процесс вместо кода ошибки |
| D6 | `MapMemory(Flexible)` | проверка бюджета flexible до взятия блокировки | гонка двух выделений |
| D7 | `sceKernelMapNamedDirectMemory` | `!has_single_bit(a) && !Is16KBAligned(a)` — выравнивание, кратное 16 КиБ, но не степень двойки, принимается | условие слабее заявленного в сообщении об ошибке |
| D8 | `sceKernelGetPrtAperture` | нет проверки `address/size` на NULL | падение |
| D9 | `MapMemory` | `total_direct_size < phys_addr + size` переполняется | проверка границы обходится |

D1–D4, D9 относятся к физической direct memory и устранены в нативной реализации P2.3.1 (D9 — в
интеграции `Map` с нативным учётом). D5–D8 — в функциях, оставшихся на мосту (см. §9).

## 5. Объём P2.3.1 (записан до реализации)

**Переносится (группа `kernel-dmem`, экспериментальная):** `sceKernelGetDirectMemorySize`,
`sceKernelAllocateDirectMemory`, `sceKernelReleaseDirectMemory` — физическая direct memory:
кому принадлежит каждый байт `[0, бюджет)`, его тип памяти, сколько виртуальных отображений его
используют. Это законченный набор: выделение и размер бюджета обслуживают реальный сценарий §2
(4 вызова размера, 3+1 выделения), а освобождение нужно, чтобы не было конфигурации «выделил
NATIVE — освободил мост по своей карте».

**Остаются на мосту:** `sceKernelMapDirectMemory`, `sceKernelMunmap`, `mmap`,
`sceKernelMapNamedFlexibleMemory`, `sceKernelMprotect`, `sceKernelQueryMemoryProtection` — их
состояние (vma_map, плейсхолдеры, подложка, защита страниц, уведомления GPU) принадлежит мосту и
им пользуется GPU-мост (класс 2); `msync`, `sceKernelMlock`, `sceKernelGetPrtAperture` — класс 3.
`sceKernelMapDirectMemory` в нативном режиме остаётся BRIDGE, но **физическую** часть (проверку
«выделено ли», эксклюзивность, учёт отображений) берёт у нативного учёта — без второй карты.

**Где состояние.** Единственная карта физической direct memory — `SecondSon::Memory::DirectMemory`
(`src\runtime\memory\direct_memory.{h,cpp}`). В нативном режиме `dmem_map` моста **не
используется**: все его операции (`Allocate`, `Free`, проверка и пометка физических участков в
`MapMemory`, возврат в `UnmapBytesFromEntry`, размер бюджета) идут в нативный учёт через интерфейс
`Core::DirectMemoryBackend` (патч `0007`). Виртуальная сторона (vma_map, плейсхолдеры, подложка,
защита) — по-прежнему только у моста.

**Как узнаёт GPU.** Без изменений: отображение и снятие делает мост, он же зовёт `rasterizer`
в прежнем порядке. Нативный `Release` снимает отображения освобождаемого диапазона через мост
(`MemoryManager::UnmapDirectPhysical`, новый метод патча `0007`): уведомление GPU и снятие вида —
**до** того, как участки станут свободными; пока снятие идёт, участки в состоянии «освобождается» —
их нельзя ни отобразить, ни выделить заново.

**Совместное переключение.** Привязка трёх функций и установка `DirectMemoryBackend` в мост —
один переключатель `--native kernel-dmem`, решение принимается до первого выделения (после
построения таблицы привязок, до загрузчика); бэкенд ставится только на нетронутую `dmem_map`
моста. Конфигурация «нативные функции + карта моста» или «функции моста + нативная карта на
полпути» невозможна. Защита GPU-памяти и VEH не меняются.

## 6. Контракт трёх функций (P2.3.1)

Страница 16 КиБ; все длины и адреса — байты, физические адреса — смещения в direct memory.

**`sceKernelGetDirectMemorySize() → u64`** — бюджет direct memory. Формула (O, константы shadPS4):
всего 5248 МиБ (PS4 Pro 5888; devkit 6656/7936) + `extraDirectMemoryMiB` + `extraFlexibleMemoryMiB`;
−128 МиБ без `extended2` (не Pro), −256 МиБ без `extended1` (Pro); минус flexible из
`SceKernelMemParam` (+ extra flexible). Для игры = `0x120000000` (G). Нативный учёт считает бюджет
сам из `SecondSonPC.toml` и параметров eboot и **сверяет** с результатом моста при старте;
расхождение — отказ запуска экспериментального режима.

**`sceKernelAllocateDirectMemory(searchStart, searchEnd, len, alignment, type, out)`** — порядок
проверок и коды как у эталона (O): `searchStart < 0 || searchEnd < 0` → EINVAL; `len == 0` или не
кратна 16 КиБ → EINVAL; `alignment` не кратно 16 КиБ (0 = 16 КиБ) → EINVAL; `type > 10` → EINVAL;
`out == NULL` → EINVAL; `searchEnd <= searchStart`, `searchEnd < len`, `searchEnd − searchStart < len`
→ EAGAIN; места нет → EAGAIN. Размещение — **first-fit**: наименьший адрес
`AlignUp(max(searchStart, начало свободного участка), alignment)`, с концом ≤ участка и ≤ `searchEnd`
(G: игра этим пользуется). Отличия от эталона: все суммы с проверкой переполнения (огромные
`alignment`/`len` → EAGAIN, без заворота). Выравнивание не степень двойки, кратное 16 КиБ,
принимается, как у эталона (A: на PS4 не проверено). Отрицательный `type` принимается, как у
эталона (A).

**`sceKernelReleaseDirectMemory(start, len)`** — `start` или `len` не кратны 16 КиБ → EINVAL;
`len == 0` → OK; `start > бюджет` → OK (ничего не делает, O). Освобождает **только выделенные**
части `[start, start+len)`, свободные пропускает (O; «checked»-вариант — ENOENT — не импортируется).
Отображения освобождаемых частей снимаются (O, H: на PS4 освобождение снимает отображения),
GPU уведомляется до освобождения. Отличия от эталона: `start + len` с переполнением → **EINVAL**
(D1; эталон освобождает до конца и оставляет отображения); конец обрезается по бюджету (D4);
снимаются ровно пересечения (D2).

**Отображение (через мост, `MapMemory(Direct)` при установленном бэкенде):** каждая страница
`[phys, phys+len)` должна быть выделена (не «освобождается») → иначе ENOMEM, первая
проблемная в порядке адресов (O); граница бюджета с проверкой переполнения (D9) → ENOMEM;
эксклюзивное отображение (SDK ≥ 2.50, без aliasing — так у игры: SDK 4.00) при уже отображённой
странице → EBUSY (O). Отображения считаются **счётчиком на страницу** (D3): `Munmap` одного вида
не делает страницу «неотображённой», пока жив другой вид.

## 7. Архитектура

```
 игра ──► NATIVE sceKernelAllocateDirectMemory / Release / GetDirectMemorySize  (src\runtime\kernel\memory.cpp)
              │                                         ▲
              ▼                                         │ Unmapper::UnmapPhysical (снять виды освобождаемых частей)
   Memory::DirectMemory  (src\runtime\memory)  ◄─── единственная карта физической direct memory
              ▲   BeginMap/EndMap, Allocate, Release, TotalSize
              │   (Core::DirectMemoryBackend, патч 0007; адаптер src\bridge\shadps4\memory_host.cpp)
 игра ──► BRIDGE sceKernelMapDirectMemory / Munmap / mmap / Mprotect … ──► Core::MemoryManager (vma_map,
              AddressSpace, подложка) ──► rasterizer / page manager / buffer+texture cache (как раньше)
```

- `DirectMemory`: упорядоченная карта непересекающихся участков `{база, размер, состояние
  Free/Allocated/Releasing, тип, число отображений}`, покрывающих `[0, бюджет)`; соседние участки с
  одинаковыми атрибутами сливаются. Один `std::mutex` на карту: операции редкие (единицы за
  запуск), глобальной сериализации чужих операций нет — виртуальная сторона живёт под своими
  блокировками моста.
- Порядок блокировок: `unmap_mutex` моста → `mutex` моста → мьютекс `DirectMemory` (самый
  внутренний; `BeginMap`/`EndMap` зовутся под блокировками моста). `DirectMemory` никогда не
  зовёт мост, держа свой мьютекс: `Release` = (1) под мьютексом собрать выделенные части и
  пометить «освобождается», (2) без мьютекса — `Unmapper` (мост: `unmap_mutex` → GPU → `mutex` →
  `EndMap`), (3) под мьютексом — Free. Ошибка `Unmapper` → откат «освобождается» → Allocated с
  прежним типом; если после снятия у части остались отображения — она не освобождается (EBUSY и
  запись в лог): физическую память с живым видом отдавать нельзя.
- `BeginMap` атомарен (проверка всех страниц, затем инкремент) и выполняется в `MapMemory` до
  поиска VA; если поиск VA не удался — `EndMap` (откат). После создания VMA ошибок нет.
- Бюджет: `DirectMemory` создаётся ненастроенным (бюджет 0 — любое выделение → EAGAIN) и
  настраивается один раз в `SetupMemoryRegions` загрузчика, пока нет ни одного выделения.

## 8. Переключатель

- `--native kernel-dmem` — включает экспериментальную группу (новый ключ в стиле `--bridge <группа>`:
  `--bridge` возвращает NATIVE-группу мосту, `--native` включает выключенную по умолчанию).
  Без ключа — **ровно прежнее поведение** (бэкенд не ставится, функции моста, NATIVE 120 / BRIDGE 275).
- Только с `--loader sspc`; `--native kernel-dmem` вместе с `--bridge kernel-dmem` — ошибка запуска.
- Решение до создания ресурсов: бэкенд ставится до загрузчика, на нетронутую `dmem_map` моста
  (иначе отказ запуска); автоматического возврата на мост посреди работы нет.

## 9. Блокеры следующего подэтапа (P2.3.2 — виртуальная память)

Почему `Map`/`Munmap`/`mmap`/flexible/`Mprotect`/`QueryMemoryProtection` не перенесены сейчас:

1. **Один владелец адресного пространства.** Конструктор `Core::MemoryManager` резервирует
   плейсхолдерами всё свободное ниже 1 ТиБ и создаёт подложку; второй менеджер на тех же адресах
   невозможен. Свой менеджер виртуальной памяти должен заменить `MemoryManager` целиком для всех
   его пользователей в пути `sspc` (§3): загрузчик (`loader_host.cpp`), стеки и кучи потоков моста
   (`threads\stack.cpp`, `thread_state.cpp`, `pthread.cpp`), `InvalidateMemory` файловых функций,
   `gnmdriver.cpp`, GPU-мост. Нативный `Map` поверх `vma_map` моста был бы обёрткой над мостом.
2. **Поверхность для GPU** (`TryWriteBacking`, `CopySparseMemory`/`BackingPages`, `ClampRangeSize`,
   `IsValidMapping`, `GetAddressSpace().Protect/GetUsableRegions`, порядок вызовов
   `Rasterizer::UnmapMemory` → снятие → `RegisterMemory`/`MapMemory`) — сначала адаптер
   `MemoryForGpu` (патч `0008`) поверх `MemoryManager` без смены поведения, с прогонами «кадры, VRAM,
   commit как раньше»; только потом его перевод на свой менеджер. **Снято в P2.3.2**: интерфейс
   `Core::GpuMemory`/`GpuMemoryListener` (патч `0008`), `docs\PHASE2_P232_GPU_MEMORY.md`.
3. **Защита страниц делится с отслеживанием записи GPU.** Page manager ставит свою защиту через
   `AddressSpace::Protect`, а `MemoryManager::Protect` гостя пишет защиту страниц напрямую и потом
   зовёт `InvalidateMemory`. Нативный `sceKernelMprotect` требует определённого правила совмещения
   гостевой защиты и защиты отслеживания (сейчас его нет — менять семантику защиты GPU-памяти и VEH
   в этом подэтапе запрещено). Плюс дефект эталона D5 (`ASSERT` на неверном диапазоне).
4. **Неизвестная семантика без наблюдений:** `msync`, `sceKernelMlock` (0 вызовов, у эталона —
   заглушки), апертуры PRT (`sceKernelGetPrtAperture`, 0 вызовов, GPU), бюджет flexible
   (`mmap`/`sceKernelMapNamedFlexibleMemory` у `libc.prx` — 0 вызовов в прогонах). Своего PS4 нет:
   всё, что не наблюдается в игре, — только по эталону (O/H).
5. **Commit подложки.** Секция-подложка `SEC_COMMIT` = 8448 МиБ (бюджет devkit Pro + 512 МиБ)
   начисляется целиком при старте, хотя игре нужно 4608 МиБ direct + flexible. Уменьшить commit можно
   только вместе со своим адресным пространством/подложкой (размер по реальному бюджету или
   `SEC_RESERVE` + commit при выделении) — это возможный выигрыш ~3 ГиБ commit для SSPC-001 (нет
   файла подкачки), но не в P2.3.1: подложкой владеет `AddressSpace` моста.

**Сделано в P2.3.2** (`docs\PHASE2_P232_GPU_MEMORY.md`): п. 2 — адаптер (интерфейс `Core::GpuMemory` +
`Core::GpuMemoryListener`, патч `0008`, без смены поведения). Дальше (план P2.3.3 — там же, §10):
интерфейс для не-GPU пользователей `MemoryManager` в пути `sspc` (загрузчик, стеки и кучи потоков,
функции ядра, `InvalidateMemory`) → свой `AddressSpace` и карта VMA (сначала в самотесте на
отдельном диапазоне выше 1 ТиБ) → `GpuMemory` над своим менеджером (тот же самотест) → переключение
одним экспериментальным ключом → `Map`/`Munmap`/`mmap`/flexible/`Mprotect`/`Query` NATIVE. Включение
P2.3.1 по умолчанию — отдельное решение после ручного подтверждения (§10).
