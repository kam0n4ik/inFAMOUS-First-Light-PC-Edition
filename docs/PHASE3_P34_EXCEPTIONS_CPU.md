# Phase 3 / P3.4 — Native Exception & CPU Runtime

Состояние на 2026-10-10. Основной документ фазы — `docs\PHASE3_INDEPENDENT_RUNTIME.md`; здесь подробности P3.4.
Уровни готовности как там: **написано** → **собирается** → **самотесты прошли** → **проверено в игре** → **по умолчанию**.

## 2. Аудит: путь исключения до P3.4

Порядок векторных обработчиков (первый вызывается первым):

```
FsHandler (свой патчер FS, First=1, только с --native fs-patch)
 → FirstChanceFilter (регистратор SSPC-002, First=1)
 → SignalHandler моста (core/signals.cpp, First=0): DispatchAccessViolation → GuestFaultSignalHandler (GPU-трекинг,
   приоритет 0) → SrtWalkerSignalHandler (1) → PatchesAccessViolationHandler (патчер моста); illegal → патчер моста;
   int3/priv → HandlePatchBreakpoint (0016); иначе g_curthread->DispatchSignal; иначе LOG_CRITICAL + Emulator::Shutdown()
 → DataFaultFilter (поздний регистратор, VirtualQuery)
 → SEH-кадры → CrashFilter (SetUnhandledExceptionFilter)
```

Найденные свойства моста: его VEH завершает процесс на **любом** не опознанном исключении, включая обработанные C++-
исключения и `__try` в коде хоста; сигналы доставляются только потокам моста (`g_curthread`), с `--native threads`
— никогда; `SIG_IGN` для синхронной ошибки возвращал управление на ту же инструкцию (бесконечный цикл).

| Событие | Владелец до P3.4 | Владелец с `--native exceptions` |
|---|---|---|
| FS-доступ (`mov r, fs:[0]`) | патчер моста или свой (P3.3) | свой CPU-патчер через диспетчер (с `--native cpu`), иначе патчер моста через контракт |
| Свой `int3` (запись живого кода) | свой FsHandler | свой CPU-патчер через диспетчер |
| `int3` патчера моста | мост (0016) | мост через контракт (`patch_trap`), только пока он владеет кодом |
| AV GPU-трекинга | мост | **мост** через контракт (`access_violation`) — до Phase 4 |
| AV SRT-walker | мост | мост через тот же контракт |
| Неподдерживаемая инструкция (SSE4a на Intel) | мост | свой CPU-патчер (`--native cpu`), иначе мост через контракт |
| Гостевой сигнал | мост (`g_curthread`) | SecondSonPC (`runtime/kernel/signal.cpp`) |
| Execute-fault | регистратор + мост | диспетчер (тот же регистратор) → сигнал гостя → фатальный путь |
| Фатальное исключение гостя | смесь (мост: лог + Shutdown; процесс часто умирал без отчёта) | SecondSonPC: поток-репортёр, отчёт, минидамп, код выхода = код исключения |
| Исключение в коде хоста (C++, SEH, assert моста) | мост гасил процесс | передаётся дальше (SEH/C++ обработчики, затем CrashFilter) |

## 3. Диспетчер (`src\runtime\cpu\exceptions.*`)

Один VEH SecondSonPC, первый в списке. Порядок для нарушения доступа:

1. **CPU-патчер** — только адреса `< 0x10000` или `≥ 0xFFFF800000000000` (FS-база 0) в зарегистрированном модуле;
2. **execute-fault** (`access == 8` или адрес = rip) — запись регистратора SSPC-002, затем сигнал/фатальный путь;
3. **мост** — `BridgeHandlers::access_violation` = `SignalDispatch::DispatchAccessViolation` (GPU-трекинг, SRT);
   время диспетчера+моста — в гистограмме, счётчик red zone;
4. не решено: гостевой код → сигнал гостя → фатальный отчёт; код хоста в PE-образе → дальше (SEH); прочий код
   (сгенерированный хостом, без unwind-данных) → фатальный отчёт.

`int3/priv`: CPU-патчер → патчер моста (если владеет кодом) → гость SIGTRAP/SIGILL или фатально; хост — дальше.
`#UD`: эмуляция SSE4a → мост → гость SIGILL или фатально. FPU/целочисленные ловушки, in-page, stack overflow: гость
— сигнал/фатально, хост — дальше. Прочее (C++, имена потоков, OutputDebugString) — дальше без изменений.

**Контракт с мостом (патч 0022, `core/signals.{h,cpp}`):** `Core::UseExternalExceptionDispatch(on_remove)` до первого
`Signals::Instance()` — мост не регистрирует свой VEH; его `RemoveHandlers` (сработавший assert моста) вызывает
`on_remove` → диспетчер переходит в режим «всё дальше», чтобы `int3` assert дошёл до фильтра необработанных. Адаптер —
`src\bridge\shadps4\exceptions_host.cpp` (там же замер `--track-stats`, как в обработчике моста).

**Горячий путь** (GPU-трекинг, десятки тысяч AV/с): без системных вызовов, блокировок, выделений и журнала —
сравнения, обработчик моста, relaxed-атомики, два `rdtsc`; для решённых AV в гостевом коде — бит в карте red zone и
разбор `CONTEXT_EX` (`GetXStateFeaturesMask`/`LocateXStateFeature`, без системных вызовов).

**Вложенность:** AV внутри обработчика владельца диспетчеризуется снова до глубины 4 (обработчик моста был
реентерабельным); глубже или любое другое исключение там — фатально («exception inside an exception handler», с
внешним исключением в отчёте). Глубина и внешнее исключение восстанавливаются RAII на любом выходе.

**Статистика** (`Exceptions::GetStats/LogSummary`, строка в журнале с каждым замером VRAM и при выходе): AV/ловушки/
`#UD` по владельцам, вложенные, execute-fault, время обработчика моста P50/P95/P99/max (гистограмма ~19 %), red zone.

## 4. Red zone

**Замер** (самотест `NativeExc(red zone)`, воспроизводимо; Windows 10 19045, Ryzen 5 5500). Функция пишет узор в
`[rsp-1024, rsp)`, вызывает исключение (AV на защищённой странице, решаемое тестовым «GPU-трекингом»), затем
считает нетронутые байты от `rsp` вниз:

| Состояние AVX в момент исключения | Нетронуто ниже `rsp` | Red zone System V (128 байт) |
|---|---|---|
| чистое (маска XSTATE = 3: x87+SSE) | 280–312 байт | цела |
| используется (маска XSTATE = 7: + AVX) | **24–56 байт** | **затёрта на 72–104 байта** |

Механизм: ядро кладёт кадр исключения (CONTEXT, CONTEXT_EX, EXCEPTION_RECORD, область XSAVE) ниже `rsp`; область
XState кончается ровно на `rsp`, а AVX-компонента (старшие половины ymm0–15, 256 байт) пишется, только когда состояние
AVX «в использовании». Тест P3.3 («kept») проверял одно значение `[rsp-8]` и потому ничего не показал.

**Кого касается.** Любого исключения на гостевом потоке в функции, держащей данные ниже `rsp`, при грязном AVX:
- GPU-трекинг моста (запись гостя в защищённую страницу) — **существует и без P3.4**: диспетчер его не создаёт и не
  устраняет;
- запасной путь CPU-патчеров (FS по первому исполнению; с `--native cpu` все 3616 мест патчатся при загрузке — 0
  исключений);
- `#UD`-эмуляция 4-байтовых `extrq` на CPU без SSE4a (Intel).

**Детектор в диспетчере.** Загрузочный проход отмечает функции, которые держат данные ниже `rsp` (операнды `[rsp-N]`
или `[rbp-N]` глубже кадра): в eboot таких **171 из 42 483**. Для каждого решённого исключения в гостевом коде
диспетчер считает: `guest_resolved`, «AVX-область легла на `[rsp-128, rsp)`» (`xstate_over_red_zone`), «rip в функции с
red zone» и оба сразу (`exposed`, первые 8 адресов — в журнал). `exposed` — верхняя граница возможных порч (red zone не
обязательно жива в момент исключения). Значения в игре — §10.

**Защита.** Исправить порчу в обработчике нельзя (данные уничтожены до вызова VEH). Варианты на будущее: статическая
защита red zone (мост имеет выключенный режим `redzone_patches`: инструкции памяти в таких функциях переносятся в
трамплины со сдвигом `rsp`), трекинг без исключений (Phase 4). Необходимость доказывается счётчиком `exposed` в игре.

Нужно хосту: SSE2–SSE4.2, POPCNT, MOVBE, AVX (с сохранением ymm системой), F16C, BMI1, LZCNT; SSE4a — эмулируется.
Проверка при запуске (`Cpu::HostMeetsGameRequirements`) останавливает запуск с перечнем отсутствующего. Нет в игре:
`insertq`, `movntss/movntsd`, скалярные `rcpss/rsqrtss`, 256-битные `vrcpps`.

### 5.2 SSE4a (`src\runtime\cpu\sse4a.*`, загрузочный проход `fs_patcher.cpp`)

| Форма | Мест в eboot | Как исполняется без SSE4a |
|---|---:|---|
| `extrq xmm, xmm` с REX (5 байт) | 23 | `jmp` на трамплин: `rax/rcx/rdx/r8` и флаги сохраняются ниже red zone |
| `extrq xmm, xmm` (4 байта) | 73 | `#UD` → диспетчер → `EmulateInContext` (регистры xmm в CONTEXT, rip += 4) |
| imm-формы, `insertq` | 0 | трамплин |
| `movntss/movntsd` | 0 | на месте → `movss/movsd` (та же запись без подсказки) |

Ни одной записи в исполняемый код: всё при загрузке. «Острова» для коротких мест (короткий `jmp` в межфункциональный
заполнитель) проверены: заполнители — `nop`, в пределах rel8 нет ни одного для 73 `extrq` (для `vrcp/vrsqrt` — 432 из
4296). Семантика — как на Zen 3 (старшие 64 бита приёмника обнуляются всеми четырьмя формами), сверена самотестом с
железом на 13 формах × 400 случайных входов, включая неопределённые по APM (совпали все).

### 5.3 Проверка пути Intel на AMD

`--cpu-emulate sse4a` (только с `--native cpu`): эмуляция включается на CPU, где SSE4a есть; 4-байтовые места
переписываются в `ud2` + `int3`, чтобы ловиться, как на Intel. Это проверка всего пути инструкций игры, **не** проверка
на Intel: другие микроархитектурные различия (RCP, тайминги) так не воспроизводятся.

### 5.4 Не сделано: точность `vrcpps/vrsqrtps` на Intel

Мост на Intel исправлял результаты под AMD (таблицы XOR) только для форм ≥ 5 байт — **87 из 4383** мест; 4296
четырёхбайтовых он оставлял без коррекции. Свой патчер этого не делает (на Intel пишет предупреждение). Полное
покрытие требует переноса соседних инструкций в трамплин с анализом переходов и LSDA — отдельная задача.

## 6. Гостевые сигналы (`src\runtime\kernel\signal.*`)

Импорты игры (libc.prx): `signal`, `sigprocmask`, `_sigprocmask`, `sigfillset`, `sceKernelDebugRaiseException`,
`...OnReleaseMode` — 0 вызовов в записанных прогонах. Группа `exceptions` (только с диспетчером). Таблица действий на
процесс, маска на поток (`thread_local`: один гостевой поток = один поток хоста в обоих менеджерах). Доставка — только
синхронных сигналов от исключений, не решённых в гостевом коде: обработчик гостя на том же потоке с `siginfo`/`ucontext`
PS4 (раскладка моста, `uc_mcontext` по 0x40), маска на время обработчика (`sa_mask` + сам сигнал без `SA_NODEFER`),
возврат — в контекст, оставленный обработчиком (rip, rsp, регистры, пользовательские флаги). По умолчанию, `SIG_IGN`
или заблокирован — действие по умолчанию: фатальный отчёт (FreeBSD тоже не возобновляет такую ошибку).

## 7. Фатальный путь

Поток-репортёр создаётся при установке и ждёт событие. Падающий поток копирует запись и CONTEXT в статическую память
(только `memcpy`), описывает поток (id/имя гостевого потока любого менеджера) — кроме переполнения стека, будит
репортёра и ждёт до 45 с. Репортёр пишет `logs\crash\fatal_<время>_<pid>.txt` (без общей блокировки), затем строки в
журнал, минидамп (один на процесс), сброс журнала моста; падающий поток завершает процесс `TerminateProcess` с кодом
исключения (никакого Shutdown из VEH). Отчёт: код, rip/rsp, модуль+смещение, адрес доступа с описанием, поток (хост и
гость), регистры, стек (чтение без исключений), внешнее исключение при вложенности, счётчики диспетчера, backends,
коммит сборки (`git describe` при configure). Аварийные пути: репортёр не закончил — одна строка в журнал напрямую через
`WriteFile` без блокировок и `TerminateProcess`; исключение на самом репортёре или второй фатал на том же потоке —
то же сразу; второй поток с фатальным исключением ждёт, процесс завершит первый.

* **Регрессии нет, ускорения нет.** Разница `PO1`/`X`/`FX` — внутри разброса одного режима (у `FX` 40,6…41,8 на листве;
  в P3.3 у одного режима 39,3…41,6). Оба прогона `X` на листве ниже обоих `PO1` на ~1 FPS — при двух прогонах на режим
  это не отличается от шума; `FX` (тот же диспетчер) с эталоном совпадает. Для вывода «без потерь» перед режимом по
  умолчанию нужна серия ABBA по 4+ прогона.
* **Диспетчер в игре** (каждый прогон): ~6,1 млн нарушений доступа за 98 с (~62 тыс./с), все решены GPU-трекингом
  моста через контракт; фатальных, переданных дальше, вложенных — 0; с мостовым патчером 3–4 ловушки его протокола
  `int3` решены через контракт. Время диспетчера + обработчика моста: P50 2,0 мкс, P95 11,4 мкс, P99 27–32 мкс, среднее
  4,1–4,4 мкс (почти всё — работа моста; сам диспетчер — сравнения и атомики).
* **Red zone в игре:** из ~5,8 млн решённых исключений в гостевом коде у 190–232 тыс. (3,3–3,9 %) AVX-область легла на
  `[rsp-128, rsp)`, 6,7–7,2 тыс. пришлись на функции, держащие данные ниже `rsp`, **одновременно — 0 во всех 6 прогонах**.
  На этой сцене порча red zone не наблюдалась; риск остаётся для других сцен (§4).
* **Путь Intel (`FXE`):** 23 трамплина, 73 места через исключение — **54,1 млн исполнений за прогон (~550 тыс./с)**.
  Работает без ошибок, но стоит **−6…−7 FPS на старте** (53,1 против 58–60); на листве потерь нет. Так же (эмуляцией в
  обработчике на каждое исполнение) работал и мост на Intel. Вывод: для Intel 4-байтовые `extrq` нужно переписывать в
  трамплины с переносом соседних инструкций, а не ловить исключением; заодно это убирает с них риск red zone (эти
  исключения сейчас в счётчики red zone не входят). Открытый пункт (§11).
* `TMFX` — один прогон: листва 42,8 и commit −3,7 ГиБ (своя память on-demand, как в P3.2/P3.3); для сравнения FPS мало.

## 11. Открытое

1. Серия ABBA ≥ 4 прогонов на режим (`PO1` против `X`/`FX`) — до решения о режиме по умолчанию.
2. Длительная сессия (≥ 30 мин) и ручная игра с `--native exceptions` (вместе с открытой ручной сессией P3.2).
3. Intel: 73 коротких `extrq` — трамплины с переносом соседних инструкций (анализ переходов и LSDA) вместо `#UD`;
   точность `vrcpps/vrsqrtps` (§5.4); проверка на реальном Intel.
4. Red zone: учёт `#UD`-эмуляций в счётчиках; при `exposed > 0` в какой-либо сцене — статическая защита функций с red
   zone (§4).
5. Исключение в коде хоста на гостевом потоке (HLE с плохим указателем гостя) — сейчас SEH/фильтр необработанных;
   отчёт с гостевым контекстом — в P3.6.

## 12. Ревью

Независимое ревью (ecc:cpp-reviewer) коммита диспетчера: критических нет; внесено (коммит `894ec24`): повторный вход
AV в обработчике (мост был реентерабелен), execute-fault на гостевом потоке — гостю (сигнал), RAII глубины, исключения
и сбои репортёра, 256 диапазонов, порядок проверок red zone, атомарная пометка. HIGH «сигналы не подключены» закрыт
коммитом сигналов. Оставлено и описано: исключение в коде хоста на гостевом потоке (HLE-функция с плохим указателем
гостя) передаётся дальше — SEH хоста или фильтр необработанных (раньше мост логировал и завершал процесс).
