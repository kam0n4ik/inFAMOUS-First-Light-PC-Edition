# Нативный draw G-буфера `0x1a1770`: анализ REA, диагностика критического пути и план

Ветка `feature/native-gbuffer-draw` (worktree `E:\SecondSonPC-native-gb`, от `6f28696` + незакоммиченный runtime-набор
из `feature/city-deep-perf`: кольцо CP, emitter, texmemo). Стенд `E:\research\deep_perf`. Push запрещён.

Метки: **[A]** — анализ кода (Ghidra 12.1.4 headless / REA), **[E]** — измерено, **[H]** — гипотеза.
Листинги декомпиляции: `E:\research\native_gb\dec_1a1770.txt`, `dec_14ad0.txt` (запускались с приоритетом Idle, пока на
стенде шли серии v1/v2, на копии проекта `E:\research\native_gb\ghidra` — рабочий проект не трогался).

## 0. Главный вывод (сначала — потому что он меняет цель)

**В целевом режиме «front+emit, ring 128» подготовка draw G-буфера `0x1a1770` НЕ лежит на критическом пути, и её
нативизация сама по себе FPS в городе не поднимет.** Критический путь здесь — поток записи Vulkan (T2). Это измерено
(§3) и совпадает с тем, почему прошлые нативные пути G-буфера (R7-Core C3, `SSPC_CITY_ENGINE_RESOURCES`) дали −1,57 и
−6 FPS: они меняли транспорт draw, но не объём работы T2.

Нативный путь, который реально сократит кадр в этом режиме, должен снимать работу с **T2** (запись draw + BindStage) или
с **T1** (разбор PM4 — SET_SH_REG user data), а не с потока фронтенда, у которого уже ~5,9 мс простоя за кадр.

Поэтому ниже: (1) полный разбор `0x1a1770` через REA, (2) диагностика с числами, (3) конкретный нативный путь, который
бьёт по T2/T1, с режимами verify/guarded/native. Сборка, verify и A/B — следующий шаг, он не выполнялся в этот заход:
стенд был занят сериями v1/v2 (сборка во время замеров запрещена — испортит их FPS). Числа FPS здесь не приводятся,
пока прогон реально не сделан.

  адресам. Переанализ не нужен: функции и дерево вызовов уже в базе.

## 2. `0x1a1770` — что это и вся цепочка ресурсов [A]

`0x1a1770(rdi M материал, rsi R контекст, rdx records записи экземпляров, ecx n, r8 mesh)` — инстанс-draw прохода
мешей G-буфера (CITY-OPT Phase 6). Декомпиляция (`dec_1a1770.txt`) слово в слово совпала с реконструкцией
`src/native_engine/reconstructed/gbuffer_draw.h` (R6-G, GAME_VERIFIED). По порядку:

1. **Stencil** (`M+0x1c` low byte != 0): считает значение `v`, и если `v != u32 R+0xde64` — пишет 4 байта
   `R+0xde64..` и зовёт `0x6229a0(R+8, v)` → `SET_CONTEXT_REG 0x10C` (DB_STENCILREFMASK). Единственная собственная
   запись функции в память — эти 4 байта.
2. `0x120280(R)` — фиксация констант кадра (когда «грязно»).
3. (`M+0x135 != 0xff`) V# = `0x45f590(eboot+0x7dff738, …)`; при `M+0x13c != 0xff` — `0x16b70(R+0x128, 2, M+0x13c, 1,&V#)`.
4. **V# записей экземпляров**: `0x61e260(&V#, records, 0xd4, n)` строит V# буфера записей (шаг `0xd4`, `n` штук); затем
   `0x16b70(R+0x128, 0x27530(0), M+0x127, 1, &V#)` — в слот VS-таблицы CUE.
5. **Вершины**: `0x16aa0(R+0x128, 2, 0, mesh+0x6c (u8 потоков), mesh+0x60 (таблица V#))` — таблица вершин VS.
6. `0x6250b0(R+8, n)` NUM_INSTANCES; `0x623740(R+8,4)` список треугольников; `0x624f80(R+8,0,2)` 16-битные индексы;
   опц. `0x628ae0` debug-маркер.
7. **Commit CUE** `0x14ad0(R+0x128)` — ключевой (§2.1).
8. `0x623c60(R+8, mesh+0x68 индексов, mesh+0x58 база, 0)` — `DRAW_INDEX_2` + 4-словный trailing NOP (сюда CITY-OPT
   Phase 6 кладёт свою метку, `draw_runs.cpp`).

Материал ставит **не** `0x1a1770`, а `0x448640(pass, R, material)` ДО него (зонд `ProbeMaterial`), и только при смене
материала: `D = [M+0x28]`; константы материала `0x169d0(cue,1,13,1,D)` и для стадии 2; семплеры `0x16eb0`; текстуры
`0x16d10` (их число — поля прохода `P+0x6c`/`P+0x80`). То есть **PS-дескрипторы draw — это память материала `[M+0x28]`,
а не что-то, что надо обходить**.

### 2.1 Почему обход SRT повторяется на каждом draw [A, подтверждено `dec_14ad0.txt`]

`0x14ad0` (commit CUE) для каждой «грязной» стадии (`flags R+0x128+0xc1c*`): берёт блок из кольца кадра
`FUN_000123d0(cue, dwords)`, `memcpy` копирует туда теневую таблицу стадии (`cue+0x4890` для стадии 3/VS, `cue+0x6090`
для 4/PS, `cue+0x9090` для 6), и `FUN_00626400(cue+0xc090, stage, slot, →новая копия)` пишет в user data шейдера
**указатель на новую копию**. Указатель таблицы ресурсов в user data **меняется на каждом draw**. Для CP такой draw —
«другие user data» → обход SRT никогда не переиспользуется по совпадению регистров (это и показали 0 попаданий в
`SSPC_CITY_ENGINE_RESOURCES`, `CITY_ENGINE_RESOURCES.md §5.1`).

**Вывод для нативизации:** весь роундтрип «engine пишет дескрипторы в user data → CUE копирует таблицу → PM4 несёт
указатель → фронтенд обходит SRT, чтобы восстановить дескрипторы» существует, чтобы заново получить то, что движок уже
держал в руках в `0x1a1770`: материал `[M+0x28]`, V# экземпляров (`0x61e260`), таблицу вершин (`mesh+0x60`), константы
объекта. Нативный путь должен строить `ResourceBindingPlan` VS/PS **из этих структур**, а не обходить скопированную
теневую таблицу.

## 3. Где кадр стоит в режиме front+emit (ring 128/2048) [E]

R8-профиль `E:\research\deep_perf\runs\d2_ring\proffemit2048_1\gpu_native.txt`, окно города 70..148 с, 2489 кадров,
пресет + `SSPC_P53_FRONTEND_THREAD=1 SSPC_VK_EMIT_THREAD=1`:

| Поток | busy, мс/кадр | idle | самое дорогое |
|---|---|---|---|
| T1 `GpuNative` | 30.70 | 0.00 | **wait: queue full 16.43** (back-pressure от T2); PM4 decode+BuildDraw 11.25 (из них SET_SH_REG VS user data 2.92, decode 2.45) |
| **T2 `GpuRecord`** | **30.44** | **0.26** | draw records 12.61; **BindStage 9.50**; run members 3.45; ApplyJournal 1.70 |
| фронтенд `GpuFrontend` | 24.76 | **5.93** | PrepareDraw G-буфер `0x1a1770` **5.93**; «прочее» 5.29; mesh `0x1a1960` 3.93; CopyStage 2.75; shadow 2.26 |

Чтение: **T2 (30.44 мс busy, простой 0.26) — стена кадра.** T1 32 мс из них 16.4 просто ждёт, пока T2 разгребёт очередь.
Фронтенд свои 24.76 мс делает и **5.93 мс простаивает** — ровно столько же, сколько стоит подготовка G-буфера. Если
убрать подготовку `0x1a1770` с фронтенда, его простой вырастет до ~11.8 мс, а кадр (определяемый T2) не изменится.

Это и есть причина, по которой нативный `0x1a1770`, снимающий работу только с фронтенда, не поднимет FPS — и почему
C3/ENGINE_RESOURCES были нейтральны/хуже. Чтобы кадр сократился, надо снять работу с **T2** (запись draw 12.6 +
BindStage 9.5) или с **T1** (SET_SH_REG VS user data 2.9 + decode 2.4).

Доля именно `0x1a1770` в T2: по счётчикам R6 `0x1a1770` ~1766 вызовов / 6460 экземпляров на кадр против ~11 917 всех
draw-записей T2; большинство записей T2 — mesh `0x1a1960` (~4340) и тени `0x43d480`. Значит идеальная нативизация
`0x1a1770` касается меньшей части T2. **Для сокращения T2 рычаг выше у `0x1a1960`/`0x43d480`** — это важно для порядка
работ (см. §6), хотя пользователь зафиксировал начать с `0x1a1770`, и мы его меряем первым.

## 4. Нативный путь, который бьёт по T2/T1 (а не по фронтенду)

Идея: для draw, помеченных зондом `0x1a1770` (`Source::GBuffer`, `draw_runs.cpp` уже ставит метку), **строить
`ResourceBindingPlan` VS и PS напрямую из аргументов движка** и класть его как готовую подготовку, так чтобы:

- **T2 BindStage** получал пребилт-план без чтения теневой таблицы по поменявшемуся указателю (сейчас BindStage читает
  `plan.buffers/images/samplers`, уже полученные обходом; но сам обход на фронтенде — это 5.9 мс, и пребилт его убирает
  для доли G-буфера; BindStage по готовому плану дешевле, когда план переиспользуется между кадрами без копий —
  §4.2);
- **фронтенд** не обходил SRT для этих draw (снимает часть 5.9 мс — но это не главный приз, см. §0);
- **T1**: план кэшируется по идентичности движка (ниже), поэтому SET_SH_REG user data этих draw можно не декодировать в
  дескрипторы (экономия на T1 — цель, measurable).

### 4.1 Ключ — идентичность движка, а не байты снимка

Существующий P5.3 Native Render Frontend (`NativeStages`, `shader_frontend.cpp`) уже умеет пропускать обход, но ключует
по **байтам снимка в памяти гостя**; из-за per-frame аллокаций CUE (§2.1) первый dword каждой 4-словной группы —
адрес — меняется каждый кадр, и кэш мимо (`native_miss_word0` в статистике фронтенда). **Нативный ключ —
`(program, mesh, material, pass)`** (идентичность, которую движок даёт в `0x1a1770`): для одного меша+материала план VS/PS
между кадрами постоянен, кроме нескольких per-draw полей:

- V# записей экземпляров (адрес/размер из `0x61e260`, меняется — это кадровый буфер);
- V# таблицы вершин (`mesh+0x60`) — постоянен для меша;
- буфер констант объекта — меняется.

План строится один раз на `(mesh,material)` и переиспользуется, патчатся только эти поля. Это снимает обход (95 % чтений
PS по §4 `CITY_ENGINE_RESOURCES.md` — статичны для материала) по-настоящему, а не перекладывает его.

### 4.2 Расположение кода (НЕ трогая `shader/*`)

`src/runtime/gpu/shader/*` — запретная зона (общий кэш шейдеров `E:\SecondSonPC\cache\shaders`). Поэтому:

- Новый модуль `src/native_engine/reconstructed/gbuffer_native_prep.{h,cpp}` — строит/кэширует `ResourceBindingPlan`
  VS/PS из `(M,R,records,n,mesh)` + рефлексии модуля (которую даёт фронтенд: биндинг→слот). Рефлексию и трансляцию
  берём готовыми у фронтенда (это не правка фронтенда — только чтение его `Program/Module`).
- Точка входа — в `ParallelCp::PrepareDraw` (`parallel_cp.cpp`, не `shader/*`): если `r.draw.engine_run==GBuffer` и
  план в кэше — заполнить `r.stage/r.ps/r.prep` из кэша вместо `frontend_->PrepareDraw`. На промахе — обычный путь +
  построить план из рефлексии и дескрипторов движка, положить в кэш.
- Дескрипторы движка берём из уже реконструированных структур: материал `[M+0x28]` (как `material_bind.h`), V#
  экземпляров (`gbuffer_draw.h`, `0x61e260`), вершины (`mesh+0x60`).

### 4.3 Режимы (env `SSPC_NATIVE_GBUFFER=verify|guarded|native`, по умолчанию off)

- **verify** — строить нативный план и одновременно обычный (фронтенд), сравнивать поле в поле: `flat`, `buffers`
  (binding/kind/desc.raw/address/size/written/formatted/status), `images`, `samplers`, `vertices`, `status_counts`,
  порядок; расхождения — в лог. Используется обычный план (нативный только сверяется).
- **guarded** — использовать нативный план, но на любом несовпадении инвариантов (материал нулевой, предикация, не тот
  DCB, не воспроизводимый commit) безопасно падать на обычный путь. Счётчики откатов.
- **native** — нативный план без сверки.

Порядок команд проверяется так же, как C3 (`native_render_layer`): нативный draw не вызывает функцию игры повторно.

## 6. Что это значит для `0x1a1960` и порядка работ

Если §5 подтвердит прогноз, следующая нативизация должна целиться в **T2**: mesh-draw `0x1a1960` (~4340 записей/кадр,
3.93 мс на фронтенде + основная масса записей T2) и тени `0x43d480`. Там же — пребилт descriptor writes для BindStage из
данных движва (BindStage 9.5 мс — вторая по величине статья T2). Нативный `0x1a1770` остаётся нужным как часть
самостоятельного пути рендера (цель порта), но для FPS в этом режиме рычаг — T2.
