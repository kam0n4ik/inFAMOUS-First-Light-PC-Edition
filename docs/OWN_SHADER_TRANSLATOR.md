# Свой переводчик шейдеров GCN → SPIR-V (Phase 4, отказ от shader_recompiler моста)

Цель — заменить переводчик моста (`third_party/shadPS4/src/shader_recompiler`, ~32 тыс. строк) своим кодом в
`src/runtime/gpu/gcn`, не меняя бэкенд. Свой переводчик реализует тот же интерфейс `Gpu::Shader::ShaderTranslator`
(`src/runtime/gpu/shader/shader_translator.h`) и включается **по программе**: что он переводит — его, остальное — мосту,
пока покрытие не станет полным.

## 2. Контракт с бэкендом (что должен выдавать свой SPIR-V)

Бэкенд строит раскладки и привязки по `ShaderReflection` и `ResourceBindingPlan` (`shader_resources.*`,
`vk_pipelines.*`), сделанным по образцу моста. Поэтому свой модуль обязан:

* **push-константы** — блок `PushData` моста байт в байт (72 байта: `xoffset, yoffset, xscale, yscale`, `buf_offsets[56]`);
* **пользовательские данные** (SGPR user data и то, что скопировал SRT-обход) — читать из буфера вида `Flatbuf`
  (`BufferKind::Flatbuf`), первые 16 dword — регистры user data;
* **привязки** — одна descriptor set, сквозная нумерация от `BindingStart` стадии: буферы, затем образы, затем семплеры
  (как `ResolveResources`); виды буферов (`Guest`, `Flatbuf`, `SharedMemory`, …) и пост-операции — те же значения;
* **входы/выходы** — те же location (атрибуты вершин из fetch-шейдера, интерполянты по `SPI_PS_INPUT_CNTL`, экспорт MRT
  по `col_format`), те же вспомогательные стадии для RECT/QUAD list;
* **отражение** — тот же состав `ShaderReflection` (ресурсы с `SharpLocation`, `mrt_mask`, `user_data_used`, …).

**SRT-обход.** Мост генерирует для него x86-код, а рантайм SecondSonPC его интерпретирует (47 форм). Свой переводчик
описывает обход своим форматом (список загрузок: откуда — регистр user data или уже скопированный dword, смещение, сколько
dword, куда во flat), а `ResolveResources` получает его вместо x86. Формат — следующий шаг этапа 4.

## 3. Модель исполнения (как GCN ложится на SPIR-V)

* Одна линия волны = один вызов SPIR-V. SGPR — значения, одинаковые во всех линиях; VGPR — свои у каждого вызова.
* **EXEC** — булево значение линии («линия активна»); векторные инструкции выполняются под условием EXEC (блоки
  `if (exec)` по участкам между записями EXEC; в начале программы EXEC = true, условие не нужно).
* VCC и 64-битные маски сравнений — тоже булевы значения линии; где нужна маска всей волны (SCC от 64-битной операции над
  маской, `s_bcnt1`, `s_ff1`, `v_readfirstlane`) — операции подгруппы (`OpGroupNonUniform*`).
* Переходы `s_cbranch_*` по SCC — однородные; по VCC/EXEC — по значению линии (неактивная линия и так пропускает код).
* Структура: заголовки циклов/ветвлений и merge-блоки — по `gcn_structure`; две правки графа (свой merge для вложенных
  if, копия хвоста перед `s_endpgm`).

## 4. Проверки

* каждый модуль — `spirv-val` (`E:\VulkanSDK\Bin\spirv-val.exe`, `--target-env vulkan1.3`);
* офлайн по захвату трансляций моста (`--gpu-shader-verify`, 619 модулей): одинаковое отражение и интерфейс;
* в игре: A/B-снимки сцен со своим переводчиком для набора программ против моста, побайтовое сравнение кадров.

## 5. Порядок работ

1. Генератор SPIR-V (`spirv_builder`): типы, константы, переменные, функции, блоки, декорации; тест — модуль проходит
   `spirv-val`.
2. Каркас трансляции compute-программы без ресурсов: SGPR/VGPR как переменные функции, структура, EXEC-предикаты.
3. ALU по частоте (`GCN_INVENTORY.txt`), затем SMRD/буферы/flat и свой формат SRT-обхода, образы/семплеры, LDS, экспорт и
   интерполяция, атрибуты вершин.
4. Включение по программе за флагом, A/B в игре, затем по умолчанию; переводчик моста — только эталон.
