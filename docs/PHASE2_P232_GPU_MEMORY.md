станут свободными (в нативном режиме страницы в это время в состоянии «освобождается»).

### 2.3. Скрытые зависимости

| # | Зависимость | Следствие для другого менеджера |
|---|---|---|
| H1 | **Тождественное отображение**: GPU-код разыменовывает гостевые адреса как адреса хоста — Liverpool читает PM4 и косвенные буферы, пишет `*event_eos->Address()` (GDS), `Rasterizer::FillBuffer/CopyBuffer` (`std::fill`/`memcpy` по гостевым адресам), хэширование в `texture_cache.cpp:126/728` | гость = хост по адресам; страницы, видимые гостю, читаемы хостом (запись в отслеживаемые — через AV в VEH) |
| H2 | **Указатели в подложку** (`backing_base + phys`) действительны всё время процесса: вся секция отображена одним видом, всегда RW(X). Через него пишут мимо защиты (`TryWriteBacking`) и читают без блокировок (`CopySparseMemory`) | нужен постоянный RW-вид всей физической памяти (или иной способ записи мимо защиты) |
| H3 | Таблица страниц подложки покрывает только адреса < 2^40 и только отображения с физической основой (direct/flexible/pooled). Анонимная память (`phys = −1`: модули, стеки, Code/Stack/System) в ней не видна: `CopySparseMemory` читает **нули**, `TryWriteBacking` возвращает false (Liverpool сделает `ASSERT`) | то же правило, либо осознанное изменение отдельным этапом |
| H4 | `TryWriteBacking` копирует VMA (вместе с `std::map` и `std::string`) в `std::vector` под shared-блокировкой — выделение памяти, возможно внутри VEH (G4) | не менялось; в своём менеджере — без выделений |
| H5 | `IsValidMapping` (ASSERT в `TryWriteBacking`/`ClampRangeSize`) проверяет только попадание в весь управляемый диапазон: свободные области «валидны» | — |
| H6 | `MemoryManager::rasterizer` ставится один раз конструктором растеризатора и не снимается; map до создания растеризатора разыменовал бы null. В пути `sspc` GnmDriver стартует до загрузчика (`StartBridgeLibraries` → `RunSspcLoader`) | порядок старта: слушатель — до первого отображения |
| H7 | Защита страниц общая у гостя и отслеживания: `MemoryManager::Protect` пишет защиту напрямую, затем `sceKernelMprotect` зовёт `InvalidateMemory` — согласованность держится на этом порядке | правило совмещения — до переноса `Mprotect` (P2.3.3+) |
| H8 | `Rasterizer::mapped_ranges` — копия «какие диапазоны видит GPU», живёт только за счёт уведомлений N1/N3 (не периодическая синхронизация) | уведомления обязаны быть полными |
| H9 | `SetPrtArea` объявляет GPU-видимой всю PRT-область без отображения («pretend»); дыры читаются нулями через `CopySparseMemory` | — |
| H10 | `MemoryMapViewer` (devtools, friend `MemoryManager`) и `SecondSonMemoryAccess` (патч `0007`, наша диагностика) читают `vma_map`/`dmem_map` напрямую | не GPU; отладочный UI и самотест |

## 3. Контракт интерфейса (`third_party\shadPS4\src\core\gpu_memory.h`, патч `0008`)

### 3.1. GPU → память: `Core::GpuMemory` (получение — `Core::GetGpuMemory()`)

| Метод | Семантика (ровно как у моста) | Срок результата | Синхронизация | Можно из VEH |
|---|---|---|---|---|
| `IsValidGpuMapping(addr, size)` (static, constexpr) | `addr + size < 2^40`, без проверки переполнения (D10) | — | нет | да |
| `ClampRangeSize(addr, size)` (невиртуальный) | `size < 1 ГиБ` → `size` **без поиска** (ранний выход перенесён в интерфейс: горячий путь); иначе — остаток области, содержащей `addr` (учитывается, даже если она свободна), плюс идущие следом отображённые области; свободная или зарезервированная область останавливает. `addr` вне управляемого диапазона — ASSERT | **снимок**: недействителен после следующего map/unmap | shared-блокировка менеджера (только для ≥ 1 ГиБ) | нет (не вызывается оттуда) |
| `CopySparseMemory(addr, dst, size)` | по страницам 16 КиБ: есть физическая основа → копия из подложки, нет → нули; `size == 0` — ничего; `addr + size ≤ 2^40` (D12) | копия; гонка с unmap — устаревшие данные, не падение | **без блокировок** | не вызывается |
| `TryWriteBacking(addr, data, size)` | ASSERT, что диапазон внутри управляемого; собирает подряд идущие области с физической основой начиная с `addr` и пишет в подложку мимо защиты; первая область без основы → `false`; частично покрытый диапазон — пишется покрытое начало, `true` (D11) | синхронно; адрес не защищён от одновременного unmap (G10) | shared-блокировка менеджера; выделяет память (H4) | **да** (G4, поток GPU) |
| `ProtectTracking(addr, size, perms)` | защита хоста `None/Read/ReadWrite` (Write-only отвергает вызывающий) на **отображённых** частях диапазона, заглушки пропускаются; гостевая защита (`vma.prot`) не меняется; execute снимается (как раньше) | — | только внутренний мьютекс `AddressSpace` (лист) | **да** (G16): без выделений, логов и новых системных вызовов, кроме прежнего `VirtualProtectEx` |
| `SystemReservedEnd()` | конец system reserved области (`0x1000000000` на Windows) | константа | нет | — |
| `SetListener(listener)` → прежний | кто получает уведомления; ставит растеризатор один раз до гостя; не синхронизирован с операциями памяти (смена — только на старте или в самотесте без параллельных отображений) | — | — | — |

Внутренние контейнеры (`vma_map`, `dmem_map`, `AddressSpace`, таблица страниц) наружу не отдаются.
Единственные «сырые» указатели, которые видит GPU, — гостевые адреса (H1) и, внутри адаптера,
указатели в подложку (H2), живущие весь процесс.

### 3.2. Память → GPU: `Core::GpuMemoryListener` (реализует `Vulkan::Rasterizer`)

| Метод | Когда | Держится | Слушателю нельзя |
|---|---|---|---|
| `OnGpuUnmap(addr, size)` | **до** изменения адресного пространства (map поверх, unmap, освобождение физической памяти — для каждого вида; PRT) | `unmap_mutex`; writer-блокировка **не** держится. Исключение — PRT (`SetPrtArea`): `OnGpuUnmap`/`OnGpuMap` вообще без блокировок (так было и до патча; игра PRT не использует) | отображать/снимать (deadlock на `unmap_mutex`); запросы `GpuMemory` (shared) — **можно**: так растеризатор выгружает данные |
| `OnGpuRegister(addr, size)` | после отображения хост-страниц и после их снятия (с объединённым диапазоном заглушки) | `unmap_mutex` + writer-блокировка | брать shared-блокировку менеджера (`TryWriteBacking`, `ClampRangeSize ≥ 1 ГиБ`) — deadlock |
| `OnGpuMap(addr, size)` | после создания области, writer-блокировка уже отпущена | `unmap_mutex` | отображать/снимать |
| `OnGuestWrite(addr, size)` | хост пишет в гостевую память мимо отслеживания (`mprotect`, чтение файла) | блокировок памяти нет | — |

Порядок одной операции: `OnGpuUnmap` → `OnGpuRegister`(ы) → `OnGpuMap`; освобождение: все
`OnGpuUnmap` видов → снятие видов (`OnGpuRegister`) → страницы свободны. Порядок блокировок не
изменился: `unmap_mutex` → `mutex` (writer) → мьютекс `AddressSpace` → мьютекс нативной
`DirectMemory` (самый внутренний, P2.3.1); page manager: `locks[page]` → мьютекс `AddressSpace`.
Адаптер своих блокировок не берёт и обратных вызовов под блокировками не добавляет — новых рёбер в
графе блокировок нет.

**Отсутствующие и частично покрытые диапазоны:** `CopySparseMemory` — нули за пределами
отображений; `TryWriteBacking` — `false`, если начало без основы, иначе запись покрытого начала;
`ClampRangeSize` — до первой свободной/зарезервированной области; `ProtectTracking` — только
отображённые части. Unmap/release одновременно с чтением: `CopySparseMemory` дочитывает подложку
(устаревшие данные, без падения), `TryWriteBacking`/`ClampRangeSize` сериализованы с изменением
карты shared/writer-блокировкой.

### 3.3. Способ вызова и цена

`GpuMemory` — абстрактный класс с виртуальными методами: в следующем подэтапе тот же exe должен
переключаться между менеджером моста и своим (как `--native kernel-dmem`), значит выбор
реализации — во время выполнения. Горячее и тривиальное оставлено невиртуальным: `ClampRangeSize`
для < 1 ГиБ (инлайн-ранний выход — подавляющее большинство вызовов) и `IsValidGpuMapping`
(`static constexpr`). Потребители кэшируют `GpuMemory*` (буферный кэш, растеризатор) или берут
глобальный объект (`GetGpuMemory()` — возврат ссылки на глобальный объект).

Замер в самотесте (нс на вызов, лучшее из 3, 1 млн вызовов; строка `INFO GpuMemory(perf)`):

| Вызов | Менеджер напрямую | Через `GpuMemory` |
|---|---:|---:|
| `CopySparseMemory` 64 Б | 6,8 | 7,8 |
| `ClampRangeSize` < 1 ГиБ | 2,83 | 1,42 |
| `ProtectTracking` 16 КиБ (`VirtualProtectEx`) | 478–493 | 485–501 |

+1 нс на копирование: даже при 1 млн вызовов в секунду это 1 мс CPU в секунду (0,1 % ядра);
+≈5 нс при ~490 нс системного вызова на `ProtectTracking` — в пределах шума (даже если бы каждое из
~55 тыс. нарушений доступа в секунду меняло защиту — ≈ 0,3 мс CPU в секунду). Игровые прогоны — §7.

## 4. Модель владения

- **Виртуальное состояние** (`vma_map`, плейсхолдеры, подложка, защита) — по-прежнему единственный
  владелец `Core::MemoryManager` моста. Второй карты нет; адаптер `BridgeGpuMemory` (в
  `memory.cpp`) **не хранит состояния** и только пересылает вызовы публичным методам менеджера.
- **Физическая direct memory** — как в P2.3.1: по умолчанию `dmem_map` моста, с `--native
  kernel-dmem` — `Memory::DirectMemory` (патч `0007`). Интерфейс GPU её не касается: GPU видит только
  виртуальную сторону и подложку.
- **GPU-состояние** (`mapped_ranges`, буферный/текстурный кэш, page manager) — растеризатор; узнаёт
  об изменениях только через `GpuMemoryListener`.
- Слушатель живёт до конца процесса (растеризатор не отписывается — как и раньше).

  анонимной памяти — `false`; через два физических участка — **D11 воспроизведён** одинаково через
  интерфейс и напрямую. `ProtectTracking` на диапазоне с дырой: меняются только виды, гостевая
  защита (`sceKernelVirtualQuery`) прежняя, результат = `AddressSpace::Protect`.
- **Переполнения.** `IsValidGpuMapping` на краях 2^40 и с переворотом суммы (D10) — явный список
  ожидаемых значений; `SystemReservedEnd` = `0x1000000000`, кольцо тесселяции = `0xff0000000`.
- **Сроки действия.** После unmap C: `ClampRangeSize` короче, C читается нулями и не пишется (ничего
  не кэшируется); после повторного отображения — прежние физические данные.
- **Порядок уведомлений** — запись последовательности: слушатель-регистратор между менеджером и
  растеризатором фиксирует для каждого уведомления, закоммичена ли страница у хоста
  (`VirtualQuery`), держится ли writer-блокировка (`try_lock_shared`), состояние физической страницы
  (нативная карта: свободна/выделена/освобождается; `dmem_map` моста) и успешен ли запрос `GpuMemory`
  из уведомления; затем пересылает растеризатору. Проверено: map (unmap до → register под
  блокировкой → map после), `mprotect` (одно `OnGuestWrite` на всю страницу 16 КиБ), `munmap`
  половины, Fixed-map поверх вида (4 уведомления), освобождение (NATIVE и BRIDGE): GPU узнаёт о виде,
  пока он отображён и страницы ещё не свободны («освобождается» в нативном режиме), свободны —
  только после.
- **Конкурентность и deadlock.** 5 потоков: map/unmap рядом с видом, гостевой `mprotect` этого вида
  (защита + `OnGuestWrite`), 3 потока GPU-запросов (`CopySparseMemory` с проверкой каждого байта,
  `ClampRangeSize ≥ 1 ГиБ`, `TryWriteBacking`, `ProtectTracking`); сторожевой таймер 90 с (при
  зависании — отчёт и `quick_exit(5)`). Ошибок и зависаний нет, вид цел и виден GPU.
- **Оба режима физической памяти** — весь сценарий в `GpuMemory(int)` (мост) и `GpuMemory(dmem)`
  (нативная карта; установка и возврат на мост проверяются).
- **Проверка самих тестов (мутации, затем откат по SHA-256):** (1) `OnGpuUnmap` в `MapMemory` под
  writer-блокировкой → падают «map» и «Fixed map» в обоих режимах; (2) `UnmapDirectPhysical`
  уведомляет GPU после снятия видов → падают только 2 проверки нативного освобождения (прежняя
  группа `KernelDmem(int)` этого **не** ловила); (3) адаптер без обрезки → 3 проверки `ClampRangeSize`
  в обоих режимах. Итого 12 падений, каждое — в своей проверке.
- **Независимое ревью** (отдельный агент, только чтение патча, тестов и контракта): критичных и
  серьёзных дефектов, изменения поведения и проверок, которые не могут упасть, не найдено.
  Исправлено по замечанию: в контракте (`gpu_memory.h`, §3.2) уточнено, что PRT (`SetPrtArea`)

## 9. Commit подложки 8448 МиБ: из чего состоит и что мешает уменьшению

**Устройство.** `AddressSpace::Impl` (мост) при старте создаёт одну секцию на файле подкачки
`CreateFileMapping2(…, SEC_COMMIT, BackingSize)` и отображает её целиком в `backing_base` (это и
есть постоянный RW-вид H2). `BackingSize = ORBIS_KERNEL_TOTAL_MEM_DEV_PRO (7936 МиБ) +
ORBIS_KERNEL_FLEXIBLE_MEMORY_SIZE (512 МиБ)` (+ extra из настроек, у нас 0) = **8448 МиБ**.
`SEC_COMMIT` начисляет весь размер в commit системы в момент создания секции, независимо от того,
что потом выделит игра; в «Private Bytes» процесса это не видно (секция разделяемая) — только в
commit системы. Физическая RAM расходуется только на тронутые страницы.

**Подтверждение по данным P2.3.1** (`logs\performance\p231_mem\M0_1`): commit системы на старте
сессии ≈ 13,9 ГиБ (31,9 − 18,3 свободно), через 1,1 с после запуска процесса — 23 906 МиБ при
private процесса 1 386 МиБ: ≈ 8,6 ГиБ commit появляются до первых выделений игры (они видны на 4-й
секунде) и не принадлежат private процесса — это секция (8448 МиБ) плюс шум остальных программ.

**Какие диапазоны секции нужны игре** (карта `--memory-map 45`, `p231_smoke`, оба прогона
одинаковы):

| Смещение в секции | Что | Объём | Используется |
|---|---|---:|---|
| `[0, 0x120000000)` | direct memory (бюджет игры 4608 МиБ) | 4608 МиБ | **вся**: 3 блока игры + 64 КиБ SceGnmDriver, все отображены |
| `[0x120000000, 0x1f0000000)` | direct сверх бюджета игры (до 7936 МиБ devkit Pro) | 3328 МиБ | нет (после `SetupMemoryRegions` бюджет урезан) |
| `[0x1f0000000, +0x1c000000)` | flexible (бюджет 448 МиБ) | 448 МиБ | 130 МиБ (сегменты модулей: `eboot.bin`, PRX — тип flexible, физ. `0x1f0000000…0x1f8230000`) |
| `[0x20c000000, 0x210000000)` | хвост flexible-области (512 − 448) | 64 МиБ | нет |

Итого используется ≈ 4738 МиБ, закоммичено и не используется этой игрой ≈ **3710 МиБ** (по
состоянию на 45-ю секунду в лесу). Файловые отображения (174 МиБ), анонимная память модулей
(code 24 МиБ) и стеки (7 МиБ) в секцию не входят. Это **оценка устройства**, не обещание
экономии: разница двух чисел не учитывает, что commit может быть нужен в другой момент игры
(flexible растёт при загрузках?), и что другой способ подложки имеет свою цену.

**Что мешает уменьшить сейчас.**
1. Секцией владеет `AddressSpace` моста, она создаётся в конструкторе `MemoryManager` — **до**
   того, как известен бюджет игры (`SetupMemoryRegions` вызывается загрузчиком позже). Размер
   секции нельзя изменить после создания, а виды на неё появляются сразу.
2. Физический адрес direct memory = смещение в секции и **виден гостю** (`Allocate` возвращает его,
   `Map` принимает): direct обязана лежать в `[0, бюджет)`.
3. Flexible начинается с фиксированного смещения `TOTAL_MEM_DEV_PRO` (задаётся в конструкторе, до
   бюджета) — поэтому секция тянется до 8448 МиБ даже при бюджете 4608. Видны ли гостю
   «физические» адреса flexible (`sceKernelVirtualQuery` и др.) — **не проверено**; если нет, их
   можно класть сразу после бюджета direct.
4. `SEC_RESERVE` (commit по требованию) — страницы такой секции коммитятся через вид
   (`VirtualAlloc(MEM_COMMIT)`) и **не декоммитятся** до закрытия секции: commit растёт до
   максимума и не возвращается при освобождении. Для этой игры это не мешает (вся direct выделяется
   один раз при старте), но в общем случае меняет поведение освобождения.
5. Контракт GPU (H2): `CopySparseMemory`/`TryWriteBacking` читают и пишут подложку для любой
   отображённой страницы — при `SEC_RESERVE` каждая отображённая страница должна быть закоммичена
   до первого отображения, иначе обращение подложки упадёт.
6. Нет файла подкачки: commit = RAM 32 ГБ, поэтому именно commit, а не RAM, — ограничение
   (SSPC-001, требование ≥ 16 ГиБ свободного commit для прогонов).

**Проверяемый эксперимент (предложение, не реализовано).**
- *E0, только измерение* (можно в P2.3.3 без смены поведения): записать в лог commit системы
  (`GetPerformanceInfo`) до и после создания секции; на момент `--memory-map N` — резидентные
  страницы секции по диапазонам таблицы выше (`QueryWorkingSetEx` по виду `backing_base`) и
  максимум `flexible_usage` за прогон. Гипотеза: скачок commit при создании = 8448 МиБ ± шум;
  резидентны только используемые диапазоны.
- *E1, за отладочным ключом, только со своим `AddressSpace`* (или отдельным патчем моста):
  секция `SEC_RESERVE` + commit при `Allocate`/отображении flexible. Гипотеза: пиковый commit
  системы в сценарии «лес» ниже на (8448 − 4608 − пик flexible) МиБ; FPS, кадры, VRAM, карты памяти
  и самотест `GpuMemory` — без изменений. Критерий: ≥ 3 чередующихся прогона на режим, commit
  считается как разница «после старта процесса − до старта» и как пик; разница должна превышать
  разброс прогонов одного режима. Отдельно — проверить, видит ли гость физические адреса flexible,
  прежде чем менять их смещение.

## 10. План P2.3.3 и обоснование объёма

**Что осталось между GPU и памятью** (после P2.3.2): H1 (тождественное отображение), H2
(постоянный RW-вид подложки), H3 (анонимная память читается GPU нулями), G10 (отложенная запись по
захваченному адресу), H7 (общая защита страниц гостя и отслеживания), D10–D12. Всё это —
требования к любому менеджеру; через интерфейс они уже проходят в одном месте.

**Главный блокер подключения своего менеджера — не GPU, а остальные пользователи
`MemoryManager`.** Конструктор менеджера моста резервирует всё свободное ниже 1 ТиБ; его лениво
создают и зовут загрузчик (`loader_host.cpp`), стеки и кучи потоков моста (`stack.cpp`,
`thread_state.cpp`, `pthread.cpp`), функции памяти ядра (BRIDGE), `InvalidateMemory` файловых
функций, devtools. Пока хоть один из них идёт мимо интерфейса, второй менеджер на тех же адресах
невозможен (два владельца адресного пространства).

Предлагаемый объём P2.3.3 (по одному механизму за шаг, без переключения игры):

1. **P2.3.3a — аудит и интерфейс для не-GPU пользователей** `MemoryManager` в пути `sspc` (тем же
   способом, что здесь: потребитель, данные, владелец, срок, блокировки; адаптер без состояния над
   мостом; без смены поведения). После него весь путь `sspc` ходит к памяти через два интерфейса
   (`GpuMemory` + новый), а менеджер моста — одна реализация.
2. **P2.3.3b — свой `AddressSpace` и карта VMA** в `src\runtime\memory`, только в самотесте на
   отдельном диапазоне выше 1 ТиБ (мост его не резервирует): плейсхолдеры, split/coalesce, секция с
   параметризуемым размером, `Protect`; карта VMA — чистая структура с моделью (случайные операции
   против постраничной модели, как `KernelDmem(n)`).
3. **P2.3.3c — `GpuMemory` над своим менеджером** (в самотесте): сценарий `GpuMemoryScenario` уже
   написан против интерфейса и модели раскладки — его можно параметризовать реализацией и
   сравнивать **последовательности уведомлений** регистратора у моста и у своего менеджера на одной
   раскладке.
4. **Переключение** — только после 1–3: `Core::SetGpuMemory` (нужно добавить: разрешено до создания
   растеризатора, т. е. до старта GnmDriver) и переключатель второго интерфейса — один
   экспериментальный ключ (`--native kernel-vmem`), решение до первого отображения, как у
   `kernel-dmem`.

**Требования к адресному пространству и подложке** (для 2–4): те же гостевые адреса
(`0x200000000` — база поиска, модули с `0x80000000`, primary TLS `0x881000000`, SceGnmDriver
`0xfe0000000`, конец system reserved `0x1000000000`, потолок 1 ТиБ при SDK ≥ 3.00), гость = хост,
страница 16 КиБ, плейсхолдеры на всём свободном ниже 1 ТиБ; одна секция подложки, direct по
смещению = физический адрес, постоянный RW-вид (H2), таблица указателей подложки для адресов
< 2^40 без блокировок; размер секции — по бюджету игры (§9, E1).

**Как проверять:** параметризованный `GpuMemoryScenario` (мост против своего менеджера, совпадение
ответов и последовательностей уведомлений); воспроизведение журнала операций памяти игры
(записать вызовы `MapMemory/Unmap/Protect/Allocate/Release` с аргументами и результатами из
прогона на мосту, проиграть на своём менеджере в самотесте, сравнить карты после каждой операции);
игровые чередующиеся прогоны до/после (как §7) и карты `--memory-map`.

**Почему такой объём, а не сразу свой менеджер:** без шага 1 нельзя переключить даже экспериментально
(второй владелец адресного пространства), а без шагов 2–3 переключение проверялось бы только игрой.
P2.3.2 показал, что подход «аудит → интерфейс без смены поведения → тесты с моделью и записью
событий → мутации» ловит ошибки порядка и блокировок, которые прежние тесты пропускали.

## 11. Непроверенное и риски

**Не проверено (нужна ручная или отдельная проверка):**
- граффити, бой, долгая сессия (> 100 с) — и в обычном режиме, и с `--native kernel-dmem`
  (`play.cmd`, `play.cmd dmem`);
- перезагрузка контрольной точки, переходы между уровнями — в автоматическом сценарии нет
  последовательности меню;
- путь `sceKernelReleaseDirectMemory` в игре (игра зовёт его только при завершении, прогоны
  закрывают окно);
- загрузчик `--loader shadps4` в игре (патч `0008` действует и на него: тот же GPU-код; проверен
  только сборкой и общим кодом);
- Linux-путь `UffdImpl` (не компилируется в нашей сборке);
- `SetPrtArea`/PRT и `MapFile`, `PoolCommit/PoolDecommit` — игра их не вызывает, тестами не покрыты
  (в них изменён только адресат уведомлений).

**Риски:**
- Виртуальный вызов на `CopySparseMemory` (+1 нс) — частота вызовов в игре не измерена напрямую;
  оценка сверху и игровые прогоны §7.
- `SetListener` не синхронизирован с операциями памяти — допустим только на старте (растеризатор)
  и в самотесте; при подключении своего менеджера нужен запрет смены после старта гостя.
- Дефекты эталона D10–D12 и H4 (выделение памяти в `TryWriteBacking`, возможно внутри VEH)
  сохранены намеренно; D11 может портить данные при выгрузке через границу блоков `0x248000000` /
  `0x268000000` — кандидат на отдельное исправление с воспроизведением.
- SSPC-002 остаётся открытой: этот этап не касается `TryPatchJit` и обработчика исключений.
