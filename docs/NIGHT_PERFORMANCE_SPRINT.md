# P4.6 — ночной спринт производительности (2026-10-11 → 10-12)

Журнал фактических результатов. Исходная точка — HEAD `a8eaf5c` (P4.6-G), ветка master. Все числа — замеры
`tools\tests\p46_runs.ps1` (окно 62–88 с, `tools\frame_stats.py`); «CP» — занятость процессора команд, мс/кадр;
«GPU» — GPU busy, мс/кадр. Один прогон = n 1; итоговые A/B — отдельной серией с повторами.

Эталонный exe: `build\ab\p46n_base` (= `a8eaf5c`). Экспериментальные сборки: `build\ab\p46n_*`.

## 1. Изменения

### N1. Постадийные таймеры только по `SSPC_GPU_TIMINGS=1`
Патч `logs\p46\pending\` применён к текущему коду (frontend, BufferCache) + 25 мест в `vk_executor.cpp`
(GuestRange, стадии draw, привязка, образы). Грубые таймеры (запись, отправка, ожидания) остались. Строки журнала
«draw stages / buffers / cache prepare» печатаются только с флагом.
Замер (один exe `p46n_hyb`, кольцо `SSPC_DIAG_RING=system` = поведение базы, `n1_sys`): пляж 23,4 FPS, CP 40,3
(база 20,1–21,5 / 44,1–47,0).

### N2. Гибридное кольцо StreamRing (CPU → кэшируемая память, GPU ← копия в видеопамяти)
`StreamRing::CreateMirror/TakeDirty`: зеркало того же размера (160 МиБ device-local) по тем же смещениям; срезы
отдают `buffer` зеркала и `data` хост-памяти. В `Executor::Flush` второй командный буфер пакета (`Batch::pre`)
копирует байты, выданные с прошлой отправки (1–2 региона), и ставит барьер COPY→ALL_COMMANDS/MEMORY_READ; он
отправляется перед буфером пакета. Корректность: каждый срез пишется CPU при записи пакета и больше не меняется;
регион кольца переиспользуется только после завершения пакета по timeline; конец предыдущего пакета — полный
барьер. `SSPC_DIAG_RING=system` — без зеркала, `=bar` — прежний опыт P4.6.
Замер (один exe, `n1_hyb` против `n1_sys`): деревня 16,8 vs 15,0 FPS, GPU 50,3 vs 57,2; пляж 23,5 vs 23,4, GPU
25,6 vs 26,4; зеркалируется ~25–35 МиБ/кадр.

### N3. Барьеры по диапазонам перед dispatch и DMA-копией
`Executor::NeedsBarrier/NoteAccesses`: после последнего глобального барьера запоминаются диапазоны гостевой памяти,
которые читали/писали dispatch и копии на шкале; dispatch/копия без пересечения (RAW/WAW/WAR) идёт без барьера.
Любая запись неизвестного объёма (draw, storage-образы, GDS, LDS, WRITE_DATA, met WAIT) — как раньше, барьер.
`SSPC_DIAG_BARRIER_RANGES=off` — прежнее поведение.
Замер `n2_bar`: деревня 17,5 FPS, GPU 46,9 (пропущено 429 тыс. барьеров за прогон; барьеры перед копиями
536 тыс. → 7,4 тыс.); пляж 23,8, GPU 25,1. Валидация — см. §2.

### N4. Кэш хост-вида для записей процессора команд
`Memory::Write` (native_backend.cpp): указатель чтения колец compute пишется после каждого пакета; `TryWriteBacking`
моста копирует VMA со вложенными std::map на каждый вызов (7 % сэмплов потока GPU на пляже). Теперь вид backing
(`BackingRun`) кэшируется (4 записи) после успешного `TryWriteBacking`; любое map/unmap гостя сбрасывает кэш.

Замер `n3_wc`: пляж 24,9 FPS, CP 38,0 (с N3: 23,8 / 39,9); деревня 18,1, CP 35,5.

### N5. Статичные мелкие диапазоны — в кэш видеопамяти вместо копирования в кольцо (`1523e1d`)
Диагностика `SSPC_DIAG_STREAM_STATS=1` (пляж, `n5_stream`): из ~35 МиБ/кадр, которые CPU копировал в кольцо,
**42 %** байт — повтор того же диапазона в том же кадре с тем же содержимым, **51 %** — без изменений с прошлого
копирования в прошлых кадрах, меняется ~2 %. Мелкие (≤16 КиБ) диапазоны только для чтения, ни одной страницы которых
нет в видеопамяти, всегда шли в кольцо — даже статичные. Теперь `BufferCache::Promotable`: если диапазон отслеживаем
(`CanArm`), бюджет позволяет и в его 64-КиБ блоки CPU давно не писал — он кэшируется (`Prepare`: одна загрузка, защита
страниц трекером). Запись CPU поверх кэшированных страниц (грубый отчёт трекера) отодвигает блок: 60, 120, … 7680
кадров диапазоны блока снова копируются в кольцо. `SSPC_DIAG_STREAM_PROMOTE=off` — прежнее поведение.
Изоляция (`n7_promo_off` на том же exe): CP пляжа 37,2 → 31,2–31,5 мс от повышения.
Замер `n6_promo`: пляж 29,5 FPS (медиана 29,9, p95 34,2), CP 31,5, поток 35 → 5,3 МиБ/кадр; гавань 27,1, CP 33,9;
деревня 18,5 (GPU 46,3). Повышений за прогон ~5 тыс.

### N6. Последнее найденное окно GuestBuffers (`47f7f26`)
Поиск окна в multimap под блокировкой для каждого диапазона (`BackingPointer`, `Get`) — ~3 % сэмплов. Последнее окно
проверяется первым (под той же блокировкой; `Drop` его сбрасывает). Изоляция: CP пляжа ~−0,8 мс (`n7_promo_off`
37,2 против N4 38,0).

### N7. Проверки диапазонов: storage-образы и GDS (`3740c2f`)
Счётчики причин оставленных барьеров показали: в деревне 68 % — «неизвестная запись» (storage-образы dispatch),
21 % — собственные «неизвестные» доступы (GDS). Storage-образы упорядочивает `ImageCache::Transition` своими
барьерами образа; GDS — отдельный синтетический диапазон. После: оставшиеся барьеры перед dispatch почти все WAW
(подряд пишут один и тот же диапазон). `n8_bar2`: деревня 19,1 FPS, GPU 45,0, CP 28,9. Валидация деревни 0.

### N8. Повторный bind pipeline и push constants не записываются (`d8a5bb2`)
85 % draw повторяют pipeline и 72 байта push constants предыдущего draw в том же командном буфере. Повторное
сравнение дескрипторов проверено и отброшено: совпадают у 0,04 % draw (новые срезы кольца каждый draw), а построение
сигнатуры стоило дороже; повторное использование flattened user data — 0 совпадений, отброшено.
A/B с чередованием (пляж, `n11_c7` против `n11_skip2`): 27,9 / 29,3 → **30,8 / 30,4 FPS**, CP 33,6 / 32,0 →
30,1 / 30,6 мс, p95 50 → 34 мс.

### Измерения GPU деревни (что на самом деле ограничивает)
- Профиль `SSPC_GPU_PROFILE=1` (`n15_prof`, с N9): ~1470 dispatch 1×1×1 очереди 1 = 17,9 мс (12–22 мкс каждый), все
  draw 9,0, промежутки (барьеры/загрузки/render pass) 8,8, write-back 3,3 мс.
- Гипотеза «медленная запись в sparse-зеркало» проверена и **отклонена**: плотные тени для всех записываемых
  привязок (`SSPC_DIAG_SHADOW_MIN_GROUPS=1`, `..._MAX_KIB=16384`, `n16`/`n17`) не изменили время самих горячих
  шейдеров (cs 0x2cfab4f00 21,9 → 22,6 мкс и т. д.), только добавили копий и барьеров.
- Горячий шейдер (дамп `logs\p44\shader_2cfab4f00_*`): 1 волна 64 потока, 4 цикла, 239 загрузок, 9 атомарных
  операций — работа одной волны, упирающаяся в задержки; ускорить можно только перекрытием dispatch.
- Измерительные переключатели `SSPC_DIAG_MEASURE=skip_q1small|skip_wb` (только для оценки; вывод неверен): без
  мелких dispatch очереди 1 GPU 44,9 → 16,5 мс; без write-back → 21,1 мс — второй замер меняет поведение игры (CPU
  читает устаревшие данные), как изоляция не используется.

### N9. Write-back только изменённых слов (`c6cc58e`)
`SSPC_DIAG_WB_DIRTY=1` (деревня): из ~48 МиБ/кадр write-back 87 % — ~3 диапазона по ~11 МиБ (пулы частиц), а GPU
меняет в них **5 % слов**. Для диапазонов ≥1 МиБ — теневая копия в видеопамяти (то, что сейчас у хоста: создаётся из
хоста один раз, каждая загрузка страниц под ней копирует те же байты хоста, копирующий write-back над ней — байты
видеопамяти); в конце пакета шейдер `wb_diff.comp` пишет в хост и тень только слова, где видеопамять отличается от
тени. Запись CPU, которую GPU не делал, больше никогда не затирается (полная копия её затирала). Мелкие диапазоны —
одна команда копирования на окно (было ~2100 команд/кадр). `SSPC_DIAG_WB_DIFF=off` — полные копии.
`n15_diff2`: деревня 19,8 FPS, GPU 42,9 мс (было 44–45), p95 67 → 51 мс; обратно скопировано 100 ГБ → 4,6 ГБ за прогон.
Валидация первой версии (`n14_val`): 0.

### N10. Порядок гостя: соседние dispatch одной очереди без синхронизации гостя — без барьера
Диагностика (`n19_ev`): из 1,34 млн dispatch, получивших барьер из-за пересечения диапазонов (почти все WAW — общий
пул частиц), в **99 %** случаев гость не делал между ними **ничего** (ни EVENT_WRITE, ни ACQUIRE_MEM, ни fence, ни
ожидания); события гостя за прогон — только ACQUIRE_MEM. На PS4 CP запускает следующий dispatch, пока идёт
предыдущий; зависимые dispatch игра разделяет CS partial flush / ожиданием. Значит, барьер между ними строже железа.
Теперь у каждого диапазона, записанного/прочитанного dispatch, есть тег (очередь, «эпоха» синхронизации гостя на этой
очереди; эпоха растёт на каждом EVENT_WRITE/ACQUIRE_MEM, fence, выполненном WAIT). Конфликт с диапазоном того же тега
не требует барьера; копии, другие очереди, записи неизвестного объёма — как раньше. `SSPC_P46_GUEST_ORDER=0` — барьер
при любом конфликте.
`n20_go` против `n20_off` (один exe): деревня **28,2 FPS** (медиана 29,9), GPU **24,3** мс против 20,5 FPS / 41,2 мс;
барьеров перед dispatch 1,3 млн → 59 тыс. Кадр (огонь, угли, частицы) визуально в норме.
Валидация + sync (`n20_val`, деревня): 0 сообщений, 292 тыс. барьеров пропущено. **Оговорка:** эти dispatch пишут в
sparse-буфер кэша; синхронизационная валидация может отслеживать sparse-ресурсы неполно, поэтому «0» здесь — слабое
доказательство; главный аргумент — семантика порядка гостя.
