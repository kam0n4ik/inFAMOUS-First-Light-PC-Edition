# P2.3 Memory Runtime и P2.4 Thread Runtime — технический план

Статус (2026-10-09): **P2.3.1 сделан экспериментально** — физическая direct memory NATIVE с
`--native kernel-dmem`, по умолчанию выключено (аудит, архитектура, результаты:
`docs\PHASE2_P23_MEMORY.md`); **P2.3.2 сделан** — интерфейс GPU ↔ менеджер памяти без смены
поведения (патч `0008`, `docs\PHASE2_P232_GPU_MEMORY.md`, там же план P2.3.3); **P2.3.3 закрыт** (финальный игровой A/B без регрессий) — интерфейс
для остальных пользователей менеджера памяти (патч `0009`), свой менеджер виртуальной памяти и адаптеры,
проверенные против моста дифференциальными тестами, игрой не используются (`docs\PHASE2_P233_MEMORY_DEPENDENCIES.md`,
`docs\PHASE2_P233_NATIVE_VMM.md`, там же готовность к P2.3.4 — переключению игры); остальное ниже — план. Phase 2 не завершена, пока виртуальная память
и потоки — план. Общие правила: один механизм за шаг, отдельный коммит, переключатель
`--bridge <группа>` на время сравнения, самотест «NATIVE против BRIDGE», затем игровые прогоны
обоими загрузчиками (с разрешения пользователя). Никогда одновременно: память + потоки +
GPU-кэш.

Источники: `docs\generated\KERNEL_AUDIT.md` (вызовы за прогон), исходники моста
(`third_party\shadPS4\src\core\memory.cpp`, `address_space.cpp`, `libraries\kernel\memory.cpp`,
`libraries\kernel\threads\*.cpp`, `video_core\page_manager.cpp`), `docs\PHASE2_PLAN.md` §P2.3/P2.4.

## P2.3 — Memory Runtime

### Что игра вызывает

13 импортов, **10 вызовов за прогон**: `sceKernelGetDirectMemorySize` ×4,
`sceKernelAllocateDirectMemory` ×3, `sceKernelMapDirectMemory` ×3 — крупные блоки один раз при
старте. Импортированы, но не вызывались: `mmap`, `msync`, `getpagesize`, `sceKernelMunmap`,
`sceKernelMprotect`, `sceKernelMlock`, `sceKernelMapNamedFlexibleMemory`,
`sceKernelReleaseDirectMemory`, `sceKernelQueryMemoryProtection`, `sceKernelGetPrtAperture`.
Большая часть памяти игры приходит не из этих вызовов, а из LLE-модулей и из моста
(`InitGnmDriverMemory`, стеки потоков, TLS, модули).

### Механизмы

| Механизм | Сейчас | Зависит от | До своего GPU-рантайма? | Риск |
|---|---|---|---|---|
| Резерв адресного пространства гостя (плейсхолдеры `VirtualAlloc2` + `MapViewOfFile3`) | мост `address_space.cpp` | — | **да**, если наружу та же поверхность, что читает GPU-мост (`MemoryForGpu`, ниже) | высокий |
| Direct memory: `GetDirectMemorySize`, `Allocate`, `Release`, поиск свободного, выравнивание (страница 16 КиБ, `alignment` — степень двойки) | мост `memory.cpp` | подложка-секция (~8,9 ГБ — это commit) | **частично**: учёт диапазонов — да; отображения с GPU-правами — только через `MemoryForGpu` | высокий |
| `MapDirectMemory` / `mmap` с GPU-правами | мост + `Rasterizer::MapMemory` | buffer/texture cache моста | **нет** без уведомления GPU-моста о map/unmap в том же порядке | очень высокий |
| Flexible memory (`MapNamedFlexibleMemory`, бюджет из `[Console]`) | мост | резерв | да (память CPU); допустим ли GPU-доступ к flexible — проверить по эталону до переноса | средний |
| Права страниц: `mprotect`, `QueryMemoryProtection` | мост | резерв | да, но `Protect` нужен и page manager моста (отслеживание записи CPU) — один источник прав | высокий |
| Shared mappings (несколько видов одной подложки) | мост: одна секция direct memory | — | да, как у эталона: виды одной секции | средний |
| Исключения доступа: защищённые страницы GPU-трекинга, патчи инструкций | мост `signals.cpp` (VEH) + `page_manager.cpp` | P2.4 «свой VEH» | **нет** до своего VEH и своего GPU-трекинга | очень высокий |
| `GetPrtAperture` (partially resident textures) | мост | GPU | **нет** | высокий |
| Память GnmDriver (`0xfe0000000`), буферы VideoOut | мост | GPU | **нет** (Phase 4) | очень высокий |

**Нельзя переносить до собственного графического рантайма:** отображения с GPU-правами без
адаптера, отслеживание записи CPU (защита страниц + обработчик в VEH), уведомления map/unmap для
buffer/texture cache, PRT, память GnmDriver и VideoOut. Это один связанный механизм «память,
которую видит GPU»; до Phase 4 он остаётся у моста, а собственный менеджер обязан отдавать ему
ровно ту поверхность, которую мост вызывает сегодня:

| Вызов GPU-моста | Где | Что обязан дать свой менеджер |
|---|---|---|
| `TryWriteBacking` | liverpool, buffer_cache, texture_cache | запись в подложку мимо защиты |
| `CopySparseMemory` | buffer_cache (4) | копирование с дырами |
| `ClampRangeSize`, `IsValidGpuMapping` | vk_rasterizer | границы отображений |
| `GetAddressSpace()->Protect`, `GetUsableRegions` | page_manager | права страниц, список регионов |
| `Rasterizer::MapMemory/UnmapMemory` | memory.cpp → rasterizer | уведомления в том же порядке (unmap — до освобождения подложки) |

### Порядок (минимальный риск)

1. **Карта VMA эталона** (`--loader shadps4` и `sspc`): адрес, размер, тип, права, имя после старта
   и после загрузки контрольной точки → `logs\vma_<loader>.txt`; инструмент сравнения. Критерий:
   две карты одного загрузчика из двух прогонов совпадают (кроме известных плавающих адресов).
2. **Адаптер `MemoryForGpu`** в `src\bridge\shadps4\` поверх `Core::MemoryManager`, GPU-мост
   переведён на него патчем `0008` (номер `0007` занят нативной direct memory P2.3.1). Поведение не меняется. Критерий: прогон до геймплея, кадры, пик
   VRAM и commit в пределах ±2 % от эталона; патч `0005` на месте. **Сделано (P2.3.2):** интерфейс
   `Core::GpuMemory` + `Core::GpuMemoryListener` объявлен в самом мосте (`core/gpu_memory.h`, как
   `DirectMemoryBackend` в `0007`), адаптер без состояния — в `memory.cpp`; результаты —
   `docs\PHASE2_P232_GPU_MEMORY.md`. Следующий шаг уточнён там же (§10): сначала интерфейс для
   не-GPU пользователей `MemoryManager`, потом свой `AddressSpace`.
3. **Запросы без состояния**: `getpagesize`, `GetDirectMemorySize` (бюджет из `[Console]`),
   `QueryMemoryProtection` (чтение у моста). Самотест: значения байт в байт.
4. **Свой `AddressSpace`** (`src\runtime\memory`): резерв плейсхолдерами по тем же адресам, одна
   секция-подложка, `Protect`. Сначала только в самотесте на отдельном диапазоне; игра — на мосте.
5. **Свой учёт direct memory** (`Allocate/Release`, выравнивание, поиск свободного): возвращаемые
   смещения сравниваются с эталоном на одном и том же сценарии вызовов.
6. **Свои `Map/Unmap/Mprotect`, flexible** — с уведомлениями через `MemoryForGpu`; переключатель
   `--bridge memory`.
   **Шаги 4–6 сделаны в P2.3.3 в самотесте** (`HostAddressSpace`, `VmaMap`, `VirtualMemory`, адаптеры
   `Core::Guest*`/`Core::GpuMemory`; дифференциальные тесты против моста по шагам, случайными операциями и под
   потоками — `docs\PHASE2_P233_NATIVE_VMM.md`); переключателя в игре ещё нет.
7. **Переключение `MemoryForGpu` на свой менеджер** — последним. Это P2.3.4: перечень оставшегося —
   `docs\PHASE2_P233_NATIVE_VMM.md` §8.

### Тесты и критерии готовности P2.3

- Самотест: каждый вызов на одинаковом сценарии в двух сторонах — адреса/смещения, права, коды
  ошибок; граничные: выравнивание не степень двойки, длина 0, пересечение, повторный unmap,
  `mprotect` на дыре, исчерпание бюджета.
- Игра: обоими загрузчиками до геймплея; 10-минутный прогон с ростом счётчика кадров; commit не
  выше эталона (нет файла подкачки: SSPC-001); ни одного нового отчёта регистратора первого шанса
  (`first-chance fault`).
- Готово, когда: все 13 импортов NATIVE без «фиктивных» обёрток над мостом, GPU-мост работает через
  `MemoryForGpu` на своём менеджере, 30 минут без падений (критерий Phase 2).

## P2.4 — Thread Runtime

### Что игра вызывает

29 импортов потоков (+4 TLS-ключа, +6 сигналов): `scePthreadSelf` ≈ 76 тыс., `scePthreadEqual`
≈ 41 тыс. (горячие), `scePthreadAttr{Init,Destroy,Setdetachstate,Setinheritsched,Setschedparam,
Setstacksize}` по ~20, `scePthreadCreate` 20 (в прогоне аудита; прежний план отмечал 22 потока),
`scePthreadJoin` 3, `AttrGetschedparam/Setaffinity/Setschedpolicy` по 2, `AttrGet/Getaffinity` по 1.
Импортированы, не вызывались: `Detach`, `Exit`, `Get/Setprio`, `Get/Setaffinity`,
`Yield`/`sched_yield`, `Once`, POSIX `pthread_*`, TLS-ключи, сигналы.

### Механизмы

| Механизм | Сейчас | Зависит от | Риск |
|---|---|---|---|
| Атрибуты (`scePthreadAttr*`) — структуры хоста, гость хранит указатель | мост | — | низкий |
| Объект потока, `Self`/`Equal` (горячие) | мост (`Pthread`, `g_curthread`) | свой объект потока | высокий: всё остальное ссылается на `Pthread*` моста (мьютексы, condvar, сигналы, cancel) |
| Создание: стек гостя | мост: область `usrstack` в **гостевом** адресном пространстве с guard-страницей (`threads\stack.cpp`) | **P2.3** (или хост-интерфейс к памяти моста) | высокий |
| TCB/TLS гостя | **наш загрузчик** (`rtld_tcb.cpp`, `Loader::Linker::CreateTcb`) | — | средний |
| FS-сегмент гостя (доступ к TLS через `fs:`) | CPU-патчер моста: статические патчи + ≈ 782 в рантайме через VEH | свой VEH | очень высокий |
| Приоритеты PS4 256…767 | мост; `common/thread.cpp` отображает на 5 уровней Windows (применяется ли к гостевым потокам — сверить) | — | средний: от него зависит порядок пробуждения семафоров/мьютексов |
| Affinity | мост **не применяет** (код закомментирован: «некоторые игры теряют производительность») | — | низкий: сохранить «не применять» |
| Join/Detach/Exit, деструкторы TLS-ключей, cleanup-обработчики | мост | объект потока | высокий |
| Cancel-точки (`PthreadTestCancel`), сигналы гостю (`DispatchSignal`) | мост | объект потока, VEH | высокий (игра сигналы не вызывает, но мост проверяет cancel в своих ожиданиях) |
| Обработка исключений: VEH, патчи инструкций, GPU-трекинг, сигналы гостю | мост `signals.cpp` | всё выше; см. SSPC-002 (`TryPatchJit` читает за границей модуля) | очень высокий |

### Порядок (минимальный риск)

1. **Атрибуты** — чистые данные; самотест байт в байт (размеры, умолчания, ошибки).
2. **TLS-ключи** (`KeyCreate/Delete`, `Get/Setspecific`) — своя таблица по идентификатору потока
   хоста (гостевые потоки — 1:1 потоки Windows); деструкторы пока вызывает мост при выходе потока
   (хук). Самотест: значения по потокам, удаление ключа, переполнение.
3. **Свой объект потока** рядом с мостовым: при создании гостевого потока мостом регистрируется
   «тень» (handle, имя, приоритет, состояние) — источник для `Self/Equal`, диагностики и будущих
   мьютексов. `Self/Equal` NATIVE только когда тень есть у **каждого** гостевого потока (включая
   главный и созданные LLE-модулями) — иначе это фиктивный NATIVE.
4. **Create/Join/Detach/Exit** — свой объект: стек через хост-интерфейс к памяти моста (до P2.3)
   с той же раскладкой `usrstack`, TCB из нашего загрузчика, приоритет по таблице эталона, affinity
   не применять (как эталон), очистка TLS-ключей и cleanup-обработчиков. Переключатель
   `--bridge thread`.
5. **Мьютексы + condvar + rwlock** (P2.2, шаг 3) — после шагов 3–4: владелец = свой объект потока.
6. **Свой VEH и FS-патчер** — последним: от него зависит каждый гостевой поток. Тот же набор мест
   патча и тот же код трамплинов, что у эталона (сравнение побайтно); без ошибки `TryPatchJit`
   (проверка границы модуля). Регистратор первого шанса остаётся первым в цепочке.

### Тесты и критерии готовности P2.4

- Самотест: атрибуты байт в байт; TLS по потокам; создание/join 100 потоков подряд, detach,
  exit с деструкторами; `Self/Equal` в каждом гостевом потоке; утечки — число потоков и хэндлов
  Windows до/после.
- Игра: порядок потоков недетерминирован — сравнивать множества имён и счётчики, а не порядок;
  число потоков как у эталона; прогон ≥ 10 мин с ростом кадров (нет deadlock); повторные
  прогоны (гонки); в конце — число живых потоков и хэндлов; ни одного нового `first-chance fault`.
- Готово, когда: все импорты потоков NATIVE, VEH и FS-патчер свои, мост больше не создаёт гостевые
  потоки, 30 минут без падений.

## Зависимости между шагами

```
P2.2 семафоры (сделано) ─► event flags ─► (P2.4 шаг 3: тень потока) ─► мьютексы+condvar+rwlock
P2.3 шаги 1–2 (карта VMA, MemoryForGpu) ─► P2.3 шаги 3–6 ─► P2.4 шаг 4 (стеки без хост-интерфейса)
P2.4 шаги 1–2 (атрибуты, TLS) — независимы, можно в любой момент
P2.4 шаг 6 (свой VEH) — последним; до него: причина SSPC-002 (серия sspc002_runs.ps1)
GPU-видимая память, GPU-трекинг, PRT, GnmDriver, VideoOut ─► Phase 4 (свой графический рантайм)
```
