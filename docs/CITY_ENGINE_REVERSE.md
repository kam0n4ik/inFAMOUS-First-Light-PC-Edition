# CITY-OPT Phase 3: где движок берёт 2 700 draw p462 города

Цель — найти в коде игры происхождение самой большой однотипной группы draw города (p462: один VS `0x2d6634b00`,
один PS `0x2d6621b00`) и понять, что из её работы повторяется от кадра к кадру. Адреса — смещения eboot (база 0, как
в проекте Ghidra); `[A]` — анализ кода, `[E]` — измерение в игре, `[H]` — гипотеза.

## 2. p462 — это проход 14 движка [E]

Трасса кадра движка, город, кадр 2800 (`runtime\sspc\logs\p53_render_trace\frame_002800.json`): контекст
`{pass 14, sub 0}` — **2 709 draw** (трасса команд нашего CP: 2 713 draw p462 в кадре 3021), 283 316 байт DCB,
16 746 пакетов, 490 800 индексов (≈ 60 треугольников на draw), **2 шейдера**, 157 текстур (пары 1024² форматов 40 и
35 — по виду альбедо + нормали), цели: `0x2fcdf0000` RGBA16F 1920×1088 и основная глубина `0x26b200000`, тест и запись
глубины у всех draw, смешивания нет. Функция подготовки прохода — `0x1914a0` (только `SetRenderTargets(R,
DAT_00e682a8[0x68])` при `DAT_01d0cbd5`). В `RENDER_ENGINE_PASSES.md` проход 14 — «однотипные объекты в HDR» (55 draw на
пляже, 206 в гавани); в городе он самый большой после теней.

## 3. Функция draw прохода 14: `0x1a1960` [A + E]

Все draw проходов идут в обёртку `drawIndex 0x623c60` (`NATIVE_RENDER_INTERFACE.md`). Её вызывают `0x1a1960`,
`0x1a1770`, `0x448b30`, `0x43d480`, `0x5a8f40`. Зонд `SSPC_DIAG_DRAW_CENSUS` (город, 3 окна по 10 с, ~245 кадров каждое)
считает вызовы по проходу контекста (`R + 0xde90`):

| Функция | Вызовов за кадр по проходам |
|---|---|
| `0x1a1960` | **проход 14: 2 805**; 12: ~500; 16: ~456; 19: ~434; 29: 176–237; 1: 134–158; 13: 43–47; 8: 36–40; 4: 34–37 … |
| `0x1a1770` | проход 1: ~1 558; 4: ~120; 6: 110 |
| `0x43d480` | ~4 763 (проход в этом прогоне не читался) |
| `0x448b30` | 0 |

Код `0x1a1960(param_1, R, instance)` (декомпиляция Ghidra, `E:\research\rea\q14\p14.txt`):

1. `mesh = **(instance + 0x18)`: `mesh+0x60` — массив V# вершинных потоков (16 байт каждый), `mesh+0x6c` — их число,
   `mesh+0x58` — адрес индексов, `mesh+0x68` — число индексов.
2. Если у экземпляра есть подмена потоков (`instance+0x20`, младшие биты `& 7`), массив V# копируется на стек и
   отдельные потоки заменяются (деформация). Зонд: **23 таких draw за кадр на все проходы**.
3. `0x16aa0(R+0x128, stage 2, 0, n, V#[])` — CUE пишет таблицу V# **каждого draw в новую память кадра**; её адрес
   попадает в user data VS `s2:s3`. Поэтому у соседних draw прохода 14 отличается только `s2` (измерено: `0x69ef0000` →
   `0x69ef0120`).
4. `0x623740(dcb, 4)` — список треугольников, `0x624f80(dcb, 0, 2)` — 16-битные индексы, commit CUE `0x14ad0`,
   `drawIndex(dcb, mesh+0x68, mesh+0x58)`.

Остальные функции draw устроены так же, но добавляют **константный буфер на каждый draw**: `0x1a1770` —
`0x61e260(…, 0xd4 байт)` (G-буфер), `0x43d480` — `0x61e260(…, 0x48 байт)`, вызывается из цикла `0x43d590` (3,5 КБ кода)
[A]. Такие draw различаются константами (по виду — трансформацией объекта [H]) и без instancing не объединяются.

## 4. Геометрия прохода 14 статична и уже лежит в видеопамяти [E]

`SSPC_DIAG_GEOM=2d6634b00:2500:300` — 300 кадров города (2500–2799), каждый draw p462 (`logs\geom\geom.tsv`, разбор
`geom.py`):

- 2 420 draw p462 в каждом кадре окна, **один и тот же набор** (2 420 индексных диапазонов во всех 300 кадрах);
- 9 680 диапазонов (3 потока вершин по 8 байт шага + индексы), 7,46 МБ; **у каждого диапазона один хеш содержимого за
  все 300 кадров** (STATIC 9 680, DYNAMIC 0, CONDITIONAL 0);
- все 2,9 млн обращений — `Residency::All`: диапазоны уже кэшированы в видеопамяти буферным кэшем и защищены от записи
  трекером страниц. **Копий CPU → GPU для геометрии p462 нет** — постоянный кэш геометрии для неё уже есть
  (`BufferCache`, инвалидация по записи CPU и GPU);
- адреса 0x2d4e…–0x2d5c… лежат в вершинной куче движка на 2,5 ГиБ (`docs/REA_ENGINE_REVERSE.md` §3) — куда стриминг
  мира загружает меши.

Стримятся каждый кадр (копия в кольцо на каждом draw) другие draw: `SSPC_DIAG_STREAM_WHO=1` — p86 (12,25 млн диапазонов,
3,4 ГБ за прогон), dispatch'и (3,3 млн), p461 (2,5 млн), p493, p694, p87…

**Что повторяется на самом деле**: движок каждый кадр заново записывает те же ~2 800 draw статических мешей (свежая
таблица V# через CUE, свой адрес индексов), а наш рантайм обрабатывает каждый из них целиком в обоих потоках — разбор
PM4 и полная подготовка стадии VS (промах мемо стадии: `s2` другой) в потоке 1, привязки, дескрипторы, состояние и
`vkCmdDrawIndexed` в потоке 2.

## 5. Патч движка не нужен [A]

Движок не пересобирает геометрию: меши постоянные (`mesh+0x58/0x60`), каждый кадр пишется только ссылка на них.
Перестройка таблицы V# через CUE — цена одного draw движка, а не копия данных. Тот же результат (одна подготовка на
серию, один draw на серию) получается в нашем рантайме без изменения кода игры (`docs/CITY_PERFORMANCE.md`, Phase 3).
