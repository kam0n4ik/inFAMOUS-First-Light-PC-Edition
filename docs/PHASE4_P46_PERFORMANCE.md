## 3. CPU-профиль

### 3.1 Инструменты P4.6.0

  на горячем пути) → `logs\gpu_frames.csv`, строка на кадр: вход в `SubmitAndFlip`, отправка, `SubmitDone`,

  занятость потока GPU (раунды CP, опрос, отправки), запись команд, ожидания GPU (`Synchronize`), простой с

  время, которое потоки игры ждали замок отправки (`WaitGpuIdle`).
- Гистограмма длительности блокировок WAIT_REG_MEM и время `Synchronize` по видам пакетов (`gpu_native.txt`).
- Счётчик FPS на экране (`vk_presenter.cpp`, левый верхний угол: FPS и мс за последнюю секунду; копия 320×30 после
  кадра в потоке показа; `SSPC_FPS_OVERLAY=0` — скрыть).

### 3.2 Структура медленного кадра (пляж, листва, до правок)
Журнал кадров (`check2`, 431 кадр в окне):
- игра входит в `SubmitAndFlip(k)` через ~0,03 мс после записи EOP(k−1) и отдаёт кадр сразу (**~85 командных
  буферов за вызов**); замок `SubmitDone` её не держит (0,1 мс/кадр); `SubmitDone(k)` — через ~33 мс после flip;
- CP идёт по кадру k **60 мс** (от отправки до точки flip), из них занят 44,5 мс (запись 34,6) и **15,4 мс стоит** на
  WAIT_REG_MEM — 27 блокировок за кадр; последняя снимается за 0,65 мс до конца кадра;
- хвост GPU после точки flip — 0,1–0,15 мс: GPU успевает за CP; кадр = задержка CP.

Гистограмма блокировок (`check2`): <200 мкс 1437 | 200–500 мкс 21 816 | 0,5–1 мс 1599 | 1–2 мс 3853 | 2–5 мс 7719 |
5–10 мс 707 | >10 мс 1968. Опыт E1 (`SSPC_DIAG_BLOCK_SPIN_US=20`, опрос каждые 20 мкс вместо сна 1 мс) — FPS 16,15,
гистограмма почти та же: **дело не в шаге опроса**.

Причина (по коду и отчёту fence): ожидаемые адреса (`0x24a6ba540`, `0x248eba540`, …) пишет **сама графическая
очередь** — `EVENT_WRITE_EOS` «signal fence» (kind 1) прямо перед `WAIT_REG_MEM` на тот же адрес: GPU гостя ждёт свои
шейдеры. У нас fence удерживается до завершения batch на GPU, поэтому каждая пара = сброс batch, полный слив GPU,
опрос, запись, продолжение записи (GPU в это время простаивает). Вывод P4.4 «флаги ставит CPU игры, удержанные метки их
не пишут» был основан на диагностике `HeldFenceSatisfies`, которая не учитывала EOS-fence (data_sel 0) — исправлено.

## 6. Оптимизации и коммиты

### 6.1 S1 — CP не останавливается там, где не остановился бы GPU гостя (`SSPC_P46_SYNC`, по умолчанию вкл.)
1. **WAIT_REG_MEM, который удовлетворит удержанный fence** (любой очереди: исполнитель записывает все очереди в один
   поток Vulkan), проходит сразу в порядке GPU; исполнитель ставит полный барьер перед следующей командой
   (`Executor::WaitMetByHeldFence`). Fence по-прежнему пишется в память только после фактического завершения работы
   — CPU игры видит его не раньше. Учитывается последний удержанный fence очереди к адресу; EOS с GDS и fence с
   часами/GDS — значение неизвестно, не проходит.
2. **WRITE_DATA в метку дисплея VideoOut** (память хоста, её не читает ни одна работа GPU) пишется при разборе пакета,
   как микро-движок CP железа, без ожидания GPU (`CommandMemory::Unordered`).
3. **DMA_DATA с GDS** (data→GDS, GDS→память, память→GDS) записывается в поток команд: `vkCmdFillBuffer`/
   `vkCmdCopyBuffer` по буферу GDS после полного барьера (`Executor::GdsOnTimeline`); запись в память гостя — через
   путь записи `GuestRange` + `timeline_writes_` (чтения CP/фронтенда ждут её), как копии память→память P4.4. Пока
   удержан fence с данными GDS (RELEASE_MEM data_sel 5, EOS GDS) — старый путь (такой fence читает GDS при
   завершении); в игре таких fence 0.

Опыты на пляже (1 прогон каждый): E2 только (1) — avg 17,8, median 19,8 (блокировок 774 вместо ~37 000, но
`Synchronize` вырос до 11,6 мс/кадр: GPU→память GDS 6,9 мс за раз — ожидание переехало); E4 (1)+(2) — 18,65;
**E5 (1)+(2)+(3) — avg 22,3, median 20,1, 1% low 15,7, p95 50,7 мс**, `Synchronize` 0.
Валидация + синхронизационная валидация E5 (`logs\p46\e5_validate`): **0 сообщений**, DEVICE_LOST 0; путь проверен
(16 645 ожиданий по удержанному fence, 1899 DMA с GDS на шкале GPU).

## 9. SSPC-020 и SSPC-021
- **SSPC-020 (дым)** — с S1 не перемерялся (PENDING). Новая гипотеза для проверки: EOP/RELEASE_MEM с часами GPU
  (`data_sel 4`, адреса `0x24be82000…38`, ~1 раз за кадр) получают значение в момент записи удержанного fence (опрос
  завершения batch), а не в момент исполнения на GPU; разности пар меток у игры ~59 мс и ~7 мс. Если игра
  подстраивает по ним эффекты, это объяснило бы зависимость мерцания от времени (P4.5: ожидание кадра вдвое снижало
  мерцание). Проверка: записывать метки GPU в позиции fence (`vkCmdWriteTimestamp2` + калибровка) и сравнить мерцание.
- **SSPC-021 (ballot wave64)** — без изменений; на производительность не влияет (один шейдер освещения).

## 10. Открытые ограничения
1. **Запись команд на CPU ~35 мс/кадр** (один поток): пляж/гавань ограничены ей; для 30 FPS нужно ≤ ~31 мс всего
   потока GPU (сейчас 43–45).
2. **GPU в деревне ~59 мс/кадр**: нужен профиль проходов (`SSPC_GPU_PROFILE=1`); кандидат — ~500 глобальных барьеров
   «всё→всё» на кадр (P4.5), половина из них перед dispatch.
3. Показ квантуется vblank 59,94 Гц: кадр 43 мс показывается как 33/50 мс.

## 11. План дальнейшего ускорения
1. Таймеры горячего пути только по `SSPC_GPU_TIMINGS=1` (подготовлено, не измерено: `logs\p46\pending\`) [оценка
   1–3 мс/кадр].
2. Профиль CPU потока GPU (`SSPC_DIAG_SAMPLE=1`) после S1 → точечные правки (повторные копии мелких диапазонов в
   кольцо — ~17 тыс./кадр, 26 МиБ; фронтенд ~12 мс; dispatch ~8 мкс каждый).
3. Профиль GPU деревни → сокращение глобальных барьеров (барьер только при пересечении диапазонов записи/чтения).
4. Если одного потока не хватит — конвейер из двух потоков (разбор PM4 + фронтенд | запись Vulkan).
5. SSPC-020: точные метки времени GPU в EOP (см. §9).
