- Направления R8-CP1..CP3 в заданной форме цели −10…15 % не дают (§6). После профиля и переписи A1 (§6.7) первый

## 2. Путь draw на потоке 1 сегодня [A]

`CommandProcessor` (PM4 → `RegisterFile`, журнал) → `BuildDraw` → `ParallelCp::Draw`:

| Шаг | Где | Что читает | Что пропускает |
|---|---|---|---|
| серия Phase 5/6 | `JoinRun` (`parallel_cp.cpp`) | группы регистров с прошлого draw, программы, user data VS (таблицы вершин), V# вершин из памяти; у G-буфера — `RedecodeStage` PS (и VS при чтении изменившегося регистра) | запись очереди, подготовку, копию стадий |
| GEOFAST | `PrepareGeometryOnly` | только прошлый draw (`index − 1`), то же поколение памяти; отличаются лишь группы VS user data / индексов / параметров | вызов фронтенда; стадии копируются из прошлой записи (`CopyStage`) |
| полная подготовка | `ShaderFrontend::PrepareDraw` (`shader/*`, только чтение) | PS, затем VS (`start` VS = `end` PS): P4.7 memo (адрес, `start`, версия runtime, эпоха программ, 16 dword user data, поколение памяти) → иначе программа, раскладка, fetch, `ResolveResources` (обход SRT по указателю снимка + `DecodeResources`), ключ специализации, модуль; затем конвейер (повтор, если модули и группы конвейера те же) | — |
| копия в запись | `CopyStage` ×2 | `StageView` фронтенда | — |

Почему полная подготовка не берёт память P4.7 (база R8 `r8b_base_city_b1`, 150 с): полных вызовов фронтенда 15,85 M
(≈ 3,4 k/кадр), стадий 33,8 M; memo — 256 k; промахи «other user data» 12,8 M (новый указатель снимка: commit
`0x14ad0` копирует тень в новый блок кольца на каждом commit), «other inputs» 20,7 M (у стадии сменилась программа —
memo одноместная), «memory changed» 26 k. Фронтенд на потоке 1 — 63,3 с за прогон.

Следствия для R8:
- память фронтенда не знает, что новый снимок побайтно равен старому, — это и есть знание Native Resource State
  (binding version);
- одноместная memo теряет чередование программ — ключ переиспользования нужен «по программе», а не «по стадии»;
- всё, что CP видит в регистрах (прямые SGPR `0x16fb0`, одиночные значения `0x16970/0x169a0`, указатель глобальной
  таблицы `CUE+0x78`, адрес fetch-шейдера, адрес программы и `RSRC1/2`), ключ CP сравнивает **сам по значениям
  регистров** — версия должна покрывать только содержимое снимка, на который указывают user data.

## 3. Канал «нативный commit → поток 1»: таблица снимков [A + код]

`src/runtime/gpu/r8/cp_native_table.{h,cpp}` (флаг включения — `SSPC_R8_CP_DIAG=1` или будущий потребитель).

- Производитель: `R7::Resources::Commit` (`resource_state.cpp`) после `recomp_14ad0` для каждого снимка VS/PS публикует
  `{адрес снимка, CUE, binding version (0, если отслеживание не полное), dwords, стадия CUE, пары SGPR указателей в снимок
  со смещениями}`. Таблица прямого отображения, 128 Ki записей по 64 байта, у каждой записи — свой seqlock (писатели —
  потоки заданий игры; читатель — поток 1). Запись делается тем же потоком и раньше, чем DCB со ссылкой на снимок
  отправлен (`SubmitFrame`): отправка упорядочивает её для потока 1 (правило §5.2.2).
- Потребитель: `R8::Find(user data стадии)` — первая пара SGPR, равная базе опубликованного снимка этой стадии, у
  которого **все** указатели commit-а стоят в user data как записаны; фильтр по границам адресов снимков.
- Ограничение: запись называет снимок, который был по этому адресу, когда его писал нативный commit. Снимок, позже
  записанный по тому же адресу писателем, которого commit не видит (`0x140d0` пути dispatch-draw, commit как код игры,
  тот же кусок арены в другом кадре), оставляет старую запись — поэтому потребитель, переиспользующий работу, сам
  проверяет байты снимка (одно чтение ≈ 62 байта и `memcmp`) — версия только указывает, с чем сравнивать.

## 4. Измерительный прототип `SSPC_R8_CP_DIAG=1` [код]

`src/runtime/gpu/r8/cp_native_diag.{h,cpp}`, вызов вокруг `frontend_->PrepareDraw` в `ParallelCp::PrepareDraw`.
Для каждой стадии, которую фронтенд действительно готовил (не P4.7 memo), строится ключ и сравнивается с 4 последними
подготовками той же программы (адрес + `RSRC1/2`) на этой стадии:

| Ключ | Состав |
|---|---|
| base | адрес программы, `RSRC1/2`, runtime-параметры, binding start, 16 user data кроме указателей в снимок |
| V | base + binding version + поколение памяти фронтенда |
| V0 | base + binding version |
| C | base + байты снимка равны + поколение памяти |
| C0 | base + байты снимка |

При совпадении ключа текущая подготовка сравнивается с сохранённой (модуль, конец привязок, flat за указателями, все
привязки) — «bad» = совпадение ключа при другой подготовке (переиспользование было бы ошибкой). Draw «покрыт», если обе
стадии — memo или совпадение без привязки внутри снимка. Время вызова фронтенда — `__rdtsc`; каждая 8-я полная стадия
повторяет свою ресурсную часть (`ResolveResources` + ключ) для оценки стоимости стадии.

Дополнительно каждая 8-я полная стадия повторяет свою ресурсную часть через наблюдающий `GuestReader`: «обход внутри
снимка» = обход SRT не читал ничего вне `[база, база + dwords·4)`, не писал в регистровую часть flat, без сбоев чтения.
Для такой стадии подготовка — функция базового ключа и байтов снимка (критерий кэша P5.3, `shader_frontend.cpp`), и
совпадение C0 вместе с равной подготовкой — доказуемое переиспользование без поколения памяти.

## 6. Дизайн R8-CP1..CP4

### 6.1 Ограничение, которое определяет всё [A]

`ShaderFrontend::PrepareDraw` готовит PS и VS одним вызовом, и изменить его в R8 нельзя. Значит, любое переиспользование
вне фронтенда — **на уровне draw целиком** (как GEOFAST и серии Phase 5/6): либо обе стадии и конвейер берутся из
сохранённого, либо draw идёт во фронтенд полностью. Фронтенд использует `d.changed` только в двух местах (пересборка
runtime-параметров и повтор конвейера); если draw обойти, накопленную маску пропущенных draw нужно передать в следующий
вызов фронтенда (`d.changed |= skipped`) — иначе изменение групп конвейера/runtime у пропущенного draw потеряется. Это
условие корректности для любого механизма R8-CP вне фронтенда.

### 6.2 R8-CP1 Native Resource State на стороне CP — сделан канал, механизма нет

- Таблица снимков (§3) — корректный и дешёвый способ донести до потока 1 знание commit: версия + границы снимка +
  регистры указателей; поиск — проход по 15 парам user data с фильтром границ и одна строка кэша.
- Ключ переиспользования стадии (обоснование эквивалентности): программа (адрес, `RSRC1/2`, эпоха программ),
  runtime-параметры, начало привязок, 16 user data вне указателей на снимок (прямые SGPR `0x16fb0`, одиночные значения
  `0x16970/0x169a0`, `CUE+0x78`, адрес fetch-шейдера — всё это регистры, и ключ сравнивает их значения; реконструкции
  `0x16fb0` не нужны), **байты снимка** (`memcmp`; версия только выбирает кандидата — запись таблицы может быть
  устаревшей) и **поколение памяти фронтенда** (обход читает память вне снимка — §5.2) либо, вместо поколения,
  доказанный при запоминании «обход внутри снимка». Сбросы `0x13d20/0x12390/0x13da0` меняют байты снимка — ключ их видит.
- Потенциал — §5.3: ≤ 0,75 мс/кадр, только PS, и вне фронтенда его не взять (VS всё равно готовится полностью).
  Вывод этапа 1 был «не строить»; по переписи A1 (PS без снимка тоже повторяются, §6.7) Lead поставил K1 первым — §8.

### 6.3 R8-CP2 Native Shader Stage Reuse — сверх P4.7 / GEOFAST / RedecodeStage

- Повторный обход SRT с новыми регистрами (RedecodeStage, `SSPC_CITY_ENGINE_RESOURCES`) уже был: стоит почти как полная
  подготовка (`docs/CITY_ENGINE_RESOURCES.md` §5.2). Нативная версия ничего не добавляет для VS (не повторяется) и мало
  для PS (§5.3).
- Единственная заметная повторяемость — PS G-буфера по байтам (17 %) — недоказуема из-за чтений вне снимка; сделать её
  доказуемой могло бы поколение памяти «по диапазонам» (дескрипторы материала в постоянной памяти) вместо глобального.
  Даже тогда это ≈ 0,26 мс/кадр. **Не строить.**

### 6.4 R8-CP3 Native Draw State и R8-CP4 обход PM4

- CP3: связь с A3 Native Render Layer как источником ключа draw не нужна — ключ CP строится из регистров и снимка,
  а данные движка (`engine_run`, `engine_material`) уже приходят в `DrawDescriptor`. Второго источника истины не вводить.
- CP4: обход PM4 для нативных draw уже мерили как P5.3: нативные commit/draw/state сами по себе +1,5 мс потока 1,
  подготовка стадий по описанию движка — основная часть +6,9 мс (`docs/NATIVE_RENDER_R6_CORE.md` §5.5). Повтора
  подготовки, на который мог бы опереться CP4, нет (§5.3); выигрыш возможен только на разборе PM4 и журнале регистров,
  а его без профиля A1 (стоимость SET_SH_REG / SET_CONTEXT_REG / NOP по видам draw) обосновать нечем.

### 6.5 Что выбрано для R8-B (после профиля и переписи A1)

1. **K1 — переиспользование подготовки PS на стороне CP** (приоритет Lead). Дизайн и развилка K1a/K1b — §8.
2. **K2 — GDS DMA на временной шкале** (`SSPC_CP_ASYNC_WRITES=gds`, CP-9, код есть). В базе R8 сливы «timeline gds» —
   12,3–13,1 тыс. за прогон, 4,80–4,98 с (≈ 1,0 мс/кадр). Мерит A1.
3. **K3 — журнал только изменившихся регистров** (66 % записей не меняют значение; сверка `RegistersHash`) — после K1.
4. Остаётся в коде (выкл.): канал `cp_native_table` и `SSPC_R8_CP_DIAG=1` — измеритель для K1.

### 6.6 Что нужно от других агентов

- A1 (профиль): разложение потока 1 вне `ShaderFrontend::PrepareDraw` по пакетам/фазам (разбор PM4, `RegisterFile`,
  журнал, `JoinRun`, записи очереди, сливы) в городе — для выбора п. 2.
- A3: полей `NativeDrawCommand` для CP не нужно (ключ — регистры и байты снимка).
- A4: реконструкции `0x16fb0` и др. для ключа CP не нужны (прямые SGPR видны как регистры).
- A5: для п. 1 регистрация verify не нужна (существующий флаг, сверка счётчиками); для будущего переиспользования
  стадий — verify по образцу `SSPC_CITY_GEOFAST=verify` (полный путь + сравнение представлений).

### 6.7 Аудит A4 (статический разбор eboot, `feature/r8-recomp` `bf1d7b3`) и профиль A1 — что меняется

- Сброс CUE (`0x13da0` → поворот кольца `0x12390`, тело `0x13d20`, каждый кадр): binding version может пережить сброс
  при равных байтах, а память старых снимков переиспользуется. Ключ таблицы снимков — адрес, поэтому запись может быть
  устаревшей (это и есть 82 «та же версия — другие байты» из §5.2). Решение в K1: версия — только предфильтр, решают
  **байты снимка (`memcmp` с сохранённой копией) + поколение памяти**; гостевые адреса снимка в план не попадают
  (первые 16 dword flat пишет исполнитель из текущего draw — `native_shared`).
- `0x16fb0` пишет SGPR мимо тени: user data сравниваются **по значению**, кроме пар указателей формы, которые
  проверяются как `user_data == база снимка + offset·4` из записи commit (`R8::Find`) — так и сделано.
- `0x140d0` (второй commit) и `0x13a50` (init, memset тени): для K1 безопасны тем же `memcmp` байтов; предложения A4
  (version 0 при `fills_stale`, проба `0x12210` → Forget) нужны, только если когда-нибудь решать по версии без байтов.
- Профиль A1 (город, поток 1 ≈ 33 мс): фронтенд 11,48 мс (57 % — ресурсы), регистровые пакеты 4,63, CopyStage 2,08,
  PM4 1,80, JoinRun 1,61, RedecodeStage 1,27, NOP 1,22, сливы GDS 1,08, Invalidate фронтенда 1,05. Перепись: 47,9 % PS
  дают тот же результат, что прошлая подготовка программы (26,5 % — те же 16 регистров, 21,5 % — новые регистры, те же
  байты снимка); VS 0,4 %. Повтор PS у 2 173 draw/кадр — 4,54 мс фронтенда (весь вызов). Диагностика §5 считала только
  стадии с найденным снимком, поэтому PS без снимка (тени и др., «те же 16 регистров») в её 0,75 мс не вошли.
- Решение Lead: **K1 = переиспользование подготовки PS на стороне CP** (R8-B), затем K3 (журнал только изменившихся
  регистров). Дизайн K1 — §8.

## 8. K1 — переиспользование подготовки PS на стороне CP (R8-B, в работе)

### 8.1 Архитектурное ограничение, которое надо решить до кода [A]

Дорогая часть — `ResolveResources` (обход SRT + дескрипторы), 57 % времени фронтенда. Она внутри
`ShaderFrontend::PrepareStage` (`shader/*`, в R8 не меняется), и `PrepareDraw` готовит PS и VS **одним вызовом**.
Отсюда — развилка, которую должен решить Lead:

- **Единственный способ пропустить ресурсную часть PS внутри фронтенда — его же нативный кэш P5.3** (`NativeStages::On`,
  `shared_[si]` = готовый StageView, ранний `return Ready` до `ResolveResources`). Он уже есть и именно это и делает.
  R6 отверг его не из-за самой идеи, а из-за **стоимости поиска**: `NativeKeyOf` = XXH3 всего ключа + чтение снимка +
  `unordered_map` + аллокации — дороже сэкономленного (CORE §5.5, профиль: `PrepareStage` 3,1 %→10,2 %). K1 «на стороне
  CP» этого поиска во фронтенде не отменяет.
- **Чисто на стороне CP ресурсную часть PS можно пропустить только обойдя фронтенд целиком для draw** (семейство
  GEOFAST: Record собирается без `PrepareDraw`). Тогда для draw нужно самому дать и VS, и конвейер:
  - PS — из CP-кэша нативно-ключевых StageView (новое);
  - VS — перепись `RedecodeStage` по VS предыдущей записи (есть) — работает, только если у предыдущего draw та же
    VS-программа (перепись дешёвая: VS не повторяется, но её программа между соседними draw та же);
  - конвейер (`prep.pipeline`, `state`) — у CP нет построителя; берётся из записи, у которой **не менялись группы
    состояния конвейера** (условие GEOFAST). Значит выигрыш K1 над GEOFAST ограничен draw, где PS-программа повторяется,
    а геометрический сосед не подходит.

Вывод для решения: «чистый CP-side PS reuse» без касания `shader/*` = обход всего draw, и его потолок определяется не
долей повторов PS (47,9 %), а долей draw, у которых одновременно переиспользуемы PS (кэш) + VS (та же программа у
соседа) + конвейер (группы не менялись). Поэтому **предлагаю Lead выбрать один из двух путей K1**:

1. **K1a (внутри фронтенда, нужен владелец `shader/*` = A?):** оставить нативный кэш P5.3, но заменить его поиск на
   дешёвый — прямое отображение по `program ^ rsrc`, ключ-сравнение байтами без XXH3, снимок брать из `R8::Find`
   (таблица уже на потоке коммитов), без аллокаций на попадание. Это чинит ровно то, что отверг R6. Ожидание (§5.3,
   перепись A1): PS-ресурс ≈ 2,0–2,8 мс/кадр. **Это и есть «идеальный потолок» Lead; достигается только правкой
   `shader/*`.**
2. **K1b (чистый CP-side, без `shader/*`):** обход draw по образцу GEOFAST с PS из CP-кэша. Корректно и в рамках
   запретов, но потолок ниже (ограничен VS+конвейером соседа) — ближе к «−1,2…1,5 мс» нижней оценки Lead и пересекается
   с уже включённым GEOFAST/сериями Phase 6.

### 8.2 Ключ и корректность (общее для обоих путей) [A]

- Ключ стадии PS: программа (адрес + `RSRC1/2` + эпоха), runtime-параметры, начало привязок, 16 user data **по
  значению** (A4 п. 3: `0x16fb0` пишет мимо тени), кроме пар указателей формы — они проверяются как
  `user_data == база снимка + offset·4` из записи commit (`R8::Find`); **байты снимка** (`memcmp` с сохранённой копией —
  версия только предфильтр, запись таблицы бывает устаревшей после сброса CUE, A4 п. 1/4); **поколение памяти** для
  того, что обход читает вне снимка, либо запомненный признак «обход внутри снимка» (замеряется в §4).
- Fallback — на границе draw: не совпало что угодно → полный `PrepareDraw`. Накопленная `d.changed` пропущенных draw
  переносится в следующий вызов фронтенда (§6.1).
- verify (`SSPC_R8_CP_STAGE_REUSE=verify`): draw готовится и переиспользованием, и полным путём; представления
  сравниваются (модуль, конец привязок, flat за указателями, все привязки — как `SamePlan` в диагностике §4), счётчик
  расхождений в `gpu_native.txt`. По образцу `SSPC_CITY_GEOFAST=verify`.
- Флаг `SSPC_R8_CP_STAGE_REUSE`, по умолчанию выкл. A/B ≥ 3 пары, город, затем 4 сцены; строки профиля `SSPC_R8_CP_PROFILE=1`
  с флагом на обеих сторонах.

### 8.3 Статус

Канал (таблица снимков) и измеритель — на месте и проверены в городе (§5). Выбор K1a/K1b — за Lead: это правка
`shader/*` против потолка. До ответа механизм не включается.
