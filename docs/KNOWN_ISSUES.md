# Известные проблемы SecondSonPC

## SSPC-001 — сбой GPU-моста при загрузке уровня (17–18 с): причина установлена, **исправлено** патчем 0005 (2026-10-08)

**Итог.** Сбой — исчерпание **системного лимита выделенной памяти Windows (commit limit)**, а не
видеопамяти и не бюджета VMA. На этой машине нет файла подкачки, поэтому лимит = объёму ОЗУ
(32 655 МиБ). При загрузке уровня GPU-мост shadPS4 одним рывком выделял ~6 ГиБ: резидентную копию
гостевого texel-буфера 2,4 ГиБ в видеопамяти **и** staging-буфер такого же размера в системной
памяти. Windows (WDDM) начисляет commit за обе (в том числе за видеопамять), и вместе с ~10 ГиБ
самого эмулятора и ~14,6 ГБ остальных программ система упиралась в лимит → драйвер отказывал
`vkAllocateMemory` во **всех** кучах → `ASSERT` shadPS4 (иногда — вторичные AV/исключения, когда
отказывал уже обычный `malloc`). Исправление: загрузка больших диапазонов порциями через staging
≤ 64 МиБ (`patches\shadps4\0005-sspc001-bounded-upload-staging.patch`).

### Точный неудачный вызов (диагностика `patches\shadps4\0004`, прогон `logs\runs\d1_oracle`)
| Параметр | Значение |
|---|---|
| Вызов shadPS4 | `vmaCreateImage` (`texture_cache/image.cpp`) в потоке `shadPS4:GpuCommandProcessor`, t = 17,23 с (в других прогонах — `vmaCreateBuffer`, staging 48 МиБ; та же картина) |
| VkImageCreateInfo | 2D, 2048×2048×1, 1 mip, 4 слоя, format 126, usage 0x27, flags 0x108; гостевой адрес 0x300510000..0x304510000 (64 МиБ) |
| VkMemoryRequirements | size 67 108 864 (64 МиБ), alignment 0x400, memoryTypeBits 0x3, prefersDedicated 1 |
| Кандидаты VMA | тип 1 (DEVICE_LOCAL, heap 0, 5954 МиБ) → тип 0 (host, heap 1, 16 328 МиБ); **бюджетная проверка VMA проходит для обоих** (VMA создан без `EXT_MEMORY_BUDGET`: бюджет = 80 % кучи, учитываются только блоки VMA) |
| Что вернуло ошибку | **`vkAllocateMemory` драйвера** — `VK_ERROR_OUT_OF_DEVICE_MEMORY` 7 раз подряд: dedicated 64 МиБ и блоки 256/128/64 МиБ в типе 1 (heap 0), затем dedicated 64 и блоки 128/64 МиБ в типе 0 (heap 1). Проба того же запроса без `WITHIN_BUDGET` — тоже отказ драйвера |
| heap 0 (VRAM) | driver usage 4334 / budget 5186 МиБ (запас ~850 МиБ): арена разреженного буфера 3043,5 МиБ (98 сырых аллокаций), dedicated-образы 489, блоки VMA 224, staging 272, прочие буферы 146 |
| heap 1 (системная) | driver usage 3754 / budget 15 560 МиБ: **staging 3472 МиБ** (2560 + 640 + …), кольца 256 |
| System commit | **32 642 / 32 655 МиБ** (свободно 13 МиБ), пик = лимит; физической памяти свободно 11,2 ГБ; private процесса 9,1 ГБ |

### Механизм
1. Старт: система 24,9 ГБ commit — ~14,6 ГБ остальные программы (замер без игры), секция гостевой
   памяти эмулятора ~8,9 ГБ (в private процесса не видна), private процесса 1,4 ГБ.
2. Загрузка уровня (t ≈ 15 с): в отрисовке (`Rasterizer::BindBuffers` → `BufferCache::ObtainBuffer`)
   игра привязывает **texel-буфер** V# `0x271258500..0x30b629440` (2467,8 МиБ). Размер верный:
   ровно `stride × num_records` дескриптора, диапазон целиком отображён (`ClampRangeSize` не урезал).
   Мост делает резидентным весь диапазон: `EnsureResident` — один `vkAllocateMemory` 2455,8 МиБ
   (DEVICE_LOCAL, backing разреженной арены), затем `SynchronizeMemory` копирует всё через **один**
   staging `HostUncached` 2560 МиБ. Через ~1 с то же для `0x248002000..0x269e00000` (542 МиБ: арена
   540 + staging 640 МиБ).
3. Крупные staging-буферы пул держит 120 кадров, но во время загрузки границ кадра нет (счётчик
   освобождений стоит на месте с 14,5 до 17 с) — они живы к моменту следующих выделений.
4. Private процесса 1,4 → 9,1 ГБ, commit системы → лимит → отказ драйвера в любой куче.

### Доказательство причинности (не только корреляция)
- **Вмешательство.** Патч 0005 убирает только временные staging-копии (−3,2 ГиБ в пике): `f2_*` —
  **4/4 прогона по 150 с прошли** (2 × `shadps4`, 2 × `sspc`), игра жива до конца (~8700 кадров),
  private процесса в пике 6,2 ГБ, commit системы в пике 29,6–29,8 ГБ. Без него в тех же условиях
  `f1_*` — 4/4 сбоя на 17 с, ранее 6/6.
- **Отвергнутое вмешательство F1** (освобождать staging ≥ 256 МиБ на следующей границе кадра): 4/4
  сбоя — границы кадра во время загрузки нет. Откачено, копия `logs\runs\_hash\0005-f1-rejected.patch`.
- **Журнал Windows** (System, `Microsoft-Windows-Resource-Exhaustion-Detector`, событие 2004
  «нехватка виртуальной памяти»): записи ровно во время каждого сбоя 08.10 (10:00–10:05, 10:36:54,
  11:13:24, 11:13:45, 11:19:58, 11:20:31, 14:33:47, 14:36:09 …), с SecondSonPC.exe в списке крупнейших
  потребителей (7,8–9,8 ГБ).
- **Почему утром и под cdb проходило.** Те же события 2004 есть и для утренних успешных прогонов
  (08:27, 09:29, 09:31) и для прогона под cdb (11:09): система доходила почти до лимита, но не за
  него. Запас — сотни мегабайт, и исход зависел от commit остальных программ (Telegram 1,7 ГБ,
  qBittorrent 1,2 ГБ, Claude 0,9 ГБ…). Почему именно под отладчиком хватило — отдельно не выяснялось
  (после причинного теста не требуется).

Vulkan validation / sync validation не включались: причина установлена вмешательством, а слои
validation сами расходуют память и меняют тайминги загрузки.

### Исправление (`patches\shadps4\0005-sspc001-bounded-upload-staging.patch`)
`BufferCache::SynchronizeMemory`: если загрузка в арену больше 64 МиБ, она идёт порциями через один
staging ≤ 64 МиБ; после каждой порции `scheduler.Finish()` (GPU скопировал → память переиспользуется).
Размеры арены, буферов и копируемые данные не меняются; ошибки не подавляются. `Finish` посреди
`Draw` допустим: сабмит планировщика сам отправляет ожидающие sparse-привязки (`on_submit`),
`BeginSession` инвалидирует динамическое состояние, `EndSession` закрывает рендер-проход. Стоимость —
ожидания GPU только при загрузках > 64 МиБ (один раз на загрузке уровня).

### Что остаётся (риск)
- Запас commit в пике ~2,8–3 ГБ — зависит от других программ. **Рекомендация (решение
  пользователя):** включить файл подкачки (например, «по выбору системы» на E:) — это поднимает лимит
  commit; SecondSonPC системные настройки не меняет.
- Арена разреженного буфера только растёт (`resident_ranges` не освобождаются): в долгой сессии с
  новыми районами объём может расти. Следить в ручном тесте (`--vram-log 5`: строки `commit sample`).
- Свой Vulkan-бэкенд (Phase 4) — с ограниченным staging и резидентностью по фактически читаемым
  страницам с самого начала.

### Инструменты
- `--vram-log N`: каждые N с — DXGI (VRAM процесса), commit (процесс и система), журнал аллокаций
  Vulkan по кучам и категориям; при сбое — то же плюс 48 последних событий и 16 крупнейших аллокаций.
- Аллокации ≥ 128 МиБ всегда пишутся отдельной строкой: запрос буферного кэша (гостевой диапазон),
  объект, стек (символизировать: `toolchain\LLVM\bin\llvm-symbolizer --obj=build\bin\SecondSonPC.exe
  --relative-address 0x…`).
- `tools\smoke_runs.ps1` (серия прогонов) + `tools\analyze_run.py` (сводка прогона: длительность,
  код выхода, «жива ли игра» по росту числа кадров, сбой, пайплайны, пик VRAM/commit, вызовы по
  владельцам, открытые файлы, изменения сохранений) → `logs\runs\<prefix>_summary.jsonl`.

## SSPC-002 — переход `Game:Main` по неотображённому адресу (редко): **исправлено патчем `0016` (2026-10-10)** — тест 4/4 падений → 0/20, игра 8/8 загрузок без падений

**Причина (P2.5, `docs\PHASE2_P25_PERFORMANCE.md` §8.1).** Рантайм-патчер моста (`core\cpu_patches.cpp`
`TryPatchJit`) побайтно пишет `jmp rel32` на трамплин TCB поверх гостевой `mov reg, fs:[disp]`, которую в этот
момент могут выполнять другие гостевые потоки. Поток, выбравший инструкцию посреди записи, выполняет «разорванный»
`jmp` (новый опкод, старые байты смещения) на модуль + 0x25xxxxxx (0x25 — SIB-байт исходной инструкции). Все 9
записанных падений ведут на `база eboot + 0x25xxxxxx`; восстановленные адреса трамплинов попадают в начало области
трамплинов. `--patch-race-test` воспроизводит падение с той же сигнатурой на мосте без исправления в 4 из 4 запусков.
**Исправление** — патч `0016`: запись через `int3` + `FlushProcessWriteBuffers` (как `text_poke_bp`), поток,
попавший на `int3`, ждёт патч и повторяет инструкцию (в том числе если ядро сообщило ловушку как
привилегированную инструкцию). Тест: 20 из 20 запусков, ~84 тыс. пойманных и возвращённых потоков. Игра: 8 из 8
загрузок без падений (серия остановлена по просьбе пользователя, который подтверждает, что игра больше не падает).

Ниже — история расследования до 2026-10-10 (выводы о «нет first-chance отчёта» и т. п. — до регистратора).

**Симптом.** Процесс завершается с 0xC0000005; в `bridge_shadps4.log`: `SignalHandler: Unhandled
Exception code 0xc0000005 at 0x700000a0cc05` — это `ZydisInputPeek` (декодер инструкций в
обработчике исключений shadPS4): игра перешла на неотображённый адрес, обработчик попытался
декодировать там инструкцию и сам упал, поэтому исходный адрес перехода не сохраняется. Собственный
обработчик SecondSonPC не успевает записать отчёт (процесс завершает обработчик shadPS4).
**Где видели.** `f1_oracle` (2026-10-08 14:41, путь `shadps4`, после открытия ролика
`v_vor_opening_no_text.bsf`, до t ≈ 15 с, commit системы 25,9 ГБ — далеко от лимита), `or_3` (10:02,
то же место в другой сборке, адрес 0x7000009eef35). В 4 прогонах после исправления SSPC-001 не
повторился. Описанные раньше «разные» сбои SSPC-001 (переход по мусорному адресу, C++-исключение
`ab_native_2`) частично могли быть следствием исчерпания commit; этот случай — нет.
**Что сделать.** Сохранять исходный контекст первого исключения в потоке до вызова декодера
(обёртка вектора исключений SecondSonPC, только запись в память) и при повторе снять адрес перехода
и стек; затем — сравнить с прогонами под отладчиком.
**Phase 2 (2026-10-08 20:19, `p2paint_sspc_1`, сборка `36fd605`, путь `sspc`):** повторился —
`0x700000a2afe5` = `ZydisInputPeek` (`zydis\src\Decoder.c:260`, символизация `llvm-symbolizer`),
поток `JobWorker1`, t = 15 с, сразу после открытия `vor_taggin_a10#tandem#0.xpps` и записи
`/savedata0/dis.dat` (флаги `0x601`) — то же место загрузки контрольной точки, что и раньше
(до Phase 2 — на эталонном пути). Частота за Phase 2: 1 из 9 игровых прогонов. Это главный
кандидат на работу перед критерием «30 минут без падений»: сначала запись контекста первого
исключения (см. выше), затем причина.

**Разбор 2026-10-09 (по исходникам моста и логам `p2paint_sspc_1`; новых игровых прогонов не было).**
*Почему теряется исходный адрес — установлено.* Обработчик shadPS4 (`signals.cpp:30`, VEH с
`First = 0`) отдаёт любое нарушение доступа `cpu_patches.cpp` `PatchesAccessViolationHandler` →
`TryPatchJit(rip)` → `GetModule(rip)` (`cpu_patches.cpp:799`) берёт ближайший модуль **ниже** rip без
проверки его конца (проверка есть только в `GetContainingModule`) → `TryPatch` декодирует по rip длиной
`module->end - code`; при rip за концом модуля разность отрицательна (как `u64` — огромна), Zydis
читает байты по неотображённому rip → второе нарушение доступа внутри обработчика (`ZydisInputPeek`).
Повторный вход: rip уже в exe → «Unhandled Exception … at ZydisInputPeek», `Emulator::Shutdown()`
(процесс не завершает) → `EXCEPTION_CONTINUE_SEARCH` → поиск обработчиков по кадрам через гостевой код
(без unwind-данных) до фильтра необработанных исключений не доходит, процесс умирает без отчёта:
в `SecondSonPC.log` прогона `p2paint_sspc_1` строки `unhandled exception` нет.
*Что из этого следует — установлено.* Первичное событие — переход/вызов/возврат гостевого кода
(поток `JobWorker1`) на адрес не ниже базы одного из гостевых модулей, неотображённый или
неисполняемый. Вложенный сбой в Zydis — вторичный (чтение за границей модуля в shadPS4) и только
прячет первичный.
*Что неизвестно.* Адрес назначения, источник (call / ret / jmp по регистру), модуль и функция,
причина. Гипотезы (не подтверждены, не исправление): гонка в системе заданий игры при загрузке
контрольной точки (указатель на функцию/объект читается до готовности или после освобождения — тогда
виновата семантика синхронизации моста), освобождение/переотображение памяти при загрузке, порча стека
гостевого потока. Наш загрузчик не подтверждён как причина: сбой был и на пути `shadps4`.
*Сделано для поиска причины:*
- `src\base\crash.cpp` — регистратор первого шанса: VEH с `First = 1` (раньше обработчика моста);
  для execute-fault (и для обращения кода вне PE-образов к незакоммиченной памяти) пишет в
  `SecondSonPC.log` блок `first-chance fault #N (SSPC-002 recorder)` (с 2026-10-09 data-fault
  классифицирует второй обработчик, стоящий после обработчика моста, — см. SSPC-004): rip и адрес с регионом
  памяти (база выделения + смещение → модуль по строкам «loading module … to 0x…»), все регистры,
  `[rsp]` (адрес возврата call) с 16 байтами перед ним, `[rsp-8]` (= rip → «ret снял плохой адрес»),
  регистры, равные rip (jmp/call по регистру), 4 КиБ стека с указателями в исполняемую память, пробу
  VRAM/commit; минидамп первого execute-fault → `logs\crash\SecondSonPC_<время>_<pid>.dmp`
  (`[Debug] crashDump`, поток-писатель, не дольше 20 с). Исключение никогда не обрабатывает — мост и игра
  видят его как раньше. Проверка — `SecondSonPC.exe --fault-test` (до кода моста): call / ret /
  jmp rax на зарезервированную память, вызов в RW-страницу (DEP), чтение незакоммиченной памяти из
  кода вне образов; не записываются: чтение из кода exe, запись в защищённую закоммиченную страницу,
  `int3` — 20/20; `--selftest` 331/0 с регистратором;
- `--user-data <папка>` — профиль сохранений для тестовых прогонов (оба загрузчика берут сохранения из
  `user_data_dir`);
- `tools\sspc002_runs.ps1` — серия коротких прогонов (по умолчанию 10 × 60 с, загрузчики по очереди,
  без нажатий: сбой был на загрузке, t ≈ 15 с) на свежей копии снимка сохранений, хэши настоящих
  сохранений до/после, не больше 50 прогонов, отказ при запущенной игре или свободном commit < 15 ГиБ,
  остановка на первом сбое с сохранением логов, `run.json`, дампа и профиля. Проверен на двойнике
  (`tools\tests\game_process_tests.ps1`), на игре **не запускался**.
*Следующий шаг (нужно разрешение на игровые прогоны):* `tools\sspc002_runs.ps1 -Runs 20` (≈ 25 мин) →
по отчёту — модуль/смещение цели и источника, тип перехода, дизассемблирование вызывающего кода
(`tools\find_calls.py`, capstone); только потом — исправление первоисточника и регрессионный тест.
Возможная правка моста (не сделана): проверка границы модуля в `TryPatchJit` — убрала бы вторичный сбой
(мост сообщал бы исходный адрес), но падение игры не устранит; регистратор уже даёт этот адрес.

**Ревью VEH 2026-10-09 (Phase 2.2.2; кода `src\base\crash.cpp` не меняли).** Проверен по 7 критериям,
дефектов не найдено: контекст исключения не изменяется (оба фильтра только читают `EXCEPTION_POINTERS`,
всегда `EXCEPTION_CONTINUE_SEARCH`, в `CONTEXT` не пишут); штатные исключения не классифицируются как
фатальные (data-fault по committed-странице GPU-трекинга и host-код → мимо, `ClassifyFault` → `Ignore`);
нет рекурсии дампов (`t_recording` thread_local + `g_dump_taken` — один минидамп на процесс +

## SSPC-006 — снятие анонимной памяти, разрезанной на несколько VMA, роняет мост (латентный дефект моста; для стеков SecondSonPC обойдено в P3.2)

**P3.2 (2026-10-10):** стеки своего менеджера потоков больше не попадают под дефект: guard — отдельный
`Reserved`-диапазон, стек — отдельное отображение поверх него (`src\bridge\shadps4\guest_stack.cpp`), поэтому каждая
VMA совпадает со своим выделением хоста, и снятие стека одним вызовом проходит на обоих менеджерах памяти без
расщепления. Стеки снимаются по-настоящему, кэш ограничен (8 стеков / 32 МиБ;
`docs\PHASE3_INDEPENDENT_RUNTIME.md` §10.2). Сам дефект в `MemoryManager::UnmapMemory` моста **не исправлялся**
(мост не меняется без нужды): мостовые потоки (AudioOut и все потоки без `--native threads`) по-прежнему стеки не
снимают.

Найдено самотестом P2.3.3a (`docs\PHASE2_P233_MEMORY_DEPENDENCIES.md`, D17), **в игре не наблюдалось**.
`MemoryManager::UnmapMemory` снимает диапазон **по одной VMA** (`UnmapBytesFromEntry` → `AddressSpace::Unmap`),
а анонимная память (Code/Stack/File/System — без физической основы) у хоста — одно частное выделение
`VirtualAlloc2`, которое Windows не умеет резать. Если VMA такой области разрезана — защитой (guard-страница
стека: `Protect(guard, NoAccess)`), именем (`NameVirtualRange`) или частичным `Fixed`-отображением, — снятие
первой части вызывает `SplitRegion` → `ASSERT "Cannot split unbacked mapping"` (падение процесса). В пути игры
стеки потоков не снимаются (кэш свободных стеков) и модули не выгружаются, поэтому не проявляется. В
самотесте `GuestMemory` стек перед снятием снова сводится в одну VMA (защита и имя возвращаются). В своём
менеджере (P2.3.3b) снятие у хоста идёт по диапазону операции целиком; частичное снятие анонимной памяти
отклоняется кодом ошибки до каких-либо изменений (без падения).

Там же — **D13**: `MemoryManager::IsValidMapping` читает `vma_map` без блокировки (проверка имени потока
при создании, `pthread.cpp`) — гонка с одновременным map/unmap. Не исправлялось (этап без смены
поведения); в своём менеджере — под reader-блокировкой.

## SSPC-007 — частично перекрывающиеся виды одной direct-памяти роняют мост при снятии (латентный дефект, не исправлено)

Найдено дифференциальным самотестом P2.3.3c (`NativeMem(rand)`, `docs\PHASE2_P233_NATIVE_VMM.md` §5, D20),

## SSPC-008 — трамплины `fs:` моста неверны для `cmp/xor` и отрицательных смещений (латентные дефекты, в игре не срабатывают)

Найдено аудитом P3.3 (`docs\PHASE3_INDEPENDENT_RUNTIME.md` §5.2), **в игре не наблюдалось**: все 3616
`fs:`-инструкций Second Son — `mov r64, qword ptr fs:[0]`. В `core\cpu_patches.cpp` моста:
* `GenerateTcbCompare` / `GenerateTcbExclusiveOr` оборачивают `cmp`/`xor` в `pushfq … popfq`: `popfq` после операции

Свой патчер SecondSonPC (`--native fs-patch`) делает оба случая правильно (флаги операции сохраняются; читается

## SSPC-009 — профайлер Tracy в сборке RelWithDebInfo держит 4 МиБ commit на каждый хост-поток (наблюдение P3.2, не исправлено)

## SSPC-010 — кадр исключения Windows затирает red zone гостя при «грязном» AVX (риск; в игре не наблюдался)

Найдено в P3.4 (`docs\PHASE3_P34_EXCEPTIONS_CPU.md` §4), воспроизводит самотест `NativeExc(red zone)`. Ядро строит кадр
исключения ниже `rsp`; его область XSAVE кончается на `rsp`, а AVX-часть (256 байт) пишется, когда состояние AVX в
использовании: нетронутыми остаются 24–56 байт ниже `rsp` (при чистом AVX — 280–312). Значит, исключение на гостевом
потоке в функции, которая держит данные в 128 байтах ниже `rsp` (System V red zone), может их испортить. Источники
исключений в гостевом коде: GPU-трекинг моста (~62 тыс./с в игре; **был всегда**, не связан с P3.4), запасной путь
патчеров FS (со своим патчером — 0), `#UD` коротких `extrq` на Intel (SSPC-011). Детектор диспетчера (`--native
exceptions`): 171 функция eboot отмечена как использующая red zone; в 6 прогонах серии `p34_ab` ~5,8 млн исключений в
гостевом коде на прогон, «AVX над red zone» 3,3–3,9 %, «в функции с red zone» ~7 тыс., **одновременно — 0**.
Устранение: статическая защита функций с red zone или трекинг без исключений (Phase 4) — когда `exposed > 0` где-либо.

## SSPC-011 — на CPU без SSE4a 73 коротких `extrq` исполняются через исключение (~550 тыс./с, −10 % FPS на старте)

## SSPC-012 — очереди событий моста: гонки, use-after-free, потерянное пробуждение (латентные; **исправлено патчем 0025**, P3.6)

Найдено аудитом P3.6 (`docs\PHASE3_P36_BRIDGE_ISOLATION.md` §1.8): Q1 глобальная таблица очередей `kqueues` без замка

## SSPC-013 — вторая, конкурирующая остановка процесса мостом; гостевой `_exit` = int3 (**исправлено**, P3.6)

На sspc-пути `Core::Emulator` не используется, но каждый `ASSERT`/`UNREACHABLE` моста (`assert_fail_impl`) и VEH моста

времени игры и `controllers->ResetLightbarColors()` по **неинициализированному** указателю (член не задаётся в
конструкторе) — вероятный AV внутри пути падения, маскирующий причину; в случае VEH — изнутри обработки исключения.
Гостевой `_exit` моста — `UNREACHABLE_MSG` → тот же путь и `int3`. Исправление: патч 0026 (`Emulator::Shutdown` → хук

`_exit` — `--native exit` (экспериментально). Проверка — группа самотеста `Lifecycle` (дочерние процессы).

## SSPC-014 — менеджер памяти моста требует непустого GPU-слушателя (латентно; обойдено в адаптере, P4.1)

`Core::MemoryManager::MapMemory` (и другие map/unmap) вызывает `gpu->OnGpuUnmap(...)` без проверки на null

слушателя-заглушку). Мост не правился (без смены поведения); для своего бэкенда (P4.4) — то же правило.

## SSPC-016 — латентные дефекты командного процессора моста (P4.2, аудит; мост не правился)

Найдены при сверке своего командного процессора с Liverpool моста (`docs\PHASE4_P42_COMMAND_PROCESSOR.md` §4, §12); в
игре не проявлялись (тень: 0 расхождений), своему процессору не переданы:
1. `SET_SH_REG` в диапазон COMPUTE_*: условие `reg_offset <= 0x200 + sizeof(ComputeProgram)/4` пропускает смещение
   0x250 (на одно дальше), и проверяется только размер, а не смещение + размер — запись, начатая внутри диапазона и
   выходящая за `cs_state`, пишет за пределы структуры очереди (`liverpool.cpp`, `ProcessGraphics`/`ProcessCompute`).
2. Подсказки размеров целей: после `SET_CONTEXT_REG` с CB_COLORn_BASE/CMASK читаются 2 слова за пакетом, после DB_Z_INFO
   с 8 регистрами — слова 20–21 после начала данных, **без проверки конца буфера**; не NOP — `ASSERT` (смерть процесса).
   Свой процессор читает те же последовательности с проверкой границы и считает отсутствующие подсказки.
3. `CLEAR_STATE` обнуляет все регистры (config, SH, uconfig), железо — только context; дошло ли это до draw — счётчик
   тени «hardware vs bridge at a draw» (§7).
4. Неизвестный опкод или type-0 → `UNREACHABLE` (уже в P4.1 §2).
5. GDS в `EVENT_WRITE_EOS` (GDS store) и `RELEASE_MEM` (data_sel 5): смещение трактуется как байты; единица не проверена
   (в игре таких меток 0 — свой процессор делает так же и помечает как непроверенное).
Свой дефект, найденный самотестом P4.2 и исправленный: декодер P4.1 (`pm4.cpp`) считал пакет с count 0x3FFF (заголовочный
NOP, `PKT3_NOP_PAD`) длиной 0x4001 слово; в игре таких пакетов не было (P4.1: 0 ошибок разбора).

## SSPC-017 — латентные дефекты кэша шейдеров и транслятора моста (P4.3, аудит; мост не правился)

Найдены при аудите пути шейдеров (`docs\PHASE4_P43_SHADER_TRANSLATION.md` §2, §5–7). В захваченных сценах не проявлялись
(ни один адрес не сменил программу, P4.2 §7); собственный frontend SecondSonPC каждого из них избегает:
1. **Кэш программ по хэшу футера** (`PipelineCache::GetProgram`, ключ `bininfo.shader_hash`): программа, переписанная на
   месте с тем же футером, берётся из кэша; разные программы с одним хэшем компилятора сливаются. SecondSonPC: идентичность
   по содержимому (XXH3-128) с ревалидацией.
2. **Неполный ключ специализации** (`StageSpecialization`): не сравниваются поля, которые транслятор читает — формат
   storage-образа для атомиков, Sint/Uint образа (только `is_integer`), `ADD_TID_ENABLE` и `MTYPE`=3 буфера, размер образа
   FMask-формата, формат неформатированного буфера, размер LDS compute (`HwComputeRuntimeInfo::operator==`). Модуль
   может быть взят для другого содержимого. SecondSonPC: ключ — надмножество.
3. **SRT-walker:** AV-обработчик заменяет сбойную загрузку на `xor` **навсегда** — после одного недоступного адреса
   программа видит 0 и тогда, когда память снова доступна; генератор для `imm << x` (`ShiftLeftLogical32` с константой
   первым операндом) сначала сдвигает счётчик на константу — неверный результат. SecondSonPC: свой интерпретатор читает
   заново при каждом обходе (поведение генератора повторено для совместимости и отмечено).
4. **Разбор fetch-шейдера** (`ParseFetchShader`): массив `loads[104]` индексируется 7-битным SDST и `SRSRC*4` до 124 (выход
   за массив); `inst_offset` (12 бит) хранится в `u8`; чтение кода без границы до `s_setpc_b64`; иная инструкция — `ASSERT`.
   SecondSonPC: свой разборщик с границами и ошибками.
5. `Info::AddBindings` (повторно используемый модуль) прибавляет по одной привязке на образ, эмиттер — `NumBindings`
   (динамический mip storage-образа): начало привязок следующей стадии различается для свежего и повторного модуля.
6. `Buffer::GetSize()` возвращает 32 бита (переполнение при `stride * num_records` ≥ 4 ГиБ, только у неверных V#).
7. Неподдерживаемый формат экспорта цвета (например, несжатый ABGR_FP16) и другие формы — `UNREACHABLE` в эмиттере:
   процесс завершается (найдено самотестом P4.3; в режиме хука SecondSonPC возвращается только неизвестный опкод).
8. Compute: `num_allocated_vgprs = VGPRS * 4` (графика — `(VGPRS + 1) * 4`); SecondSonPC повторяет для равенства модулей.
9. **Транслятор меняет `RuntimeInfo` при трансляции:** `InjectClipDistanceAttributes` делает `++num_inputs`, а изменённые
   параметры сохраняются в первой перестановке программы. Следующий draw с теми же параметрами её уже не находит, и
   программа **транслируется второй раз**: в захвате 2 дубликата перестановок с одинаковым SPIR-V. Захват SecondSonPC
   (патч 0031) поэтому берёт параметры до трансляции.

Отдельно: `CLEAR_STATE` моста обнуляет SH-регистры (SSPC-016 п.3), поэтому PS USER_DATA_4 у моста 0, а у железа 0xEFE000.
В P4.3 доказано, что **на исполнение это не влияет**: в слотах, которые расходятся, железо user data не загружает
(USER_SGPR), и программы их не читают (по IR: 0 из 241). Подробности — `docs\PHASE4_P43_SHADER_TRANSLATION.md` §8.

## История расследования SSPC-001 (до установления причины)

### Непустое SystemName → падение после записи настроек (Phase 0)

**Симптом.** Если `sceSystemServiceParamGetString(6 /*SystemName*/)` возвращает непустую строку,
игра через ~20–30 с (после заставок, во время загрузки `sh-world_village(sunbreak)` и записи
`/savedata0/dis.dat` с флагами `0x601`) падает. Сбои всегда разные: `ErrorOutOfDeviceMemory` в
`video_core/buffer_cache/buffer.cpp:105`, access violation в потоке `GpuCommandProcessor`, C++-исключение
там же, переход `Game:Main` по мусорному адресу (обработчик shadPS4 затем падает в `ZydisInputPeek`).

**Бисекция (2026-10-08, `logs\runs\diag_*`).**

| Прогон | Экспорты SecondSonPC | Результат |
|---|---|---|
| ru_first, ru_second, diag_en | все 4 | падение (175–234 пайплайна) |
| diag_nocounter | все 4, без счётчика | падение — счётчик ни при чём |
| diag_stock | штатный `Emulator::Run` в нашем бинарнике | ок |
| diag_noexports | нет | ок, 250 пайплайнов |
| diag_observers_only | `sceKernelOpen/Stat` (наблюдатели) | ок, 508 пайплайнов |
| diag_paramstring_only | всё, кроме `ParamGetInt` | **падение** |

`ParamGetInt` в этих прогонах возвращает игре то же, что shadPS4 (вызывается только с `Lang`), поэтому
единственное поведенческое отличие — непустой `SystemName`.

**Что известно.** Игра (`0x15d6ee`) копирует строку в объект настроек по адресу `0xE17170 + 0x70`
(refcounted string через `0x60d8d0`), только если первый байт не 0. Заглушка shadPS4 буфер не заполняет,
и фактически игра получает пустое имя. На реальной PS4 имя всегда непустое (например, `PS4-123`), то
есть игра это поддерживает — проблема в связке Phase 0 (bridge shadPS4 или наш слой), а не в игре.

**Временное решение.** `[System] name = ""` по умолчанию: `ParamGetString` по-прежнему корректно
заполняет буфер (строка `""` с завершающим нулём, проверка размера), но игра идёт по тому же пути, что и
в эталоне. Непустое имя можно задать в `SecondSonPC.toml`, при этом в лог пишется предупреждение.

**Что сделать.** Найти потребителей поля `+0x70` (динамически: watchpoint на запись/чтение
`0xE171E0`), понять, где путь расходится, и устранить причину до Phase 3 (SaveData), так как она
связана с записью `dis.dat`.

**Воспроизведение.** `powershell -ExecutionPolicy Bypass -File E:\SecondSonPC\tools\repro_sspc001.ps1
[-Loader sspc|shadps4] [-Seconds 90] [-Name PS4-SSPC001]` — запуск с непустым SystemName через флаг
`--system-name` (TOML не меняется); итог `REPRODUCED` / `NOT REPRODUCED`, улики в
`logs\runs\sspc001_<loader>`.

**Обновление 2026-10-08 (Phase 1): тот же сбой и при пустом SystemName.** Подпись та же:
`ErrorOutOfDeviceMemory` в `video_core` (`buffer.cpp:104`, `image.cpp:121`) или C++-исключение в
`GpuCommandProcessor`, через 17–20 с после старта, при подгрузке уровня. Проявляется на
**неизменённом пути Phase 0** (`--loader shadps4`, загрузчик и FS shadPS4): `logs\runs\or_1..3`,
`fresh_oracle` — 4 падения из 4 подряд, в том числе с пустыми сохранениями (`fresh_*`; прежние
сохранения перенесены в `userdata\savedata_backups\2026-10-08_10-04-41_before_fresh_start`). Утром
того же дня тот же путь проходил 60 с в 3 прогонах из 3 (`m1_oracle`, `m1_oracle2`, `ru_phase0`),
новый Loader — 4 падения из 9 до этой серии: частота плавает и от кода SecondSonPC не зависит.
GPU: NVIDIA RTX 2060, 6 ГБ (свободно 5,4 ГБ перед прогонами).

Что известно точно: сбой не зависит от загрузчика SecondSonPC (оба пути) и от сохранений; связь с
SystemName в бисекции Phase 0, вероятно, случайна (малая выборка). Что **не** доказано: что это
ошибка shadPS4 — причина пока не установлена. Неудачная аллокация (`video_core/buffer_cache/buffer.cpp`
`UniqueBuffer::Create`): `vmaCreateBuffer` с `VMA_ALLOCATION_CREATE_WITHIN_BUDGET_BIT` (+
`DEDICATED_MEMORY` для буферов с device address) → VMA отказывает, если аллокация превышает
**бюджет видеопамяти процесса**, который сообщает ОС (VK_EXT_memory_budget / DXGI), а он меньше при
занятой другими программами VRAM. Гипотеза для проверки: бюджет процесса в момент сбоя исчерпан;
размер запрошенного буфера и состояние бюджета снимаются журналом `--vram-log` (DXGI
`QueryVideoMemoryInfo`, код SecondSonPC; GPU-код shadPS4 не меняется).

**Замер (2026-10-08 10:3x, `logs\runs\vram_oracle`, путь `--loader shadps4 --no-counter --vram-log 2`,
пустые сохранения не требовались).** Бюджет процесса (local) 5186 МиБ из 6144. Первые ~14 с
использование ~370 МиБ; затем за ~4 с: 1012 → 3484 МиБ local (non-local 456 → 3017 МиБ); в момент
сбоя 4398 МиБ local + 3737 МиБ non-local, assert `0x80000003` в `assert_fail_impl` ←
`UniqueBuffer::Create` (`ErrorOutOfDeviceMemory`). То есть запрос не помещается в оставшиеся
~790 МиБ бюджета на всплеске выделений при подгрузке уровня. Размер самого запроса без правки GPU-кода
не снять. Причина всплеска (что именно выделяет ~4 ГиБ за 4 с) не установлена — следующий шаг, когда
дойдём до GPU (Phase 4), либо раньше, если сбой станет блокировать проверки.

**Под отладчиком сбоя нет (2026-10-08 11:08, cdb, `--vram-log 2`, путь sspc).** Игра медленнее из-за
уведомлений отладчика о page fault, проходит тот же пик (4156 → 4334 МиБ local — ровно уровень, на
котором обычные прогоны падают) и работает ~145 с без сбоя (до остановки по тайм-ауту). Значит, сбой зависит от тайминга:
при нормальной скорости на пике подгрузки уровня очередная (временная) аллокация не помещается в
бюджет; при замедлении успевает освободиться память, удаление которой отложено. Буферный кэш к этой
точке одинаков в прошедших и упавших прогонах (≈48,8 тыс. резидентных блоков разреженной арены,
одна миграция арены), то есть пик не связан с маршрутом игры.

## SSPC-018 — собственный Vulkan-бэкенд (P4.4): известные пробелы на маршруте не проявились

`--gpu-backend sspc` (экспериментально, по умолчанию выключено; `docs\PHASE4_P44_NATIVE_VULKAN_RENDERING.md` §9):
1. Вытесняются только загруженные образы (бюджет 40% видеопамяти, ≤3 ГиБ); записанные GPU образы (цели) копятся —
   на маршруте их сотни; на долгой игре со сменой уровней — следить за VRAM.
2. Записанный GPU образ (цель рендеринга) не перезагружается, если CPU позже записал по его адресу текстуру того же
   формата и размера (нет освобождения устаревших образов при повторном использовании адреса).
3. Нет ExpandImage моста (меньший образ в больший по слоям/mip) и BC поверх несжатого — такие текстуры загружаются из
   памяти гостя (на маршруте только при загрузке уровня, 2 случая).
4. Запись шейдеров в sparse-зеркало буферного кэша на RTX 2060 / 596.21 медленнее плотной в ~150 раз: dispatch от 8
   групп пишут в плотные «тени», draw с UAV — напрямую.
5. ~16,5 FPS на маршруте: игра держит один кадр в полёте и ждёт настоящего завершения EOP (`0x248000000`), кадр =
   задержка однопоточного командного процессора (~44 мс) + ответ игры.

## SSPC-019 — мост по умолчанию: тёмная экспозиция (сумерки вместо дня) из-за выключенных readbacks

Путь по умолчанию (мост shadPS4, `readbacks_mode` = Disabled). На эталонном маршруте мост показывает тёмную
«сумеречную» сцену; с `SSPC_DIAG_BRIDGE_READBACKS=2` (precise) — дневную, как собственный бэкенд (`logs\p44\diag\h1_bridge_ref`,
`h2_bridge_readbacks`). Причина: CPU игры читает результат GPU (яркость для экспозиции), а без readbacks видит
устаревшую память; кроме того мост пишет метки EOP при разборе пакета, раньше завершения GPU. Цена исправления в
мосте — 43 → 21 FPS на маршруте. Решение (включать ли readbacks по умолчанию) — за пользователем; переключатель
`SSPC_DIAG_BRIDGE_READBACKS=1|2` — диагностика, по умолчанию ничего не меняет.
