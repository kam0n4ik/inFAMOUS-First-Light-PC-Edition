# План переноса улучшений Second Son на First Light

Правила:
- Эксперименты не включаются автоматически.
- Каждое включение по умолчанию проходит A/B на FL: серия с флагом и без, одна сцена, `logs\frametimes.csv`.
- Проверенное и экспериментальное разделено: проверенное идёт в `play.cmd`, экспериментальное — только на страницу
  «Эксперименты» или в `play_experimental.cmd`.

## Этап B — первый запуск и загрузка до меню

Шаги и результаты описаны в BOOT_REPORT.md.

Порядок действий:
1. Запустить `play_safe.cmd` и пройти по логу шаги 1–10.
2. Если упало: `logs\crash\*.dmp`, последние строки лога, `COMMON_STUB … called`.
3. Затем `play.cmd` и сравнение с базой.

Что вероятнее всего потребует работы:
- **libSceJson2.** Если `Initializer::initialize` или `Parser::parse` вызываются на загрузке, нужна HLE: настоящий парсер
  JSON со структурой `sce::Json::Value` по ABI SDK. Нули вместо неё возвращать нельзя: `Value::operator[]`
  возвращает ссылку.
- **Неподдержанные пакеты PM4.** В логе `CpError`; реализовать нужную форму пакета.
- **Отказы транслятора GCN.** Падение в рекомпиляторе shadPS4: поддержать инструкцию в своём трансляторе.

## Этап C — общие улучшения рантайма (без хуков, переносятся сразу)

Всё это уже есть в `core\` и работает на FL без изменений игровой логики:
- нативные kernel, память, CPU, SaveData, Pad, AudioOut, NP;
- `R10_AJM=native` (ATRAC9);
- `R10_SYSRT=native`;
- командный процессор native, VK emit thread/batch;
- асинхронные пайплайны, R9 pipeline cache, heap window;
- журнал фризов (F12);
- меню ПК по F1;
- счётчик FPS (F10), полный экран (F11);
- клавиатура и мышь как DS4, гироскоп, тачпад.

Что включено в `play.cmd` по умолчанию, а что ждёт A/B на FL:

| Флаг | В `play.cmd` FL | Почему |
|---|---|---|
| CP_MODE=native, CP_ROUND_NODRAIN, CP_ASYNC_WRITES, CP_ASYNC_FLIP, CP_RING=128, P411_ASYNC_ACQUIRE, P53_FRONTEND_THREAD | да | Общие; на SS в стандартном пресете давно |
| VK_EMIT_THREAD + VK_EMIT_BATCH | да | Общие; на SS +2,2 мс T2 (39,1 → 41,5 FPS) |
| ASYNC_PIPELINES, R9_PCACHE, R9_HEAP_WINDOW, REA_MERGE_RUNS | да | Общие |
| CITY_PERFORMANCE (только уровень PM4) | да, без ENGINE_OPT и ENGINE_GBUFFER_RUNS | Общая логика пакетирования. Если на FL будут артефакты, сравнить с `play_safe.cmd` |
| R11_EARLY_SUBMIT=256 | **нет** | Один TDR в R11 без установленной причины; сначала A/B на FL |
| NATIVE_GBUFFER, P54_EARLY_SUBMIT | нет (0) | Хуки SS |
| FB_ASYNC_COMPUTE и линия AQ, REA_DEFER_WAIT_B | нет | Экспериментальные. Потеря устройства, зависание из-за 128 fences, хуже 1 % low на Neon Dash |
| FB_LAZY_WB, REA_HEAP_READS, PIPE_PREFETCH, R10_SCHED, R10_SPREAD, R12_* | нет | Экспериментальные, нет выигрыша, или привязаны к SS |

## Этап D — перенос хуков движка (по значимости)

Метод одинаков для всех пунктов:
1. Сигнатурный поиск тела функции SS в eboot FL. Байты опкодов, ModRM, непосредственные значения и смещения полей
   сохраняются; rel32 и disp32 от RIP заменяются масками.
2. Новый RVA и новый FNV-1a 64 для FL.
3. Таблица мест **по продукту** (не замена адресов SS!).
4. Проверка в игре.

Все места D1–D7 найдены и проверены `researchl_sites_build.py` (сверка по обоим eboot, FNV повторно посчитаны отдельно); таблица — `researchl_sites.md`. Каждый хук по-прежнему проверяет хеш тела функции и не ставится при несовпадении.

Инструмент с маскированием `tools/native-reconstruction/function_hashes.py` лежит в теге `archive/dev-tools-20261023`
репозитория SS.

| # | Возможность | Места в SS | Признак переноса |
|---|---|---|---|
| D1 | Разрешение и пропорции 21:9 / 32:9 / 16:10 / 4:3 | 0x1eff47 / 0x1eff55 / 0x1f03f8 | **В коде:** 0x2369d7 / 0x2369e5 / 0x236e88 |
| D2 | Переключатель размера рендера + отступы HUD | FrameBegin 0x1f0be0, 0x300b00, 0x18e210 | **В коде:** 0x237670, 0x382420, 0x1bc1d0; глобалы HUD 0x1f272c0…cc |
| D3 | Меню ПК из меню паузы (Esc) | 0x27db10 / 0x27e210 | **В коде:** 0x2e75a0 / 0x2e7ad0 (пролог 17 у обеих), поля +0x2c; kind 7 не измерен, поэтому F1 на FL работает всегда |
| D4 | Прямая камера мышью | Интегратор камеры 0x14d6f0 | **В коде:** 0x171410; блокировки +0x7d0, пределы params2 +0x1d0/+0x220, инверсия +0x785/+0x786 |
| D5 | Исправление гонки счётчика ссылок | 0x1be900 / 0x1be8a2 (байтовые шаблоны, не зависят от позиции) | **В коде:** 0x1fe540 / 0x1fe4e2 |
| D6 | FOV, TAA | 0x580580, 0x472810, 0x581a10, 0x1929c0 | **В коде:** 0x65af10, 0x51c840, 0x65c210, 0x1c0b40 (нечёткий кандидат 0x1c1a20 был неверен) |
| D7 | DLSS / FSR / генерация кадров | Требуют D2 + D6 + камеру FL | Камера FL 0x81a41f8 в коде; доступны, когда переключатель (D2) установлен |
| D8 | Качество дыма, частиц, теней, текстур, отражений, дождя, пост-эффектов | см. PROJECT_AUDIT.md | Проверять по одному с A/B |
| D9 | Нативный G-buffer, CITY-OPT по тегам, REA-3, ранняя отправка | 0x1a1770, 0x43d480, 0x3ee470, 0x1f1e30 | Только после D1–D6 |

Пока места не найдены, пункты настроек, которые на FL ничего не делают, видны в меню (см. TODO: флаг возможностей
игры).

## Этап E — 60 FPS на RTX 2060 6 ГБ / 6C12T / 1080p

1. Запустить базу (`play_safe.cmd`) и `play.cmd` на одном маршруте; с F12-метками и без них.
2. Цифры занести в PERFORMANCE_BASELINE.md: FPS, 1 % low, время T1 / T2 / GPU и фризы из журнала фризов.
3. Найти узкое место: T1 (PM4), T2 (запись Vulkan), GPU или ожидание compute игры. Решение искать по узкому месту.
4. **60 FPS не заявлять без воспроизводимого теста.** Тест — сцена, длительность, флаги, `frametimes.csv`.
