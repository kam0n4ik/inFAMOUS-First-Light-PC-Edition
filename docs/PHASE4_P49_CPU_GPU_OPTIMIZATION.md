# P4.9 — узкие места CPU/GPU: измерения и оптимизации (краткий отчёт)

Дата 2026-10-12. База — P4.8 (Performance Inspector), exe `build\ab\p49_base`. `--gpu-backend sspc`, Ryzen 5 5500 +
RTX 2060. Файлы игры, эффекты и качество не менялись. Логи — `logs\p49\`.

## 1. Метод и поправки к измерениям

- **Окно A/B деревни — 25–50 с** (до поворота камеры: ~5600 draw, ~1630 dispatch во всех прогонах). После поворота число
  draw зависит от FPS (поворот по времени): 3300–4300 draw в разных прогонах — для A/B непригодно.
- **Overhead Inspector** (3 прогона без него против 4 с ним, деревня 30–50 с): CP 36,2 → 37,2 мс (+~1 мс, в пределах
  разброса ±1,1 мс), GPU busy без изменений (27,6–28,1 мс). Цифры ТЗ корректны по порядку величины.
- **«11,93 мс фронтенда»** — доля сэмплов бакета (28,3 %) × период кадра (42,2 мс): статистика, включительно с чтениями
  памяти фронтендом, не таймер.
- **Пустые `st_*_us`**: пофазные таймеры работали только с `SSPC_GPU_TIMINGS=1` (дорого). Добавлен режим
  `SSPC_GPU_TIMINGS=sample[:N]` — таймеры на каждой N-й команде (по умолчанию 32), суммы ×N в Inspector и в логе.
- **Каталог эффектов** не находился для копий exe в `build\ab\<имя>` (искался ровно на 3 уровня выше) — теперь поиск
  поднимается по всем родительским каталогам.

## 2. Что ограничивает FPS в деревне

CPU командного процессора. Тяжёлый участок: CP 36–38 мс, GPU 27,6 мс, кадр ~40 мс (25 FPS, 40–50 % кадров на третьем
vblank). Для стабильных 33,3 мс нужно CP ≤ ~29,5 мс. Разбивка потока GPU по сэмплам (до поворота, кадр 42 мс):

| часть | доля потока | мс/кадр |
|---|---|---|
| `Executor::Draw` (5600 draw) | 51 % | ~21 (фронтенд 8,0, привязки 4,5, драйвер+push-дескрипторы ~3, динамика 1,4) |
| `Executor::Dispatch` (1630 dispatch, ~6 мкс каждый) | 25 % | ~10 (привязки 4,7 — из них `BufferCache::Prepare` 2,2 и `VirtualProtect` 1,0; фронтенд 2,3; драйвер 1,5) |
| разбор PM4 | ~12 % | ~5 |
| ожидание конца пакета (простой) | ~6–8 % | — |

Фронтенд (PrepareStage): обход SRT + разбор ресурсов 46 % (из них чтения памяти `TimelineReader::Read` ~1,6 мс/кадр,
83 тыс. чтений/кадр), `ProgramCache::Get` 14 % (поиск + перепроверка программы раз в кадр), `FetchCache::Get` 13 %,
ключ специализации 10 %. Мемо стадий P4.7 попадает в 25 %; для compute — никогда: в трассе подряд одинаковых dispatch
(программа + диапазоны) 1,4 %.

## 3. Подсистемы (Inspector, деревня 30–55 с; CPU — запись, GPU — метки по категориям)

| подсистема | CPU мс | GPU мс | операций/кадр | вывод |

| Тени | 6,6 | 1,0 | 2885 draw | 2,3 мкс/draw — самые дешёвые draw, дорого числом; объединять нельзя (разные данные инстансов) |

## 4. Главный поток игры

`eboot.bin+0x53b340` — не опрос EOP, а игровой `delay(мкс)` (`0x53b2b0`): при ≥501 мкс — системный сон, иначе спин на
`rdtsc` без `pause`. Вызывается из 15 мест; кого именно ждёт — по сэмплам не видно (гостевые стеки не разворачиваются).
Держит одно ядро (98 %), FPS не ограничивает. Убрать — только патч гостевого кода (не делалось).

## 5. Оптимизации и A/B (деревня, 25–50 с, одинаковая сцена)

| изменение | результат | решение |
|---|---|---|
| **A** — очередь инвалидаций образов без аллокаций, `NextFlipId` без мьютекса | CP 36,5 → 36,2 (n=5/2) — шум | **не оставлено** (`logs\p49\change_A_not_kept.patch`) |
| **B** — загрузка блока буфера 64 КиБ целиком (`SSPC_P49_BLOCK_UPLOAD=1`) | загрузок и `VirtualProtect` в 10 раз меньше (725 → 73 тыс. за прогон), барьеров перед загрузками 606 → 59 тыс.; **GPU −6,0 мс** во всех 4 парах (27,5 → 21,5); CP: +3,2 / −3,0 / +0,2 мс — шум; FPS без изменений | **выключено по умолчанию** |
| **C** — памятки указателей перед `unordered_map` программ, fetch-шейдеров и текстур (`SSPC_P49_LOOKUP_MEMO=0` выключает) | 2 пары ABBA: CP 39,1 → 37,3 и 37,3 → 34,8 мс; FPS 23,3 → 24,3 и 24,2 → 25,9; кадры >33 мс 55 → 45 % и 47 → 31 % | **включено** |

Оговорка по C: в обеих парах один знак, но разброс базы между прогонами ±1,1 мс; по сэмплам механизм подтверждён
частично — доля `TexMemo` 1,6 → 0,6 % потока, `FetchCache`/`ProgramCache` почти не изменились (у них дорога
перепроверка раз в кадр, а не поиск). Честная оценка эффекта — 0,5–2 мс CP.

Почему B не поднял FPS: кадр ограничен CPU (CP 36 мс > GPU 27 мс). Выборочные таймеры показывают, что B снижает и CPU
привязок (`st_bind` −1,0…−1,8 мс, `st_range` −1,0…−1,6 мс в обеих парах), но общий CP плавает сильнее. Рост CP в
первой серии — выброс (один сегмент 48 мс), в диагностических парах не повторился. B станет полезен, когда CP опустится
ниже GPU; перед включением нужны Vulkan Validation + Sync Validation.

Итог по показателям (среднее, base → C): FPS 23,8 → 25,1; 1 % low 16,4 → 17,3; P95 50,6 → 50,4 мс; P99 58,7 → 58,4 мс;
CP 38,2 → 36,0; record 30,7 → 28,9; GPU 28,2 → 27,6. VRAM без изменений (~1557 МиБ).

## 6. Проверки

- C, режим `SSPC_P49_LOOKUP_MEMO=verify` (каждое попадание сверяется с поиском в карте): 23 157 523 / 0 расхождений.
  Записи карт не удаляются, эпохи/`dirty` проверяются у самой записи — инвалидация не изменилась.
- Самотест default: 1310 проверок, 0 ошибок. Прогоны: потерь устройства 0, `[Error]` 0.
- Vulkan Validation не запускалась: C не меняет команды GPU; B выключен.

## 7. Не подтвердилось

- Сам Inspector ↔ большой overhead (+7 мс «без Inspector» — оказалось другой сценой после поворота).
- Мемо стадий для compute (исправление версии runtime): подряд одинаковых dispatch 1,4 % — выигрыша не будет.
- B как ускорение FPS при текущем CPU-пределе.

## 8. Аудит параллельной записи команд (без реализации)

- **Строго по порядку PM4/GNM:** разбор пакетов и файл регистров (каждый draw читает регистры «на момент» draw);
  синхронные ответы исполнителя командному процессору (`WriteOnTimeline`/`CopyOnTimeline`/`GdsOnTimeline` возвращают
  «записано ли», `Synchronize`, WAIT_REG_MEM, удержанные fence до завершения GPU); сама запись в один command buffer.
- **Можно вынести в отдельный поток:** фронтенд (обход SRT, ключи, модули) — ему нужны снимок регистров и читаемая
  память; запись Vulkan (привязки, кэш буферов, барьеры, `vkCmd*`) — на втором потоке по очереди готовых команд.
  По сэмплам: поток 1 (PM4 + фронтенд) ≈ 15 мс, поток 2 (привязки + барьеры + драйвер) ≈ 19 мс против 36 сейчас.
- **Связи, которые придётся развязать:** исполнитель сообщает фронтенду о записях GPU (`GuestMemoryChanged` → мемо);
  чтения фронтенда ждут незавершённых записей GPU (`TimelineReader` → `SyncFrom`, за прогон 0 раз); решения
  «записано ли на шкале GPU» нужны CP сразу; `Executor::Draw`/`BindStage` читают регистры напрямую.
- **Однокадровая синхронизация игры:** кадр k+1 приходит только после EOP кадра k, поэтому перекрытия кадров нет —
  хвост GPU (~3–4 мс) всегда в кадре; параллелить можно только внутри кадра. Тогда GPU (27,6 мс, с B ~21,5) станет
  пределом, и B начнёт давать FPS.
