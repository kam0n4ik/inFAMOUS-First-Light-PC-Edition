## 2. Функции [A, E]

### 2.1 `0x448640` Material::Bind (0x15f байт, хеш `0x22c6fc74651c7374`, 12 вызывающих)

```
System V: (rdi pass P, rsi context R, rdx material M) -> ничего (все вызывающие перезаписывают RAX)
cue = R + 0x128
M == 0: ничего
D = [M + 0x28]                                           блок дескрипторов материала
(u32[D] | (u64(u32[D+4] & 0xfff) << 32)) != 0:          у первого V# (константы материала) есть адрес
    0x169d0(cue, 1, 13, 1, D); 0x169d0(cue, 2, 13, 1, D)
для i < u32[P+0x80] (перечитывается каждый круг):        сэмплеры
    0x16eb0(cue, stage(u8[P+0x71+4i]), u8[P+0x70+4i], 1, D + 0x20 + s32[P+0x84]*32 + u16[P+0x72+4i]*16)
для i < u32[P+0x6c] (перечитывается каждый круг):        текстуры
    0x16d10(cue, stage(u8[P+0x2d+4i]), u8[P+0x2c+4i], 1, D + 0x20 + u16[P+0x2e+4i]*32)
stage(x) = 0x27530(x) = u32[0x987c80 + 4x]
```

Сама функция пишет только свой стек; всё её поведение — последовательность вызовов трёх сеттеров. `0x27530`
вызывается, а не встраивается (хеш закреплён как `assumed`).

### 2.2 Сеттеры `0x169d0` / `0x16d10` / `0x16eb0`

То же семейство, что R5-C (`NATIVE_RECOMP_CUE.md` §2): `(rdi cue, esi stage, edx slot, ecx count, r8 src) -> rax = cue`,
таблица раскладки стадии `[cue + 0xc180 + 8·stage]`, запись `u16[table + T + 2·(slot+i)]`; бит 15 — прямой
`0x626520` (setUserDataRegion) в DCB, иначе — дескриптор в тень стадии, затем флаг `cue + 0xc1d0 + stage`.

| Функция | T | Дескриптор | Вызов `0x626520` | Хеш |
|---|---|---|---|---|
| `0x169d0` SetConstantBuffers | `0xe2` | V#, 16 байт | 4 dword | `0x01bd288a9d982d39` |
| `0x16d10` SetTextures | `0x22` | T#, 32 байта (`vmovups ymm`) | 8 dword | `0x722df3b62820c187` |
| `0x16eb0` SetSamplers | `0xc2` | S#, 16 байт | 4 dword | `0xe7d4270a2029dbec` |

Все — 0xc6 байт. `reconstructed/cue_set_buffers.{h,cpp}` обобщён на 5 видов (`kVertexBuffers`, `kBuffers`,
`kConstantBuffers`, `kTextures`, `kSamplers`): таблица `kRva / kTableOffset / kDescriptorBytes`, одна шаблонная
реализация.

## 3. Установка под пробой

При `SSPC_CITY_ENGINE_GBUFFER_RUNS=1` `DrawRuns::InstallFromEnvironment` (`bootstrap.cpp`) ставит пробы входа раньше
Native Engine на `0x1a1770`, `0x1a1960`, `0x43d480` и `0x448640`. Вход функции тогда — переход пробы, хеш тела не
сходится, и прежний установщик отказывал.

- `engine/guest_probe.{h,cpp}`: `InstallEntryProbe(..., void** original_slot)` запоминает установленную пробу
  (`ProbeRecord`: вход, проверенная функция, длина пролога, исходные байты пролога, переменная оригинала);
  `FindEntryProbe(entry)`. Пробы CITY-OPT (`draw_runs.cpp`) передают свои переменные оригинала.
- `native_function_registry.cpp` `InstallFunction`: если на входе стоит проба той же функции (rva, размер, хеш),
  её проверенная запись заменяет проверку хеша, клон строится из байтов до пробы (`OriginalBytes`), а вместо второго
  перехода в переменную оригинала пробы записывается диспетчер. Проба по-прежнему видит каждый вызов, а там, где
  раньше шёл оригинал, теперь идёт диспетчер (реконструкция или клон). В логе установки:
  «below the entry probe already on it».
- Без пробы поведение прежнее.

## 5. `0x14ad0` CUE::Commit

0x1184 байта, хеш `0x8bb6e7985e565584`, 953 инструкции, 99 прямых вызовов 24 функций, класс рекомпилятора
SUPPORTED. Для каждой стадии с грязной тенью: снимок (`0x123d0`), копия тени в него (memcpy), указатель user data
(`0x626400`), отдельные значения (`0x626520`), prefetch (`0x623630`), привязка шейдера через Gnm
(`0x625100…0x625aa0`), диапазон регистров (`0x624cb0` с дескриптором от `0x638540`); затем флаги сбрасываются.

Факты о побочных эффектах [A: P-code]:

- **По абсолютным адресам `0x14ad0` не пишет.** Читает один абсолютный адрес — слот GOT канарейки стека
  `0xd9de00` (два чтения).
- Пишет CUE: флаги и две 16-байтные записи тени стадии. Через вызываемые функции — арену снимков, DCB и Gnm.
- Чистые построители `0x61e0c0`, `0x61e330`, `0x639250`, `0x6393a0`, `0x639450`, `0x6394e0` не вызывают ничего и не
  пишут по абсолютным адресам. `0x638540` вызывает `0x63bb50`, а тот — HLE-импорты, поэтому `0x638540` записывается,
  а не исполняется.
- Арность каждой записываемой функции — регистры, которые она читает до записи, по её P-code
  (`E:\research\native-r5\r5d\arity.py`): `0x626520`, `0x638540` — 5; `0x626400` — 4; `0x623630`, `0x624cb0`,
  `0x625220/300/370/3e0/510/6a0`, memcpy — 3; `0x123d0`, `0x625100/1c0`, `0x625a40/aa0` — 2.

Сверка без двойных побочных эффектов (`reconstructed/cue_commit.{h,cpp}`):

- Оригинал — клон, у которого 18 вызовов с побочными эффектами перенаправлены на записывающие заглушки
  (`CodeRedirect`). Реализация — `recomp_14ad0` с теми же заглушками через `recomp_set_redirect` (в генераторе теперь
  до 32 целей на поток, было 4).
- Каждый прогон — на своей копии CUE (0xc710 байт в буфере 0x20000). Аллокатор выдаёт снимки из арены потока, memcpy
  копирует только в неё. В DCB, Gnm и настоящий CUE ничего не попадает. Затем выполняется один настоящий вызов.
- Сравниваются записанные вызовы (цель; регистры, которые цель читает; указатель в копию — как смещение; указатель на
  стек — как 32 байта, на которые он указывает), обе копии CUE целиком и арена.
- Стек под прогоном обнуляется (0xf00 байт, меньше страницы), чтобы неинициализированные локальные переменные были
  равны. После теневых прогонов он обнуляется ещё раз — там, где пойдёт настоящий вызов. Без этого мусор теневых
  прогонов попадал в неинициализированные локальные переменные настоящего вызова: офлайн это давало отличия
  verify / guarded / bench от оригинала, а native и original — нет.
- Указатель на стек распознаётся по окну 64 КБ под текущим `rsp`, а не по TEB: гостевой поток может жить на своём
  стеке.
- Две копии CUE на выборку — дорого, поэтому verify и guarded сверяют каждый N-й вызов (`SSPC_NATIVE_ENGINE_SAMPLE`,
  по умолчанию 256).
- Генератор случаев держит индекс 16-байтной записи тени в окне стадии (0x600 dword), как в игре. Со случайным
  14-битным индексом запись попадала на указатели самого CUE, и падал уже оригинал eboot.

### 5.1 Две ошибки, найденные в игре [E]

1. **Падение `r5d_recomp5_verify`.** Native Engine ставится до релокаций (`bootstrap.cpp`: установка до
   `linker.Execute` → `RelocateAll`). Пролог `0x14ad0` читает канарейку через слот GOT `eboot+0xd9de00`, а он при
   установке ещё 0: клон в self-check читал `[0]`. Self-check теперь на время кладёт в слот указатель на свою
   канарейку (проверка записи через `VirtualQuery`, восстановление RAII). Тест ставит `cue_commit` с `*слот = 0` и
   проверяет 0 после: без исправления он падал так же, с ним — PASS. Коммит `5d8f6ee`.
2. **Отказ self-check в игре.** Отличались 12 байт одного снимка (арена `+0xe94…+0xe9f`): `0x123d0` выдаёт 0x30
   байт, `0x639450` заполняет 0x24, хвост никто не пишет. Тень потока (`new Shadow`) не инициализирована, а
   `arena_dirty` начинался с 0: первый прогон (оригинал) видел мусор кучи, второй — нули своего `memset`. Значение
   менялось от запуска к запуску (`0x22`, `0x04`); в тесте свежая куча случайно была нулевой. Теперь первый прогон
   потока очищает всю арену (96 КБ один раз), дальше — только занятое предыдущим прогоном. Коммит `bbf1dc6`.
   Проверено заодно: `0x14ad0` не читает регистры, оставленные вызываемыми (четыре кандидата линейного прохода
   `E:\research\native-r5\r5d\leftover.py` — две ветви одного if/else), поэтому `recomp_call`, возвращающий только
   RAX/RDX/XMM0-1, для неё точен.

Выигрыша от перевода не ждём: это тот же x86-64 (`NATIVE_ENGINE_RECONSTRUCTION.md` §9). Ценность — проверенная точка,
где тень стадии превращается в user data, для будущего нативного рендера.
