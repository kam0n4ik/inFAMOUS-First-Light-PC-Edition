## 2. R2: внутреннее состояние CUE [A]

CUE = R + 0x128 (контекст рендера R, 254 слота пула + пре/пост + 5 деформации). Стадии CUE — нумерация Gnm:
0 CS, 1 PS, 2 VS, 3 GS, 4 ES, 5 HS, 6 LS, 7 [?]. Стадии draw слоя (`kStageVs = 0`, `kStagePs = 1`) — это стадии
CUE 2 и 1.

### 2.1 Поля

(в DCB, минуя тень); иначе — смещение в dword в тени стадии. Сеттер **всегда** ставит грязный флаг стадии, даже если
записал те же байты.

### 2.3 Commit `0x14ad0` для стадии с флагом (VS/PS) [A, `native_draw.cpp` CommitStage]

1. `n = u16[layout]`, `snap = alloc(n)` (`0x123d0`), `memcpy(snap, тень, 4n)`.
2. Указатели в снимок (`0x626400`, пара SGPR): байт 7 → `snap`, 8/9/0xA/0xB → `snap + u16[0x16/0x1A/0x1C/0x1E]·4`,
   у VS ещё 5/6 → `+0x18/+0x20`.
3. Прочие значения user data: байт 0xC → `CUE+0x78` (пара), 0xD/0xE → одно значение `+0xC0E0/+0xC100 + st·4` (у VS
   `+0xC0E8/+0xC108`, у PS `+0xC0E4/+0xC104`), у VS байт 4 → `CUE+0xC130` (пара), 0xF → `hi16·lo16` из `+0xC6E8`.
4. Флаги стадии сбрасываются.

Время жизни: тень — весь контекст (между кадрами старые дескрипторы остаются); снимок — неизменен после записи, живёт до
конца исполнения кадра (кусок арены кадра); значения user data — регистры SH GPU: сохраняются до перезаписи, но между
буферами разных контекстов их может переписать чужой DCB — поэтому после сброса CUE значения считаются неизвестными.

## 3. R3: Native Resource State (`SSPC_R7_RES_STATE=1|verify`, по умолчанию выкл.)

### 3.1 Источники

| Источник | Как наблюдается | Что даёт |
|---|---|---|
| 7 сеттеров (`0x16aa0/0x16b70/0x169d0/0x16d10/0x16eb0/0x16c40/0x16de0`) | `CueSetBuffers::SetObserver` — вызов в начале диспетчера во всех режимах, кроме Original | какие dword тени меняются (memcmp с тенью до записи), прямые SGPR (бит 15), записи вне окна стадии |

| сбросы `0x13d20`, `0x12390` | входные пробы (`InstallEntryProbe`, свой ProbeSite с FNV пролога) | привязки CUE устаревают до следующего commit; значения user data забываются |

### 3.2 Версии

На (CUE, стадия) — две версии, обе — уникальные id (номер потока в старших битах):
- **content** (`cv`) — меняется только когда сеттер реально меняет dword тени / прямое значение или пишет вне окна
  (тогда — все стадии CUE); кольца ES/GS в commit — стадии 3/4;
- **binding** (`version` в `NativeStageResources`) — выставляется на снимке commit; **сохраняется**, если cv, указатель
  раскладки, число dword и значения user data (прямые и записанные commit-ом) те же, что у прошлой привязки, иначе новая.

Равные binding-версии одной (CUE, стадии) ⇒ побайтно равные снимки, та же раскладка и те же значения user data.
`Fill` выдаёт стадию, только если привязка текущая: commit был после сброса, раскладка та же, грязный байт CUE = 0 и
cv не менялась после привязки (иначе `fills_stale` — commit мимо наблюдения). `version = 0`, если отслеживание не
полное (не все 7 сеттеров установлены, commit не native/guarded).

Не покрывается версией: память, на которую указывают дескрипторы (текстуры, константные буферы, глобальная таблица
`CUE+0x78`), и прямые SGPR из `0x16fb0` (один вызывающий, `0x192890`) — их потребитель обязан проверять как сейчас.

### 3.3 Доказательство корректности

- офлайн (`r7_resources_tests.cpp`): случайные последовательности вызовов настоящих сеттеров eboot (клоны), commit
  `recomp_14ad0` через `Resources::Commit` (его вызываемые Gnm — записывающие заглушки, user data как у GPU), смена
  шейдера, одиночные значения, сбросы через пробу `0x13d20`; после каждого commit для каждой выданной стадии:
  снимок == тень; равная версия ⇒ равные байты/раскладка/user data; указатели формы и прямые значения == записанным
  user data; дельта покрывает все отличия от прошлого снимка. Плюс негативный тест: неотслеживаемая запись в тень
  обязана дать verify-нарушение;
- игра (`SSPC_R7_RES_STATE=verify`): каждый снимок сравнивается с прошлым той же binding-версии
  (`verify_violations`), тень — с последним снимком, пока cv не менялась (`verify_shadow_violations`, ловит неизвестных
  писателей), и после каждого commit — то, что выдаёт `Fill`, с тенью (`verify_fill_mismatch`).

## 6. R4: кэширование ресурсов — только по измерениям [E, A]

Что можно было бы кэшировать на стороне CUE и сколько это стоит (окно 70..140 с `r7r_r3_state_verify`, ≈ 2240 кадров):

| Кандидат | Потенциал | Цена/риск | Решение |
|---|---|---|---|
| пропуск избыточных вызовов сеттеров (те же байты) | 39,5 % вызовов (CB 66 %) ≈ 25 k вызовов/кадр | сам вызов — десятки нс (native); выигрыш только если не ставить грязный флаг → commit не делает снимок = «CUE snapshot reuse» | **не делается**: отвергнуто в R5/R6 (R6 dedup = +0,00 FPS), новой гипотезы нет |
| повторное использование снимка при той же binding-версии | 15,1 % снимков ≈ 2,8 k/кадр; средний снимок — 15,5 dword (62 байта) | экономия ≈ 2,8 k × (alloc + memcpy 62 Б) ≈ единицы мкс/кадр; новый указатель всё равно нужен CP | **не делается**: потенциал ниже шума, тот же R6-dedup |
| кэш декодированных дескрипторов по версии (сторона CP) | см. §7 | требует правок `src/runtime/gpu/shader/*` | только предложение (§7.3) |

Равенство нигде не определяется по указателю: binding-версия выводится из сравнения байтов при записи (сеттер) и
проверена побайтно (§5). Память, на которую указывают дескрипторы, не кэшируется и версией не покрывается.
Итог R4: **реализаций кэша нет — отрицательный результат по измерениям** (producer-сторона не имеет потенциала;
consumer-сторона закрыта запретом на `shader/*`).

## 7. R5: A) CUE → PM4 → CP → Vulkan против B) CUE → Native Resource State → pipeline [E, A]

### 7.1 Что делает A сейчас (город, `r7r_r1_all_native`, весь прогон 150 с, `gpu_native.txt`)

- поток 1 CP — **30,4 мс/кадр** при кадре 31 мс (32,2 FPS; запись/поток 2 — 24,4 мс, GPU — 17,3 мс): поток 1 —
  узкое место; из него «frontend on the processor's thread» — 62,6 с за прогон;
- draws 47,1 M, из них 30,2 M идут «by their bindings only» (CITY-OPT Phase 5 engine runs: привязки ведущего draw);
  оставшиеся ≈ 16,8 M draw — через `PrepareStage`;
- P4.7 memo стадий: «taken again» 243 k из 35,4 M; промахи — «other user data» 13,2 M (новый указатель снимка на
  каждый commit) и «other inputs» 21,9 M; SRT reads 752 M (≈ 21 чтение на подготовку);
- Phase 6: VS-walk заново по изменившимся регистрам 1,25 M, PS 0,1 M.

### 7.2 Что даёт B (тот же поток данных без разбора PM4 и чтения снимка)

| | A (CP) | B (Native Resource State) |
|---|---|---|
| источник | SET_SH_REG user data → указатель снимка → SRT walk (чтения guest memory) | `NativeStageResources`: snapshot, shape (смещения), direct[], dwords — сразу из CUE |
| равенство с прошлым | только по указателю/16 dword + memory_gen (новый снимок = промах) или XXH3+memcmp снимка (P5.3) | **version** (u64) — без чтения снимка; доказано «равна → байты равны» |
| что изменилось | неизвестно → полный rewalk/decode стадии | **маска изменённых dword** (`ChangedDwords`) между двумя снимками стадии |
| измеренный потенциал | — | версия сохраняется у **15,1 %** снимков; изменённые dword — **55 %** от размера таблиц (т.е. частичный decode сэкономил бы ≤ 45 % работы decode на остальных) |
| стоимость производителя | 0 | `SSPC_R7_RES_STATE=1`: см. §7.4 |

Чего B не даёт: «other inputs» (программа, регистры VS/PS, вершинный формат) — их ключ остаётся за CP; память под
дескрипторами (текстуры/CB) — по-прежнему memory_gen/отслеживание записей CP; кольца ES/GS (стадии 3/4) — версия
сбрасывается при каждом commit с кольцами.

### 7.3 Предложение формата для CP ([shared], реализует R7-Core / владелец `shader/*`)

1. R7-Core при построении `NativeDrawCommand` вызывает `R7::Resources::Fill(cue, cmd.resources)` (заголовок
   `native_engine/r7/resources/resource_state.h`); при `version != 0` стадия передаётся CP в trailing-NOP / `StreamOp::Draw`
   рядом с id формы P5.3: `{u64 version, u64 snapshot, u16 shape_id, u32 direct_mask}`.
2. Фронтенд (`PrepareStage`): отдельный memo «ресурсная часть стадии» с ключом `(cue, stage, version, program)` —
   при совпадении берётся прежний `ResourceBindingPlan` без SRT walk и XXH3/memcmp снимка; «other inputs» остаются
   прежним ключом.
3. Опционально: маска изменённых dword (`ChangedDwords`, 0x600 бит) — повторный decode только дескрипторов,
   пересекающих изменённые dword (нужен индекс «dword → дескриптор» из walk).
4. Проверка: в verify-режиме CP сравнивает план из memo с полным decode (как P5.3 verify).

Оценка выигрыша сверху: ≤ 15 % подготовок ресурсной части стадии без walk; при 62,6 с frontend за прогон и доле
ресурсной части неизвестной (нет счётчика времени в `shader/*`) — **не измерено**; без инструментирования фронтенда
прирост FPS не заявляется.

### 7.4 Стоимость производителя B и разбивка по стадиям (серия `r7rs_state`, ABBA × 3, bench.lock) [E]

A = 10 реконструкций native (7 сеттеров, material_bind, cue_commit recomp, object_constants); B = A +
`SSPC_R7_RES_STATE=1`. Окно 70..148 с, `native_engine_ab.py`:

|---|---|---|---|
| avg FPS | 32,38 (31,92..32,76) | 32,22 (31,93..32,62) | −0,16 (внутри разброса) |
| 1 % low FPS | 26,94 (25,86..27,74) | 26,19 (25,17..27,55) | −0,75 (внутри разброса) |

Стоимость отслеживания **не измерима** (в шуме); ошибок нет ни в одном прогоне. Не PERFORMANCE_VERIFIED в смысле
