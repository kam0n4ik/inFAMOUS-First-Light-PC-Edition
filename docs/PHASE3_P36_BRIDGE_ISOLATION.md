# Phase 3 / P3.6 — Bridge Isolation & Runtime Boundaries

Живой документ подэтапа (начат 2026-10-10 16:40, HEAD на старте `d2ded75`, код = сборка `1801d84`, эталон «B» —
`build\ab\p35_final`). P3.6 — изоляция зависимостей, а не удаление shadPS4 и не новый графический бэкенд.

Три состояния (не эквивалентны):

* **NATIVE** — реализация принадлежит SecondSonPC; внутреннее состояние моста не используется (кроме явно
  записанного внешнего контракта).
* **ADAPTED BRIDGE** — реализация в мосте, SecondSonPC обращается к ней через свой ограниченный интерфейс с явными
  правилами владения и времени жизни.
* **DIRECT BRIDGE** — прямая зависимость от внутренностей shadPS4, не изолированная (или не изолируемая в P3.6).

Адаптер не переводит функцию из BRIDGE в NATIVE.

### 1.2 Граница сборки (как есть)

| Цель | Что | Пути заголовков | Связь с мостом |
|---|---|---|---|
| `sspc_runtime` (static) | `src\app\config,paths`, `src\base`, `src\input`, `src\loader`, `src\runtime`, `src\trace` | только `src\` + fmt, toml11, SDL3, Zydis | **заголовков shadPS4 не видит** (путей нет) — граница компиляции уже есть |

* Компоновка: SDL3, Zydis, fmt, toml11 — из externals моста (свой код линкуется с ними напрямую; это сторонние
  библиотеки, не shadPS4).
* **Обход границы, который путями заголовков не ловится:** объявление символа моста в своём коде (`namespace
  Libraries::Kernel { int foo(); }`) соберётся и слинкуется (один exe). Поиск по `src\` (без `src\bridge`): таких
  объявлений нет; упоминания `Core::`, `Common::`, `Libraries::` — только в комментариях.
* **Мост → SecondSonPC на уровне компиляции:** 8 пропатченных файлов shadPS4 включают 3 заголовка слоя адаптеров:
  `bridge\shadps4\track_diag.h` (диагностика P2.5, 0014), `gpu_alloc_diag.h` (SSPC-001, 0004),
  `perf_opts.h` (переключатели P2.5, 0015/0018–0020). Это цикл «адаптеры ↔ shadPS4» внутри одной цели моста; свой
  runtime в нём не участвует.
* Правило «заголовки shadPS4 только в `src\bridge\`» нигде не проверялось автоматически (только поиском вручную).

### 1.4 Циклы

* **Компиляции:** свой runtime ацикличен (shadPS4 не видит). Цикл «слой адаптеров ↔ shadPS4» (§1.2) — внутри цели
  моста.
* **Времени выполнения** (через указатели функций, не через заголовки):
  * errno: `Kernel::Host::Errno` (SecondSonPC) → `__Error()` моста → с `--native errno` ячейка SecondSonPC (0023);
  * часы: `Kernel::Host::ProcessTimeUs` → `sceKernelGetProcessTime` моста → с `--native clock` часы SecondSonPC (0024);
  * исключения: диспетчер SecondSonPC → `DispatchAccessViolation` моста → трекинг страниц → `Core::GpuMemory` →
    выбранный менеджер (свой с `--native memory`) → `GpuMemoryListener` → растеризатор моста;
  * память: загрузчик SecondSonPC → `Loader::Host` → `Core::GetGuestVirtualMemory()` → (свой менеджер) → уведомления
    GPU-моста.
  Циклы ожидаемые (адаптер «туда и обратно»); у каждого состояния один владелец. Новых в P3.6 не добавлять.

### 1.8 Очереди событий — факты

* **Единственная очередь игры — `trophyEqueue`** (создаёт `Game:Main`, eboot 0x55b24d): подсистема трофеев; рабочий
  поток в цикле (eboot 0x55b793/0x55b8a7) ждёт `sceKernelWaitEqueue(num=1, timo=NULL)`, затем
  `sceKernelDeleteUserEvent` и разбор команды; `AddUserEvent`+`TriggerUserEvent` — 0x55b31b/0x55b337. За прогон:
  Create 1, AddUserEvent 1, Trigger 1, DeleteUserEvent 1, Wait 2, Delete 0. Второе ожидание висит до выхода.
* **Графика в очереди игры ничего не доставляет.** `sceVideoOutAddFlipEvent/AddVblankEvent` игра не импортирует;
  `sceGnmAddEqEvent/DeleteEqEvent/GetEqEventType` импортированы, но в eboot это только переходники-заглушки
  (0x63b7f0…) — 0 вызовов во всех прогонах и ручных сессиях. Кадры синхронизируются опросом
  `sceVideoOutIsFlipPending` (~4 900 за прогон) и ожиданием флипа на GPU (`sceGnmInsertWaitFlipDone`, метки). Прежние
  записи «VideoOut/Gnm доставляют флипы и EOP в очереди игры» для этой игры неверны.
* **Дефекты моста (латентные, в игре не срабатывали):**
  * Q1 `kqueues` — глобальная `unordered_map` без замка; читают гостевые потоки, PresentThread (`GetEqueue` на каждом
    vblank при зарегистрированных событиях) и таймеры, пишут Create/Delete → гонка данных;
  * Q2 ключ таблицы `s32`, дескриптор `s64` — усечение;
  * Q3 `sceGnmAddEqEvent` захватывает **сырой `EqueueInternal*`** в обработчик прерывания GPU; `DeleteEqueue` без
    `DeleteEqEvent` → use-after-free в потоке GPU при следующем EOP; `delete` очереди при ожидающем потоке — тоже UAF;
  * Q4 `TriggerEvent` будит `notify_one`: два ожидающих с `num=1`, два события подряд → второй может не проснуться
    (потерянное пробуждение);
  * Q5 таймеры (asio) захватывают `this` очереди — UAF после удаления;
  * Q6 VideoOut: `flip_events`/`vblank_events` меняются гостевым потоком без замка, пока PresentThread их обходит;
    `DeleteFlip/VblankEvent` удаляет событие с идентификатором **порта**, а не Flip/Vblank, и `erase(find(...))` без
    проверки.

### 1.9 Кандидаты на адаптеры и решения

| Кандидат | Решение | Почему |
|---|---|---|

| host-интерфейсы (`Kernel::Host` и др.) | оставить | уже узкие интерфейсы своих потребностей |

## 2. P3.6.1 / P3.6.6 — граница сборки и её автоматическая проверка

Граница уже была (§1.2), но держалась на соглашении. Теперь она проверяется при каждой сборке
(`cmake\sspc_boundary_check.cmake`, чистый CMake, без Python; вызывается из `CMakeLists.txt`, когда меняется исходник,
патч или список разрешений; нарушение — ошибка сборки):

| Правило | Что ловит |
|---|---|
| 1. Свой runtime (`src\` кроме `src\bridge\` и `src\app\main.cpp`) включает только заголовки SecondSonPC и не включает слой адаптеров (`bridge/...`) | новый `#include` заголовка shadPS4 в своём коде (его и путями не найти — но правило даёт понятное сообщение и ловит `bridge/`) |
| 2. Свой runtime не называет пространства имён моста (`Libraries`, `Core`, `Common`, `VideoCore`, `Vulkan`, `AmdGpu`, `Shader`, `Frontend`, `Platform`, `Dev`, `ImGui`, `Storage`, `Emulator`) вне комментариев и строк | обход границы объявлением символа моста (компилируется и линкуется без заголовка — один exe) |
| 3. Файл слоя адаптеров (`src\bridge\**` кроме `generated\`, `src\app\main.cpp`) включает только заголовки shadPS4 из своей строки `cmake\sspc_boundary_allowlist.txt` (владелец, причина) | новую прямую зависимость адаптера от внутренностей моста; строку без владельца/причины; файл без строки |
| 4. Патчи моста включают только перечисленные заголовки SecondSonPC (`bridge -> …`: `track_diag.h`, `gpu_alloc_diag.h`, `perf_opts.h`) | новую зависимость моста от SecondSonPC (новый цикл) |

Отчёт `build\sspc_boundary_report.txt` (инвентаризация, метрика 2 в цифрах): свой runtime — **106 файлов, 231 include,
все свои, пространств имён моста нет**; слой адаптеров — **40 файлов, 108 прямых include 50 разных заголовков shadPS4**
(все в списке разрешений; устаревшие записи списка показываются); мост → SecondSonPC — 3 заголовка из 8 файлов (патчи
0004, 0014, 0015, 0018–0020); точки контракта, добавленные патчами (`UseTcbKey`, `SetEventInterceptor`,
`SetUserServiceEventSink`, …). `generated\bridge_exports.cpp` (объявления всех BRIDGE-экспортов, генерируется из
таблицы импортов) — исключение, явно.

Пределы инструмента: только `#include "…"` (угловые — системные и сторонние библиотеки); комментарии снимаются построчно
(`//`, однострочный `/* */`, строки блока, начинающиеся с `*`); использование через макрос или псевдоним пространства
имён не видно; дерево shadPS4 проверяется через его патчи (только они могут добавить зависимость от SecondSonPC).
Проверка **не утверждает «изоляция достигнута»**: она фиксирует текущий список прямых зависимостей и не даёт ему
незаметно расти.

Тест проверки: `tools\tests\boundary_check_tests.ps1` — 13 случаев на образцах: каждое нарушение даёт ошибку со своим
сообщением; упоминание в комментарии/строке и свой заголовок проходят; устаревшая запись попадает в отчёт — **13/13**.

Что P3.6.1 поменяла в самом коде границы: новые прямые зависимости добавлены только в слой адаптеров
(`event_queue_host.cpp` → `equeue.h`; `lifecycle_host.cpp` → `emulator.h`, `common/logging/log.h`; самотесты), свой
runtime получил два своих контракта (`Kernel::EventQueues`, `Lifecycle`) и ни одного заголовка моста.

## 3. P3.6.2 — очереди событий

### 3.1 Решение: ADAPTED BRIDGE (владелец — libkernel моста)

Перенос владения не нужен (§1.9): в игру графика события не доставляет, единственная очередь — трофейная; Phase 4
заменяет GnmDriver/VideoOut, а не libkernel, и будет доставлять события через контракт. Второй таблицы очередей нет.

### 3.2 Архитектура после P3.6

```
игра ──sceKernelCreateEqueue/WaitEqueue/Add|Trigger|DeleteUserEvent/DeleteEqueue──► libkernel моста (equeue.cpp)
                                                                                       таблица: shared_mutex,
GnmDriver: обработчик прерывания EOP ──EqueueTriggerEvent(EqueueId)──┐                 ключ s64, shared_ptr<очередь>
VideoOut: PresentThread (flip, vblank) ──EqueueTriggerEvent(EqueueId)┼──► FindEqueue(id): дескриптор + serial
таймеры (io_context) ──EqueueTriggerEvent(EqueueId)──────────────────┘
SecondSonPC Kernel::EventQueues::Owner (контракт для GPU-бэкенда Phase 4) ──► event_queue_host.cpp ──► тот же API
```

* **Идентичность:** `EqueueId` = дескриптор + serial объекта (serial не переиспользуется). Производитель хранит id, не
  указатель. Удалённая очередь и новая очередь с тем же дескриптором — разные: доставка по старому id ничего не делает.
* **Время жизни:** таблица держит `shared_ptr`; поиск под `shared_lock` и удержание на время вызова. Удаление: сначала
  из таблицы (под `unique_lock`), потом дескриптор — новый `Create` не получит номер, пока старая очередь в таблице.
* **Ожидание:** `WaitForEvents` прежняя (условная переменная очереди), `TriggerEvent` будит **всех** ожидающих.
* **Удаление во время ожидания:** ожидающий держит объект; производители его больше не находят; он просыпается по своему
  тайм-ауту или по событию, уже зарегистрированному (как BSD-`close` очереди: ждущий `kevent` не прерывается). Без
  тайм-аута — ждёт; на выходе процесса такой поток завершает `ExitProcess` (проверено, §4). Поведение PS4 при удалении
  очереди с ожидающим потоком не подтверждено — игра так не делает (её ветка удаления ждёт окончания рабочего потока).
* **Ошибки гостевого API** прежние: `EBADF` (нет очереди), `EFAULT` (нет массива), `EINVAL` (num < 1, имя/указатель),
  `ENAMETOOLONG`, `ENOENT` (нет события), `ETIMEDOUT` (ничего за тайм-аут, и при опросе).
* **User-события** остаются «уровневыми» (без `Clear`): ожидание возвращает их снова, пока игра их не удалит — так
  трофейный поток игры и работает (ждёт → `DeleteUserEvent`).
* **Горячий путь:** у игры нет ни одного события VideoOut/Gnm, поэтому на кадр ничего не добавилось (список событий порта
  пуст; на vblank — пустой цикл под уже бравшимся `vo_mutex`). Флип берёт `vo_mutex` один раз на кадр.

### 3.3 Контракт `Kernel::EventQueues` (`src\runtime\kernel\event_queues.h`)

`Find(handle) → QueueId`, `AddEvent(id, ident, filter, udata)`, `RemoveEvent(id, ident, filter)`,
`Trigger(id, ident, filter, data)`; фильтры `User`, `VideoOut`, `GraphicsCore`; любой поток; семантика данных
(для VideoOut — подсказка: верхние 48 бит сохраняются, ниже — 12 бит TSC и 4-битный счётчик срабатываний) записана в
заголовке. Владелец ставится при старте (`InstallKernelHost`). Реализация — `event_queue_host.cpp` поверх API патча 0025.

### 3.4 Исправленные дефекты моста (патч 0025)

Q1 (таблица без замка), Q2 (ключ `s32`), Q3 (сырой указатель в обработчике прерывания GPU; `delete` при ожидающем),
Q4 (`notify_one`), Q5 (таймер захватывал `this`), Q6 (списки событий VideoOut без замка; удаление не того события,
`erase(find)` без проверки). В игре ни один не срабатывал — латентные (`KNOWN_ISSUES.md` SSPC-012).

### 3.5 Тесты

Группы `EventQueues` (43), `EventQueues(mt)` (8), `EventQueues(gnm)` (11) — в `--selftest` и `--selftest --native
memory`: ошибки и тайм-ауты гостевого API; user-события как у трофейного потока; блокирующее ожидание просыпается по
событию, а не по тайм-ауту; два ожидающих — оба просыпаются от одного события; удаление при ожидающем (он кончает
по своему тайм-ауту, объект жив); контракт: GPU-событие, флип (аргумент и счётчик 2 после двух срабатываний), user-
событие с данными, удаление; идентичность при повторном дескрипторе; гонки: 4 производителя × 20 000 при 2 потоках
создания/удаления 3000 очередей и потоке поиска/опроса — все доставки, ни одной ошибки; удаление при 4 доставляющих
производителях — до удаления доставлено, после — отказ; прерывание EOP после удаления очереди без
`sceGnmDeleteEqEvent` (было UAF) — ничего; новая очередь регистрирует то же прерывание (другой ключ) и получает его.
**Мутация:** с прежним `notify_one` проверка «два ожидающих» падает (второй проснулся через 5000 мс по тайм-ауту).

## 4. P3.6.3 — жизненный цикл процесса

### 4.1 Один владелец остановки: `src\base\lifecycle.{h,cpp}` (SecondSonPC)

* **Штатная остановка** — `Lifecycle::Exit(code, reason)` или `std::quick_exit` кем угодно (обработчик `at_quick_exit`):
  первый вызвавший выигрывает (атомарный CAS `Running → Exiting`), выполняет шаги **один раз**, на своём потоке, пока
  остальные потоки работают; затем `quick_exit(code)` → `ExitProcess` (потоки моста и игры гасит ОС).
* **Шаги — по стадиям**, внутри стадии по порядку добавления:
  1. *reports*: счётчики импортов, итоги своих runtime (патчер, исключения, часы, потоки, память), процесс (HANDLE,
     потоки, commit) + сброс журналов;
  2. *services*: остановка backup-потока сохранений моста (ждёт записываемую копию);
  3. *storage*: закрытие кэша шейдеров моста (дописывает очередь, его статистика — в журнал моста);
  4. *devices*: подсветка контроллеров;
  5. *logs*: «session end», сброс обоих журналов.
* **Одновременный выход:** проигравшие `Exit` ждут (их снимет `ExitProcess`); `Exit` изнутри шага — немедленный
  `TerminateProcess` с кодом первого выхода (шаги не могут выполниться дважды). Устаревший `std::quick_exit` другого
  потока во время шагов `Exit` не «паркуется», а ждёт их окончания и сам завершает процесс: UCRT выполняет обработчики
  `at_quick_exit` под своим замком выхода, и ожидание в обработчике держало бы его, пока победитель не сможет вызвать свой
  `quick_exit` (найдено при перепроверке, тест `quick-exit-during-exit`).
* **Сторож:** если шаги не уложились в 30 с (шаг ждёт поток, который не ответит), запись без замков
  (`Log::EmergencyWrite`) и `TerminateProcess(code)`. Раньше зависший шаг вешал выход навсегда.
* **Фатальный путь** (`Lifecycle::EnterFatal`, lock-free): репортёр P3.4 (`Cpu::Exceptions::Fatal`) и фильтр
  необработанных исключений (`crash.cpp`) входят в него первыми; после этого ни одна штатная остановка не выполняет
  шаги (ждёт; процесс завершает фатальный путь своим `TerminateProcess`). Внутри обработки исключений ничего не
  останавливается и не закрывается — экстренный путь P3.4 не менялся (одна атомарная запись).
* **Мост больше не начинает свою остановку** (патч 0026): `Emulator::Shutdown()` (из любого `ASSERT` моста и из его
  VEH) вызывает хук SecondSonPC — одна строка в журнал без замков и сброс журналов; `Emulator`, созданный этими путями,
  не делает стартовой работы и не регистрирует `at_quick_exit`.

### 4.2 Пути остановки после P3.6 (сравнить с §1.6)

| # | Событие | Теперь |
|---|---|---|
| S1 | окно закрыто | `Lifecycle::Exit(0, "the window was closed")` → шаги → `ExitProcess` |
| S2 | ошибка старта | окно сообщения → `Lifecycle::Exit(1, "a start-up failure")` |

### 4.3 Порядок старта (без изменений по составу)

`main` → `RunGame`: … `InstallLifecycle` (шаги, `Install(30000)`, хук моста — до любого кода моста, который может
упасть в `ASSERT`) → журнал моста → `InstallGuestCpu` → `InstallKernelRuntime` → менеджер памяти → окно → `Signals`

### 4.4 Не сделано / пределы

* Потоки моста (GpuCommandProcessor, PresentThread, AudioOut, кэш шейдеров IO, io_context) не останавливаются явно —
  их гасит `ExitProcess`, как до P3.6. Явная остановка GPU-моста — работа Phase 4 (своего бэкенда).
* Сторож не покрывает `ExitProcess` после шагов (отключение DLL: драйвер Vulkan, SDL) — сторожа гасит сам `ExitProcess`.
  Замена на `TerminateProcess` отвергнута: драйвер может не записать свой кэш.
* Объект `Emulator` по-прежнему создаётся в пути `ASSERT` моста (`common\assert.cpp` в дереве поколения кэша шейдеров —
  не трогается), но он инертен.
* `_exit` вызывается 0 раз во всех прогонах — проверен самотестом в дочернем процессе, не игрой.

### 4.5 Тесты

Группа `Lifecycle` — 9 случаев, каждый в дочернем процессе (`--lifecycle-child`): `Exit(7)` (код, шаги по стадиям при

(код 42). Игровые прогоны закрываются окном через S1 (§8).

### 6.3 Контракт будущего бэкенда (требования, без фиксации архитектуры)

* **Создание/уничтожение:** выбор бэкенда один раз при старте (как менеджер памяти: флаг, до первого обращения), без
  смешения владельцев; уничтожение — шаг `Lifecycle` (дождаться GPU, сбросить кэши); фатальный путь ничего не ждёт.
* **Гостевая память:** через `GpuMemory`-контракт (перенесённый в SecondSonPC) — не через менеджер напрямую.
* **Командные буферы:** приём `dcb/ccb` (и ASC) с той же семантикой очередей, что у игры (порядок, `SubmitDone`, idle).
* **События:** EOP/флип — через `Kernel::EventQueues` и метки в гостевой памяти (`TryWriteBacking`).
* **Синхронизация:** `IsFlipPending`, `WaitFlipDone`-метки, idle; время — часы SecondSonPC.
* **Состояние устройства/ошибки:** ошибка устройства — фатальный путь с отчётом (как P3.4), без «тихих» продолжений.
* **Диагностика:** время кадра по флипам, время потока команд, число draw/dispatch, счётчики трекинга — для сравнения с
  мостом в одних и тех же сценах (`perf_runs`).
* **VideoOut:** минимальная связь — регистрация буферов, флип по маркеру, статус флипа, метки, частота.

**OPEN QUESTIONS** (нужны до проектирования интерфейсов команд): какие PM4-пакеты и их варианты реально шлёт игра
(статистика по типам за кадр); как игра использует ASC (одна очередь `sceGnmMapComputeQueue`); используются ли
`DingDong`/`WaitRegMem` на метках между очередями; форматы GNF/тайлинг образов игры; какие шейдерные стадии и
расширения (ES/GS/LS/HS) нужны; объём и частота копий констант (P2.5 §14.2c); точная семантика `flip_rate` и vblank
при пропуске кадров на консоли.

## 7. Совместимость флагов

| Флаг | Что | Требует | Отказ при старте |
|---|---|---|---|
| `--native memory` | свой менеджер памяти | `--loader sspc` | с `kernel-dmem` |
| `--memory-commit on-demand` | commit по требованию | `memory` | без `memory` |
| `--native threads` | свои потоки | — | с `--bridge kernel-*` |
| `--native cpu` (`fs-patch`) | свой патчер, SSE4a | — | (на CPU, где нужны другие патчи моста, — мостовой с предупреждением) |

| `--native errno`, `--native clock` | errno, часы | `--loader sspc` | повторная установка |
| `--native kernel-memory` | функции памяти libkernel | `memory` | без `memory` |
| **`--native exit`** (P3.6) | гостевой `_exit` через `Lifecycle` | `--loader sspc` | неизвестная группа — отказ (общая проверка) |

Без флагов (по умолчанию) P3.6 меняет: патч 0025 (очереди — тот же владелец, безопасный доступ), патч 0026 и `Lifecycle`
(тот же набор шагов выхода, один владелец, сторож), проверку границы при сборке. Новых экспериментальных режимов по
умолчанию нет. Проверенные комбинации — §8.1.

вывода (SPIR-V моста как эталон перевода).

констант в потоковый буфер, интервалы/барьеры, привязки, один поток записи команд, GPU-трекинг (~60 тыс. AV/с).

неверный темп vblank (бимодальность 30/60), трекинг страниц через исключения, отсутствие кэша пайплайнов.

на CPU, а не GPU (§14.2c P2.5), но это профиль одной сцены. Первая подфаза Phase 4 — корректность, не ускорение.
