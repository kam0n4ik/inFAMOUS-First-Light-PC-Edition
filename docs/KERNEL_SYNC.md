# Native Kernel Synchronization Layer (Phase 2, P2.2)

Синхронизация libkernel: что игра импортирует, в каком порядке это переносится с моста shadPS4 на
собственную реализацию, как устроен слой и чем проверен. Источники: `docs\generated\KERNEL_AUDIT.md`
(вызовы за прогон аудита), `tools\find_calls.py` (места вызова в `eboot.bin`), реализация эталона
`third_party\shadPS4\src\core\libraries\kernel\threads\*.cpp`.

## 1. Инвентарь и анализ зависимостей (C1)

Вызовы — за прогон аудита; «места в eboot» — прямые вызовы из `eboot.bin` (остальные импорты —
из LLE-модулей `sce_module`).

| Группа | Импорты | Вызовов | Места в eboot | Риск | Решение |
|---|---|---:|---|---|---|
| 1. Мьютексы | `scePthreadMutex{Init,Destroy,Lock,Unlock,Trylock}`, `scePthreadMutexattr{Init,Destroy,Settype,Setprotocol}`, POSIX `pthread_mutex_*`, `pthread_mutexattr_*` (19) | ≈ 28,8 млн | Lock 553, Unlock 621, Init 335 | высокий | **NATIVE** (P2.2.3, группа `kernel-mutex` вместе с condvar) |
| 2. Семафоры | `sceKernel{Create,Wait,Signal,Delete}Sema` (4) | ≈ 122 тыс. | 1 / 2 / 2 / 1 (одна обёртка `0x66a0c0…0x66a123`) | средний | **NATIVE** (этот шаг) |
| 3. Event flags | `sceKernel{Create,Delete,Set,Wait}EventFlag` (4) | ≈ 8,8 тыс. | 22 / 32 / 6 / 17 | средний | следующий шаг |
| 4. Event queues | `sceKernel{Create,Delete,Wait}Equeue`, `sceKernel{Add,Trigger,Delete}UserEvent` (6) | 6 | Create 1, Wait 2 | высокий | с Phase 4: в очереди игры пишут VideoOut/GnmDriver моста (flip, EOP) |
| 5. Condvar | `scePthreadCond{Init,Destroy,Wait,Broadcast,Signal,Timedwait}` (6) | ≈ 1,3 млн | Wait 15, Broadcast 45 | высокий | **NATIVE** (P2.2.3, группа `kernel-mutex`: ждут на мьютексах) |
| 6. Прочее | RW-блокировки `scePthreadRwlock*` (7, ≈ 2,7 тыс.; импортирует только Fios2); `__error` (errno) | — | rwlock в eboot нет | высокий / средний | rwlock — **NATIVE** (P2.2.3, отдельная группа `kernel-rwlock`); errno — последним (общий со всеми BRIDGE-функциями) |

### Подробно по группам

**Семафоры.** `s32 sceKernelCreateSema(SceKernelSema* sem, const char* name, u32 attr, s32 init, s32 max,
const void* opt)`, `s32 sceKernelWaitSema(SceKernelSema, s32 need, u32* timeout_us)`,
`s32 sceKernelSignalSema(SceKernelSema, s32 count)`, `s32 sceKernelDeleteSema(SceKernelSema)`; ABI —
System V (guest → host). Дескриптор в SDK — указатель (8 байт); обёртка игры читает его как qword
(`mov rdi, [rdi]`); эталон пишет и читает 32 бита (индекс таблицы) — так же делает нативная версия.
Игра: 20 семафоров при запуске, `attr = 1` (FIFO), ожидание всегда `need = 1` без таймаута,
удаления нет. Память: объект хоста, гость хранит только дескриптор. Ошибки: `EINVAL` (параметры,
переполнение max), `ESRCH` (дескриптор), `ETIMEDOUT`, `EACCES` (удалён во время ожидания),
`ECANCELED`, `EBUSY` (poll). Ожидание: FIFO или по приоритету потока, потребность в N токенах,
таймаут с записью остатка. Планировщик: нужен только приоритет вызывающего потока (через
`Kernel::Host`). Объекты самостоятельны: код моста семафоры игры не использует (поиск по
`third_party\shadPS4\src`). Риск deadlock — средний (потеря пробуждения = зависание ждущего).

**Event flags.** 64-битный шаблон; ожидание AND/OR, очистка CLEAR_ALL/CLEAR_PAT, атрибуты
SINGLE/MULTI-waiter и FIFO/PRIO, таймаут с остатком, результат-шаблон; `ECANCELED`/`EACCES` при
отмене/удалении, `EPERM` для второго ждущего у SINGLE. Самостоятельные объекты; 22 места создания
и 32 удаления — объекты живут коротко (загрузки), удаление при ожидании — реальный сценарий.

**Мьютексы / condvar / rwlock.** Гость хранит указатель на объект хоста в своей памяти; статический
инициализатор = NULL, объект создаётся лениво при первом `lock`. Типы: обычный, recursive,
errorcheck, adaptive; ошибки `EINVAL`, `EBUSY`, `EDEADLK`, `EPERM`. Нужна идентичность потока-владельца
(гостевые потоки — потоки Windows 1:1, хватит идентификатора потока хоста). Горячий путь: каждая
лишняя микросекунда ≈ 29 с CPU за 150 с игры. Перенос только целиком (condvar ждёт на мьютексе),
после проверки, какие функции моста получают указатели на мьютексы игры.

**Event queues.** Очереди создаёт игра, события в них кладут VideoOut (flip) и GnmDriver (EOP) моста —
перенос без собственного графического рантайма разорвал бы эту связь.

## 2. Архитектура слоя (C2)

`src\runtime\kernel\sync.h` — общее для всех объектов, без заголовков shadPS4:

- **`HandleTable<T>`** — дескрипторы → `shared_ptr<T>`. Порядок выдачи как у `SlotVector` эталона
  (наименьший свободный, освобождённые — LIFO), ёмкость задаёт вид объекта (семафоры — 65 535).
  Удалённый объект живёт, пока его держат ждущие потоки (у эталона — use-after-free).
- **`Waiter` / `WaitList`** — ждущий поток на своём стеке; порядок пробуждения: приоритет (меньше —
  раньше), FIFO среди равных, или чистый FIFO. Пробуждение = причина (`Signaled` / `Deleted` /
  `Canceled`) + личный `std::binary_semaphore`; причина пишется под замком объекта, поэтому таймаут,
  совпавший с сигналом, разрешается по причине — сигнал не теряется.
- **`Block()`** — сон с таймаутом (мкс) или без; ожидание без таймаута дольше 60 с один раз пишет
  `[Kernel] thread N has been waiting on <объект> …` (диагностика зависаний; на быстрый путь не влияет).
- Примитивы Windows: `std::mutex` (SRWLOCK) и `std::binary_semaphore` (WaitOnAddress) — только как
  «замок» и «будильник». Семантику PS4 (порядок, потребность в N токенах, причины) реализует слой, а
  не семафоры Win32 (у тех нет FIFO/приоритетного порядка и ожидания N единиц).
- Что остаётся от моста: приоритет гостевого потока (`Kernel::Host::CurrentThreadPriority`, потоки —
  BRIDGE до P2.4; для потока хоста — самый низкий приоритет вместо падения эталона).
- Переключатель: группа экспортов. `--bridge kernel-sema` возвращает семафоры эталону (проверено:
  NATIVE 75 → 71).

### Семафоры: отличия от эталона

Сознательно иначе, чем у эталона (эталон здесь ошибается):
1. удаление при ожидании — объект живёт до выхода ждущих (у эталона они берут замок уничтоженного);
2. остаток таймаута после сигнала не уходит ниже 0 (у эталона — переполнение `u32`);
3. `Signal` при `tokens + count > 0x7fffffff` — `EINVAL` (у эталона переполнение `s32`, UB, сигнал
   принимается): единственная строка «KNOWN» в самотесте.

Как у эталона (и не как у libkernel): `need` и `count` не проверяются на `< 1`; дескриптор — 32 бита.

### Семафоры: что проверено (C4)

| Требование | Проверка (`--selftest`) |
|---|---|
| ошибочные параметры, дескрипторы | `Create` с NULL-именем, `attr 3`, `init -1`, `max 0`, `init > max`; `Wait/Signal/Delete` на `0xffff`, `0x7fffffff`, удалённом — коды совпадают с эталоном |
| повторное ожидание | ожидание снова после таймаута и после успеха |
| удаление при ожидании | 2 ждущих (без таймаута и с таймаутом 5 с) → оба `EACCES`, у таймаутного остаток 0, дескриптор недействителен; FIFO-ждущий после удаления → `EACCES` |
| таймауты | 30 мс → `ETIMEDOUT`, остаток 0, список ждущих пуст; сигнал через 20 мс при таймауте 2 с → OK, остаток записан; таймаут 0 |
| несколько ждущих | 2 ждущих, `Signal 1` будит ровно одного; второй — следующим сигналом |
| приоритеты пробуждения | FIFO-семафор: порядок прихода при любых приоритетах; приоритетный: 500 → 600 → 600 (первый пришедший) → 700; ждущий `need 3` пропускается ждущим `need 1` (как у эталона) |
| потерянные сигналы | 4 производителя × 4 потребителя × 5000: все токены потреблены, 0 осталось, никто не ждёт |
| завершение процесса при активном ожидании | поток оставлен ждать навсегда; самотест завершается (`quick_exit`) |
| отмена | `Cancel(5)` → ждущий `ECANCELED`, токенов 5; `Cancel(-1)` → начальное значение; `Poll` |

**НЕ ПРОВЕРЕНО:** игра с нативными семафорами (загрузка, геймплей, отсутствие зависаний);
приоритетный порядок с настоящими гостевыми потоками (в игре — только FIFO-семафоры, `attr = 1`);
поведение при `need`/`count` < 1 от LLE-модулей (в eboot — только 1).

### Event flags: реализация и отличия от эталона

`sceKernel{Create,Delete,Set,Wait}EventFlag` (NID `BpFoboUJoZU` / `8mql9OcQnd4` / `IOnSvHzqu6A` /
`JTvBflhYazQ`) — ровно 4 импорта игры (подтверждено по `docs\generated\imports.csv` и
`import_table.inc`); Clear/Poll/Cancel игра не импортирует (реализованы для тестов). 64-битный шаблон
бит; ожидание AND/OR, очистка на пробуждении CLEAR_ALL (весь шаблон в 0) / CLEAR_PAT (`&= ~ждущие
биты`); атрибуты SINGLE/MULTI-waiter и FIFO/PRIO; таймаут с остатком; результат-шаблон; коды EPERM
(второй ждущий у SINGLE), ETIMEDOUT, EACCES (удалён при ожидании), ECANCELED, ESRCH, EINVAL
(шаблон 0, конфликт attr, неверный waitMode), ENAMETOOLONG (имя ≥ 32). Общий слой `sync.h`:
`HandleTable<EventFlag>` (ёмкость 65 535) и `Sync::Waiter`/`Block`; приоритет — `Kernel::Host`.

Сознательно иначе, чем у эталона (эталон здесь менее надёжен):
1. дескриптор через `HandleTable` (`shared_ptr`): удалённый при ожидании флаг живёт до выхода ждущих;
   мусорный/устаревший дескриптор → ESRCH (у эталона `delete ef` — use-after-free / двойное
   освобождение); дескриптор, отдаваемый игре, **1-based** (никогда не 0; у эталона — указатель кучи);
2. остаток таймаута пишется в `*pTimeout` при пробуждении по `Set` (у эталона он только обнуляется при
   таймауте, на успехе не трогается);
3. конфликтующий attr (FIFO|PRIO, SINGLE|MULTI) и неверный waitMode → EINVAL (у эталона `UNREACHABLE`/UB);
4. приоритетные ждущие — «меньше значение раньше», FIFO среди равных (как семафоры и `Kernel::Host`);
   у эталона event flag порядок обратный.

Как у эталона: `Set` будит всех подходящих ждущих в порядке очереди (ранний CLEAR-ждущий может
забрать биты раньше позднего); при ThreadMode SINGLE второй ждущий получает EPERM даже при готовом
шаблоне. ABI: дескриптор в SDK — указатель (8 байт), игра хранит и возвращает его как есть — нативная
версия пишет в него 1-based хэндл шириной 8 байт (как эталон пишет указатель).

### Event flags: что проверено (C4)

| Требование | Проверка (`--selftest`) |
|---|---|
| ошибочные параметры | `Create` NULL ef/имя, opt-param, attr > 0x22, имя ≥ 32 → ENAMETOOLONG; attr FIFO\|PRIO и SINGLE\|MULTI → EINVAL; waitMode AND\|OR и CLEAR_ALL\|CLEAR_PAT → EINVAL; шаблон 0 → EINVAL; NULL/удалённый дескриптор → ESRCH — коды совпадают с эталоном на безопасных путях |
| AND / OR | немедленно выполненные AND и OR (результат — текущий шаблон); блокировка до `Set`, частичный `Set` не будит AND-ждущего |
| CLEAR | CLEAR_ALL обнуляет шаблон на пробуждении; CLEAR_PAT снимает только ждущие биты; `Clear(pattern)` = `&= pattern` |
| несколько ждущих | один `Set` будит всех подходящих OR-ждущих (каждый видит шаблон); 32 ждущих — широковещательное пробуждение |
| порядок | FIFO: первый пришедший будится первым при любых приоритетах; PRIO: 500 → 600 → 700 |
| таймауты | 30 мс → ETIMEDOUT, остаток 0, результат — текущий шаблон, список пуст; `Set` в пределах 2 с → OK, остаток записан |
| удаление / отмена при ожидании | 2 ждущих (без таймаута и с 5 с) → оба EACCES, у таймаутного остаток 0, дескриптор недействителен; `Cancel(pattern)` → ECANCELED, результат = шаблон, счётчик, биты = шаблон |
| SINGLE | второй ждущий у SINGLE-флага → EPERM |
| повторное использование | `Create` после `Delete` переиспользует освобождённый дескриптор |
| потерянные пробуждения | 32-поточная эстафета (CLEAR_ALL, по одному `Set`) — разбужены все, ни один не потерян |
| Poll | OK при готовом шаблоне (с очисткой), EBUSY без |

**НЕ ПРОВЕРЕНО:** event flags в игре (оба загрузчика; путь `shadps4` их не использует); атрибуты
реальных флагов игры (22 создания / 32 удаления за прогон аудита) и AND/OR/CLEAR/таймауты в бою.

## 4. Мьютексы, condvar, RW-блокировки (Phase 2.2.3)

### Аудит зависимостей (до переноса)

- **Кто в мосте получает мьютексы/condvar игры.** Поиск по `third_party\shadPS4\src`: кроме самих
  `threads\{mutex,condvar}.cpp` — `libc_internal` (`_Mtxinit/_Mtxlock/...`, `fflush` → `_Lockfilelock`),
  `np_common` (`sceNpMutex*`, `sceNpCond*`). Игра импортирует из них только `fflush`
  (libSceLibcInternal, из `libSceFios2.prx`, 1 вызов за прогон): Fios2 передаёт ей `_Stdout` своего
  импорта libSceLibcInternal, а этот объект в таблице привязок **не разрешён** (UNRESOLVED) — FILE
  libc.prx с нативным мьютексом до `fflush` моста не доходит. `scePthreadOnce` (BRIDGE) мьютексов не
  использует (атомарное состояние).
- **Мьютекс и condvar неразделимы.** `CondWait` эталона сам отпускает и берёт мьютекс
  (`IsOwned/CvUnlock/CvLock` по объекту эталона), а `Signal/Broadcast` откладывают пробуждение через
  флаг `Deferred` мьютекса и очередь потока (`curthread->WakeAll()` в `Unlock`). Нативный мьютекс с
  condvar эталона (или наоборот) сломал бы оба — одна группа `kernel-mutex`. `--bridge kernel-condvar`
  принимается как имя той же группы (с предупреждением в логе).
- **Гостевой код пишет внутрь объекта мьютекса.** Дизассемблирование `libc.prx`
  (`tools\find_calls.py --module ...\sce_module\libc.prx`): сразу после `scePthreadMutexInit`
  — `mov rax,[mtx]; or dword ptr [rax+0x20], 0x100` (адреса 0x5b96a, 0x5bbf1, 0x5d81c), то есть libc
  ставит `PMUTEX_FLAG_PRIVATE` в слово флагов объекта. Эталон держит там `m_flags`
  (`static_assert(offsetof(PthreadMutex, m_flags) == 0x20)`). Остальные обращения к `+0x20` рядом с
  вызовами мьютексов в libc.prx — поля собственной обёртки libc (мьютекс в ней по `+8`, condvar по `+0x10`).
- **RW-блокировки** — отдельные объекты, их функции получает только Fios2; ни одна другая функция
  их не принимает → отдельная группа `kernel-rwlock`.
- **Что осталось от моста:** ничего. Владелец — идентификатор потока хоста (гостевые потоки —
  потоки Windows 1:1); `g_curthread` эталона не нужен. Отмена потоков (`pthread_cancel`) игра не
  импортирует — точки отмены в ожиданиях не нужны.

### Устройство

- `src\runtime\kernel\pthread_sync.h` — объект мьютекса с раскладкой libthr/эталона до `+0x24`:
  `0x00` владелец (id потока, 0 — свободен), `0x08` счётчик рекурсии, `0x0C` спины, `0x14` протокол,
  **`0x20` флаги** (тип в младшем байте, `0x100` от libc), `0x24` слово блокировки
  (0 свободен / 1 занят / 2 занят и, возможно, есть спящие). Тип читается из `+0x20` при каждом
  захвате; после инициализации SecondSonPC это слово **не пишет** (`or` у libc неатомарный — эталон
  пишет туда `Deferred` в горячем пути).
- `mutex.cpp` — захват: CAS 0→1; иначе спин (adaptive, 2000 итераций, только протокол NONE — как
  эталон), затем `exchange(2)` и сон на слове (`std::atomic::wait` = WaitOnAddress); отпускание:
  `exchange(0)`, при «2» — `notify_one`. Статические инициализаторы `NULL` (error-check) и `1`
  (adaptive) создаются под одним замком при первом использовании; `2` — уничтожен.
- `condvar.cpp` — очередь `Sync::WaitList` (FIFO, как TAILQ libkernel) под замком condvar; ждущий
  встаёт в очередь **до** освобождения мьютекса (сигнал после освобождения его найдёт); мьютекс
  освобождается целиком (все уровни рекурсии) и восстанавливается после пробуждения;
  `scePthreadCondTimedwait` — относительный таймаут в мкс (`reltimedwait_np` libthr).
- `rwlock.cpp` — `std::mutex` + две `std::condition_variable` как механизм; правила — libthr:
  писатели в приоритете, но поток, уже держащий чтение (счётчик `rdlock_count` на поток, по всем
  rwlock), проходит мимо ждущего писателя (иначе рекурсивное чтение зависло бы).
- Уничтоженные объекты всех трёх видов не освобождаются (списки «retired»; десятки объектов за час
  игры): поток, ещё выходящий из ожидания, читает валидную память.

### Отличия от эталона (сознательно)

1. `CondDestroy` при ждущих → `EBUSY` (libthr); эталон удаляет объект под ними.
2. `CondWait` с уничтоженным мьютексом (значение 2) → `EINVAL` (libthr `_mutex_owned`); эталон вызывает
   `IsOwned()` на «объекте» по адресу 2 (UB, проверка `this <= 2` выкидывается компилятором) и
   отвечает `EPERM` — единственная строка «KNOWN» в `KernelCond`.
3. Повторный захват normal-мьютекса владельцем: libkernel — взаимоблокировка, эталон — assert (падение
   процесса); SecondSonPC пишет Critical в лог и блокирует поток (семантика PS4, видна в логе).
4. Нет «отложенного пробуждения» (Deferred): разбуженный сигналом поток сразу пытается взять
   мьютекс. Корректность не меняется; цена — возможный лишний цикл сна, измеряется по FPS.
5. RW-блокировки: приоритет писателей (libthr) вместо «читатели первыми» эталона
   (`Common::SharedFirstMutex` — писатель может голодать); `unlock` без удержания → `EPERM` (у эталона
   `unlock_shared()` — UB); тип атрибута проверяется эталоном только для SDK ≥ 4.50 — игра SDK 4.00.
6. Владелец и `PTHREAD_PRIO_INHERIT/PROTECT`: протокол хранится, приоритеты не повышаются (эталон
   тоже не повышает).
