# Phase 4 · P4.6 — аппаратное GPU-профилирование (NVIDIA Nsight Graphics) и разбор кадра

Статус: **В РАБОТЕ** (2026-10-11). Продолжение P4.6 после S1 (`951a76a`). Все числа — измерения на этом ПК; оценки
помечены «[оценка]». У каждого числа указан источник:

- **[GT]** — NVIDIA Nsight Graphics GPU Trace (аппаратные счётчики и временная шкала NVIDIA);
- **[TS]** — Vulkan timestamp queries SecondSonPC (`SSPC_GPU_PROFILE=1`: метка времени после каждой команды) —
  программная инструментализация, не аппаратная трасса;
- **[FL]** — журнал кадров (`logs\gpu_frames.csv`, `tools\frame_stats.py`): GPU busy = метки начала/конца пакета;
- **[CP]** — таймеры процессора команд SecondSonPC (строки «recording per frame» журнала);
- **[ST]** — счётчики бэкенда при выходе (`gpu_native.txt`).

Рабочие файлы: `logs\p46\gpu_profile\` (захваты Nsight), `logs\p46\g3_*…g7_*` (прогоны с профилем и A/B).

## A. Совместимость Nsight Graphics

| | |
|---|---|
| GPU | NVIDIA GeForce RTX 2060 6 ГБ, TU106 (Turing) |
| Драйвер | 596.21 (не менялся) |
| ОС | Windows 10 22H2 (19045), сессия Claude — повышенная (admin) |
| Vulkan | SDK 1.4.363 (`E:\VulkanSDK`), устройство Vulkan 1.3 |
| Nsight Graphics | **2026.2.0.26134** (build 37991608), распакован `msiexec /a` в `E:\tools\NsightGraphics-2026.2` |

Выбор версии (официальные release notes): 2026.3 требует драйвер **R615+** — с 596.21 не подходит; 2026.1 и 2026.2
требуют **R591.86+** — подходят. GPU Trace официально поддерживает Turing и новее; в 2026.x Turing помечен «support
will be removed in a future release». Установщик — официальный сервер NVIDIA, подпись «NVIDIA Corporation» валидна.

Что потребовалось:
1. Распаковка MSI без установки (без System32 и реестра).
2. **С разрешения пользователя** — две записи в `HKLM\SOFTWARE\Khronos\Vulkan\ImplicitLayers` (слои
   `VK_LAYER_NV_nomad` и `VK_LAYER_NV_GPU_Trace` из папки Nsight). Причина: в повышенной сессии загрузчик Vulkan
   игнорирует пути слоёв из переменных окружения и HKCU; без записи слой Nsight внедрялся в процесс, но не
   активировался (vkcube при этом трассировался как «Direct3D 12» через DXGI-показ драйвера). Слои спят, пока ngfx не
   задаст `ENABLE_VK_LAYER_NV_*=1`. Бэкап ключа: `E:\Installers\NsightGraphics\ImplicitLayers_backup.reg`.
3. Права на счётчики: в повышенной сессии ERR_NVGPUCTRPERM нет; глобальная настройка счётчиков **не менялась**.

Что работает: GPU Trace запуска игры через `ngfx.exe` (`tools\tests\p46_gputrace.ps1`), аппаратные счётчики
«Throughput Metrics» (единственный набор для Turing), отладочные метки VK_EXT_debug_utils (`SSPC_GPU_MARKERS=1`),
автоэкспорт таблиц (`FRAME`, `GPUTRACE_FRAME`, `D3DPERF_EVENTS` — время по меткам, `GPUTRACE_REGIMES` — 92 метрики по
меткам).

Ограничения, найденные на практике:
- `--platform "Windows (x86_64)"` перехватывается Qt (`-platform`) → ngfx падает (Qt6Core 0xC0000409) — параметр не
  передаётся.
- ngfx снимает приложение после трассы — нужен `--keep-going` (иначе нет журналов выхода игры).
- Сбор Shader Pipelines (по умолчанию) у нашей игры: +0,7–1,4 ГБ памяти процесса во время трассы, системный commit
  29,3/32,6 ГБ (без файла подкачки), файл трассы — 8-байтный заголовок, игра снята извне (`g1_village_b`). С
  `--disable-collect-shader-pipelines --disable-collect-external-shader-debug-info` трасса успешна (`g1_village_c`,
  110 МБ).
- **Возмущение:** кадр под трассой ~400 мс против ~57 мс без неё **[GT]/[FL]** (≈7×). На Turing GPU Trace снимает
  счётчики на границах диапазонов; у кадра с ~5000 draw, ~1700 dispatch и ~1100 полными барьерами это доминирует.
  Абсолютные миллисекунды GPU Trace для нашего кадра **непригодны**; относительный вклад мелких команд завышен.
  Метрики по диапазонам (`REGIMES`) заполнены только для первых нескольких диапазонов кадра.
- Классификатор автоматического режима Claude не даёт запускать захват самостоятельно («Unauthorized Persistence») —
  захваты запускал пользователь через `!` в сессии.
- Не проверялись: `--multi-pass-metrics`, real-time shader profiler, Graphics Capture (VK_EXT_external_memory_host и
  sparse-буферы, скорее всего, не поддерживаются захватом).

Вывод: GPU Trace на этой конфигурации **работает** и даёт аппаратные счётчики, но из-за 7-кратного возмущения
разбивку кадра по времени даёт **[TS]** (накладные ~10 %), а **[GT]** используется для качественной картины
(загрузка SM/L2/DRAM диапазона).

Интерпретация: в compute-диапазонах GPU почти не загружен — ни SM, ни кэши, ни DRAM. Время уходит на задержки

## E. Барьеры

**[ST]** деревня, весь прогон `g2_village_markers` (1574 кадра): 1 794 487 глобальных барьеров «всё→всё»
(`ALL_COMMANDS/MEMORY_WRITE → ALL_COMMANDS/MEMORY_READ|WRITE`, `Executor::GlobalBarrier`) ≈ **1140 на кадр**:

| Место (`GlobalBarrier(site)`) | Всего | На кадр | Причина |
|---|---|---|---|
| 8 перед dispatch | 1 050 928 (58,6 %) | ~668 | была любая запись хранилища с прошлого барьера (`pending_writes_`) |
| 5 перед DMA-копией / GDS на шкале | 366 461 (20,4 %) | ~233 | `CopyOnTimeline`: та же проверка; копии в среднем ~600 байт, подряд идущие копии разделены барьером |
| 6 перед загрузкой посреди пакета | 279 676 (15,6 %) | ~178 | `BeforeUpload` |
| 1/2/3 тени записи dispatch | 3 × 46 933 (5,2 %) | ~89 | копия в плотную тень и обратно |
| 7 перед draw | 3 556 | ~2 | |
| 4 перед WRITE_DATA | 0 | 0 | |

Стоимость **[TS]**: все промежутки «перед командой» (барьер + загрузки + смена render pass) — 9,7 мс/кадр. Кроме
прямой стоимости, барьер между каждой парой dispatch исключает их перекрытие на GPU: 1550 dispatch очереди 1 идут
строго последовательно (п. C.1). Отдельно стоимость сериализации не измерена (нужен опыт без барьера между
независимыми dispatch).

Корректность (P4.5, S1): барьеры перед командами после записи хранилища нужны — гость пишет буферы шейдерами, и
следующая команда может их читать; S1 опирается на барьер после WAIT по удержанному fence (`WaitMetByHeldFence` →
`pending_writes_`). Сужать без доказательства непересечения диапазонов нельзя.

| CP, мс/кадр (запись) | 63,1 / 50,8 (45,7 / 35,6) | 52,7 (38,3) | **46,4 (37,4)** | 50,9 (42,0) |

Вывод (предварительный, n = 1–2): BAR ускоряет **GPU** в обеих сценах (−14 / −5 мс), но запись CPU в BAR
(write-combined память через PCIe, ~33 МиБ/кадр мелкими кусками) удлиняет запись команд на пляже на ~4,5 мс; пляж
ограничен CPU, поэтому там FPS падает. Правильная форма изменения — **запись CPU в кэшируемую память + одна копия
в видеопамять перед пакетом** (GPU читает видеопамять). Включать `SSPC_DIAG_RING=bar` по умолчанию **нельзя**.

## I. Дым SSPC-020

1. **Факт по коду:** `CommandProcessor::WriteFence` (command_processor.cpp) записывает для data_sel 3/4 значение
   `ClockSample()` в момент записи fence. Для удержанных fence (Isolated) это момент, когда CP обнаружил завершение
   пакета (опрос timeline), а не момент исполнения команды на GPU. Две метки в одном пакете получают почти одно время;
   метки в соседних пакетах — интервал между завершениями пакетов (пакет — до 500 draw).
2. **CPU игры читает эти метки каждый кадр** (`SSPC_DIAG_WATCH=24be82000 SSPC_DIAG_WATCH_READS=1`,
   `logs\p46\g9_watch_clock`, `g10_watch_pairs`): инструкции eboot `0xace6f1a`/`0xace6f1d` (база eboot 0xab50000 →
   функция `0x196ef0`) читают пары 64-битных меток `+0x00/+0x08`, `+0x10/+0x18` (таймер A, двойной буфер по
   чётности кадра) и `+0x20/+0x28`, `+0x30/+0x38` (таймер B) через ~1,3 и ~2,2 мс после отправки кадра.
3. **Код игры** (дизассемблирование eboot): `0x196ef0` — GPU-таймер: `30000 / частота × (конец − начало)` по
   младшим 32 битам, т.е. время в тысячных долях кадра 30 FPS (1000 = 33,3 мс). Метки ставятся EOP-событием 0x28
   (BOTTOM_OF_PIPE_TS) с data_sel 4 (функции `0x196e50`/`0x196ea0`). Потребитель — `0x3ed6a0` (и копия `0x3ed7b0`):
   адаптивный **уровень качества** `this+0xca0` (3 уровня, таблица порогов `0xaaa900`: уровень 0 (0; 100), 1 (20; 100),
   2 (20; ∞)): повысить, если уровень ≤ 1, запас `1000 − t2 < 50` и `t1 ≥ 100`; понизить, если
   `t1 < max(порог, 0,25 · запас)`; `t2` — таймер A (кадр, глобальный объект `+0x118`, его же читает `0x472810`
   вместе с уровнем), `t1` — таймер B (проход, `this+0xca8`).
4. **Значения у нас** (400 кадров пляжа): таймер A 45–71 мс (среднее 48,3) — интервал между завершениями пакетов, а не
   работа GPU (~26 мс по timestamp пакетов); таймер B ≈ 0,002–0,007 мс в 255 кадрах (начало и конец в одном пакете),
   1,5–2,0 мс в 145 кадрах (между ними граница пакета), максимум 2,03 мс — порог повышения (3,33 мс) не достигается.
   При таких значениях контроллер прижат к уровню 0 и **не колеблется** в этом окне.
5. Вывод: зависимость игры от меток GPU-часов **доказана**, их значения у нас **неверны** (не время исполнения), но
   связь с мерцанием дыма на пляже этим путём **не доказана** — уровень в окне замера не меняется. Возможное влияние —
   другой уровень качества эффекта, чем на PS4. Семантика меток **не менялась**. Следующий шаг (по команде): метки в
   позиции команды (`vkCmdWriteTimestamp2` + калибровка VK_EXT_calibrated_timestamps), затем сравнить мерцание и
   уровень `this+0xca0` (адрес объекта — из регистров при вызове `0x3ed6a0`).
6. Побочный эффект диагностики: страница без доступа не импортируется в Vulkan (одна ошибка «cannot be imported» за
   прогон) — только в режиме `SSPC_DIAG_WATCH_READS=1`.

- **Что точно ограничивает FPS:** пляж и гавань — CPU-запись команд (один поток, ~6,7 мкс на draw); деревня — GPU,
  причём не шейдеры draw (20 %), а ~1550 микро-dispatch асинхронного compute гостя, которые у нас выполняются строго
  последовательно и ждут данные через PCIe, плюс барьеры и write-back. CP деревни тоже ~51–64 мс.
- **Ошибочные гипотезы:** «листва/дым — главные потребители GPU в деревне» — нет (все draw 13,5 мс); «~500 барьеров»
  — в деревне ~1140; «кольцо в BAR — бесплатное ускорение» — нет, на CPU-ограниченном пляже оно замедляет запись.
- **Первым оптимизировать:** таймеры по флагу (дёшево, CP); кольцо «кэш CPU → видеопамять GPU одной копией»
  (GPU деревни); затем write-back и барьеры.
- **Оставить инструменты:** `SSPC_GPU_PROFILE=1` + `logs\gpu_profile_full.txt` (разбивка по видам/очередям),
  `SSPC_GPU_MARKERS=1` + `tools\tests\p46_gputrace.ps1` (Nsight), `SSPC_DIAG_SAMPLE=1`,
  `SSPC_DIAG_WATCH(_READS)`.
- **Мешает 30 FPS:** пляж — CP 43–47 мс > 33; деревня — GPU ~60–66 и CP ~51–64 мс > 33.
- **Мешает 60 FPS:** нужен кадр ≤ 16,7 мс — однопоточная запись команд (~6,7 мкс/draw × 5800 draw ≈ 39 мс) в
  принципе не укладывается без конвейера потоков / многопоточной записи; GPU деревни — без перекрытия асинхронного
  compute (отдельная очередь) и без устранения PCIe-задержек.
