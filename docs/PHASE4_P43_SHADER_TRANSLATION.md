# Phase 4 / P4.3 — Native Shader Translation & Pipeline Cache

Статус: **см. §20**. Игру по-прежнему рисует мост shadPS4 (по умолчанию, без изменений). Подсистема подготовки шейдеров и
пайплайнов SecondSonPC работает на описаниях draw/dispatch своего командного процессора (P4.2): находит программы,
определяет их идентичность по содержимому, переводит GCN → SPIR-V через собственный интерфейс транслятора (реализация —
адаптер над транслятором моста), разбирает ресурсы, строит ключи специализаций, кэширует модули и пайплайны. В игре —
только в тени моста (`--gpu-shaders`, диагностика) и офлайн (`--gpu-shader-verify`); на GPU ничего не исполняется (P4.4).

Связанные документы: `PHASE4_P42_COMMAND_PROCESSOR.md` (описания draw/dispatch, регистры, тень), `PHASE4_GRAPHICS_BACKEND.md`
(стратегия), `PATCHES.md` (0030, 0031), `KNOWN_ISSUES.md` (SSPC-017, SSPC-018). Пометки: **[К]** — подтверждено кодом или
прогоном, **[Пр]** — предположение.

## 1. Архитектура ShaderFrontend

```
CommandProcessor (P4.2) ── DrawDescriptor / DispatchDescriptor + RegisterFile (семантика железа)
   │
ShaderFrontend::PrepareDraw / PrepareDispatch          (поток-владелец: поток командного процессора)
   │ стадии фрагмент → вершина (привязки нумеруются сквозь стадии пайплайна, как у транслятора)
   │   программа  PGM_LO/HI ─ ProgramCache: адрес → идентичность (стадия, длина, XXH3-128 кода); копия кода
   │   runtime    поля регистров стадии (RuntimeParams) — пересобираются только при изменении их групп P4.2
   │   layout     ресурсы программы для этих runtime-параметров = отражение её первой трансляции
   │   fetch      FetchCache: fetch-шейдер draw (свой разборщик, ошибки вместо ASSERT)
   │   ресурсы    SRT-обход (свой интерпретатор walker'а) → flat user data → V#/T#/S#/вершинные V#
   │              → ResourceBindingPlan (привязка, адрес, размер, статус каждого ресурса)
   │   ключ       SpecializationKey (runtime + начало привязок + поля дескрипторов, от которых зависит трансляция)
   │   модуль     по ключу: есть → готов; нет → создаётся Pending, задание транслятору (фоновый поток)
   ▼ пайплайн: модули + фиксированное состояние (GraphicsPipelineState) → PipelineStateCache; без поиска, если не
     менялись ни модули, ни группы регистров состояния (PipelineStateGroups)
DrawPreparation: готов (id пайплайна, модули, планы ресурсов) или ждёт (стадия и причина названы)
```

* **Владение и потоки.** Кэши программ, fetch-шейдеров и пайплайнов, планы ресурсов, статистика — один поток-владелец,
  без блокировок. Модуль создаётся владельцем в состоянии Pending; транслятор (фоновый поток или вызывающий) заполняет
  `Module::result` и публикует его `state.store(release)`; владелец читает после `load(acquire)`. Объекты `Program`/
  `Module` живут до уничтожения frontend (unique_ptr, адреса стабильны); задание держит указатели на них и копии
  входов (flat, код fetch, V#). Код программы — копия в `Program::code`, не изменяется после создания.
* **Ничего не исполняется на GPU**, гостевая память не пишется, страницы не отслеживаются. Ожидающий draw никогда не
  исполняется «чем-нибудь похожим»: статус Pending/Failed/NoProgram/FetchError/Unsupported.
* Файлы: `src\runtime\gpu\shader\` — `gcn_program.*` (футер, извлечение, идентичность, RSRC), `shader_types.h`
  (RuntimeParams, DeviceProfile, отражение), `runtime_params.*`, `shader_resources.*` (дескрипторы, fetch, SRT,
  ResourceBindingPlan, SpecializationKey), `shader_cache.*`, `pipeline_state.*`, `shader_frontend.*`,
  `shader_translator.*` (интерфейс), `shader_capture.*` (захват, офлайн-сверка, вид пайплайна моста).

## 2. Транслятор моста через адаптер

**Решение:** собственный транслятор GCN не пишется — используется проверенный транслятор shadPS4 (декодер, IR, ~25
проходов, эмиттер SPIR-V на sirit; GPL-2.0-or-later) **только через интерфейс SecondSonPC** `ShaderTranslator`
(`shader_translator.h`). Реализация — `src\bridge\shadps4\shader_translator_host.cpp` (граница интеграции, allowlist
`cmake\sspc_boundary_allowlist.txt`).

| Остаётся кодом shadPS4 | Принадлежит SecondSonPC |
|---|---|
| декодер GCN, CFG, IR, проходы (SSA, константы, ресурсы, flatten SRT, lowering), эмиттер SPIR-V; генерация x86-кода SRT-walker'а | какую программу, её код (своя копия, идентичность), runtime-параметры (из своих регистров P4.2), профиль устройства (свой Vulkan), начало привязок, **все чтения гостевой памяти** транслятора (через `GuestReader`), **SRT-обход** (свой интерпретатор walker'а), разбор fetch-шейдера (проверка до транслятора), отражение (свои типы), ключи, кэши, пайплайны, решения что транслировать и когда |

* `src\runtime\` не включает ни одного заголовка shadPS4 и не держит его объектов (проверка границы при каждой сборке;
  голое `Shader::` в своём коде запрещено — это имя пространства моста). Адаптер: свои типы ↔ `Shader::Info/RuntimeInfo/
  Profile`; глобальных объектов эмулятора не использует (свой `Shader::Pools`, свой мьютекс).
* **Патч 0030** (минимальный, без хука — ничего не меняется): `Shader::GuestReads` + thread_local `CurrentGuestReads()`
  — транслятор читает V# вершинных буферов, код fetch-шейдера, константы тесселяции через хук и отдаёт ему SRT-обход;
  неизвестный опкод в режиме хука возвращается флагом `translation_failed` (адаптер сообщает `UnsupportedOpcode`),
  а не `ASSERT`; общий буфер кода walker'ов (`g_srt_codegen`, 32 МиБ) пишется под мьютексом (адаптер транслирует на
  своём потоке рядом с потоком GPU моста).
* **Потокобезопасность [К, аудит]:** единственное общее изменяемое состояние транслятора — `g_srt_codegen` (+ его
  регистрация AV-обработчика); `Common::Decoder` используется только для дампов; остальное — в `Pools` и объектах
  вызова. Адаптер сериализует свои трансляции; мост и адаптер параллельны (мьютекс 0030). Самотест: 4 потока × 4
  трансляции — одинаковый SPIR-V.
* Что **не** сделано: транслятор не переписан; его ASSERT/UNREACHABLE внутри проходов и эмиттера (например,
  неподдерживаемый формат экспорта — найдено самотестом) по-прежнему завершают процесс — так же, как в мосте.

## 3. Схема GCN → SPIR-V

```
PGM_LO/HI → [ReadProgram: футер OrbShdr (по токену s_mov_b32 vcc_hi или поиск в 64 КиБ), длина ≤ 1 МиБ, копия кода]
         → TranslationRequest {стадия, код, адрес, user data[16], RuntimeParams, DeviceProfile, BindingStart,
                               GuestReader | flat/fetch/V# заданные}
adapter:  RuntimeParams → Shader::RuntimeInfo (BuildRuntimeInfo моста поле в поле); DeviceProfile → Shader::Profile
          Shader::TranslateProgram (CurrentGuestReads = адаптер):
             decode → CFG → IR → SSA/константы → ResourceDiscover → FlattenExtendedUserdata
                 (walker сгенерирован; RefreshFlatBuf → хук: свой SrtProgram по GuestReader | заданный flat)
             → ResourcePatching → … → структуризация → DCE → CollectShaderInfo
          скан IR: GetUserData → какие user data читает программа (после оптимизации)
          Shader::Backend::SPIRV::EmitSPIRV(profile, runtime, program, bindings)
          → TranslationResult {SPIR-V, ShaderReflection (ресурсы и их SharpLocation, flat размер, walker, fetch,
                               user_data_used, mrt, …), flat и V#, которые трансляция видела, время}
```

|---|---|---|---|
| PS (SPI_SHADER_PGM_*_PS) | Fragment | да | готовится полностью |
| VS | Vertex | да (VGT_SHADER_STAGES_EN = 0) | готовится полностью |
| CS (COMPUTE_PGM_*) | Compute | да (DCB и ASC) | готовится полностью |
| ES+GS (+копи-шейдер в VS) | Vertex+Geometry | **0** draw (группы GS/ES не менялись после старта, P4.2 §7) | `Unsupported` с причиной |

Отсутствие GS/тесселяции в записанных сценах **не доказывает** их отсутствия во всей игре **[Пр]**: проверены пляж, листва,
вступление; конфигурации стадий считаются каждым draw (`unsupported`).

## 5. Идентичность и инвалидирование программ

* **Идентичность = стадия + длина + XXH3-128 кода** (`ProgramIdentity`); адрес в неё не входит (одна программа по двум
  адресам — одна; адрес нужен только ресурсам: инлайн-константы относительно программы). Хэш футера (`shader_hash`
  компилятора) записывается, но не используется как ключ: **кэш программ моста индексируется именно им** — программа,
  переписанная на месте с тем же футером, была бы взята из кэша (SSPC-017). Коллизия 128-битного хэша (два разных кода)
  отказывается (`ProgramError::Collision`), никогда не сливается (самотест с принудительным хэшем).
* **Fallback вместо трекинга записей (решение P4.3):** адрес доверяется до ревалидации — при первом использовании в эпохе
  (кадре; `Validation::PerFrame`, по умолчанию) или при каждом использовании (`PerBind`, `--gpu-shader-validation
  per-bind`) футер и код читаются заново и сравниваются с копией (memcmp); другой код → другая программа (старая
  остаётся по идентичности и вернётся без трансляции). Окно PerFrame: программа, переписанная **внутри кадра** между двумя
  её использованиями, будет замечена со следующего кадра (то же окно, что у проверки подписи тени P4.2).
* `Invalidate(addr, size)` помечает адреса, перекрывающие записанный диапазон (код + футер), для чтения при следующем
  использовании — точка подключения слушателя памяти исполнителя P4.4 (`MemoryListener::OnGuestWrite/OnUnmap`, контракт
  P4.1). **Второго трекера страниц нет**, обработчиков исключений не добавлено (SSPC-010 не затрагивается).

## 6. Кэши

### 6.1 Модули и специализации
Модуль = программа + `SpecializationKey`. Ключ (слова + XXH3-64): байты `RuntimeParams` (поля регистров стадии; поля
других стадий нулевые — равенство байтов = равенство), начало привязок (если есть ресурсы), форма fetch-шейдера и форматы
вершинных V#, по каждому буферу/образу/семплеру — валидность и поля, которые читает транслятор. Хэш — индекс, совпадение
подтверждается всеми словами (коллизия считается и не сливает).

### 6.2 Полнота ключа (аудит транслятора)
Транслятор читает из дескрипторов больше, чем сравнивает `StageSpecialization` моста — модуль моста может быть взят для
другого содержимого (латентно, SSPC-017): формат storage-образа для атомиков (`GetFormat`), Sint vs Uint образа (в ключе
моста только `is_integer`), `ADD_TID_ENABLE` и `MTYPE`=3 (Coherent) буфера, размер образа FMask-формата, формат данных
неформатированного буфера (сдвиг адреса), размер LDS compute (`HwComputeRuntimeInfo::operator==` его не сравнивает).
**Ключ SecondSonPC — надмножество ключа моста**: он содержит эти поля (сырые форматы и выборки), поэтому один модуль
SecondSonPC никогда не соответствует двум модулям моста (проверяется в игре и офлайн, §10, §11); обратное — несколько
модулей SecondSonPC на один мостовой — допустимо (более тонкий ключ, лишние трансляции) и измеряется.

### 6.3 Layout
Ресурсы программы зависят от кода и runtime-параметров (например, буфер плоскостей отсечения), реже — от дескрипторов
(FMask убирает образ из списка). Первый модуль программы для данных runtime-параметров транслируется без ключа; его
результат даёт layout и собственный ключ (из того flat/V#, что трансляция видела). Расхождение списка ресурсов модуля с
layout считается (`layout_mismatch`).

### 6.4 Пайплайны
`GraphicsPipelineState` (поля регистров, байтовое сравнение): модули VS/PS; topology; poly mode; provoking vertex; clip
space; depth clip/clamp; форматы и сэмплы глубины/трафарета (при валидном буфере); logic op; режим цвета; CB_SHADER_MASK;
mrt из отражения; по каждой цели — INFO (формат, тип числа, swap, bypass), формат экспорта, blend (если включён), маска
записи, сэмплы. **Динамическое состояние (не в ключе):** viewport, scissor, depth bias, blend constants, stencil ref,
depth bounds, тесты глубины/трафарета, cull, front face — как бэкенд моста с extended dynamic state. Если с прошлого draw не
менялись модули и группы регистров состояния (`PipelineStateGroups()`, вычисляются из списка регистров) — пайплайн берётся
без построения состояния и поиска.

## 7. Ресурсы: ResourceDescriptor / ResourceBindingPlan

* Декодеры V# (таблица 8.5 Sea Islands ISA), T# (8.11, 8 и 128-битный), S# (8.12) — свои; поля сверены с раскладками
  `AmdGpu::Buffer/Image/Sampler` моста на 2000 случайных дескрипторах каждого вида (самотест).
* Где дескриптор: `SharpLocation` из отражения (одна загрузка или по dword: смещение во flat / непосредственное);
  встроенные (user data), указательные (SRT-таблицы — обход walker'а), вершинные (таблица V# fetch-шейдера), compute — те
  же механизмы. Post-ops моста повторены: OR dword1, смещение на адрес программы (инлайн-константы), cube → 2D array,
  128-битный T# (pitch = width), четыре операции семплера.
* **SRT-обход:** транслятор генерирует x86-walker; SecondSonPC декодирует его байты (Zydis) один раз в микрооперации
  (47 форм генератора; любая другая — отказ с названием инструкции) и интерпретирует: регистры rdi (тегированный указатель:
  user data / гостевой), r10, ecx, edx, флаги cmp, свой стек; чтения гостевой памяти — только через `GuestReader`
  (40 бит, без исключений); неудачное чтение даёт 0 и считается (как пропатченная загрузка моста), но **следующий обход
  читает снова** (у моста AV-обработчик патчит загрузку в `xor` навсегда — SSPC-017). Проверено против нативного
  исполнения тех же байтов (самотест).
* План: для каждого ресурса — привязка (сквозная нумерация: буферы, образы с числом привязок, семплеры), дескриптор
  после post-op, адрес/размер, статус: `Ok`, `Null`, `WrongType`, `OutOfRange`, `BadLocation`, `Unresolved`. **Никаких
  молчаливых нулевых подстановок**: что не разобрано — помечено и посчитано.
* Не входит в P4.3: резидентность, tiling/детайлинг, кэш текстур, размеры образов в байтах (P4.4).

## 8. CLEAR_STATE / PS USER_DATA_4

**Вывод: различие безопасно — на исполнение шейдеров оно не влияет [К].** Обоснование, три независимых уровня:

1. **Семантика пакета.** `CLEAR_STATE` загружает в регистры контекста значения clear state; SH-регистры (программы,
   RSRC, USER_DATA) пакетом не затрагиваются — так моделирует его свой командный процессор P4.2 (`RegisterFile::
   ClearContext`), так же поступают драйверы AMD (таблица clear state содержит только context-регистры) **[Пр: по коду
   драйверов, без доступа к документации PS4]**. Мост обнуляет все регистры (SSPC-016 п.3) — это его отличие.
2. **Железо не передаёт слот шейдеру.** Аппаратура загружает в s0..s(N−1) только первые N слотов user data, N =
   `SPI_SHADER_PGM_RSRC2_PS.USER_SGPR`. Тень (`p43_ab\SS`, `p43_ss2`, `p43_ss3`, ~8 млн draw каждая): **86 746–102 886 draw**
   с отличием слота PS user data (USER_DATA_4 = 0xEFE000 у железа, 0 у моста; также USER_DATA_8..10) — **ни в одном** из
   них слот не < USER_SGPR: в примерах у PS 4 user SGPR (s0–s3).
3. **Программы не читают s4.** По IR после оптимизации (адаптер сканирует `GetUserData`): из **241** различной
   PS-программы захвата s4 не читает **ни одна** (в 236 USER_SGPR > 4 — это другие программы, им слот задаётся явно); в
   тени — 0 draw, где программа читает отличающийся слот (19 draw — программа ещё не была готова сказать).

Регрессионные проверки: `GpuCp(...)` P4.2 (CLEAR_STATE держит SH), счётчики тени (`--gpu-shaders`: draws, loaded, read),
офлайн-сверка (`--gpu-shader-verify`: «the program reads s4 in 0»). Свой бэкенд сохраняет SH по железу; мост не правился
(слепой патч не нужен: эффекта нет).

## 17. Ограничения

1. **Ни один модуль и пайплайн не исполняется на GPU**; Vulkan-пайплайны (layout, графические/compute объекты) не
   создаются — проверяется только приём SPIR-V драйвером (`vkCreateShaderModule`). Игровая графика идёт через мост.
2. Транслятор — код shadPS4 (через адаптер); его ASSERT/UNREACHABLE в проходах и эмиттере завершают процесс (как у моста);
   в режиме хука возвращается только неизвестный опкод.
3. Идентичность — ревалидация раз за кадр (окно внутри кадра) или при каждой привязке (дороже); трекинга записей своего
   нет — подключение к слушателю памяти исполнителя (P4.4) через `Invalidate`.
4. Стадии GS/ES/HS/LS не готовятся (`Unsupported`): в записанных сценах их нет, во всей игре не доказано.
5. Ключ специализации — надмножество моста (несколько своих модулей на один мостовой — лишние трансляции); ключ
   пайплайна — поля регистров, не производные Vulkan-значения (см. §12 о числе пайплайнов).
6. Профиль устройства — свой запрос Vulkan; `sparse_page_shift` принят 16 (у моста — из гранулярности sparse-буфера), атомики
   float2 не запрашиваются — отличия от профиля моста перечислены офлайн-сверкой.
7. Захват (`--gpu-shader-capture`) пишет трансляции, которые мост сделал в этом прогоне (с тёплым кэшем — ни одной: захват
   с `--no-shader-cache`); программы, не встретившиеся в маршруте, не проверены.
8. SRT-обход и V# вершин в игре читаются асинхронно с записью игрой (как и мостом); расхождение момента чтения видно в
   сверке flat user data (§10.2).
9. Длительные проверки (30-мин soak, ручная игра) по решению пользователя не проводились.

## 18. Подготовка P4.4

* **Готово для исполнителя:** `DrawPreparation` (готовность, id пайплайна), по стадиям — модуль (SPIR-V, отражение:
  привязки set 0 — буферы, образы с числом привязок, семплеры; push-константы транслятора — как у моста), план ресурсов
  (адреса, размеры, дескрипторы, статусы), runtime-параметры; `GraphicsPipelineState` — всё фиксированное состояние;
  перечень динамического состояния (§6.4) с версиями P4.2 (`dynamic_version`, `targets_version`).
* **Контракты:** `ShaderTranslator` (любая реализация), `GuestReader` (в игре — CopySparse; для исполнителя — тот же),
  `ProgramCache::Invalidate` (для слушателя памяти исполнителя), `DeviceProfile` из своего Vulkan.
* **Что P4.4 строит на этом:** `VkPipelineLayout`/`VkDescriptorSetLayout` из отражения (push descriptors, как требует
  фундамент P4.1), `VkShaderModule` из модулей, `VkPipeline` по `GraphicsPipelineState` (dynamic rendering с форматами
  целей), привязку ресурсов по плану (буферы/образы — кэш ресурсов P4.4), динамическое состояние по версиям.
