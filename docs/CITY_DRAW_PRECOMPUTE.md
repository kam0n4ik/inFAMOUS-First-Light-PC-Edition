# CITY-OPT Phase 4: подготовка draw один раз, а не на каждом draw

Цель — не делать повторно ту часть подготовки draw, которая не меняется, и сократить работу обоих CPU-потоков
GPU-бэкенда в городе (оба ~30 мс на кадр). Стенд и сцена — как в `docs/CITY_PERFORMANCE.md`. Метки: `[A]` — анализ
кода, `[E]` — измерение, `[H]` — гипотеза.

## 1. Что делается на каждом draw и что из этого можно переиспользовать

Перепись `SSPC_DIAG_PREP_CENSUS=<первый кадр>:<кадров>` (новая диагностика, `parallel_cp.cpp`): каждый draw окна по
паре VS/PS — время подготовки в потоке 1, время записи в потоке 2, ответ GEOFAST и причина отказа, какие группы
регистров и слоты user data изменились относительно предыдущего draw, причина конца серии склейки. Город, кадры
2200–2499 (`logs/runs/p4_census1`), 12 259 draw за кадр:

| Вид draw (40 самых дорогих классов) | draw / кадр | поток 1, мкс/draw | поток 2, мкс/draw |
|---|---|---|---|
| с обходом SRT хотя бы в одной стадии (G-буфер, освещение, p462 — PS) | 4 668 | 1,98 | 3,34 |
| без обхода SRT (тени, мелкие проходы) | 2 463 | 0,74 | 1,78 |

Подготовка draw в потоке 1 — 23 мс за кадр из ~31 мс работы потока (остальное — разбор PM4, запись регистров, журнал).

| Операция | Входы | Класс | Уже переиспользуется | Инвалидация |
|---|---|---|---|---|
| разбор PM4, запись регистров (`RegisterFile::Write`, журнал) | пакеты кадра | per-draw | — (это сам поток команд) | — |
| параметры среды стадии (`BuildGraphicsRuntime`) | регистры групп `kRuntimeGroups` | versioned | да: пересчёт только при изменении групп | версии групп |
| программа шейдера (`ProgramCache::Get`) | адрес + код | versioned | да (P5.2: доверие по отслеживанию записи) | запись в страницы кода |
| раскладка (`FindLayout`), fetch shader (`FetchCache`) | программа + среда; адрес fetch | immutable / versioned | да | эпоха программ |
| обход SRT (`ResolveResources`) | user data + таблицы в памяти | **per-draw**: таблицы пишутся заново каждый кадр | P4.7 мемо стадии (точные входы) | поколение памяти |
| разбор дескрипторов (`DecodeResources`) | user data (+ результат обхода) | per-draw, дёшево | **Phase 4: шаблон** | — |
| ключ специализации + модуль | план ресурсов | versioned: тот же ключ → тот же модуль | **Phase 4: проверка ключа** | — |
| конвейер (`GetGraphics`) | модули + группы `PipelineStateGroups` | versioned | да (`pipeline_reuse`) | версии групп |
| копия стадии в запись (`CopyStage`) | — | per-draw | FB-6 (эксперимент, выкл.) | — |
| поток 2: цели (`target_cache_`) | версии групп целей | versioned | да | версии групп, эпоха образов |
| привязки буферов (`GuestRange`) | диапазоны draw | per-draw адреса, резидентность versioned | кэш буферов (резидентность, поколения блоков) | запись CPU/GPU |
| образы (`TexMemo`) | T# + эпоха | versioned | да | эпоха кэша образов |
| дескрипторы (`PushDescriptors`) | привязки | per-draw разница | тень дескрипторов (P4.7) | смена раскладки |
| динамическое состояние | версии групп | versioned | Phase 1 `DYN_MEMO` | версии групп |
| вершины/индексы | диапазоны draw | per-draw | Phase 3 склейка + кэш геометрии | `RangeVersion` |

Почему «статичный между кадрами» не значит «можно не готовить»: у теневого draw (`0x43d480`, раздел 4) таблица V# и
константы пишутся в новую память кадра каждый кадр — адреса в user data другие в каждом кадре, хотя меш и шейдер те же.
Неизменны программа, модуль, конвейер, раскладка привязок; изменчивы адреса буферов в user data.

## 2. Шаблон draw в потоке 1 — `SSPC_CITY_DRAW_CACHE=1`

Расширение GEOFAST (Phase 3, `ParallelCp::PrepareGeometryOnly`): шаблон — подготовка предыдущего draw. Раньше draw брал
её, только если изменилась одна геометрия (таблица V# вершин). Теперь — и если изменились другие user data VS и/или PS
(V# константного буфера, T#), но только у стадии **без обхода SRT** (весь план — разбор регистров):

1. те же проверки, что у GEOFAST (запись предыдущая и подготовленная, поколение памяти фронтенда то же, изменились
   только группы user data VS/PS, индексов и параметров draw, программы и `rsrc` те же, адрес fetch shader тот же,
   нет записей в память);
2. `ParallelCp::RedecodeStage`: план стадии заново из новых user data той же функцией, что и полная подготовка
   (`GS::DecodeResources` с рефлексией первого модуля раскладки, вершинные V# — прочитанные из таблицы этого draw),
   ключ специализации (`GS::BuildSpecializationKey`) обязан совпасть с ключом модуля, а границы привязок — с
   прежними; иначе — полная подготовка.

Хранится только шаблон предыдущего draw: ни сериализации, ни копий сверх записи. Инвалидация — поколение памяти
фронтенда (любая запись, меняющая код/таблицы), изменённые группы регистров (журнал), смена программ.

Проверка `SSPC_CITY_GEOFAST=verify SSPC_CITY_DRAW_CACHE=1` — каждый быстрый draw ещё и полностью, сравнение по полям:
**21 997 772 draw, 0 расхождений** (`logs/runs/p4_dcverify1`). Быстрых draw — 22 млн за прогон вместо 11,9 млн у
одного GEOFAST (VS разобран заново 10 млн раз, PS 0,66 млн). Тени — 98 % своих draw через шаблон, 0,6 мкс вместо
0,8 мкс.

## 3. Склейка draw с разными константами — `SSPC_CITY_INSTANCING=1`

Поток 2. Phase 3 склеивал только draw, отличающиеся геометрией. Тени (~4 800 draw) отличаются ещё и константным
буфером. Теперь:

- `Executor::Batchable`: буферы VS могут различаться адресом и размером (формат, шаг, флаги — те же, ≤ 4 КиБ, адрес
  кратен 4), если `InstanceBufferOk` доказал по SPIR-V модуля: буфер читается только через смещение
  `buf_offsets` переводчика (`BitFieldUExtract` слова push-констант), а слова его V# в плоских user data — либо как
  шаг (`BitFieldUExtract(w1, 16, 14)`, одинаковый в серии), либо копируются в переменную, которую никто не читает
  (переводчик копирует все user SGPR при входе);
- `vk_instancing.cpp`, `PatchDrawIndexOffsets`: к смещению такого буфера добавляется `DrawIndex * stride`
  (`BuiltIn DrawIndex`, `DrawParameters`). Больше в SPIR-V ничего не меняется; результат проходит `spirv-val`
  (Vulkan 1.3). Правленый модуль — только в памяти процесса (id ≥ 0x40000000), в манифест конвейеров не пишется;
  переводчик и поколение кэша шейдеров не затронуты;
- `GatherInstanced`: блок каждого draw копируется с хоста (только если копия на хосте актуальна: нет ожидающей записи
  CPU/GPU/таймлайна) в кольцо с шагом 256/1024/4096 байт, хвост блока — нули;
- запись — `vkCmdDrawMultiIndexedEXT` (`VK_EXT_multi_draw`, включается при создании устройства **только** с этим
  флагом): draw выполняются по порядку, каждый со всеми своими экземплярами. Разное число экземпляров в серии —
  отрезки с одинаковым числом, по вызову на отрезок; отрезок не с начала серии переставляет дескриптор копий на свой
  первый draw (`DrawIndex` в каждом вызове с 0);
- геометрия: если все диапазоны вершин и индексов серии резидентны в кэше буферов в одном буфере и смещения кратны
  шагу — без копии (`ZeroCopyBatch`: исходные индексы, `vertexOffset`/`firstIndex` каждого draw); иначе — копия
  Phase 3.

Откат на любом шаге (правленый конвейер ещё строится асинхронно, блок констант не актуален) — серия пишется по одному
draw; одиночный draw с правленым конвейером читает свой блок (`DrawIndex` 0).

Разбор движка (раздел 4) объясняет форму: у теневого draw столько экземпляров, сколько каскадов он покрывает, и
константный буфер — массив записей по 0x48 байт на экземпляр.

## 4. Связь с движком (REA / Ghidra)

`E:\research\rea\q14\p43.txt`, `p44.txt` (Ghidra 12.1.4, копия проекта; REA не анализирует функции рендера PE-обёртки —
`docs/CITY_ENGINE_REVERSE.md` §1):

- `0x43d590` — цикл теневых кастеров: для каждого объекта списка видимости вызывает `0x43d480` [A];
- `0x43d480` [A]: `0x61e260(V#, addr, 0x48, n)` строит V# константного буфера (слово 1 — шаг `0x48 << 16`, слово 2 —
  `n` записей), `0x16b70` ставит его в user data через CUE, `0x16aa0` — таблица V# вершин меша, `0x6250b0(dcb, n)` пишет
  PM4 `0xC0002F00` = `NUM_INSTANCES n`, затем `drawIndex 0x623c60`;
- значит, теневой draw — `n` экземпляров одного меша, константы — `n` записей по 0x48 байт, выбираемых номером
  экземпляра [A]. Измерено: у соседних теневых draw `n` часто разное (причина 15 конца серии до разбиения на отрезки)
  [E];
- `0x1a1960` (проход 14, p462) — без констант на draw: склеивается Phase 3 [A + E].

Патч движка не нужен для этой работы: всё, что меняется между draw, видно в командах; движок каждый кадр заново пишет
таблицы в память кадра, и подготовить их заранее нельзя — адреса новые [A].

## 5. Предварительная подготовка до запуска / при загрузке сцены

Что уже готовится заранее (до Phase 4): SPIR-V модулей (дисковый кэш шейдеров), конвейеры (манифест + `VkPipelineCache`
+ статический предиктор, окно подготовки перед игрой). Что из подготовки draw могло бы попасть в такой кэш:

- шаблон draw (раздел 2) — нет: строится из user data текущего кадра (адреса таблиц и констант в памяти кадра) и
  годится только для следующего draw. Сериализовать нечего — всё неизменное (модуль, конвейер, раскладка) уже в кэшах;
- правленые модули склейки и их конвейеры — могли бы готовиться при запуске. Измерено: откатов «конвейер ещё не
  собран» — 88–156 за прогон (асинхронная сборка занимает доли секунды), т. е. выигрыш от подготовки заранее — сотни
  draw за весь прогон. Не делалось: не окупает усложнение (записи правленого SPIR-V в дисковый кэш);
- геометрия серий — ключи по адресам гостевой памяти, между запусками другие (стриминг мира).

## 7. Принято и отклонено

- `SSPC_CITY_DRAW_CACHE=1` — корректно (verify 0), меньше работы потока 1; в пресет не включено (FPS не доказан).
- `SSPC_CITY_INSTANCING=1` (+ `=ab:<n>` для сравнения изображений) — корректно (Validation 0, тени и глубина бит в
  бит), меньше записи потока 2 и команд Vulkan; в пресет не включено. Создаёт `VK_EXT_multi_draw` только с флагом.
- Отклонено: склейка с копией геометрии теней (−27 % FPS); подготовка правленых конвейеров при запуске (откатов
  сотни за прогон — не окупается); сериализация шаблонов draw между запусками (их входы — память текущего кадра).
- Не делалось: склейка в потоке 1 до подготовки (ранняя склейка): шаблон уже снимает подготовку члена серии до
  ~0,4–0,7 мкс, остаток — разбор PM4 и регистров, которые нужны и для склеенного draw; reusable secondary command
  buffers: команды серии зависят от адресов и констант текущего кадра (копии констант, `firstIndex`/`vertexOffset`),
  повторно исполнить записанный буфер нельзя без его перезаписи.

## 8. Ограничения

- Склейка по `DrawIndex`: чтение константного буфера за пределами его размера внутри шага даёт нули (как robust-чтение
  у одиночного draw), за пределами шага — блок следующего draw (у одиночного — нули). Движок такие чтения не делает
  [H: не проверено для всех шейдеров].
- Отрезки с одинаковым числом экземпляров короткие (в среднем ~1,6 draw на вызов multi-draw): теневые draw соседних
  объектов покрывают разное число каскадов.
- 60 FPS не достигнуто и этим путём не достижимо: снимать нужно одновременно ~15 мс в каждом из двух потоков.
