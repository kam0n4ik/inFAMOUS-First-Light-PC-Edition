## 2. P4.1.1 — аудит графического пути (по коду)

Полная карта — `PHASE4_GRAPHICS_BACKEND.md` §1–§2. Главное:
1. Игра рисует только через `sceGnmSubmitAndFlipCommandBuffers` — **ровно 1 вызов на флип** (`ForWorkload`,
   `RequestFlip*`, `sceVideoOutSubmitFlip` не вызываются) **[К]** (счётчики импортов `p36_ab\*\calls.json`).
2. Draw-функции GnmDriver (`sceGnmDrawIndex` ≈ 2950/кадр) только пишут PM4 в буфер игры; всё исполнение — один поток
   `shadPS4:GpuCommandProcessor` (Liverpool): разбор PM4, `Rasterizer` (запись Vulkan), кэши, презентация кадра.
3. Неизвестный опкод/type-0 → `UNREACHABLE` (смерть процесса) **[К]**; EOP/WRITE_DATA/RELEASE_MEM пишутся в гостевую
   память **при разборе пакета**, не по выполнению на GPU **[К]**; `GpuClock64` — `std::chrono`, не часы SecondSonPC.
4. Синхронизация: `SubmitDone` ставит `submission_lock` — игра опережает поток моста не больше чем на кадр; `WAIT_REG_MEM`
   на метке VideoOut — сон потока до флипа; флип — NOP `PatchedFlip` → IRQ `GfxFlip` → `PrepareFrame` (на потоке моста) →
   `PresentThread` на vblank.
5. Vulkan моста: одно устройство, одна очередь (graphics = present), `vulkan-1.dll` грузится динамически (своего лоадера
   в сборке под Windows нет), vulkan-hpp с динамическим диспетчером и VMA определены в мосте.
6. Компоненты «A» (Liverpool…PageManager) и «B» (VideoOut, Presenter, IRQ флипа) заменяются только вместе; GnmDriver и
   VideoOut — только вместе (`driver.cpp:276` разыменует `presenter`).
7. Найдено по пути (не исправлялось — без смены поведения моста): `DebugState.DumpingCurrentReg()` берёт `shared_lock`
   на каждый draw/dispatch; `bindPipeline` на каждый draw без сравнения; ключ пайплайна пересчитывается на каждый draw.

## 4. P4.1.3 — граница собственного графического бэкенда

* **Реестр владельцев** `src\runtime\gpu\backend.{h,cpp}`: ресурсы `CommandStream`, `MemoryListener`, `WriteTracking`,
  `Presentation`; один владелец на ресурс, второму — отказ с именем владельца; выбор бэкенда (`SelectBackend`) один раз
  на процесс. В игре (sspc-путь) bootstrap до старта GnmDriver записывает мост владельцем всех четырёх (`bootstrap.cpp`).
  Интерфейс `Gpu::Backend` (Start/Stop/State) — минимальный, без заготовок «на будущее».
* **Контракт гостевой памяти** `src\runtime\gpu\gpu_memory.h` — перенос `Core::GpuMemory` в заголовки SecondSonPC (пункт 1
  готовности Phase 4 из P3.6 §10) с той же семантикой порядка уведомлений; адаптер `src\bridge\shadps4\gpu_memory_host.cpp`
  поверх выбранного менеджера (моста или своего): `SetListener` только для владельца `MemoryListener`; **отказывает, если
  в слоте менеджера уже есть слушатель** (рендерер моста) — второй трекер не появится; форвардер с атомарной целью.
  **Найдено в самотесте:** менеджер моста вызывает слушателя на каждом map/unmap без проверки на null
  (`core\memory.cpp:641`) — снятый слушатель обрушивает процесс; адаптер поэтому никогда не оставляет слот пустым (ставит
  «пустого» слушателя).
* **Ответы на вопросы о памяти:** адресное пространство — у выбранного менеджера (один владелец); GPU-отображения и
  физическая память — там же; трекинг страниц — `PageManager` моста через `ProtectTracking`, AV — через VEH моста или
  диспетчер SecondSonPC (патч 0022); мост получает уведомления как `GpuMemoryListener` (рендерер); свой бэкенд — через
  `Gpu::GuestMemory::SetListener` (уже работает в самотесте); частичный unmap — интервалы режутся, образы, пересекающие
  диапазон, освобождаются целиком без выгрузки (`texture_cache.cpp:189-196`); алиасы — трекинг по VA, запись через второй
  вид той же физической памяти не замечается **[Пр]**; два трекера невозможны: свой бэкенд работает только если
  GnmDriver/VideoOut моста не запущены (иначе рендерер моста держит слот, а реестр — владельца), отключение старого
  трекера = не вызывать `RegisterLib` GnmDriver (происходит само, если у Gnm и VideoOut нет BRIDGE-импортов).
* Остаётся на P4.4: слот обработчика трекинга в диспетчере исключений SecondSonPC (сейчас там только `BridgeHandlers`).

## 5. P4.1.4 — Vulkan foundation

`src\runtime\gpu\vulkan\vk_foundation.{h,cpp}`: системный `vulkan-1.dll` через свою таблицу функций (C API) — **без
второго лоадера, без vulkan-hpp-диспетчера и VMA** (они определены в мосте и конфликтовали бы); заголовки — цель
`Vulkan::Headers` из externals (только заголовки).

* **Уровень A:** instance (API 1.3; surface-расширения для проверки презентации; validation — если установлен), перечень
  устройств с их возможностями против требований бэкенда (API 1.3, `VK_KHR_push_descriptor`, `VK_EXT_robustness2` +
  robustBufferAccess2/robustImageAccess2/nullDescriptor, `vertex_attribute_divisor`, dynamicRendering, synchronization2,
  timelineSemaphore, bufferDeviceAddress, robustBufferAccess) и необязательных (external_memory_host,
  graphics_pipeline_library, descriptor_buffer, extended_dynamic_state3, …), выбор (дискретная → встроенная → больше
  видеопамяти; `--gpu-device N`), device с очередями graphics+compute(+present), асинхронный compute, transfer; проверка
  ресурсов (буфер + образ RGBA8, очистка на графической очереди, копия в буфер, чтение и сверка, sentinel в буфере);
  управляемая остановка (ожидание устройства, обратный порядок); счётчик живых объектов (утечки).
* **Уровень B:** своё Win32-окно «diagnostic colour…, NOT a game frame», surface, swapchain FIFO, очистка пульсирующим
  цветом, презентация; закрытие окна пользователем — штатная остановка; свёрнутое окно — отказ с причиной.
* Режим: `--gpu-probe` (A), `--gpu-probe-window <s>` (A+B), отчёт `logs\gpu_probe.txt`. `--gpu-backend sspc` для игры
  **отклоняется** с объяснением (никакого тихого перехода на мост).
* Результат на этом ПК — §9.

## 6. P4.1.5 — шейдеры и ресурсы (исследование)

* Шейдер находится по `SPI_SHADER_PGM_*`/`COMPUTE_PGM_*`; сырой GCN в памяти игры; ключ — `shader_hash` из футера
  «OrbShdr»; fetch-шейдер — по `S_SWAPPC_B64`. Транслятор моста: GCN → IR → ~25 проходов → SPIR-V (sirit); стадии
  VS/PS/CS (+ES/GS/LS/HS в коде; GS onchip и streamout не поддержаны). Внешних зависимостей мало: 4 флага настроек,
  `Core::Signals` (SRT-walker), заголовки `video_core\amdgpu`, часть `common` — **можно взять через адаптер** (GPL-2.0-or-
  later совместима).
* Кэш (поколение `96fe973b`, ПК пользователя): 1 242 программы (VS 189, FS 527, CS 526), 1 597 перестановок, 857
  графических и 532 compute-пайплайна, 90,5 МБ; **GS/тесселяции в кэше нет** (в посещённых сценах). Поколение с патчем
  0027 — новое (меняется дерево `video_core`), прогрето заново (`p41_warm`: 619 программ, 482 пайплайна).

## 7. Производительность (ответы на вопросы задания)

1. **Чем ограничена листва:** CPU-работой потока GpuCommandProcessor — на кадр 27,2 мс работы при кадре 27,3 мс (поток
   занят ~100 %), из них **24,4 мс — draw-пакеты** (5 366 draw × ~4,5–5,2 мкс). Ожидание метки VideoOut в листве ≈ 0
   (поток не успевает к vblank) **[К]** (с диагностикой; без неё кадр короче — §7.6).
2. **Поток с наибольшим CPU:** `shadPS4:GpuCommandProcessor` (подтверждает профиль P2.5).
3. **Вклад обработки PM4 (без draw):** ~2,8 мс/кадр в листве (регистры 1,2, NOP, dispatch, прочее) — ~10 %.
4. **Вклад трекинга памяти:** 70–90 тыс. AV/с в игре (`p41_base`, VEH-сводка), обработка на потоках гостя/GPU;
   отдельного времени в этой статистике нет — `--track-stats` (P2.5) измеряет его; в P4.1 не перемерялся.
5. **Ожидания GPU:** в лёгких сценах поток ~13 % времени спит на метке VideoOut (ждёт флип/vblank) — не «ожидание GPU»,
   а темп 60 Гц; простой ~1 %; flush ~0,2 %.
6. **Число draw/dispatch:** мир ~2 540 draw, листва ~5 370 (×2,1); dispatch ~60/кадр.
7. **Распределение кадра (листва):** draw 89 %, регистры 4 %, остальное ~7 %.
8. **Что оптимизировать первым:** стоимость draw на CPU (ключ пайплайна и специализация на каждый draw, привязки,
   копии констант) — в своём командном процессоре с признаками изменения состояния (P4.2–P4.3).
9. **Что выгодно заменить своим кодом:** разбор PM4 с файлом регистров и «грязными» группами, выбор пайплайна по
   изменённому состоянию, путь констант без копий.
10. **Что может испортить картинку:** пропуск «лишних» пакетов/барьеров, кэширование по неполному ключу, неверные
    метки EOP по времени, пропуск NOP-подсказок размеров целей.
