# Phase 4 / P4.2 — Native GPU Command Processor

Статус: **см. §15** (итог и критерии). Игру по-прежнему рисует мост shadPS4 (по умолчанию, без изменений). Свой командный
процессор SecondSonPC **разбирает весь поток PM4 игры, ведёт свою модель регистров и формирует описания draw/dispatch**;
в игре он работает только в тени моста (`--gpu-shadow`, ничего не пишет и не ждёт) и офлайн на записанных трассах
(`--gpu-replay`). На GPU он ничего не исполняет (Vulkan-бэкенд — P4.3/P4.4).

Связанные документы: `PHASE4_P41_GPU_FOUNDATION.md` (фундамент, данные PM4), `PHASE4_GRAPHICS_BACKEND.md` (стратегия),
`PATCHES.md` (0028, 0029), `KNOWN_ISSUES.md` (SSPC-015, SSPC-016). Пометки: **[К]** — подтверждено кодом/прогоном,
**[Пр]** — предположение.

## 1. Архитектура

```
отправки игры (SubmitAndFlip: DCB; DingDong: участки кольца ASC)
   │  копия отправки (тень) или чтение через CommandMemory (изолированно)
   ▼
CommandProcessor  (src\runtime\gpu\command_processor.*)   — один владелец-поток, без блокировок внутри
   │  очереди: графическая (0) и compute 1..64; у каждой — FIFO отправок, стек кадров (отправка, перенесённый
   │  через конец кольца пакет, indirect-буферы до 4 уровней), бюджет слов на отправку (защита от петель)
   │  Pm4::Decode (pm4.h, P4.1) → обработчик пакета → RegisterFile / ComputeRegisters
   │  draw/dispatch → DrawDescriptor / DispatchDescriptor (ключ конвейера — из хэшей групп)
   ▼
GpuWork (интерфейс): Draw, Dispatch, CacheAction, Flip, Fence, Dma, Interrupt
   │  тень: учёт и сверка (cp_shadow.*) · воспроизведение: счёт (cp_replay.*) · самотест: запись
   ▼  (P4.3/P4.4: Vulkan-бэкенд, завершение работы → CommandProcessor::CompleteWork)
```

* **Два режима (выбираются при создании):**
  * `Mode::Shadow` — рядом с другим исполнителем того же потока (мост): только состояние и описания; никаких записей в
    гостевую память, ожиданий, меток, прерываний, DMA, обновления указателя чтения кольца — всё это сообщается в
    `GpuWork`, но не делается второй раз.
  * `Mode::Isolated` — единственный исполнитель своей памяти: CPU-стороны пакетов исполняются. `WRITE_DATA`/`DMA_DATA` —
    в момент разбора (так их делает micro engine CP); `EVENT_WRITE_EOP/EOS`, `RELEASE_MEM` — **ждут работу GPU перед
    собой**: при наличии невыполненных draw/dispatch метка держится до `CompleteWork(queue, seq)` и пишется в порядке
    очереди; при пустом конвейере — сразу; `WAIT_REG_MEM` блокирует очередь до выполнения условия. Ничего не
    объявляется сделанным, пока не сделано.
* **Модель памяти CP:** `CommandMemory` (Read/Write с границами); процессор **никогда не разыменовывает гостевой
  адрес**: отправки и indirect-буферы читаются в собственные буферы (переиспользуются, рост считается), пакет
  декодируется только в пределах буфера. Запись в ещё не разобранные пакеты потока (DMA/WRITE_DATA в свой же буфер —
  приём Gnm для косвенного dispatch на compute-очереди) учитывается: изолированно копия пакета исправляется, в тени
  dispatch становится косвенным с адресом источника DMA.
* **Ошибки:** неизвестный опкод, нереализованная форма, обрезанный/короткий пакет, регистр вне окон, нечитаемый или
  слишком глубокий indirect-буфер, превышение бюджета, нечитаемая память, переполнение очередей → `CpError` с очередью,
  глубиной, адресом, опкодом и причиной; отправка отбрасывается. Изолированно очередь остаётся в ошибке до `Reset`
  (дальше ничего не исполняется), в тени (`resume_after_fault`) — продолжает со следующей отправки. Ни одного
  `UNREACHABLE`/чтения за границей (у моста неизвестный опкод — смерть процесса).
* **Потоки:** процессор однопоточный (владелец — один поток); тень принимает отправки из потоков игры в свою очередь
  под мьютексом (копия при отправке), обрабатывает на потоке GPU моста.
* **Владение:** тень **ничего не захватывает** в реестре владельцев (`backend.h`): мост остаётся владельцем всех ресурсов
  GPU, второго слушателя памяти и второго трекинга страниц нет (память читается через `Gpu::GuestMemory::CopySparse`,
  без исключений).

## 4. Регистры и отслеживание изменений

* Окна: config [0x2000, 0x2C00), SH [0x2C00, 0x3000), context [0xA000, 0xA400), uconfig [0xC000, 0xD000) — 0x2400
  регистров; запись вне окон — ошибка пакета. Compute [0x2E00, 0x2E50) — отдельно на каждую очередь (как у железа).
* **36 групп**, каждый регистр — ровно в одной (проверяется самотестом): программы стадий (6), user data стадий (6),
  форматы/адреса целей цвета, глубина (формат/цель/границы/очистка), depth-stencil, stencil ref, blend, blend
  constants, viewport, scissor, raster, depth bias, shader interface, geometry, index state, draw params, ресурсы
  контекста, **«прочее» context/SH (в ключе конвейера — неизвестное считается важным)**, primitive type, прочее uconfig,
  config.
* Запись сравнивается до сохранения: изменение помечает группу «грязной», увеличивает её версию и обновляет **хэш группы**
  (XOR 64-битного перемешивания пары «индекс, значение» — O(1) на изменение; проверяется против полного пересчёта
  самотестом). Запись того же значения не меняет ничего.
* Ключ конвейера: группы `kPipelineGroups` (программы, форматы целей, depth-stencil, blend, raster, shader interface,
  geometry, primitive type, прочее context/SH) — пересчитывается **только** когда одна из них изменилась, из 16 готовых
  хэшей групп. Динамическое состояние (viewport, scissor, blend constants, stencil ref, depth bias/bounds) и адреса
  целей в ключ не входят, у них свои версии. Точное содержимое групп остаётся в регистрах для проверки совпадения
  ключа при поиске в кэше (P4.3).
* **Отличия моста от железа (зеркало `BridgeMirror` воспроизводит их для сверки):** CLEAR_STATE моста обнуляет все
  регистры (железо — только context); INDEX_BUFFER_SIZE мост держит вне регистров; DRAW_INDIRECT/DRAW_INDEX_INDIRECT
  мост не пишет VGT_DRAW_INITIATOR. Дошло ли отличие CLEAR_STATE до какого-нибудь draw — §7.

## 5. Описания draw/dispatch

`DrawDescriptor` (заполняется из регистров; ~750 байт; копирование без выделений): номер работы очереди, адрес пакета,
вид, индексность/косвенность, число индексов и экземпляров, база/тип/предел индексов, смещения индексов, initiator,
primitive type, stages enable, адрес аргументов и SH-смещения (косвенные), активные стадии, `ShaderRef` всех стадий
(адрес программы, RSRC1/2), user data активных стадий, маска встроенных дескрипторов, **ключ и версия конвейера,
версии динамического состояния и целей, маска изменённых с прошлого draw групп**, подсказки размеров целей.
`DispatchDescriptor`: группы (или адрес косвенных), initiator, размер группы потоков, программа, user data, версии.
Содержимое шейдера по адресу **не идентифицируется** (это P4.3/P4.4: нужен трекинг записей страниц); тень проверяет
подпись программы (футер `OrbShdr`) раз на адрес за кадр и считает адреса, где программа сменилась (§7).

## 6. Модель памяти GPU

* Чтение команд — только через `CommandMemory` с границами; в игре (тень) — `Gpu::GuestMemory::CopySparse` (никогда не
  падает, незамапленное читается нулями), в воспроизведении — память трассы, в самотесте — 1 МиБ тестовой памяти.
* Отправки копируются тенью в момент `SubmitGfx/SubmitAsc` (поток игры): после патча флипа драйвером, до исполнения
  мостом; срок жизни копии — пока процессор не закончил отправку. Указатели на гостевую память не заимствуются.
* Записи CPU-стороны (изолированно): в порядке потока; метки после работы GPU — в порядке очереди по `CompleteWork`.
* Нужно для P4.3/P4.4 (контракты есть, реализации нет): DMA и writeback на GPU-таймлайне (сейчас CP-сторона), доступ
  к коду шейдеров с идентичностью содержимого (трекинг записей — слот в диспетчере исключений, SSPC-010: новых
  массовых механизмов на исключениях в P4.2 не добавлено), GPU-видимые буферы и цели рендеринга, синхронизация
  CPU/GPU через `CompleteWork`, асинхронный compute (очереди 1..64 независимы, метки ждут работу своей очереди).

## 7. Тень и офлайн-воспроизведение

### 7.1 Тень в игре (`--gpu-shadow`), сцена «пляж» → листва, 98 с

Пять прогонов с тенью (`p42_warm\ST` — холодный кэш; `p42_ab\p42-ST2`, `p42-SH_1`, `p42-SH_2`; `p42_sem\p42-SH`), каждый
~98 с, ~3 700–4 000 кадров, ~190–200 млн пакетов **[К]**:

| | на прогон | всего |
|---|---|---|
| контрольные точки (перед draw / dispatch) | 10,8–11,7 млн (≈11 млн / ≈200 тыс.) | **≈56 млн** |
| расхождения (адрес пакета, нет отправки, отказ процессора, регистры SH/context/uconfig, compute, размер буфера индексов, база косвенных аргументов, подсказки размеров, смена программы по адресу) | **0** | **0** |
| ошибки разбора / неизвестные пакеты | 0 | 0 |

Что тень увидела о потоке игры (прогон `p42_warm\ST`): регистров записано 311 млн, **значение меняют 34,1 %**; ключ
конвейера пересчитан в 26,6 % draw, разных ключей 14 101 за прогон, ≈640 за кадр; группы, меняющиеся чаще всего: user
data VS (99 % draw), index state (96 %), draw params, программы PS/VS (26 %), raster (22 %), stencil ref, shader
interface (9 %); **99 % пакетов DMA_DATA — предвыборка `CP_DMA_READ_TAGS`** (5,7 млн; копий память→память ≈16 на
кадр, данные→GDS 1/кадр, GDS→память 0,5/кадр — в P4.1 предвыборки считались копиями «1,26 МБ/кадр»); метки EOP типов 4
и 40, EOS 47 (CS_DONE) и 48 (PS_DONE), RELEASE_MEM 47, GDS-меток 0, переносов пакетов через конец кольца 0, записей DMA
в пакеты потока 0; подсказки размеров целей 1,03 млн, пропущенных 0; 1 822 программы по адресу, **ни один адрес не
сменил программу** (подпись `OrbShdr` проверяется раз на адрес за кадр).

**Отличие моста от железа, доходящее до draw:** CLEAR_STATE моста обнуляет SH-регистры, железо — нет. В прогоне
`p42_sem\p42-SH` у **150 081 draw (≈39 на кадр, 1,4 %)** PS USER_DATA_4 (0x2C10) у модели железа 0xEFE000, у моста 0
(игра задаёт его до CLEAR_STATE и не повторяет). Загружает ли шейдер этот слот (USER_SGPR из RSRC2) — счётчик добавлен, но прогон с ним не выполнялся (PENDING). Тень этого не исправляет
(сверка идёт с мостом), но для своего бэкенда (P4.3/P4.4) поведение железа — сохранять SH — и есть правильное **[Пр]**:
у моста эти draw могут получать 0 вместо указателя.

Цена тени на потоке GPU моста: 6,2–6,6 мс на кадр (120–129 нс на пакет: копия отправки, свой разбор, сравнение 9 КиБ
регистров перед каждым draw) — листва ~30 FPS вместо ~45. Это диагностический режим; FPS с ним с обычными прогонами не
сравнивается.

### 7.2 Трассы и воспроизведение (`--gpu-trace`, `--gpu-replay`)

Формат: `SSPCTRC1`, записи {тип, размер, данные}: H (текст), R (состояние моста на старте: регистры окон, размер буфера
индексов, база косвенных аргументов, подсказки), Q (регистры compute очереди при первом появлении), S (отправка, как её
взяла тень), M (прочитанная командная память: indirect-буферы), C (состояние моста перед каждым draw/dispatch: хэш
окон SH/context/uconfig, хэш compute, служебное), F (все регистры моста каждые 256 точек), X (флип), E (итог).

| Трасса (3 кадра) | Отправок | Пакетов | Draw / dispatch | Контрольных точек | Полных сверок | Итог |
|---|---:|---:|---|---:|---:|---|
| `beach_40` (мир, 40 с; 4,9 МБ) | 200 | 162 436 | 7 598 / 156 | 7 754 | 30 (0 регистров отличаются) | **MATCH** |
| `foliage_75` (густая листва, 75 с; 8,3 МБ) | 254 | 244 847 | 16 130 / 146 | 16 276 | 63 (0) | **MATCH** |

Найдено по пути (ошибка инструмента, не процессора): игра каждый кадр переписывает тот же indirect-буфер ASC, а память

## 10. VideoOut, граница презентации и SSPC-015

**Граница владения.** GnmDriver (приём отправок: `SubmitAndFlip/Submit/SubmitDone/DingDong/MapComputeQueue`, патч
флипа и метка буфера) и VideoOut (буферы показа, очередь флипов, vblank, метки буферов, статус и события флипа,
`IsFlipPending`) переключаются **только вместе**: ресурсы реестра `CommandStream` и `Presentation` берёт один бэкенд
(`backend.h`); у моста `RegisterLib` GnmDriver создаёт и Liverpool, и презентер, а `PresentThread` разыменовывает
презентер (P4.1 §2). В P4.2 оба по-прежнему у моста; свой процессор не захватывает ни одного ресурса.

**Минимальный интерфейс кадра и флипа (в коде, используется самотестами):** процессор на маркере флипа вызывает
`GpuWork::Flip(FlipMarker{queue, packet_addr, after_seq})` — «команды кадра переданы GPU до работы `after_seq`»;
бэкенд сообщает выполнение работы `CommandProcessor::CompleteWork(queue, seq)`, после чего процессор пишет удержанные
метки EOP/EOS/RELEASE_MEM в порядке очереди (и сообщает прерывания). Владелец презентации (P4.4) получает `Flip`,
ждёт выполнения `after_seq` (timeline semaphore Vulkan), ставит кадр на ближайший vblank, затем обнуляет метку
предыдущего буфера (так отпускается `WAIT_REG_MEM` игры — `sceGnmInsertWaitFlipDone`) и обновляет статус флипа.

**Карта своего VideoOut для P4.4:** регистрация буферов (`sceVideoOutRegisterBuffers`: адреса, формат, тайлинг —
детайлинг при показе), очередь флипов с ожиданием GPU по `after_seq`, поток презентации с тактом vblank (60 Гц,
`flip_rate`), окно и swapchain — свои (уровень B P4.1 уже есть), метки буферов в порядке флипов, статус флипа
(count/tsc/process time/текущий буфер/pending), события flip/vblank через `Kernel::EventQueues` (игра их не использует,
но контракт нужен), `IsFlipPending`. Отличие от моста, которое стоит сделать: мост берёт кадр только в начале такта
(`driver.cpp`: кадр, поставленный сразу после проверки, ждёт до 16,7 мс; в прогонах — 13,3 мс в среднем от готовности
до взятия) — свой презентер может ставить кадр по сигналу готовности к ближайшему сроку vblank.

**SSPC-015 (временная линия `--frame-pacing`, `p42_ab\p42-FP_1/2`, `frame_pacing.{csv,txt}`) [К]:**

| окно | работа потока GPU между маркерами флипа | CPU-время потока / реальное | интервалы показа | доля ~33 мс |
|---|---|---|---|---|
| пляж 32–52 с | 16,67 мс (P95 17,4) | 0,91 (поток ждёт метку VideoOut ~3 мс/кадр) | 16,67 мс, 60 FPS | 0 % |
| листва 64–97 с | **22,2 мс** (P50 22,0, P95 23,6–24,2) | **0,99** | **22,2 мс**, 45,0 FPS, P50 16,8 | 33 % |

* Интервалы показа — **только** 16,7 или 33,3 мс (интервалов 20–28 мс: 0): сетка 60 Гц квантует моменты показа.
* Средний интервал показа **равен** средней работе потока GPU (22,24 vs 22,23 мс): презентация не теряет пропускную
  способность; кадров в секунду ровно столько, сколько успевает поток GPU моста.
* В листве поток GPU на CPU 99 % времени: **вытеснения нет**; кадры с работой > 25 мс — это больше CPU-работы (27 мс CPU
  против 21,9), а не простой. Игра почти не ждёт (`SubmitAndFlip` блокируется на 0,1 мс).
* Вывод: «медленный режим» — не отдельное состояние и не 30 Гц: это прогоны, где работа потока GPU в листве > 25 мс
  (тогда P50 из двух значений прыгает 16,7 → 33,3, а FPS 37–40). Разброс работы между сессиями (P4.1: 25–27 мс при
  параллельно работавших агентах; здесь 22,2 мс без них) — нагрузка на CPU от других процессов (общие ядра SMT, кэш,
  частота), а не вытеснение потока **[Пр]**. Лечится не vsync, а уменьшением CPU-работы на draw (цель P4.3–P4.6).
  Критерий для A/B: FPS/средний кадр окна и доля 33 мс, не P50. KNOWN_ISSUES SSPC-015 переклассифицирован.

## 12. Независимое ревью

ecc:cpp-reviewer (только чтение): **CRITICAL нет**. HIGH: H1 переполнение таблицы записей в неразобранные пакеты
(молча) → ёмкость 64 и отказ при неизвестных байтах; H2 пакет, записанный DMA из памяти, тень декодировала из старой
копии → тень сверяет и **содержимое** пакета с мостом (новый вид расхождения), такой пакет отказывается явно; H3 с
`copyGPUBuffers` тень молча ломалась → включение тени отказывается с причиной — **все исправлены**. MEDIUM: M1
перекрывающиеся чтения в памяти трассы → поиск покрывающего куска; M3 нет compute-регистров графической очереди в
начале трассы → добавлены; M4 трасса compute с продолжения перенесённого пакета → очередь начинается со следующего
участка; M5 отчёт тени при остановленном потоке GPU → публикация раз в секунду, запись под мьютексом; M6 гонки
`--frame-pacing` (acquire, пропуск незаписанных слотов); M7 чтение подписи шейдера вне 40 бит и повторный поиск → проверка
границы и кэш отказов; M8 форматирование на горячем пути при рассинхроне → только для первых 64 — **исправлены**; M2
(память трассы применяется к моменту контрольной точки) — **записано**: риск только при перезаписи того же буфера между
двумя чтениями без контрольной точки, расхождение тогда видно как несовпадение, не как ложный MATCH. LOW: L1 пустой
chain-IB, L2 частичная запись SET_SH_REG, L3 маркер после сброса, L4 повторная привязка очереди, L5 повтор
BeforePacket, L6 int_sel RELEASE_MEM, L7 лишний буфер DMA в тени, L10 переполнение очереди при воспроизведении —
исправлены; L8 (DingDong на полный круг = как у моста), L9, L11 — записаны. Регрессионные проверки — в GpuCp(errors).

## 13. Известные ограничения

1. **Ни один draw/dispatch не исполняется на GPU** (уровень 4 — ни у одного опкода); метки EOP/EOS/RELEASE_MEM
   изолированно ждут `CompleteWork`, которого в игре некому вызвать — поэтому в игре процессор только в тени.
2. Идентичность шейдера — по адресу и RSRC; содержимое не отслеживается (нужен трекинг записей, P4.4); тень лишь
   проверяет подпись раз на адрес за кадр (смен не найдено).
3. Дескрипторы ресурсов (V#/T#/S#) не разбираются: в описании draw — user data (указатели или встроенные дескрипторы,
   помеченные по NOP-маркерам драйвера).
4. Не реализованы (контролируемая ошибка): COND_EXEC, MEM_SEMAPHORE, REWIND, DRAW_*_MULTI, LOAD_*_REG,
   SET_SH_REG_OFFSET, SET_CONTEXT_REG_INDIRECT, COPY_DATA, весь CE (CCB), предикация, type-0, WRITE_DATA в один адрес,
   EVENT_WRITE ZPASS_DONE/статистика, DMA с адресным пространством регистров (кроме предвыборки) — в игре их нет.
5. Единица смещения GDS в EOS/RELEASE_MEM не проверена (в игре таких меток 0); GDS — модель CP (64 КиБ), без шейдеров.
6. ACQUIRE_MEM не задерживает CP (это барьер для GPU); CPU-стороне после него порядок дают метки игры.
7. Трасса начинает очередь compute с начала её отправки; пакет, перенесённый через конец кольца на старте записи, в
   трассу не попал бы (в записанных трассах переносов 0).
8. Тень стоит 6,2–6,6 мс на кадр потока GPU моста (диагностика); CCB тень не видит (игра его не использует).
9. Изолированный режим проверен синтетическими потоками самотеста, не реальной игрой (у игры нет своего GPU-исполнителя).
