# Кэш шейдеров и пайплайнов (P2.4, патч моста 0013)

Состояние на 2026-10-10. Графический рантайм — Vulkan-бэкенд shadPS4 (мост), до своего (Phase 4).

## Что было не так

Аудит (`logs\` 23 сессий, код `video_core\renderer_vulkan\vk_pipeline_cache.cpp`, `cache_storage.cpp`):

* **Внутри одного процесса повторной компиляции нет.** Ключ программы — хэш из футера `OrbShdr` гостевого
  шейдера; перестановки — `StageSpecialization`; ключи пайплайнов без адресов и покадрового состояния.
  Ни один хэш шейдера или пайплайна не компилировался дважды ни в одном логе, в том числе в сессии
  10-08 с четырьмя перезагрузками уровня. Строка `Compiling vs shader 0x… (permutation)` — *другая
  специализация* того же шейдера (до 23 у одного VS), а не повтор.
* **Кэша между запусками не было.** В мосте есть дисковый кэш (`Storage::DataBase`, предзагрузка
  `WarmUp`), но `pipeline_cache_enabled = false` по умолчанию, SecondSonPC его не включал. Каждый запуск
  exe заново переводил ~900–1350 шейдеров (+280–400 перестановок) и создавал ~650–1500 пайплайнов,
  хотя набор между запусками совпадает на 99 %.
* **Компиляция синхронная**, внутри draw/dispatch на потоке `GpuCommandProcessor`: каждый новый
  шейдер/пайплайн останавливает кадр. `VkPipelineCache` драйвера создавался пустым и не сохранялся.

Включить кэш моста как есть было нельзя — при тёплом старте он сломал бы игру или графику:

| # | Дефект | Последствие |
|---|---|---|
| 1 | SRT-walker (x86-код из кэша) исполнялся без своего обработчика нарушений доступа | падение на первом нулевом указателе в SRT |
| 2 | индекс перестановки = порядок обнаружения; повторно использованный индекс перезаписывал `.meta/.spv`, старые ключи собирались с чужим шейдером | неверный пайплайн, возможен сбой драйвера |
| 3 | `sdata.fragment` (discard-шейдер эмуляции clip distance, NVIDIA) не сохранялся | предзагруженный depth-only пайплайн без стадии — геометрия за плоскостями отсечения |
| 4 | `infos/modules` не сбрасывались после неудачного ключа | лишняя стадия от предыдущего ключа |
| 5 | гонка счётчика IO-потока; очередь не дописывалась при закрытии | вечный холостой цикл / потеря записей |
| 6 | нет проверки целостности, неатомарная запись | обрезанный файл → `ASSERT` в `Serialization::Reader` → падение |
| 7 | нет учёта версии транслятора | после изменения рекомпилятора — устаревший SPIR-V |
| 8 | несовпадение профиля отключало кэш навсегда; `VkPipelineCache` создавался после предзагрузки | кэш не наполняется; без кэша драйвера |

Все исправлены в `patches\shadps4\0013-persistent-shader-cache.patch` (`docs\PATCHES.md`); ревью
(ecc:cpp-reviewer) — 10 замечаний средней/низкой тяжести, все внесены.

## Как устроено

* `SecondSonPC.toml`:
  ```toml
  [ShaderCache]
  enabled = true
  dir = 'cache\shaders'
  ```
* Каталог: `<dir>\CUSA00004\<поколение>-<vendor>-<device>-<driver>\`, например
  `cache\shaders\CUSA00004\98482ec6ba9ba2bc-10de-1f08-95054000\`.
  * **поколение** — первые 16 hex SHA-256 от git-деревьев `shader_recompiler`, `video_core`, `common`
    состояния «HEAD + все патчи» и версии компилятора (`cmake\shadps4_bootstrap.cmake`, печатается при
    конфигурации). Любой патч, меняющий перевод или формат кэша, даёт новое поколение — старое не читается;
  * GPU/драйвер — второй уровень (SPIR-V зависит от профиля устройства); профиль ещё и сверяется
    побайтно, при несовпадении каталог очищается и наполняется заново;
  * поколения, не использовавшиеся 30 дней, удаляются при открытии (только каталоги с маркером
    `generation`); сборки для A/B своё поколение не теряют.
* Файлы: `*.spv` (SPIR-V), `*.meta` (Info + специализация + XXH3 SPIR-V), `*.key` (ключ пайплайна +
  XXH3 каждой meta), `profile.bin`, `vulkan.bin` (данные `VkPipelineCache` + vendor/device/driver/UUID),
  `generation`. У каждого — заголовок 24 байта: magic, формат, размер, XXH3. Запись — `.tmp<pid>` и
  переименование. Повреждённые и неподходящие файлы удаляются при предзагрузке.
* При запуске (главный поток, до игры): каталог открывается, `VkPipelineCache` создаётся с данными
  `vulkan.bin`, все ключи предзагружаются (модули + пайплайны). При игре новые шейдеры/пайплайны
  компилируются как раньше и дописываются в кэш потоком `PipelineCacheIO`.
* Флаги: `--shader-cache <dir>` (свой каталог, тестовые прогоны), `--no-shader-cache`,
  `--clear-shader-cache` (удаляет поколения в `[ShaderCache] dir` и выходит). Ручная очистка — этот
  флаг или удаление папки `cache\shaders`.
* Замеры (без логирования на каждый кадр): строка `Shader cache stats (...)` в `bridge_shadps4.log`
  раз в 10 с, пока идут компиляции, и при выходе — скомпилировано (промахи), предзагружено и
  использовано (попадания), время перевода/SPIR-V/модулей/пайплайнов, простой GPU-потока, число
  остановок > 5/20/100 мс. `tools\perf_report.py` выносит её в `report.md` вместе с числом кадров
  > 33,3/50/100 мс. Режимы `perf_runs.ps1`: `C0` — без кэша, `C1` — тестовый кэш `logs\p24\sc_test`.

## Результаты (Salmon Bay, начало обучения, RTX 2060, драйвер 596.21)

Сессии `logs\performance\p24_sc`, `p24_sc_warm`, `p24_sc_crash`, `p24_sc_final`.

| | холодный (1-й запуск) | тёплый (после перезапуска exe) |
|---|---|---|
| скомпилировано шейдеров | 551 + 217 перестановок | **0** |
| скомпилировано пайплайнов | 505 графических + 81 compute | **0** (576 взяты из кэша) |
| простой GPU-потока на компиляции | **2289 мс**, 586 остановок (153 > 5 мс, макс. 113 мс) | **0 мс** |
| перевод GCN→IR / SPIR-V / модули / пайплайны | 954 / 111 / 10 / 1215 мс | 0 |
| предзагрузка при запуске | — | 249–314 мс |
| кадров > 100 мс за прогон 100 с | 15 | **4** |
| самый длинный кадр (загрузка) | 3817 мс | 1784 мс |
| FPS в установившейся сцене | 17,15 | 17,92 (в пределах разброса) |
| размер на диске | 34,7 МиБ блобов + 7,8 МиБ `vulkan.bin` (≈ 43 МБ, 2125 файлов) | — |

* Повторная загрузка той же сцены **в том же процессе** не компилировала и раньше; **после перезапуска**
  теперь тоже не компилирует. Новая сцена компилируется один раз — при первом посещении.
* FPS установившейся сцены от кэша не меняется: кэш убирает рывки загрузки и первых секунд сцены,
  а не стоимость кадра. 30 FPS кэшем не достигаются (сцена 17–18 FPS ограничена другим — ниже).
* Стабильность: падение SSPC-002 на 15-й секунде загрузки возникает и без кэша. Серия `p24_sc_crash`
  (чередование): **без кэша 2 из 13, с тёплым кэшем 1 из 13**; за все серии — на тёплом кэше 4 из 22,
  без кэша или с холодным 2 из 16. Связи с кэшем нет (поток `JobWorker`, `jmp` на незамапленный адрес
  из функции задания; кэш меняет только GPU-поток).

## Что остаётся (рывки не только от шейдеров)

* В этой сцене **45 тыс. нарушений доступа в секунду** — отслеживание записей CPU в память GPU
  мостом через защиту страниц (VEH). Это CPU-время игровых потоков на каждом кадре; в старой сцене
  «лес» было ~11,7 тыс./с. Вероятная главная причина 17–18 FPS — вне задачи кэша.
* Асинхронная компиляция / pipeline libraries (`VK_EXT_graphics_pipeline_library` на устройстве есть,
  мост не использует) — серьёзный рефакторинг `PipelineCache` и привязки ресурсов; при тёплом кэше
  выигрыш остаётся только для первой встречи шейдера. Не делалось.
* Предзагрузка растёт с кэшем (вся игра — тысячи пайплайнов): сейчас 0,25–0,3 с на ~580 пайплайнов;
  при необходимости — параллельная предзагрузка.
* 2 ключа холодного прогона всегда отбраковываются (мост сохраняет одну специализацию под индексами
  0 и 1) — безвредно, удаляются.
