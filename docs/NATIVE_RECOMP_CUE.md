Адреса — смещения eboot CUSA00004 (база 0). Метки: [A] анализ кода, [E] измерение, [?] не разобрано. Дата — 20.10.2026.

## 2. Что делают функции [A, E]

```
System V: (rdi cue, esi stage, edx slot, ecx count, r8 src) -> rax = cue
table = [cue + 0xc180 + (s64)stage * 8]            раскладка user data привязанного шейдера стадии
для i в 0..count-1:
  entry = u16[table + T + (slot + i) * 2]           T = 0x10a (вершинные буферы, 0x16aa0) / 0x22 (ресурсы, 0x16b70)
  0xffff         — слот шейдером не используется
  бит 15         — 0x626520([cue + 0xc090], stage, entry & 0x3fff, src + 16 i, 4): SET_SH_REG прямо в DCB
  иначе          — 16 байт V# в тень стадии: cue + 0x90 + (s32)(stage * 0x600) * 4 + (entry & 0x3fff) * 4
byte[cue + 0xc1d0 + (s64)stage] = 1                «ресурсы стадии изменены» — commit 0x14ad0 снимет тень
```

Арифметика адресов взята у оригинала: стадия расширяется со знаком для таблицы и флага, смещение тени —
`(s32)(stage·0x600)·4`, слот — беззнаковый индекс. Запись и дескриптор читаются заново на каждом слоте, потому что
вызываемая функция может изменить память. Дескриптор читается целиком до записи, как у пары `vmovups` в оригинале.
Длина обеих функций — 0xc6, хеши тел — `0xf6c333198de2deed` и `0x713c9f7b4b870c4d`.

Нагрузка в игре [E]: ~12,2 тыс. и ~16,1 тыс. вызовов на кадр (verify, 20.10.2026; совпадает с замером MEASURE в §3
`NATIVE_ENGINE_RECONSTRUCTION.md`: 12 347 и 16 324 вызова, 325 и 320 мкс на кадр).

## 3. Как сверяется функция с внешним вызовом

У прежних функций (`0x11c890`, `0x1f0870`) не было вызовов, которые пишут вне сравниваемой памяти. Здесь вызов
`0x626520` дописывает пакеты в командный буфер. Если исполнить его дважды (оригинал на тени и замена на тени), в
настоящем DCB окажутся лишние пакеты. Поэтому:

- **Записывающий клон оригинала.** `CloneGuestFunction(..., redirects)` (`guest_code_clone.h`, новое `CodeRedirect`)
  копирует тело и перенаправляет `call 0x626520` на переходник `jmp [rip+0]` после тела; переходник ведёт в
  `CueSetBuffers::Record`. Клон отказывается строиться, если перенаправление не использовано. Его строит шаг
  установки `FunctionSpec::prepare` (новое поле реестра) до self-check.
- **Ручная реализация** в теневом прогоне зовёт `Record` через `thread_local`, а на живом пути — настоящий `0x626520`.
- **Машинно переведённая** — через новый экспорт модуля `recomp_set_redirect(from, to)`. В генераторе (`pcode2c.py`)
  каждая цель вызова проходит через `call_target()`: при совпадении с `from` в этом потоке вызов идёт в `to`. Без
  экспорта установщик оставляет ручную реализацию.
- **Сравниваются** диапазоны CUE, которые вызов читает или пишет: окно тени стадии `0x1800`, хвост `0xc080..0xc1e0`
  (контекст, указатели таблиц, флаги) и записи за пределами окна (14 бит индекса достают дальше). Кроме них —
  записанные вызовы (5 регистров аргументов целиком и 16 байт дескриптора) и возвращённый `rax`. Вызовы со стадией
  вне 0..7 или слотами за 64-м не сверяются (счётчик skipped; в игре таких 0).
- **live-diff** — результат настоящего вызова против теневого оригинала: ловит записи других потоков между ними.
- **Self-check** при установке — 1000 сгенерированных случаев на целых теневых буферах (любая лишняя запись видна)
  против записывающего клона. Настоящий оригинал при self-check не запускается: его вызов записал бы мусор в
  настоящий DCB.
- **Случай расхождения** (`Case`: стадия, слот, число, контекст, записи таблицы, дескрипторы) пишется в
  `logs/native_engine/cases_<key>.txt` и воспроизводится `--replay` против eboot.

Выгрузка P-code (`E:\research\native-r5\cue14ad0\pcode.json`, `pcode_dump.py`) и классификация `pcode2c.py`:

| Показатель | Значение |

| Класс рекомпилятора | **SUPPORTED** |
| Инструкции / операции P-code | 953 / 4668 |
| SIMD / FP / CALLOTHER | 0 / 0 / нет |
| Вызовы | 99 прямых, 0 косвенных, 0 хвостовых, 0 switch, 0 атомиков |
| Приватный стек / стековые аргументы | 200 байт / 0 |
| Стоимость в игре (MEASURE, §3) | 11 985 вызовов, 1109 мкс на кадр включительно — самая дорогая функция CUE |

Вызываемые (22 функции; число мест вызова):

| Цель | Мест | Что (`GNMX_RECONSTRUCTION.md`, `RENDER_ENGINE_ARCHITECTURE.md`) |
|---|---|---|

| `0x626520` | 16 | setUserDataRegion — отдельные значения user data [A] |

| `0x625100`, `0x625220`, `0x625370`, `0x625a40`, `0x625aa0`, `0x6251c0`, `0x625300`, `0x6253e0`, `0x625510`, `0x6256a0` | по 1 | диапазон установки шейдеров Gnm `0x625100…0x625aa0`: PS, VS, GS, ES и альтернативный путь `0x6251c0`/`0x625300` [A]; стадия каждой из остальных [?] |
| `0x624cb0` | 1 | запись диапазона регистров [A] |
| `0x61e0c0`, `0x61e330`, `0x638540`, `0x639250`, `0x6393a0`, `0x639450`, `0x6394e0` | по 1 | [?] |

Что из этого следует:

- **Перевести можно**, классов отказа нет. **Сверить сейчас нельзя**: верхушка вызовов пишет в DCB и в CUE-аллокатор.
  Схема §3 перенаправляла одну цель, здесь их 22. Для сверки нужны записывающие заглушки для каждой цели с
  возвращаемыми значениями (`0x123d0` возвращает адрес снимка, по которому `0x14ad0` дальше копирует тень и пишет
  указатели). Иначе — запись оригинала и сравнение пакетов PM4. Это задача отдельной итерации.
- **Выигрыша от перевода нет** [A]: переведённый код — тот же x86-64 (§9 `NATIVE_ENGINE_RECONSTRUCTION.md`). Смысл
  `0x14ad0` для порта другой: это точка, где тень стадии превращается в user data
  (`GFX_CONTEXT_LAYOUT.md` §2.1, «естественная точка перехвата» для нативного рендера).
- Статус: **ANALYZED** (рекомпилятор — LIFTABLE), в реестр не добавлена.
